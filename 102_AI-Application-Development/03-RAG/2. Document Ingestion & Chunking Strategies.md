## 🤔 STEP 1 — Prediction Before Explanation

> **Let me ask you first:**
> *"Imagine you take a 100-page enterprise financial audit report and chop it into strict blocks of 200 characters each. What happens when a user asks: 'What was the Q3 operating margin for the European cloud division?'"*

A beginner usually thinks:
> *"The vector database will find the chunks with 'operating margin' and 'Q3' and everything will work fine."*

An experienced AI engineer knows:
> **Strict character or naive slicing tears meaning to pieces.**
> If the text says:
> `"...operating margin for European Cloud Division was [SPLIT] 24.5%, down 2% YoY..."`
> The first chunk contains the metric name without the number. The second chunk contains numbers without the context of which division they belong to. Neither chunk answers the user's question, and your RAG system completely fails.
>
> **Chunking is the foundational act of defining the atomic unit of semantic meaning in your retrieval architecture.**

# 📌 PART 1 — The Core Trade-Offs of Chunk Size

```
                     CHUNK SIZE SPECTRUM & TRADE-OFFS
                     
    Small Chunks (64 - 256 tokens)             Large Chunks (1024 - 4096 tokens)
  ◄─────────────────────────────────────────────►
  • High Embedding Precision                • Rich Context for Generation
  • Fast Vector Comparisons                 • Harder for Embedding Model to Capture Core Meaning
  • Risk: Loss of surrounding context       • Risk: Noise & irrelevant information in prompt
  • Lower generation cost per chunk         • Higher token cost per prompt
```

| Dimension | Small Chunks (100–256 tokens) | Medium Chunks (512–1024 tokens) | Large Chunks (2048+ tokens) |
|---|---|---|---|
| **Retrieval Accuracy (Precision)** | ⭐⭐⭐⭐⭐ Extremely high | ⭐⭐⭐ Good | ⭐ Low (embedding vector is diluted) |
| **Context Completeness (Recall)** | ⭐ Low (misses background) | ⭐⭐⭐⭐ High | ⭐⭐⭐⭐⭐ Maximum |
| **Noise in LLM Context** | Minimal | Moderate | High (dilutes attention) |
| **Best Used For** | Direct fact extraction, FAQ matching | General Q&A, documentation | Summarization, multi-hop synthesis |

# 📌 PART 2 — The 6 Production Chunking Strategies

### 1. Fixed-Size Slicing with Sliding Overlap
The simplest baseline: slice by fixed character or token counts with an overlapping buffer (e.g., 500 tokens with 50-token overlap).
- **Pros:** Fast, constant compute cost.
- **Cons:** Slices words, paragraphs, code blocks, or tables arbitrarily in half.

### 2. Recursive Character Splitting (LangChain / LlamaIndex Standard)
Iteratively attempts to split text along natural semantic boundaries using a hierarchy of delimiters:
```python
separators = ["\n\n", "\n", ". ", " ", ""]
```
1. Splits on double newlines (paragraphs).
2. If any paragraph exceeds `chunk_size`, splits that paragraph on single newlines.
3. If still too large, splits on sentences (`. `).
4. If still too large, splits on words (` `).
- **Why it wins:** Preserves natural paragraph and sentence integrity whenever possible.

### 3. Document-Structure-Aware (Markdown, HTML, Code AST)
Splits based on explicit document hierarchy:
- Headers (`#`, `##`, `###`) delineate logical sections.
- Code blocks (functions, classes) are parsed via Abstract Syntax Trees (Tree-sitter) so no function body is split from its docstring or signature.
- Table headers are repeated across table row splits so every row retains column semantics.

### 4. Semantic Chunking (Embedding-Distance Triggered)
Instead of arbitrary length boundaries, semantic chunking monitors the cosine similarity between adjacent sentences:
1. Split text into individual sentences.
2. Generate an embedding for each sentence.
3. Calculate cosine distance between sentence $i$ and sentence $i+1$.
4. Whenever the distance exceeds a statistical threshold (e.g., 95th percentile of distance shifts), inject a chunk break.
