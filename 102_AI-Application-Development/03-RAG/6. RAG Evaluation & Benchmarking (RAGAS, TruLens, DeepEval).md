# RAG evaluation: a reproducible protocol

Reviewed October 9, 2026. Frameworks such as Ragas, TruLens and DeepEval can implement parts of an evaluation; their names do not define correctness or establish a universal release threshold. The [reviewed Ragas source](../../research/sources.json) documents its current quickstart, but provider-backed evaluation was not executed in this review.

## Separate the questions you are measuring

| Layer | Question | Evidence |
|---|---|---|
| Data | Are the sources authorized, current and correctly parsed? | Provenance, document/version checks, access and deletion tests |
| Retrieval | Did the system find relevant evidence? | Reviewed relevance judgments, Recall@k, nDCG@k and per-query rankings |
| Generation | Is the answer correct and supported by its cited evidence? | Reviewed answer/citation labels, claim support, abstention and contradiction cases |
| Workflow | Did the user achieve the intended goal safely? | End-state checks, authorized actions, policy compliance and escalation review |
| Operations | Does it meet the workload's budget and reliability needs? | Measured latency, failures, retries, token/compute cost and load conditions |

Groundedness is not factual truth: an answer can faithfully repeat a stale or false document. Relevance is not correctness. An answer can be relevant but unsupported, or correctly abstain when no answer is available. Keep those outcomes distinct.

## Construct a real evaluation set

Use authorized, de-identified workflow samples with expert-reviewed evidence and expected behavior. Supplement with a licensed public dataset such as [BEIR](https://github.com/beir-cellar/beir) for a retrieval baseline, keeping its task definition intact. Record corpus, query and relevance-label revisions.

For each case, retain query/task ID, source document IDs and versions, allowed resources, expected answerability, relevance labels, expected claims or actions, and review history. Include unsupported questions, ambiguous questions, conflicting/stale evidence, language/domain slices, and permission boundaries. Split by source family or time when random splitting would leak closely related material.

LLM-generated questions and answers are **synthetic candidates**, not authoritative ground truth. Keep them separate from real observations. Review labels against sources, document coverage and generation bias, and do not use a model's generated answer to prove that same model is correct.

## Establish retrieval baselines

Start with lexical retrieval and compare dense retrieval under the same corpus, queries, relevance judgments and evaluation protocol. Add fusion or reranking only after diagnosing failures and measuring improvement. Tune on development data; inspect the held-out test once the configuration is fixed.

Recall@k measures how many labeled relevant documents are retrieved. nDCG@k measures ranking quality using the task's graded relevance labels. Context precision/recall and answer-level faithfulness in evaluation frameworks are different quantities; record their exact implementation and inputs. Unjudged documents are not necessarily irrelevant. Undefined metrics on cases without relevant labels need an explicit exclusion/reporting policy.

Store per-query outputs, including failures and empty retrievals. For a comparison, compute paired differences on the same queries and report an appropriate uncertainty estimate. Cluster by document/customer when observations are related. Confidence intervals cannot compensate for an unrepresentative sample or incorrect labels.

## Calibrate LLM judges

Keep a human-reviewed calibration set separate from prompt development and final testing. Record judge model/version, prompt, temperature, response schema and parsing failures. For pairwise judgments, swap presentation order and inspect disagreements. Evaluate error rates by slice, including verbosity, refusal and citation formatting effects.

Report agreement with human judgments under your actual rubric; there is no demonstrated universal “85% alignment at 1% of the cost.” Distinguish judge disagreement, invalid output, unavailable provider, skipped evaluation, and a negative result. Do not replace missing judgments with passing scores.

## Turn evaluation into a release decision

Specify acceptance criteria before observing the release result. Separate absolute requirements from allowed regressions and from metrics used only for diagnosis. Calibrate thresholds to the actual task, risk and measurement uncertainty; values such as 0.95 faithfulness or 0.85 context precision are not universal standards.

Include:

- Dataset, code, package, model and judge revisions; prompt/configuration hashes.
- Executed task IDs, scored/skipped/error counts, labels and per-case results.
- Baselines, ablations, failure slices and paired comparisons.
- First-token and full-completion latency measured separately, workload/concurrency, and total evaluation cost.
- Authorization/cache-isolation tests, source freshness/deletion behavior and invalid-citation checks.
- Canary/rollback criteria and responsibility for reviewing ambiguous results.

The older code sample used an unpinned framework API and fictional policy answers. It has been removed rather than presented as an executed evaluation. Use the selected framework's versioned official example, configure your own approved provider securely, and report its actual run status.
