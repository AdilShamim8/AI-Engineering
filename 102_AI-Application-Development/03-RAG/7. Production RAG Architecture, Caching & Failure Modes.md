# Production RAG: authorization, caching and recovery

Reviewed October 9, 2026. The architecture below describes responsibilities, not a verified latency/cost benchmark. Similarity scores do not establish identity, authorization, answer correctness or a safe cache hit.

## Request boundaries

```text
Authenticated caller and server-derived authorization scope
    -> scoped cache lookup with source-version checks
    -> retrieval constrained by permitted resources
    -> optional reranking over permitted evidence
    -> generation and citation validation
    -> response plus access-controlled telemetry
```

Check identity and permissions before retrieving from either the cache or the corpus. Do not accept an arbitrary `tenant_id` or clearance list from the caller as proof of authorization. A server must derive those values from its authenticated principal and policy.

## Filtered retrieval example

This example was exercised in Qdrant's in-memory mode with `qdrant-client==1.15.1`. It tests selection within a small fixture, not production authentication, index configuration or server behavior. Use an integration test with the actual deployed server version before release.

```python
from qdrant_client import QdrantClient, models


def secure_retrieve(
    client: QdrantClient,
    query_vector: list[float],
    user_tenant_id: str,
    user_security_clearance: list[str],
    top_k: int = 5,
):
    # Values must come from trusted application authorization state.
    # Missing scope fails closed; it never becomes an unfiltered search.
    if not user_tenant_id or not user_security_clearance:
        return []
    if top_k < 1:
        raise ValueError("top_k must be positive")
    security_filter = models.Filter(
        must=[
            models.FieldCondition(
                key="tenant_id", match=models.MatchValue(value=user_tenant_id)
            ),
            models.FieldCondition(
                key="access_level", match=models.MatchAny(any=user_security_clearance)
            ),
            models.FieldCondition(
                key="is_active", match=models.MatchValue(value=True)
            ),
        ]
    )
    return client.query_points(
        collection_name="enterprise_knowledge",
        query=query_vector,
        query_filter=security_filter,
        limit=top_k,
        with_payload=True,
    ).points
```

The example uses a simple tenant-plus-clearance policy. Real applications may need per-document ACLs, group membership, deny rules and policy revisions. Filtering one query is not a guarantee of zero leakage. Test missing scope, cross-tenant IDs, unauthorized document identifiers, revoked access, deleted/inactive documents, and every alternate read path.

## Treat cached answers as protected data

Scope a cache entry to the tenant, effective permissions/policy revision, source revisions, prompt/model configuration and any user-specific context. Revalidate access and source freshness on a hit. Document invalidation behavior after an ACL change, deletion or policy update. A global cache keyed only by query similarity can return another user's protected answer.

Semantic similarity does not prove equivalent intent: different dates, account numbers, product tiers or negation can change the answer. Begin with an exact scoped cache where appropriate; evaluate any semantic reuse policy against reviewed false-hit cases. Calibrate the threshold for the chosen embedding and workload. Do not reuse a universal cosine cutoff.

A cache hit can avoid a generation call, but embeddings, storage, lookup and networking still have costs. Measure hit rate, false-hit rate, invalidation lag and end-to-end latency under the actual workload. The earlier “80% savings,” “12ms,” and “$0.00” claims were not demonstrated measurements and have been removed.

## Update documents without exposing inconsistent versions

Record source ID, version, content hash, authorization metadata and indexing status. Build and validate a new version before publishing it for retrieval, then atomically switch the active view or use a documented consistency protocol. Invalidate affected caches. Remove/tombstone old chunks and enforce the active-version filter on every retrieval path.

A hash detects changes; it does not perform deletion or access revocation. Test interruptions during ingestion, retries, old-version references, cache invalidation and recovery. Verify deletion in source storage, indexes, caches and trace retention according to the application's policy.

## Separate latency and reliability measures

Measure retrieval time, first-token latency, full-response latency and time to a correct task outcome separately. Streaming can improve perceived responsiveness; it does not shorten the work needed to complete an answer. State payload sizes, model/configuration, concurrency, cache conditions, region and cold/warm behavior when publishing results.

Use bounded retries, request deadlines, admission control and circuit breakers. A fallback provider/model must be evaluated for the same task, privacy constraints, refusal behavior and structured-output contract. Do not silently convert an unavailable provider into a passing result.

## Failure review

| Failure | Investigation and control |
|---|---|
| Unauthorized evidence or cached answer | Server-derived scope, resource-level checks, cache partitioning, revocation tests |
| Prompt injection in documents | Treat retrieved text as untrusted data; constrain tools and privileges outside model text |
| Missing or stale evidence | Source/version checks, retrieval diagnostics, reviewed abstention/escalation behavior |
| Unsupported citations | Validate cited IDs/spans and claim support; log reviewable failures |
| Inconsistent document update | Versioned ingestion, atomic publication, invalidation and recovery tests |
| Overload or provider outage | Measured capacity, bounded queues/retries, deadlines and validated fallback |

Delimiters, strict prompts and semantic thresholds can help structure processing, but none alone enforces authorization or proves resistance to injection.
