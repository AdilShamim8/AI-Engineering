# 🔑 TOPIC 1: API Integration

---

> 🧠 **First Principles Question:**
> *"How do two completely different software systems talk to each other?"*
>
> Beginner assumes: *"They just connect somehow"*
>
> Real answer: **They agree on a CONTRACT called an API.**
> API = A set of rules for HOW to ask and HOW to answer.

---

## 🔍 1. What is an API?

```
📌 API = Application Programming Interface

Simple English:
An API is a WAITER in a restaurant.

YOU = Your code (the customer)
KITCHEN = External service (Google, Stripe, OpenAI)
WAITER = API (takes your order, brings back food)

You don't go into the kitchen directly.
You tell the waiter (API) what you want.
The kitchen does its work.
The waiter brings back the result.

You never need to know HOW the kitchen works.
You just know HOW to talk to the waiter.
```

## 🧱 3. First-Principles Breakdown

```
🧱 Every API Call Has 5 Components:

1. ENDPOINT (WHERE to go)
   https://api.openai.com/v1/chat/completions
   └── Protocol: https://
   └── Domain: api.openai.com
   └── Path: /v1/chat/completions

2. METHOD (WHAT ACTION to do)
   GET    → Read/fetch data (like reading a menu)
   POST   → Create/send data (like placing an order)
   PUT    → Update entire record (like replacing order)
   PATCH  → Update partial record (like modifying order)
   DELETE → Remove data (like canceling order)

3. HEADERS (WHO you are + HOW to talk)
   Authorization: Bearer sk-abc123  ← Your identity
   Content-Type: application/json  ← Data format
   Accept: application/json        ← Response format

4. BODY (WHAT you're sending)
   {
     "model": "gpt-4",
     "messages": [{"role": "user", "content": "Hello"}],
     "temperature": 0.7
   }

5. RESPONSE (WHAT comes back)
   Status Code: 200 (OK) / 404 (Not Found) / 429 (Rate Limit)
   Body: { "id": "chatcmpl-abc", "choices": [...] }
```

```
import requests
import os
from dotenv import load_dotenv

def fetch_top_news(topic: str, count: int = 5) -> list:
    """
    Fetch top news articles on a topic.
    
    Input:  topic = "artificial intelligence"
    Output: List of articles with title, description, url
    """
    
    url = "https://newsapi.org/v2/everything"
    
    headers = {
        "X-Api-Key": os.getenv("NEWS_API_KEY")  # API key in header
    }
    
    params = {
        "q": topic,           # Search query
        "sortBy": "publishedAt",  # Latest first
        "pageSize": count,    # How many articles
        "language": "en"      # English only
    }
    
    response = requests.get(url, headers=headers, params=params)
    
    # ALWAYS check status code
    if response.status_code == 200:
        data = response.json()
        articles = []
        
        for article in data["articles"]:
            articles.append({
                "title": article["title"],
                "description": article["description"],
                "url": article["url"],
                "published": article["publishedAt"]
            })
        
        return articles
    
    elif response.status_code == 401:
        raise Exception("Invalid API Key — Check NEWS_API_KEY")
    
    elif response.status_code == 429:
        raise Exception("Rate limit hit — Too many requests")
    
    else:
        raise Exception(f"API Error: {response.status_code}")
```

## 🔒 6. Authentication Methods — Complete Guide

```
TYPE 1: API KEY
────────────────
Simplest. A secret string that identifies you.

# In Header (most common):
headers = {"Authorization": "Bearer sk-abc123"}
headers = {"X-API-Key": "your_api_key_here"}

# In URL params (less secure):
url = "https://api.example.com/data?api_key=abc123"

Used by: OpenAI, NewsAPI, most simple APIs
Security: Medium (anyone with key can use it)

────────────────────────────────────────────────

TYPE 2: OAUTH 2.0
──────────────────
Used when you access ANOTHER user's data.
More complex but more secure.

Flow:
1. User clicks "Connect with Google"
2. Google shows permission screen
3. User approves
4. Google gives you a TOKEN
5. You use token to access user's data

Used by: Google, Slack, GitHub, Salesforce
Security: High (user controls permissions)
When to use: When building for other users

────────────────────────────────────────────────

TYPE 3: BASIC AUTH
────────────────────
Username + Password encoded in base64.
Less common in modern APIs.

import base64
credentials = base64.b64encode(b"username:password")
headers = {"Authorization": f"Basic {credentials.decode()}"}

Used by: Some legacy APIs, JIRA
Security: Low-Medium (avoid when possible)

────────────────────────────────────────────────

TYPE 4: JWT (JSON Web Token)
──────────────────────────────
Signed token containing your identity + permissions.
Self-contained — no database lookup needed.

Structure: header.payload.signature

Example JWT:
eyJhbGciOiJIUzI1NiJ9.    ← Header (base64)
eyJ1c2VySWQiOiIxMjMifQ.  ← Payload (base64)
abc123xyz                  ← Signature (HMAC)

headers = {"Authorization": f"Bearer {jwt_token}"}

Used by: Modern REST APIs, your own backend
Security: High (signed, tamper-proof, expirable)
```

## 📊 HTTP Status Codes — Complete Map

```
STATUS CODE FAMILY TREE:

1xx → INFORMATIONAL (Rare in practice)
├── 100 Continue
└── 101 Switching Protocols

2xx → SUCCESS ✅
├── 200 OK            → Request succeeded
├── 201 Created       → New resource created (POST)
├── 204 No Content    → Success, nothing to return (DELETE)
└── 206 Partial Content → Partial file download

3xx → REDIRECT 🔀
├── 301 Moved Permanently → URL changed forever
├── 302 Found            → Temporary redirect
└── 304 Not Modified     → Use cached version

4xx → CLIENT ERROR ❌ (YOUR fault)
├── 400 Bad Request    → Your request is malformed
├── 401 Unauthorized   → Not authenticated (no/bad key)
├── 403 Forbidden      → Authenticated but no permission
├── 404 Not Found      → Resource doesn't exist
├── 408 Timeout        → You took too long
├── 409 Conflict       → Resource conflict (duplicate)
├── 422 Unprocessable  → Validation error in your data
└── 429 Too Many Req   → Rate limit hit (slow down!)

5xx → SERVER ERROR ❌ (THEIR fault)
├── 500 Internal Error → Server crashed (their bug)
├── 502 Bad Gateway    → Upstream server failed
├── 503 Unavailable    → Server overloaded/maintenance
└── 504 Gateway Timeout → Upstream server timed out

ENGINEER RULE:
4xx = Fix YOUR code/request
5xx = Wait and RETRY (their problem, usually temporary)
```

## 🧮 7. Rate Limiting — The Math

```
Rate Limits = API's throttle on how many calls you can make

Common Rate Limit Types:
1. Per Second:  60 calls/second
2. Per Minute:  1000 calls/minute
3. Per Hour:    10000 calls/hour
4. Per Day:     100000 calls/day

Example: OpenAI GPT-4
├── 10,000 TPM (tokens per minute)
├── 500 RPM (requests per minute)

If your system sends 1000 requests/minute:
└── 500 succeed ✅
└── 500 get 429 error ❌

MATH: Calculate if you'll hit rate limits

requests_per_day = 10000  # Your traffic
api_limit_per_day = 1000  # API limit

if requests_per_day > api_limit_per_day:
    # Need to either:
    # 1. Throttle requests: add delays
    # 2. Cache responses: don't repeat calls  
    # 3. Upgrade plan
    # 4. Use multiple API keys (if allowed)
    
    requests_per_second = api_limit_per_day / 86400
    delay_between_calls = 1 / requests_per_second
    # → Wait 0.0864 seconds between each call
```

## ❌ 8. API Integration Failure Modes

```
1. HARDCODED SECRETS (Most Dangerous!)
   api_key = "sk-abc123"  ← In source code
   → Pushed to GitHub → Scraped by bots → API abused
   Solution: ALWAYS use environment variables

2. NO TIMEOUT SET
   response = requests.get(url)  ← No timeout
   → Server hangs → Your code waits forever
   Solution: response = requests.get(url, timeout=30)

3. NOT HANDLING RATE LIMITS
   Loop sending 10000 requests → All fail after 100
   → All work lost
   Solution: Retry with backoff on 429

4. IGNORING RESPONSE STRUCTURE CHANGES
   API returns data["result"]["items"]
   API updates → Now returns data["data"]["results"]
   → Your code crashes with KeyError
   Solution: Schema validation, version pinning, alerts

5. NOT VALIDATING RESPONSES
   Assuming response.json()["field"] always exists
   → KeyError when API returns error response
   Solution: Always check status code first, then parse

6. SYNCHRONOUS CALLS FOR EVERYTHING
   Calling 100 APIs sequentially → Each takes 1s = 100s
   Solution: Async calls (asyncio) → All 100 in ~1s

7. NO CACHING
   Same API called 1000x with same parameters
   → Rate limit hit + unnecessary cost
   Solution: Cache responses with TTL (Redis, etc.)
```

# 🔑 TOPIC 2: Function Calling

---

> 🧠 **Most Important Concept in AI Automation:**
> *"How does an LLM actually USE external tools?"*
>
> Beginner assumes: *"LLM just generates text, can't do actions"*
>
> Real answer: **Function Calling bridges LLM reasoning with real-world actions.**
> This is what transforms a chatbot into an AI Agent.

---

## 🔍 1. What is Function Calling?

```
📌 Function Calling:
A feature where you tell an LLM:
"These are the TOOLS available to you.
 When needed, call them by outputting 
 structured JSON with the function name and parameters."

The LLM doesn't EXECUTE the function.
The LLM DECIDES which function to call with which arguments.
YOUR code actually executes the function.
Then you give the result back to the LLM.
```

---

## 💡 2. Intuition / Analogy

### 👨‍💼 Smart Manager and Assistants

```
Traditional LLM (No Function Calling):
You: "What's the weather in London?"
LLM: "I don't have access to real-time weather data."
→ Useless for real-world tasks

You: "What's the weather in London?"

LLM thinks: "I need weather data.

LLM outputs: 
{
  "function_call": {
    "name": "get_weather",
    "arguments": {"city": "London", "unit": "celsius"}
  }
}

YOUR CODE: Calls actual weather API → Gets data
           Gives data back to LLM

LLM: "It's currently 15°C in London with cloudy skies
      and a 70% chance of rain this afternoon."
→ Useful! Real-time! Accurate!
```

```

Step 1: DEFINE TOOLS
You tell LLM: "These tools exist"
{
  "name": "get_weather",
  "description": "Get current weather for a city",
```

```python
def execute_tool(tool_name: str, tool_args: dict) -> str:
    """
    Routes LLM's function call to the actual Python function.
    Returns result as JSON string (LLM needs string format).
    """
    
    function_map = {
        "get_weather":  get_weather,
        "search_news":  search_news,
        "send_email":   send_email,
        "calculate":    calculate
    }
    
    if tool_name not in function_map:
        return json.dumps({"error": f"Unknown tool: {tool_name}"})
    
    try:
        result = function_map[tool_name](**tool_args)
        return json.dumps(result)
    except Exception as e:
        return json.dumps({"error": str(e)})

            tool_choice="auto"  # LLM decides when to use tools
        )
        
        message = response.choices[0].message
        
        # CASE 1: LLM wants to call tools
        if message.tool_calls:
            
            # Add LLM's tool request to conversation history
            messages.append(message)
            
            # Process EACH tool call (LLM can call multiple at once!)
            for tool_call in message.tool_calls:
                
                tool_name = tool_call.function.name
                tool_args = json.loads(tool_call.function.arguments)
                
                print(f"🔧 Calling tool: {tool_name}")
                print(f"   Args: {tool_args}")
                
                # ACTUALLY EXECUTE THE TOOL
                tool_result = execute_tool(tool_name, tool_args)
                
                print(f"   Result: {tool_result}")
                
                # Add tool result to conversation
                messages.append({
                    "role": "tool",
                    "tool_call_id": tool_call.id,
                    "content": tool_result
                })
        
        # CASE 2: LLM gives final text answer
        elif message.content:
            print(f"\n🤖 AI: {message.content}")
            return message.content
    
    return "Max iterations reached"
```

## ❌ 5. Function Calling Failure Modes

```
1. WRONG FUNCTION DESCRIPTION
   Bad:  "name": "get_weather", "description": "weather"
   Good: Detailed description of WHEN and HOW to use it
   → LLM calls wrong function for the task

2. AMBIGUOUS PARAMETER NAMES
   Bad:  "param1", "val", "x"
   Good: "city_name", "temperature_unit", "date_range"
   → LLM fills wrong values

3. NOT HANDLING TOOL ERRORS
   Tool returns error → LLM gets error → Gets confused
   Solution: Always return structured error with explanation

4. MISSING REQUIRED FIELD VALIDATION
   LLM sometimes skips required fields
   → Your function crashes with missing argument
   Solution: Validate args before calling function

5. INFINITE TOOL CALLING LOOP
   Tool result → LLM calls same tool again → Infinite loop
   Solution: Max iteration limit (shown in code above)

6. EXPOSING DANGEROUS TOOLS WITHOUT GUARDRAILS
   LLM gets tool: delete_database(table_name)
   User says: "Clean everything up"
   LLM calls: delete_database("users") ← DISASTER
   Solution: Require human confirmation for destructive actions
```

## 💡 2. The 3 Types of Databases You Must Know

```
TYPE 1: SQL DATABASE (Relational)
──────────────────────────────────
Data organized in tables with rows/columns.
Relationships between tables.
Use SQL query language.

Think: Excel spreadsheets that can talk to each other.

Examples: PostgreSQL, MySQL, SQLite
AI Use Cases:
├── Store user conversations/history
├── Save AI processing results
├── Query structured business data
└── Track automation logs

TYPE 2: NoSQL DATABASE (Document)
───────────────────────────────────
Data stored as flexible JSON documents.
No strict schema (fields can vary per document).
Faster for simple lookups.

Think: A filing cabinet with labeled folders.

Examples: MongoDB, DynamoDB, Firestore
AI Use Cases:
├── Store chat history with varying structure
├── Cache API responses
├── Store AI model outputs
└── User preferences/profiles

TYPE 3: VECTOR DATABASE
─────────────────────────
Stores data as mathematical vectors (embeddings).
Searches by MEANING, not exact keywords.
Core technology behind RAG (Retrieval Augmented Generation).

Think: Library organized by topic/meaning, not by title.

Examples: Pinecone, Weaviate, ChromaDB, pgvector
AI Use Cases:
├── Semantic search ("find similar documents")
├── RAG (give LLM relevant context from knowledge base)
├── Recommendation systems
└── Duplicate detection
```

```python
# ─────────────────────────────────────────────────────────

def semantic_search(
    query: str,
    n_results: int = 3,
    category_filter: str = None
) -> list:
    """
    Find most semantically similar documents to query.
    
    WHY THIS IS MAGICAL:
    Query: "Can I get my money back?"
    → Converts to embedding vector
    → Finds documents closest in vector space
    → Returns refund policy (even without word "money back"!)
    
    Traditional keyword search would MISS this.
    Semantic search GETS it. ✅
    """
    
    # Build where filter if category specified
    where_filter = None
    if category_filter:
        where_filter = {"category": category_filter}
    
    results = knowledge_base.query(
        query_texts=[query],    # Your search query
        n_results=n_results,    # How many results to return
        where=where_filter,     # Metadata filter (optional)
        include=["documents", "metadatas", "distances"]
    )
    
    # Format results
    formatted_results = []
    for i in range(len(results["documents"][0])):
        formatted_results.append({
            "text": results["documents"][0][i],
            "metadata": results["metadatas"][0][i],
            "similarity_score": 1 - results["distances"][0][i]
            # Distance 0 = identical, Distance 1 = opposite
            # Score 1 = identical, Score 0 = opposite
        })
    
    return formatted_results

# ─────────────────────────────────────────────────────────
# COMPLETE RAG (Retrieval Augmented Generation)
# ─────────────────────────────────────────────────────────

def rag_answer(user_question: str) -> str:
    """
    RAG = Retrieve relevant knowledge → Augment LLM prompt → Generate answer
    
    This prevents hallucination by grounding LLM in real documents.
    """
    
    # STEP 1: RETRIEVE - Find relevant documents
    relevant_docs = semantic_search(query=user_question, n_results=3)
    
    if not relevant_docs:
        return "I don't have information about that in my knowledge base."
    
    # STEP 2: AUGMENT - Build context from retrieved docs
    context = "\n\n".join([
        f"Document {i+1} (Score: {doc['similarity_score']:.2f}):\n{doc['text']}"
        for i, doc in enumerate(relevant_docs)
    ])
    
    # STEP 3: GENERATE - LLM answers using context
    response = client.chat.completions.create(
        model="gpt-4",
        messages=[
            {
                "role": "system",
                "content": """You are a helpful customer support assistant.
                             Answer questions ONLY based on the provided context.
                             If the context doesn't contain the answer, 
                             say so clearly.
                             Never make up information."""
            },
            {
                "role": "user",
                "content": f"""Context from knowledge base:
                               {context}
                               
                               Customer Question: {user_question}
                               
                               Please answer based on the context above."""
            }
        ],
        temperature=0.1  # Very low → factual, grounded answers
    )
    
    return response.choices[0].message.content
```

## 🧮 Vector Database Math

```
HOW SIMILARITY SEARCH WORKS:

1. Text → Embedding Vector:
   "Can I get my money back?"
   → [0.23, -0.45, 0.78, 0.12, -0.33, ...]  (1536 dimensions)

2. Stored document vectors:
   "Refund Policy: 30 days..."
   → [0.25, -0.43, 0.76, 0.14, -0.31, ...]  (similar direction!)

3. Cosine Similarity:
   similarity = cos(θ) = (A · B) / (|A| × |B|)
   
   High similarity (close to 1.0) → Documents are semantically similar
   Low similarity (close to 0.0)  → Documents are unrelated

WHY COSINE SIMILARITY?
Because we care about DIRECTION (meaning), 
not MAGNITUDE (length of text).

A 1-word doc and a 1000-word doc about same topic
→ Same direction in vector space
→ High cosine similarity ✅

DIMENSIONS = MEANING:
Each dimension in the vector represents a 
latent "semantic feature"
(roughly: topic, sentiment, style, etc.)

Similar meanings → Similar directions in 1536-dimensional space
```

```python
def extract_pdf_content(pdf_path: str) -> dict:
    """
    Extract text, tables, and metadata from PDF.
    
    pdfplumber is better than PyPDF2 because:
    - Handles scanned PDFs better
    - Extracts tables as structured data
    - Preserves page structure
    """
    
    result = {
        "total_pages": 0,
        "text_by_page": [],
        "full_text": "",
        "tables": [],
        "metadata": {}
    }
    
    with pdfplumber.open(pdf_path) as pdf:
        
        result["total_pages"] = len(pdf.pages)
        result["metadata"] = pdf.metadata  # Author, date, etc.
        
        for page_num, page in enumerate(pdf.pages, 1):
            
            # Extract plain text
            page_text = page.extract_text() or ""
            result["text_by_page"].append({
                "page": page_num,
                "text": page_text
            })
            result["full_text"] += page_text + "\n"
            
            # Extract tables (returns list of lists)
            page_tables = page.extract_tables()
            for table in page_tables:
                if table:
                    # Convert to pandas DataFrame
                    df = pd.DataFrame(
                        table[1:],    # Data rows
                        columns=table[0]  # Header row
                    )
                    result["tables"].append({
                        "page": page_num,
                        "data": df.to_dict(orient="records")
                    })
    
    return result
```

```python
class RespectfulScraper:
    """
    Scraper that respects robots.txt and rate limits.
    A good AI engineer is an ethical engineer.
    """
    
    def __init__(
        self,
        base_url: str,
        delay_range: tuple = (1, 3),  # Random delay between requests
        user_agent: str = "MyAIBot/1.0 (contact@mycompany.com)"
    ):
        self.base_url = base_url
        self.delay_range = delay_range
        
        self.session = requests.Session()
        self.session.headers.update({
            "User-Agent": user_agent,
            "Accept": "text/html,application/xhtml+xml",
            "Accept-Language": "en-US,en;q=0.9"
        })
        
        # Check robots.txt on initialization
        self.robot_parser = self._load_robots_txt()
    
    def _load_robots_txt(self) -> RobotFileParser:
        """Parse robots.txt to know what we can/cannot scrape"""
        rp = RobotFileParser()
        robots_url = f"{self.base_url}/robots.txt"
        rp.set_url(robots_url)
        
        try:
            rp.read()
            print(f"✅ robots.txt loaded from {robots_url}")
        except Exception as e:
            print(f"⚠️ Could not load robots.txt: {e}")
        
        return rp
    
    def can_scrape(self, url: str) -> bool:
        """Check if we're allowed to scrape this URL"""
        is_allowed = self.robot_parser.can_fetch("*", url)
        if not is_allowed:
            print(f"🚫 robots.txt disallows scraping: {url}")
        return is_allowed
    
    def fetch_page(self, url: str) -> BeautifulSoup | None:
        """Fetch and parse a web page"""
        
        if not self.can_scrape(url):
            return None
        
        # Polite delay between requests
        delay = random.uniform(*self.delay_range)
        time.sleep(delay)
        
        try:
            response = self.session.get(url, timeout=30)
            response.raise_for_status()
            
            soup = BeautifulSoup(response.content, "html.parser")
            return soup
        
        except requests.exceptions.HTTPError as e:
            print(f"❌ HTTP Error: {e}")
            return None
        
        except requests.exceptions.Timeout:
            print(f"⏱️ Timeout scraping: {url}")
            return None
    
    def scrape_article(self, url: str) -> dict:
        """
        Extract structured data from a news article.
        
        Returns:
        - title
        - author
        - published date
        - main text content
        - images
        - links
        """
        
        soup = self.fetch_page(url)
        if not soup:
            return {"error": "Could not fetch page"}
        
        result = {"url": url}
        
        # Extract title (try multiple common selectors)
        title_selectors = ["h1", "article h1", ".article-title", 
                          ".post-title", '[property="og:title"]']
        for selector in title_selectors:
            element = soup.select_one(selector)
            if element:
                result["title"] = element.get_text(strip=True)
                break
        
        # Extract meta description
        meta_desc = soup.find("meta", {"name": "description"})
        if meta_desc:
            result["description"] = meta_desc.get("content", "")
        
        # Extract published date
        date_selectors = [
            '[property="article:published_time"]',
            "time[datetime]",
            ".publish-date",
            ".article-date"
        ]
        for selector in date_selectors:
            element = soup.select_one(selector)
            if element:
                result["published"] = (
                    element.get("datetime") or 
                    element.get("content") or 
                    element.get_text(strip=True)
                )
                break
        
        # Extract main text content
        # Remove navigation, ads, footers first
        for element in soup.select("nav, footer, .ads, .sidebar, script, style"):
            element.decompose()
        
        article_body = soup.select_one(
            "article, .article-body, .post-content, main"
        )
        
        if article_body:
            paragraphs = article_body.find_all("p")
            result["content"] = " ".join([
                p.get_text(strip=True) 
                for p in paragraphs 
                if len(p.get_text(strip=True)) > 50  # Skip short snippets
            ])
        
        # Extract images
        images = soup.find_all("img", src=True)
        result["images"] = [img["src"] for img in images[:5]]  # Max 5
        
        return result
```

```python
        {{
            "score": <0-100 integer>,

        response = client.chat.completions.create(

    def update_contact_with_ai_score(
        self,

    ):

        self.client.crm.contacts.basic_api.update(

    def generate_personalized_email(self, contact_properties: dict) -> dict:
        """
        Generate personalized sales email based on contact profile.
        
        NOT generic template — genuinely personalized by AI!
        """
        
        response = client.chat.completions.create(
            model="gpt-4",
            messages=[
                {
                    "role": "system",
                    "content": """You are an expert B2B sales copywriter.
                                 Write personalized, concise, value-focused emails.
                                 Never use generic phrases like 'I hope this finds you well'

                    "role": "user",

                    Name: {contact_properties.get('firstname')}
                    Title: {contact_properties.get('jobtitle')}
                    Company: {contact_properties.get('company')}

                    Key benefit: Saves 10 hours/week per rep
                    
                    Requirements:
                    - Subject line
                    - 3-4 sentences max body
                    - Specific call-to-action
                    - Reference their specific role/company
                    
                    Return JSON: {{
                        "subject": "...",
                        "body": "...",
                        "cta": "..."
                    }}"""
                }
            ],
            temperature=0.7,  # Some creativity for email
            response_format={"type": "json_object"}
        )
        
        return json.loads(response.choices[0].message.content)
    
    def full_lead_enrichment_pipeline(self, contact_id: str):
        """
        Complete AI-powered lead enrichment workflow:
        1. Get contact from HubSpot
        2. AI scores the lead
        3. AI generates personalized email
        4. Update HubSpot with results
        5. Send email via SendGrid
        6. Log activity in HubSpot
        """
        
        print(f"🚀 Starting enrichment for contact {contact_id}")
        
        # Step 1: Get contact
        contact = self.get_contact(contact_id)
        print(f"   📋 Contact: {contact.get('firstname')} - {contact.get('company')}")
        
        # Step 2: AI lead scoring
        score_result = self.ai_score_lead(contact)
        print(f"   🎯 AI Score: {score_result['score']}/100 ({score_result['tier']})")
        
        # Step 3: Generate email (only for hot/warm leads)
        email_content = None
        if score_result["tier"] in ["hot", "warm"]:
            email_content = self.generate_personalized_email(contact)
            print(f"   ✉️  Email generated: {email_content['subject']}")
        
        # Step 4: Update HubSpot
        self.update_contact_with_ai_score(
            contact_id=contact_id,
            ai_score=score_result["score"],
            tier=score_result["tier"],
            reasoning=score_result["reasoning"]
        )
        
        # Step 5: Send email to hot leads
        if score_result["tier"] == "hot" and email_content:
            send_ai_report_email(
                to_email=contact["email"],
                to_name=f"{contact.get('firstname', '')} {contact.get('lastname', '')}",
                subject=email_content["subject"],
                report_html=f"<p>{email_content['body']}</p><p>{email_content['cta']}</p>"
            )
            print(f"   📤 Personalized email sent!")
        
        return {
            "contact_id": contact_id,
            "score": score_result["score"],
            "tier": score_result["tier"],
            "email_sent": score_result["tier"] == "hot"
        }
```

**Q: How does RAG work? Walk me through the full process.**

```
Strong Answer:

"RAG = Retrieval Augmented Generation.
It solves the hallucination problem by grounding 
LLM responses in real documents.

The process has 3 phases:

INDEXING PHASE (Offline, done once):
1. Take your documents (PDFs, docs, web pages)
2. Split into chunks (~500 tokens each)
3. Convert each chunk to embedding vector using 
   embedding model (OpenAI text-embedding-3-small)
4. Store vectors + original text in vector database
   (Pinecone, ChromaDB, Weaviate)

RETRIEVAL PHASE (Every query):
1. User asks: 'What is our refund policy?'
2. Convert question to embedding vector
3. Find top-k most similar document chunks 
   using cosine similarity in vector DB
4. Retrieve original text of those chunks

GENERATION PHASE:
1. Build prompt: 'Here is relevant context: {retrieved_docs}
                  Answer this question: {user_question}'
2. LLM generates answer grounded in retrieved context
3. Optional: Ask LLM to cite which docs it used

The KEY benefit: LLM never makes up information
that contradicts your actual documents.
You can also update documents without retraining the LLM —
just re-index the new document.

Failure modes I watch for:
- Retrieval fails (wrong chunks returned) → Bad answer
- Chunks too large or too small → Poor retrieval
- Question phrased very differently from documents → Low similarity
- Documents not updated after policy changes → Stale answers"
```

**Q: Design a function calling system for a travel booking agent**

```
Strong Answer:

"I'd define these tools:

1. search_flights(origin, destination, date, passengers)
   → Returns available flights with prices
   
2. search_hotels(city, check_in, check_out, guests, budget)
   → Returns available hotels
   
3. get_weather_forecast(city, date)
   → Returns weather for travel planning
   
4. book_flight(flight_id, passenger_details)
   → Actually books (DANGEROUS — needs confirmation!)
   
5. book_hotel(hotel_id, guest_details, payment_token)
   → Books hotel room
   
6. calculate_total_cost(flight_price, hotel_price, days)
   → Math tool for trip total

Key engineering decisions:

TOOL DESCRIPTIONS matter most.
Be VERY specific about when to use each tool.
Bad description = wrong tool called.

CONFIRMATION before destructive actions.
Before book_flight executes:
→ Show user what will be booked
→ Require explicit confirmation
→ Then execute

PARALLEL tool calls for efficiency.
search_flights and search_hotels can run simultaneously.
LLM can call multiple tools in one response.

TOOL OUTPUT VALIDATION.
Parse tool output before giving to LLM.
Malformed JSON from API → Give LLM clean error message.

SAFETY RAILS.
book_flight requires valid flight_id from search_flights.
Cannot book without searching first.
Prevents hallucinated flight IDs."
```

# ⚠️ Common Mistakes Beginners Make

```
API MISTAKES:
❌ Hardcoding API keys in source code
   → GitHub exposure → Account hacked → Massive bill

❌ Not setting timeout on HTTP requests
   → Hangs forever on network issues

❌ Assuming response.json() always works
   → Server returns HTML error page → json.loads crashes

❌ Not implementing retry for 429/500 errors
   → 30% of production API calls fail silently

FUNCTION CALLING MISTAKES:
❌ Poor tool descriptions
   → LLM calls wrong tool → Wrong action taken

❌ Not validating tool arguments from LLM
   → LLM passes wrong type → Function crashes

❌ Exposing destructive tools without confirmation
   → AI deletes important data on misunderstanding

❌ No max iteration limit in agent loop
   → Infinite tool calling → Infinite API cost

DATABASE MISTAKES:
❌ SQL injection via string formatting
   f"SELECT * FROM users WHERE name = '{user_input}'"
   → Security disaster

❌ Not using connection pooling
   → New DB connection per request → Exhausts connections

❌ Fetching entire table when you need 10 rows
   → Performance disaster at scale

❌ No indexes on queried columns
   → Full table scan → Slow → Timeouts

FILE HANDLING MISTAKES:
❌ Not handling encoding (UTF-8 vs Latin-1)
   → Crashes on special characters

❌ Loading entire large file into memory
   → 10GB CSV → RAM exhausted → Crash
   → Use pandas chunking!

❌ Not cleaning temp files after processing
   → Disk fills up over time

SCRAPING MISTAKES:
❌ Not respecting robots.txt
   → Legal liability, IP ban

❌ No delay between requests
   → Rate limited or IP banned

❌ Scraping with exact CSS selectors
   → Site changes layout → Everything breaks immediately
```

# 🧠 Engineer Mindset

```
🧠 How a Senior AI Engineer Thinks About Tool Integration:

Q1: "Do I really need to build this integration?"
    → Maybe an existing library handles it (Zapier, LangChain)
    → Build only when you need custom control

Q2: "What are the security implications?"
    → Where are API keys stored? (Env vars, secrets manager)
    → What data am I sending to external APIs? (PII concern)
    → Am I complying with ToS? (Legal risk)

Q3: "What happens when this tool fails?"
    → Do I have a fallback?
    → Is this tool critical path or optional enhancement?
    → What's the user experience when tool fails?

Q4: "What are the cost implications at scale?"
    → API cost × calls/day × growth rate
    → When do I need to add caching?
    → When do I hit rate limits?

Q5: "How do I test this?"
    → Mock external APIs in unit tests
    → Use sandbox/test environments
    → Test with real API in staging (limited)

GOLDEN FRAMEWORK: For every tool integration ask:
SECURITY:     Who has access? What data leaves?
RELIABILITY:  What if it's down? Retry strategy?
COST:         How much at 10x current volume?
TESTING:      How do I test without real API calls?
MONITORING:   How do I know when it breaks in production?
```
