# 🔴 PART 1: Why Keyword Search Is Insufficient for Semantic Tasks

## 🧱 Start From First Principles — The Core Problem

Let me ask you a super simple question first.

These two sentences — are they the same?

```
Sentence A: "I can't get my phone to turn on"
Sentence B: "My mobile device won't power up"
```

**You as a human:** YES! Same problem. Same meaning.

**A traditional database:** ❌ TOTALLY DIFFERENT! Not even one word matches!

> **This is the entire reason Vector Databases exist.**

---

## 📖 What Is Keyword Search?

Most classical systems like TF-IDF or BM25 treat text as a **bag of words** — they count how often words appear, adjust for rarity, and **assume overlap = relevance.**

This works… until it doesn't.

### 🎯 The Hidden Assumption That Breaks Everything

Classic keyword search is built on a **dangerous assumption**: Users and documents use the **same words.**

But in real life, this assumption is almost always false.

**Real examples where keyword search completely fails:**

| User Types | Document Has | Keyword Match? | Should Match? |
|-----------|-------------|----------------|---------------|
| "car won't start" | "vehicle fails to ignite" | ❌ 0 words match | ✅ Yes! |
| "feeling sad" | "experiencing depression" | ❌ 0 words match | ✅ Yes! |
| "cheap food near me" | "affordable restaurants nearby" | ❌ 0 words match | ✅ Yes! |
| "ML model training slow" | "neural network optimization bottleneck" | ❌ 0 words match | ✅ Yes! |

---

## 📖 Understanding the Failure — Intent Mismatch

This is called an **intent mismatch**: **lexical similarity** (same words) fails to capture **semantic similarity** (same meaning).

There are **4 specific ways** keyword search fails for AI tasks:

---

### ❌ Failure Type 1: Synonym Problem

```
User query:   "automobile accident"
Document has: "car crash"

Keyword match = 0   (But meaning is 100% same!)
```

---

### ❌ Failure Type 2: Paraphrase Problem

```
User query:   "What's the weather like?"
Document has: "How is the climate today?"

Keyword match = 0   (But same question!)
```

When you read the questions "What's the weather like?" and "How's the weather today?", you instantly know they mean the same thing. But **a traditional database searching for exact matches would see these as completely different strings.**

---

### ❌ Failure Type 3: Context & Ambiguity Problem

The word **"bank"** has 2 completely different meanings:
- 🏦 Financial bank
- 🌊 River bank

Context doesn't exist in keyword systems. "Bank" (money) = "bank" (river). To a production system, those are **identical — and that's fatal for search.**

---

### ❌ Failure Type 4: Multimedia & Multimodal Problem

Classic search engines rely on tokenization, synonyms, and inverted indexes, which are fast and scalable, but often **fail to capture user intent** or handle complex queries. They also **struggle with image, audio, and video searches.**

You cannot keyword-search an image. There are no words inside a picture file!

---

### 🔴 The Bottom Line — Traditional Search Has a Fundamental Ceiling

PostgreSQL, MySQL, and Oracle have powered enterprise systems for decades, optimized for clearly defined schemas, transactional integrity, and predictable performance. They **excel at answering what you asked, not what you meant.**

Modern AI systems don't just look for exact matches — they look for **meaning**. They need to understand similarity, context, and relationships buried in text, images, and signals. A relational database can tell you that two records share an ID, but **it can't tell you that two sentences mean the same thing.**

# 🟡 PART 2: From Symbolic Matching → Semantic Similarity

## 🏛️ The Historical Journey — How We Got Here

This is the **evolution of how computers understood language.** Think of it as 3 generations of thinking.

---

## 🧱 Generation 1: Symbolic / Rule-Based Systems (1950s–1990s)

### What was it?

Before the 1990s, approaches for solving NLP problems were **predominantly symbolic**. Symbolic systems directly model abstract concepts and the innate structure of the human mind. Elementary semantics are represented by symbols. Complex semantics are represented by a group of symbols combined by operations and syntactic structures. Many early AI advances utilized a symbolic approach to AI programming, striving to create smart systems by modeling relationships and using symbols and programs to convey meaning.

### Simple Example:

```
Rule-based system for customer support:
IF query contains "refund" → show refund policy
IF query contains "delivery" → show shipping info
IF query contains "broken" → show warranty page
```

### Why this fails:

```
User types: "My item arrived damaged, I want my money back"
Contains: "refund"? ❌  "delivery"? ❌  "broken"? ❌
Result: No match found! → Frustrating user experience
```

**Problem:** You can't write rules for every possible way a human might say something. Language is infinite in its variation.

---

## 🧱 Generation 2: Statistical / Keyword Methods (1990s–2013)

### TF-IDF and BM25 — The Smart Keyword Systems

These were smarter than pure rules. Instead of exact word rules, they counted and scored words statistically.

**TF-IDF = Term Frequency × Inverse Document Frequency**

```
"Frequency of a word in THIS document"
×
"How rare this word is across ALL documents"
= Importance score of that word
```

**Example:**

```
Document: "The quick brown fox jumps over the lazy dog"

Word: "fox"    → TF = 1/9 = 0.11 | Rare word → High IDF → High score ✅
Word: "the"    → TF = 2/9 = 0.22 | Very common → Low IDF → Low score ✅
Word: "jumps"  → TF = 1/9 = 0.11 | Medium rare → Medium score ✅
```

**Why TF-IDF was better:** Rare words that appear in a document are probably what the document is ABOUT.

**Why TF-IDF still fails:**

```
Document 1: "automobile engine repair"
Document 2: "car motor fixing"

Query: "vehicle engine maintenance"

TF-IDF score with Doc 1 = LOW (only "engine" matches)
TF-IDF score with Doc 2 = LOW (zero words match!)

But BOTH documents are about the same thing!
```

Traditional keyword-based searches **struggle to capture the deeper relationships between words**, images, and structured data.

---

## 🧱 Generation 3: Semantic / Embedding Methods (2013–Present)

### The Revolution: Word2Vec → BERT → Modern Embeddings

Semantic similarity — the task of quantifying how much two pieces of text mean alike — has long been a cornerstone of NLP. The evolution traces a journey from **early lexical methods to today's advanced, context-aware models.**

This evolution traces from traditional NLP techniques such as **kernel-based methods to the most recent research work on transformer-based models**, categorized as knowledge-based, corpus-based, deep neural network-based methods, and hybrid methods.

### The Key Shift in Thinking:

| Old Thinking (Symbolic) | New Thinking (Semantic) |
|------------------------|------------------------|
| Compare CHARACTERS | Compare MEANING |
| Exact word match | Conceptual closeness |
| "cat" ≠ "kitten" | "cat" ≈ "kitten" (very close!) |
| Rules written by humans | Patterns learned by AI |
| Works on structured data | Works on ANY data |

---

### 🌟 The 2013 Breakthrough: Word2Vec

Word2Vec was the first proof that **meaning could be geometric** — represented as positions in mathematical space.

Early models that learn word meaning from co-occurrence in text (such as Word2Vec-style and GloVe-style embeddings) were the **first proof that meaning could be geometric**. Relationships like **king − man + woman ≈ queen** changed NLP forever.

Let me show you what this means:

```
Vector("King")   - Vector("Man") + Vector("Woman") = Vector("Queen")

This is MATH operating on MEANING!

King = [0.9, 0.1, 0.8, ...]  (Royal + Male + Power)
Man  = [0.1, 0.9, 0.1, ...]  (Male)
Woman= [0.1, 0.1, 0.9, ...]  (Female)
Queen= [0.9, 0.1, 0.9, ...]  (Royal + Female + Power)

Do the math → King - Man + Woman ≈ Queen   ✅ MAGIC!
```

But Word2Vec had one fatal flaw:

Context doesn't exist in Word2Vec. **"Bank" (money) = "bank" (river)** — same word, same vector, completely different meaning.

### The 2018 Solution: BERT (Contextual Embeddings)

BERT solved this by reading the ENTIRE sentence before creating a vector. Now "bank" in "river bank" and "bank" in "bank account" get DIFFERENT vectors — because BERT reads the full context.

```
"I went to the river bank"     → "bank" vector points toward WATER
"I went to the bank to deposit" → "bank" vector points toward FINANCE
```

**Modern embedding models (OpenAI, Cohere, etc.) are even more powerful versions of this idea.**

# 🟢 PART 3: Embeddings as Numerical Representations

## 🧱 What Is an Embedding — From Absolute Zero

### The Core Question: How Do You Turn Meaning Into Math?

**Step 1 — The Problem:**

Computers don't understand words. Computers only understand numbers.

```
Computer sees: "cat" → ??? (computer has no idea what this means)
Computer sees: [0.23, -0.41, 0.87, 0.12, ...] → CAN COMPUTE! 🎉
```

**Step 2 — The Insight:**

If we make similar things have similar numbers → math becomes meaning!

```
"cat"    → [0.90, 0.10, 0.20, 0.05, ...]
"kitten" → [0.85, 0.12, 0.22, 0.04, ...]  ← Very close to "cat"!
"server" → [0.10, 0.90, 0.70, 0.80, ...]  ← Far from "cat"
```

Now a computer can measure: "cat and kitten are similar" using pure math!

---

## 📐 What Is an Embedding Model?

Embedding models are ML techniques that **render words and phrases into complex numerical representations**, which are then classified based on their context and relationships.

Think of the embedding model as a **Translation Machine:**

```
Input:  Any Data (Text / Image / Audio / Video / Code)
           ↓
    [Embedding Model - Deep Neural Network]
           ↓
Output: A Fixed-Length List of Numbers (the Vector)

Example:
"The dog is running fast"
           ↓
[OpenAI text-embedding-3-small]
           ↓
[0.023, -0.412, 0.871, 0.034, -0.209, 0.567, ..., 0.112]
 ← ——————————— 1536 numbers total ————————————————————→
```

---

## 🌍 What Do These Numbers Actually Mean?

This is the deep question. Each number represents a **latent feature** — a hidden dimension of meaning.

Because each dimension represents a **latent feature — an inferred characteristic learned through mathematical models and algorithms** — vector representations capture hidden patterns. A vector search query for "smartphone" can also return semantically related results such as "cellphone" or "mobile device," even if those exact words do not appear.

Let's make it visual with a simplified 3D example:

```
Imagine each word has 3 features: [Animal?, Tech?, Danger?]
                                    (0-1)   (0-1)   (0-1)

"dog"        = [0.95,  0.02,  0.10]
"cat"        = [0.93,  0.01,  0.05]
"laptop"     = [0.01,  0.97,  0.02]
"lion"       = [0.90,  0.01,  0.85]
"virus"      = [0.02,  0.80,  0.95]

Distance:
dog ↔ cat = SMALL  → They are similar ✅
dog ↔ laptop = BIG → Very different ✅
lion ↔ dog = MEDIUM → Both animals, but lion is dangerous ✅
```

In reality, modern embeddings have **768 to 3072 dimensions** — each capturing incredibly subtle aspects of meaning!

---

## 📊 Types of Embeddings You Must Know

These vectors are typically generated by machine learning models like **transformers or convolutional neural networks** and capture semantic meaning in a way that traditional databases are not built for.

| Data Type | Model | Output |
|-----------|-------|--------|
| Text | OpenAI, BERT, Sentence-BERT | Dense vector [1536d] |
| Images | CLIP, ResNet, ViT | Dense vector [512d] |
| Audio | Wav2Vec, Whisper | Dense vector [768d] |
| Code | CodeBERT, StarCoder | Dense vector [768d] |
| Multimodal | CLIP, ImageBind | Shared vector space |

---

## 🔑 The Key Property of Embeddings — The Golden Rule

Embeddings represent words and sentences in a manner that captures their semantic meaning, and these representations contain a list of real-valued numbers, where **words or sentences with similar meanings are located close to each other in the vector space.**

```
GOLDEN RULE:
Similar Meaning → Similar Vector → Small Distance Between Vectors

Different Meaning → Different Vector → Large Distance Between Vectors
```

# 🔵 PART 4: Why Similarity Search Requires Specialized Indexing

## 🧱 The Performance Problem — Why Normal Indexing Fails

### First, What Is Indexing in a Normal Database?

Think of a book's INDEX at the back. Instead of reading every page to find "Machine Learning," you check the index → "Machine Learning: pages 45, 89, 122."

Normal databases use **B-Trees** as their index:

```
B-Tree Index Example (for age column):

              [50]
            /      \
         [25]       [75]
        /    \     /    \
      [10]  [30] [60]  [90]

Search: "Find age = 30"
→ Start at 50 → go left (30 < 50) → go right (30 > 25) → FOUND!
Only visited 3 nodes out of 7! Very fast!
```

**B-Trees are perfect for:** Exact matches (id = 123), Range queries (age > 25), Sorting.

---

### 🚨 Why B-Trees Completely Fail for Vector Search

Traditional databases use indexing methods like B-trees and hash tables, which are well-suited for **scalar data types**. These indexing methods are designed for **efficient exact-match searches and range queries**. Vector databases employ specialized indexing methods optimized for high-dimensional spaces, like HNSW.

**The core mismatch:**

```
B-Tree asks: "Is this EQUAL TO that?" (exact match)
Vector Search asks: "Is this SIMILAR TO that?" (nearest neighbor)

These are fundamentally different questions!
A B-Tree cannot answer "find the 5 most similar vectors to [0.2, 0.8, ...]"
```

---

### 🔥 The Brute Force Problem — The Billion Operations Issue

Without smart indexing, what must you do?

```
You have: 1 million documents stored as 1536-dimensional vectors
User asks: one question (1536-dimensional query vector)

Brute force approach:
Compare query to document 1: 1536 multiplications + additions
Compare query to document 2: 1536 multiplications + additions
...
Compare query to document 1,000,000: 1536 multiplications + additions

Total = 1,536,000,000 mathematical operations per query!
```

Each search query compares your input against every vector in your database. With 1024- or 1536-dimensional vectors, that's **over a billion floating-point operations per million vectors searched**. Your search feature becomes unusable.

---

### 💀 The Curse of Dimensionality — The Math Enemy

Indexes like B-trees or hash maps **fall apart in high dimensions** — a phenomenon known as the **curse of dimensionality**. As dimensions increase, **nearly all points appear equidistant**, making scans and traditional indexes increasingly ineffective.

Let me explain this curse intuitively:

```
2D Space (x, y coordinates):
  Point A = (1, 0)
  Point B = (0, 1)
  Distance A to B = √(1² + 1²) = 1.41

1536D Space (1536 coordinates):
  If we add 1534 more dimensions, and each adds a tiny bit of distance...
  ALL points become roughly the same distance from each other!

  Distance(A,B) ≈ Distance(A,C) ≈ Distance(A,D) ≈ Distance(A,E)

Nearest neighbor becomes meaningless because nothing is "close" — 
everything is equally far!
```

Traditional similarity-based indexes like KD-tree work well on **low-dimensional data** but perform weakly on high-dimensional data due to the curse of dimensionality. Since neural embeddings are normally **high-dimensional vectors (several hundreds of dimensions)**, they require high-dimensional similarity-based indexing methods.

---

### ✅ The Solution: Approximate Nearest Neighbor (ANN) Search

The brilliant insight that powers all vector databases:

**You don't need perfect results.** Finding the 10 most similar items out of a million is nearly identical to finding the absolute top 10, but the approximate version can be **a thousand times faster.**

Vector databases solve this with specialized algorithms that **avoid brute-force distance calculations**. Instead of checking every vector, they use techniques like hierarchical graphs and spatial partitioning to examine only a **small percentage of candidates** while still finding nearest neighbors.

---

### 🏆 The Key Indexing Algorithms (Overview — Deep Dive Later)

Techniques such as **flat indexing, Hierarchical Navigable Small World (HNSW), and Locality Sensitive Hashing (LSH)** help balance precision, search speed, memory usage, and scalability.

```
HNSW (Best for Speed + Recall):
Think: Multi-level highway map
- Level 3: Skip directly to the right neighborhood (fast)
- Level 2: Narrow down the street
- Level 1: Find exact house
→ Search millions of vectors in <10ms ✅

IVF (Best for Large Scale):
Think: Library shelves organized by topic
- First find the right shelf (cluster)
- Then search only within that shelf
→ Reduces 1M comparisons to ~1K ✅

LSH (Best for Memory Efficiency):
Think: Hash buckets for similar items
- Similar vectors → same bucket
- Search only within bucket
→ Fast but lower recall ✅
```

---

### 📊 The Speed vs. Accuracy Tradeoff — Engineer Decision

| Method | Search Speed | Accuracy | Use Case |
|--------|-------------|----------|----------|
| Brute Force | 😱 Very Slow | 100% Perfect | <10K vectors only |
| IVF | ⚡ Fast | 95-98% | Millions of vectors |
| HNSW | ⚡⚡ Very Fast | 97-99% | Production standard |
| LSH | ⚡ Fast | 85-95% | Low memory environments |

# 🧪 PART 6: Failure Modes — Where It All Breaks

Understanding failures is what separates junior and senior engineers in interviews.

---

## ❌ Failure 1: The Vocabulary Gap (Keyword Search)

```
Keyword search for medical records:
Patient complaint: "I feel like my heart is racing and I'm short of breath"
Medical document uses: "tachycardia and dyspnea"

Keyword match = 0   →  Critical information MISSED!
```

Due to the ambiguity of language, synonyms, and other roadblocks, **keyword search will sometimes fail to find the right response.**

---

## ❌ Failure 2: Domain Mismatch in Embeddings

A general-purpose embedding model trained on Wikipedia will perform badly on:
- Medical terminology
- Legal documents
- Code search
- Domain-specific slang

**Why:** The model has never seen these domain words in context during training. Its vectors for "tachycardia" and "fast heart" are FAR apart — but they should be close!

**Fix:** Use domain-specific fine-tuned embedding models.

---

## ❌ Failure 3: Exact Match Terms Fail in Vector Search

```
User searches: "Product SKU-XY-2024-89"
Vector search: Returns semantically "similar" SKUs — but user wants EXACT one!

"SKU-XY-2024-89" and "SKU-XY-2023-88" are extremely similar numerically
but completely different products!
```

**Fix:** Use hybrid search — combine vector similarity with exact keyword/filter matching.

---

## ❌ Failure 4: B-Tree Index Fails High-Dimensional Data

Traditional databases are not optimized for similarity search because their indexing structures (e.g., B-trees, hash indexes) are **designed for exact matches and don't efficiently support distance calculations in high-dimensional spaces.**

```
B-Tree on 1536-dimensional vectors:
- Every vector looks "different" from every other vector
- B-tree degrades to full table scan
- 1M vectors × 1536 dims = 1.5 BILLION operations
- Response time: Minutes instead of milliseconds!
```

---

## ❌ Failure 5: Storing Raw Vectors in a Traditional DB

Embeddings are dense, high-dimensional floating-point vectors. Naive storage in relational tables or JSON documents results in: **Large storage footprints** (hundreds of GB to TBs for millions of vectors), **poor cache locality** and memory efficiency, and **slow scan performance**, especially if vectors are stored in row-major formats instead of block-aligned layouts optimized for similarity search.

# 🎤 PART 7: Interview Questions & Strong Answers

## 🟢 Beginner Questions

---

**Q1: Why is keyword search not enough for AI applications?**

> **Strong Answer:**
> "Keyword search relies on exact word matching — it can only find documents that share the same words as the query. This fails when users use synonyms, paraphrases, or ask questions differently than documents are written. For example, a user asking 'car won't start' will never find a document about 'vehicle ignition failure' via keyword search. AI applications need to understand *intent and meaning*, not just word overlap. This is the fundamental limitation that vector databases and semantic search solve."

---

**Q2: What is an embedding? Why is it useful?**

> **Strong Answer:**
> "An embedding is a dense numerical vector representation of data — text, image, audio, or any other type. It's generated by a neural network model that has learned to compress the *meaning* of data into a fixed-length list of numbers. The key property is: similar things have similar vectors — they are close together in vector space. This makes it possible to do mathematical similarity computation on abstract concepts. Without embeddings, a computer has no way to measure that 'cat' and 'kitten' are related."

---

**Q3: What is the difference between a vector database and a traditional database?**

> **Strong Answer:**
> "The core difference is in the type of question they answer. A traditional database answers 'Find records WHERE condition is EQUAL TO value' — it's designed for exact match queries using B-tree indexes. A vector database answers 'Find items that are MOST SIMILAR IN MEANING to this query' — it's designed for approximate nearest neighbor search using specialized indexes like HNSW. Traditional databases are excellent for structured data, ACID transactions, and CRUD operations. Vector databases are purpose-built for semantic search, RAG pipelines, and AI applications. In production, you almost always use both together."

---

## 🟡 Intermediate Questions

---

**Q4: Why can't we just add a vector column to PostgreSQL and do similarity search there?**

> **Strong Answer:**
> "You can — pgvector does exactly this — but it has real limitations at scale. The core problem is that B-tree indexes, which PostgreSQL uses, cannot efficiently index high-dimensional vectors. As the number of dimensions increases, a phenomenon called the curse of dimensionality means all vectors appear equidistant, making the index degrade to a full table scan. For 1 million vectors with 1536 dimensions, that's 1.5 billion floating-point operations per query. Dedicated vector databases implement specialized ANN indexes like HNSW that can search millions of vectors in under 10ms. pgvector added HNSW support in v0.5.0, making it more viable, but for high-scale or low-latency requirements, a dedicated vector database still outperforms."

---

**Q5: What is the curse of dimensionality and why does it matter for vector search?**

> **Strong Answer:**
> "The curse of dimensionality is a mathematical phenomenon where as the number of dimensions grows, all points in the space begin to appear equally distant from each other. In a 2D space, we have clear notions of 'near' and 'far.' In a 1536-dimensional space, the distance between any two random points converges to nearly the same value — making the concept of 'nearest neighbor' meaningless. For vector search, this means traditional distance-based indexes like KD-trees completely break down above ~10 dimensions, since they degrade to brute-force linear scans. This is why vector databases use specialized approximate algorithms like HNSW that are specifically designed to navigate high-dimensional geometry efficiently."

**Q6: Design a semantic search system for 10 million customer support tickets. What are your technical decisions?**

> **Strong Answer:**
> "I would structure the system as follows:
> - **Embedding model**: OpenAI text-embedding-3-small (1536d) for English, or BAAI/bge-m3 for multilingual
> - **Chunking**: Each ticket is already a short text, so no chunking needed; just clean and normalize
> - **Vector DB**: Qdrant (self-hosted) for cost at this scale, with HNSW indexing
> - **Metadata filtering**: Index by date, category, priority, resolved status in metadata — this enables filtered search like 'find similar tickets from last month that were resolved quickly'
> - **Hybrid search**: Combine vector search with BM25 for ticket IDs and exact error codes
> - **Evaluation**: Measure recall@5 and MRR against human-labeled relevant tickets
> - **Failure monitoring**: Track queries where top-1 similarity score < 0.75 — these likely indicate domain coverage gaps in the embedding model
> - **Scaling**: Horizontal sharding by date range, with replica read nodes for query load distribution"

# ⚠️ PART 8: Common Beginner Mistakes

| Mistake | Why Wrong | What To Do Instead |
|---------|-----------|-------------------|
| "Vector DB replaces SQL DB" | They solve different problems | Use both together |
| "Higher dimensions = always better" | Curse of dimensionality | Benchmark for YOUR domain |
| "Any embedding model will work" | Domain mismatch causes poor search | Choose model trained on similar domain |
| "Exact word search ≠ semantic search" misunderstood | Sometimes exact match IS needed | Use hybrid search for both |
| "Cosine similarity always works for images" | Images may need Euclidean distance | Match distance metric to data type |
| "Vector DB can replace an LLM" | Vector DB finds, LLM generates | They work TOGETHER not instead |
| "Store full documents in the vector" | Full doc loses specific detail | Always chunk before embedding |

# 🧠 PART 10: Engineer Mindset — Think Like a Senior

```
When I approach a new AI project, I ask:

❓ Question 1: What type of search do users need?
   → Exact match only?  → Traditional DB is fine
   → Semantic/meaning?  → Need vector DB
   → Both?              → Hybrid approach

❓ Question 2: How large is my dataset?
   → <10K docs?         → FAISS locally is fine
   → 10K–1M?           → pgvector or Chroma
   → 1M–1B?            → Dedicated: Qdrant, Pinecone, Weaviate

❓ Question 3: What embedding model for my domain?
   → General English?   → OpenAI text-embedding-3
   → Code?              → CodeBERT
   → Multilingual?      → Cohere multilingual-v3 / BAAI/bge-m3
   → Images?            → CLIP

❓ Question 4: What are my latency requirements?
   → <10ms?             → HNSW, in-memory
   → <100ms?            → HNSW with disk offloading
   → <1s acceptable?    → IVF

❓ Question 5: Do I need metadata filtering?
   → Yes (date, category, user_id)? → Qdrant or Weaviate
   → No?                → Any vector DB works

❓ Question 6: What can AI automate vs. what must I decide?
   AI automates: Embedding generation, ANN search, ranking
   I decide: Model choice, chunking strategy, evaluation criteria,
             metadata schema, indexing algorithm, failure thresholds
```
