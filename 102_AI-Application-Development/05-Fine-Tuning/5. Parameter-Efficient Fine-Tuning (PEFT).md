## 2. The Three Problems PEFT Must Solve

```
PROBLEM 1: MEMORY
──────────────────
Full fine-tuning requires loading ALL parameters
+ gradients + optimizer states into GPU memory.
For large models, this is physically impossible
on available hardware.

PROBLEM 2: COMPUTE
────────────────────
Training ALL parameters means computing gradients
for ALL parameters in every backward pass.
For 70B parameters → enormous compute cost.
Even with big GPUs → takes weeks.

PROBLEM 3: CATASTROPHIC FORGETTING + STORAGE
─────────────────────────────────────────────
If you fully fine-tune the SAME base model for:
→ Customer service bot (Task A)
→ Medical assistant (Task B)
→ Code generator (Task C)

You need THREE separate copies of the full model.
LLaMA 70B × 3 tasks = 3 × 140 GB storage = 420 GB

And each fine-tune risks destroying knowledge
from the previous task (catastrophic forgetting).

PEFT must solve ALL THREE simultaneously.
```

# 📦 TOPIC 2 — Freezing Base Weights

---

## 1. What Does "Freezing" Mean?

### Simple English Definition:

> **Freezing** a parameter means telling the training process: **"Do NOT update this parameter during training."** The weight stays exactly the same throughout the entire fine-tuning process — as if it were locked in place permanently.

```
FREEZING IN CODE (PyTorch):

for param in model.parameters():
    param.requires_grad = False   ← FROZEN

# Only specific parts remain trainable:
for param in adapter_layers.parameters():
    param.requires_grad = True    ← TRAINABLE

WHAT requires_grad MEANS:
→ requires_grad = True  → Calculate gradient → update this weight
→ requires_grad = False → SKIP this weight → it never changes
```

---

## 2. Why Can You Freeze And Still Learn?

### This Is The Deep Question — And The Answer Is Beautiful

```
BEGINNER'S CONFUSION:
"If I freeze most of the model, how can anything change?
 How does the model learn if the weights don't change?"

THE ANSWER:
Learning happens in the TRAINABLE PARTS ONLY.
But the frozen parts still PARTICIPATE in computation.

ANALOGY — A PIPE SYSTEM:
────────────────────────────
Imagine water flowing through pipes.

FROZEN WEIGHTS = Existing pipes (shape doesn't change)
ADAPTER WEIGHTS = A small new valve you install in the system

When you turn the valve (adapter), you redirect water flow.
The old pipes don't change — but the overall FLOW PATTERN changes.
The output of the system changes.

IN NEURAL NETWORKS:
Frozen layers still transform the input.
They still produce intermediate representations.
The trainable adapter layers modify THESE representations.
The final output changes — even though frozen weights are fixed.
```

---

## 3. Gradient Flow in Frozen vs Trainable Layers

### This Is Critical For Deep Understanding

```
NEURAL NETWORK DURING TRAINING — TWO PHASES:

FORWARD PASS:
─────────────
Input → [Frozen Layer 1] → [Frozen Layer 2] → [Adapter] → Output
          (computes)         (computes)          (computes)
          
ALL layers participate in forward computation.
Frozen layers DO transform the input.
They just won't be updated.

BACKWARD PASS (Where Freezing Matters):
─────────────────────────────────────────
Loss → ∂Loss/∂output → ... → ∂Loss/∂adapter_weights → UPDATE
                                                          ↑
                       Gradients flow back through here.
                       Only adapter weights GET UPDATED.

For frozen layers:
Loss → ∂Loss/∂frozen_weights → COMPUTED but DISCARDED
                                (requires_grad=False)

WAIT — Why compute gradients through frozen layers
        if we discard them?

ANSWER:
We need gradients to PASS THROUGH frozen layers
(in the backward direction) to REACH the adapter layers.

Frozen layers act like a HIGHWAY for gradients.
They don't absorb the gradient (no update).
But they pass it along to the trainable layers behind them.

VISUAL:

FORWARD:  Input →→→→→→→→→→→→→→→→→→→→→→ Output
                 (frozen)  (frozen)  (adapter)

BACKWARD: Input ←←←←←←←←←←←←←←←←←←←← Loss
          (not updated) (not updated) (UPDATED ✅)
          
Gradient flows backward through frozen layers.
Only adapter updates happen.
```

---

## 4. What Actually Happens Inside Frozen Weights During PEFT?

### The Representation Hypothesis

```
THE DEEP INSIGHT FROM RESEARCH:

When a large model is pretrained on massive data,
its frozen weights learn RICH REPRESENTATIONS.

Think of it like this:

Each layer transforms the input into a new "view" of the data.

Layer 1: Sees basic word patterns ("dog", "cat", "runs")
Layer 5: Sees grammatical structures (subject-verb agreement)
Layer 10: Sees semantic relationships ("doctor" near "medicine")
Layer 20: Sees high-level concepts ("intent", "instruction type")

THESE REPRESENTATIONS ARE ALREADY GREAT.
They were learned from trillions of tokens.
WE DON'T WANT TO CHANGE THEM.

WHAT PEFT DOES:
Instead of relearning these representations from scratch,
PEFT adds small modules that COMBINE and REDIRECT
these existing representations.

IT IS LIKE:
You have a magnificent painting.
You don't repaint it.
You just add a new frame that changes
how the light hits it — and changes the viewer's perception.

The painting (frozen weights) = unchanged.
The frame (adapter) = small addition.
The perception (model output) = meaningfully different.
```

## 5. Partial Freezing Strategies

```
NOT ALL PEFT FREEZES EVERYTHING EQUALLY.
Engineers choose WHICH layers to freeze strategically:

STRATEGY 1: FREEZE ALL, ADD ADAPTERS
──────────────────────────────────────
→ Freeze 100% of original model
→ Add small adapter modules
→ Only train adapters
→ Used by: LoRA, Houlsby Adapters
→ Efficiency: Maximum ✅
→ Risk: Adapters must do all the work

STRATEGY 2: FREEZE EARLY LAYERS, TRAIN LATE LAYERS
────────────────────────────────────────────────────
→ Early layers (1-N/2): Frozen (learn universal patterns)
→ Late layers (N/2-N): Trainable (task-specific patterns)
→ Used by: Feature extraction + fine-tuning hybrid
→ Rationale: Late layers are more task-specific anyway
→ Requires: More memory than full freezing

STRATEGY 3: TRAIN ONLY SPECIFIC COMPONENTS
────────────────────────────────────────────
→ Freeze: Attention weights, MLP weights
→ Train only: Bias terms (BitFit method)
→ Train only: Layer normalization parameters
→ Very parameter-efficient (< 0.1% trainable)
→ Works surprisingly well for many tasks

STRATEGY 4: ADAPTIVE FREEZING (Advanced)
──────────────────────────────────────────
→ Use importance scores to decide which to train
→ Layers with high task importance → unfreeze
→ Layers with low importance → freeze
→ Used by: AdaLoRA, Diff Pruning
→ Computationally expensive but optimal efficiency

CHOOSING A STRATEGY:
Very little compute → Strategy 1 (full freeze + adapters)
Moderate compute → Strategy 2 (partial freeze)
Tiny compute → Strategy 3 (bias only)
Research setting → Strategy 4 (adaptive)
```

# 📦 TOPIC 3 — Adapter-Based Training

---

## 1. The Original Adapter (Houlsby et al., 2019)

### Where It All Started

```
HISTORICAL CONTEXT:
In 2019, researchers at Google asked:
"Can we fine-tune BERT for 100 different tasks
 without storing 100 copies of BERT?"

THEIR SOLUTION: Adapter Modules
→ Add small new layers INSIDE the transformer
→ Freeze everything else
→ Only train these small new layers

RESULT:
→ One copy of BERT (frozen)
→ 100 tiny adapter files (one per task)
→ Load adapter at runtime for the desired task
→ Same performance as full fine-tuning!
```

### The Original Adapter Architecture:

```
TRANSFORMER BLOCK (without adapter):
─────────────────────────────────────
Input
  ↓
[Multi-Head Attention]
  ↓
[Layer Norm]
  ↓
[Feed-Forward Network]
  ↓
[Layer Norm]
  ↓
Output

TRANSFORMER BLOCK (with Houlsby Adapter):
───────────────────────────────────────────
Input
  ↓
[Multi-Head Attention]  ← FROZEN
  ↓
[ADAPTER MODULE] ← NEW! TRAINABLE
  ↓
[Layer Norm]           ← FROZEN
  ↓
[Feed-Forward Network] ← FROZEN
  ↓
[ADAPTER MODULE] ← NEW! TRAINABLE
  ↓
[Layer Norm]           ← FROZEN
  ↓
Output

TWO ADAPTER MODULES PER TRANSFORMER BLOCK.
Adapters are inserted after attention AND after FFN.
```

## 2. Inside An Adapter Module

### The Three-Layer Structure:

```
ADAPTER MODULE INTERNALS:

Input (d_model dimensions, e.g., 768 for BERT-base)
  ↓
[DOWN-PROJECTION]
  Linear layer: d_model → r
  (Compress from 768 → 64 dimensions)
  (r = bottleneck dimension, much smaller than d_model)
  ↓
[ACTIVATION FUNCTION]
  Usually ReLU or GeLU
  (Add non-linearity)
  ↓
[UP-PROJECTION]
  Linear layer: r → d_model
  (Expand back from 64 → 768 dimensions)
  ↓
[RESIDUAL CONNECTION]
  Output = UP_PROJ + Input (add original input back)
  ↓
Output (d_model dimensions, same as input)
```

### Why The Residual Connection Is Critical:

```
THE RESIDUAL CONNECTION TRICK:

Output = Adapter(Input) + Input

WHY THIS IS BRILLIANT:

At the START of training:
→ Adapter weights are initialized near zero
→ Adapter(Input) ≈ 0 (near-zero output)
→ Output ≈ 0 + Input = Input
→ Adapter is INVISIBLE — model behaves like original!

As training progresses:
→ Adapter weights gradually become non-zero
→ Adapter(Input) starts to matter
→ Output starts changing meaningfully
→ Adapter gradually steers the model's behavior

THE RESULT:
→ Training is stable (starts from working model)
→ No risk of destroying original capabilities at start
→ Gradual, controlled adaptation
→ If adapter weights stay near zero → no effect (safe default)

THIS IS CALLED: NEAR-IDENTITY INITIALIZATION
It ensures PEFT training starts from a stable point.
```

## 5. LoRA — The Core Mathematical Insight

### From Absolute Zero 🐢

#### Step 1 — Understand What A Weight Matrix Is

```
In a Transformer, the key operations are:
Q = W_Q × X    (Query projection)
K = W_K × X    (Key projection)
V = W_V × X    (Value projection)
O = W_O × X    (Output projection)

Where:
X     = Input (d_model × sequence_length matrix)
W_Q   = Query weight matrix (d_model × d_model)
Q     = Query matrix (d_model × sequence_length)

For LLaMA 7B, d_model = 4096
W_Q is a 4096 × 4096 matrix
= 16,777,216 parameters IN JUST ONE WEIGHT MATRIX
```

#### Step 2 — The Low-Rank Hypothesis

```
THE KEY INSIGHT FROM LoRA PAPER:

"When a large pre-trained model is adapted to a
 downstream task, the CHANGE IN WEIGHTS (ΔW)
 has a LOW INTRINSIC RANK."

WHAT DOES LOW RANK MEAN?

A matrix has LOW RANK when:
→ Its information can be compressed into fewer dimensions
→ The matrix can be decomposed into two smaller matrices

HIGH RANK MATRIX (Complex):
[1.2  3.4  2.1  0.9]
[4.5  2.3  1.8  3.2]    Every row/column is independent
[0.8  1.1  3.7  2.4]    Cannot be compressed easily
[3.3  0.5  2.0  1.7]    Rank = 4 (full rank)

LOW RANK MATRIX (Simple):
[2    4    6    8  ]
[1    2    3    4  ]    Row 1 = 2 × Row 2 = 2 × Row 3/3
[0.5  1    1.5  2  ]    All rows are multiples of same row!
[1    2    3    4  ]    Rank = 1 (very low rank)

LOW RANK = The matrix's information lives in a
            much lower dimensional space.

THE CLAIM:
When you go from "general language model"
to "medical question answering model,"
the REQUIRED WEIGHT CHANGES are low-rank.
You don't need to change weights in a complex,
full-rank way. A simpler, low-rank change is enough.
```

#### Step 3 — LoRA's Mathematical Solution

```
STANDARD FINE-TUNING UPDATE:
W_new = W_original + ΔW

Where ΔW is a full d × d matrix.
For 4096 × 4096: 16.7 million parameters to learn.

LORA'S APPROACH:
ΔW ≈ B × A

Where:
A = (r × d) matrix   → small matrix (r rows, d columns)
B = (d × r) matrix   → small matrix (d rows, r columns)
r = rank (tiny number, typically 4 to 64)

The product B × A is a (d × d) matrix
— same shape as ΔW —
but parameterized by MUCH fewer values!

PARAMETER COUNT:
Full ΔW: d × d = 4096 × 4096 = 16,777,216 parameters

LoRA ΔW ≈ B × A:
A: r × d = 8 × 4096 = 32,768 parameters
B: d × r = 4096 × 8 = 32,768 parameters
Total: 65,536 parameters

RATIO: 65,536 / 16,777,216 = 0.39%

SAME EFFECT. 0.39% OF THE PARAMETERS.
```

#### Step 4 — The Complete LoRA Forward Pass

```
STANDARD FORWARD PASS (No LoRA):
h = W × x
(W is frozen during fine-tuning)

LORA FORWARD PASS:
h = W × x + (B × A) × x × scaling_factor

WHERE:
W  = Original frozen weight matrix
x  = Input
A  = LoRA matrix A (trainable)
B  = LoRA matrix B (trainable)
scaling_factor = α/r  (scaling constant)

α (alpha) = scaling hyperparameter (usually same as r or 2r)
r = LoRA rank (bottleneck dimension)

WHY THE SCALING FACTOR α/r?
→ Keeps the magnitude of LoRA output consistent
   regardless of the rank r chosen
→ When you change r, you don't need to retune learning rate
→ Standard practice: set α = 2r or α = r
```

## 6. LoRA — Step-by-Step Visual

```
INSIDE LORA (for one weight matrix, e.g., W_Q):

INPUT x (dimension d = 4096)
         │
         ├──────────────────────────────┐
         │                              │
         ↓                              ↓
  ┌──────────────┐              ┌──────────────┐
  │  W_Q (frozen)│              │ A (trainable)│
  │  4096 × 4096 │              │  r × 4096    │
  │              │              │  (r=8 here)  │
  └──────────────┘              └──────────────┘
         │                              │
         │                              ↓
         │                    ┌──────────────────┐
         │                    │  B (trainable)   │
         │                    │  4096 × r        │
         │                    └──────────────────┘
         │                              │
         ↓                              ↓
    W_Q × x                    (B × A) × x × α/r
   (main output)              (LoRA output = small correction)
         │                              │
         └──────────────┬───────────────┘
                        ↓
                   h = W_Q×x + B×A×x×α/r
               (combined output)

WHAT A AND B LEARN:
A learns: How to PROJECT the input to low-rank space
B learns: How to EXPAND from low-rank back to output space
B×A learns: The OPTIMAL SMALL CORRECTION to the frozen weights
```

## 7. LoRA Initialization — Why B=0 Is Genius

```
CRITICAL DETAIL: HOW ARE A AND B INITIALIZED?

A: Initialized with RANDOM GAUSSIAN VALUES
   (small random numbers, normal distribution)

B: Initialized with ALL ZEROS

WHY B = ZERO?

At the start of training:
ΔW = B × A = 0 × A = 0 (zero matrix)

This means:
h = W × x + 0 × x = W × x

The LoRA contribution is EXACTLY ZERO at start!
The model starts behaving IDENTICALLY to the original model.

WHY IS THIS BRILLIANT?
→ Training starts from a STABLE, WORKING STATE
→ No risk of random initialization breaking the model
→ LoRA gradually "grows" from zero as training proceeds
→ The original model capabilities are preserved at start
→ This is why LoRA training is so stable

CONTRAST WITH BAD INITIALIZATION:
If B was random at start:
→ ΔW = B × A ≠ 0 immediately
→ Random large outputs would disrupt model
→ Training would be unstable from step 1
```

## 10. QLoRA — Fine-Tuning On Consumer Hardware

### The Technique That Democratized Fine-Tuning

```
YEAR: 2023
AUTHORS: Dettmers et al. (University of Washington)
PAPER: "QLoRA: Efficient Finetuning of Quantized LLMs"

THE PROBLEM QLoRA SOLVES:
Even with LoRA, loading a 70B model requires ~140 GB
in 16-bit (bf16) precision.
No consumer GPU can handle this.

QLORA'S SOLUTION: QUANTIZE the base model first.
Then apply LoRA on top of the quantized base.
```

### What Is Quantization?

```
QUANTIZATION = Reducing the precision of numbers

Normal float: 32 bits (fp32)
Half float:   16 bits (bf16, fp16)
Int8:          8 bits (INT8)
Int4:          4 bits (NF4 - Normal Float 4)

WHAT THIS MEANS IN MEMORY:

A 70B parameter model:
fp32:  70B × 4 bytes = 280 GB  ← Way too much
bf16:  70B × 2 bytes = 140 GB  ← Still too much
INT8:  70B × 1 byte  = 70 GB   ← Getting better
INT4:  70B × 0.5 byte = 35 GB  ← Fits on 2 × A100 40GB!

QLORA USES 4-BIT QUANTIZATION.
A 70B model fits in about 40GB.
YOU CAN FINE-TUNE IT ON A SINGLE A100 80GB!
Or a 7B model on a single RTX 4090!
```

---

### The Three QLoRA Innovations:

```
INNOVATION 1: 4-BIT NF4 QUANTIZATION
──────────────────────────────────────
Standard 4-bit quantization loses too much information.
QLoRA uses NF4 (Normal Float 4) — a special data type.

WHY NF4?
Neural network weights follow a normal (Gaussian) distribution.
NF4 is designed specifically for this distribution.
It puts more quantization levels near zero (where most weights are)
and fewer at extremes.

Result: Much better accuracy than naive 4-bit quantization.

VISUAL:
Standard 4-bit: Equal spacing between values
[----|----|----|----|----|----|----|----|]

NF4: More values clustered near zero (where weights live)
[--|-|-|||||||-|-|--|-------|----------|]
       ↑
    Dense near zero = better for neural network weights

INNOVATION 2: DOUBLE QUANTIZATION
────────────────────────────────────
Even the quantization constants (used to quantize weights)
take up memory.

Double quantization = Quantize the quantization constants too!
Sounds recursive — but saves ~0.37 bits per parameter.
For 70B model: saves ~2.6 GB. Significant!

INNOVATION 3: PAGED OPTIMIZERS
────────────────────────────────
During training, memory usage spikes when processing
large batches.
Paged Optimizers use NVIDIA unified memory:
→ When GPU memory is full, optimizer states PAGE to CPU RAM
→ When needed again, page back to GPU
→ Like virtual memory in your operating system
→ Prevents out-of-memory crashes during training
→ Training can proceed even with memory spikes
```

---

### QLoRA Architecture — The Full Picture:

```
QLORA TRAINING SETUP:

BASE MODEL (frozen, 4-bit NF4 quantized)
   ← Occupies ~35 GB for 70B model
   ← Cannot learn directly (quantized)
   ← But provides rich representations

LORA ADAPTERS (trainable, bf16 precision)
   ← Tiny: ~0.5% of parameters
   ← Full precision (16-bit) for accurate gradients
   ← These are the ONLY things that update

COMPUTATION FLOW:
Input → [4-bit Base Model] → dequantize to bf16 for compute
                           → [LoRA adapters in bf16]
                           → combined output in bf16
                           → Loss calculation
                           → Gradients → update LoRA ONLY
                           → Base model NEVER changes

WHY DEQUANTIZE FOR COMPUTE?
4-bit numbers are too imprecise for matrix multiplication.
So we dequantize to bf16 during the forward pass,
compute, then discard the bf16 values.
Only the 4-bit values stay in memory long-term.
```

## 11. Other PEFT Methods — Important Overview

### Prefix Tuning

```
YEAR: 2021 (Li and Liang, Stanford)

CORE IDEA:
Don't change ANY model weights at all.
Instead, add trainable "virtual tokens" to the
BEGINNING of every layer's key and value matrices.

VISUAL:

Standard attention input:
[Token1, Token2, Token3, ..., TokenN]

Prefix Tuning attention input:
[PREFIX_1, PREFIX_2, ..., PREFIX_k, Token1, Token2, ..., TokenN]
 ↑ These k prefix tokens are TRAINABLE ↑

What are prefix tokens?
→ They are NOT real words
→ They are trainable continuous vectors
→ They represent "task context" in a learned way
→ They are prepended to EVERY attention layer

BENEFIT:
→ Base model is completely untouched
→ Prefix tokens "steer" attention patterns
→ Very parameter efficient (k prefix tokens per layer)

DRAWBACK:
→ Adds k tokens to every sequence → increases input length
→ More complex to implement than LoRA
→ Less popular now that LoRA dominates
```

### Prompt Tuning

```
YEAR: 2021 (Lester et al., Google)

SIMPLER VERSION OF PREFIX TUNING:
→ Only add soft prompts to the INPUT layer
→ NOT to every transformer layer
→ Even fewer parameters than Prefix Tuning

VISUAL:
Input to model:
[SOFT_TOKEN_1, SOFT_TOKEN_2, ..., SOFT_TOKEN_k, 
 "Translate to French:", "Hello world"]

SOFT TOKENS: Trainable embedding vectors
HARD TOKENS: Real words (frozen embedding lookup)

FINDING:
Works well for large models (11B+)
Works poorly for smaller models (<1B)
Large models can "interpret" soft prompts better.
```

### BitFit — The Simplest PEFT Method

```
YEAR: 2021 (Ben-Zaken et al.)

IDEA: Only train the BIAS TERMS of the network.
      Freeze everything else.

WHAT ARE BIAS TERMS?
Every linear layer: y = W×x + b
W = weight matrix (frozen in BitFit)
b = bias vector (trained in BitFit)

PARAMETER COUNT:
BERT-base biases: ~0.1% of total parameters
→ 100,000 parameters out of 110,000,000

PERFORMANCE:
Surprisingly competitive for many classification tasks.
Usually worse than LoRA for generation tasks.

WHEN TO USE:
Very limited compute → BitFit as baseline.
Ablation studies → Test if tiny param count works.
Classification fine-tuning → Often works well.
```

### IA³ — Infused Adapter by Inhibiting and Amplifying

```
YEAR: 2022 (Liu et al.)

IDEA: Learn vectors that SCALE (inhibit or amplify)
      the existing activations — not matrix multiplications.

MATH:
Standard: h = W × x
IA³:      h = l ⊙ (W × x)

Where:
l = learned vector (tiny! just d dimensions)
⊙ = element-wise multiplication

WHAT THIS MEANS:
l can SCALE each dimension of the output.
l > 1 → amplify that dimension
l < 1 → inhibit that dimension
l ≈ 0 → suppress that dimension completely

PARAMETER COUNT:
Even fewer than LoRA!
Only d parameters per targeted weight matrix
(vs. 2 × r × d for LoRA)

WHEN TO USE:
Few-shot learning scenarios
Very limited compute
When LoRA still uses too much memory
```

## 3. Gradient Checkpointing — Trading Compute For Memory

```
THE PROBLEM WITH ACTIVATIONS:

During FORWARD PASS:
Layer 1 → Activation 1 (saved for backward)
Layer 2 → Activation 2 (saved for backward)
...
Layer 32 → Activation 32 (saved for backward)

All 32 activation tensors saved in GPU memory simultaneously!
For long sequences + large models = ENORMOUS memory cost.

WHY ARE ACTIVATIONS SAVED?
During backward pass (computing gradients):
Gradient at Layer k needs Activation at Layer k.
So all activations must be kept in memory.

GRADIENT CHECKPOINTING SOLUTION:
Instead of saving ALL activations:
→ Only save activations at CHECKPOINTS (e.g., every 4 layers)
→ During backward pass:
   → When you need an intermediate activation
   → RECOMPUTE it from the nearest checkpoint
   → Use it for gradient computation
   → Then discard it

TRADE-OFF:
Memory saved: ~60-70% reduction in activation memory
Compute cost: ~33% more forward computations

FOR FINE-TUNING:
Memory is the bottleneck, not compute.
Gradient checkpointing is almost ALWAYS worth it.

IN CODE (HuggingFace Trainer):
training_args = TrainingArguments(
    gradient_checkpointing=True,  ← This one line
    ...
)
```

## 4. Mixed Precision Training — bf16 and fp16

```
THE IDEA:
Don't use 32-bit floats for everything.
Use 16-bit floats where possible.

WHY TWO TYPES OF PRECISION?

fp16 (16-bit IEEE float):
→ Range: Very small (±65,504)
→ Risk: Overflow/underflow on large gradients
→ Needs: Loss scaling to prevent underflow

bf16 (Brain Float 16):
→ Range: Same as fp32 (much larger than fp16!)
→ No overflow risk
→ Slightly less precision than fp16 but much more stable
→ Preferred for LLM training

MIXED PRECISION STRATEGY:
──────────────────────────
Weights:          bf16 (stored in GPU)
Compute:          bf16 (fast GPU tensor cores)
Gradients:        fp32 (full precision for accuracy)
Optimizer states: fp32 (full precision for accuracy)

WHY MIXED?
→ bf16 for storage/compute = speed + memory savings
→ fp32 for gradients/optimizer = numerical stability

MEMORY SAVINGS vs FULL FP32:
Model weights:    2x smaller (fp32 → bf16)
Gradients:        Same (kept fp32)
Optimizer:        Same (kept fp32)
Activations:      2x smaller (computed in bf16)
Net savings: 25-40% memory reduction

SPEED IMPROVEMENT:
A100 GPU bf16 performance: 312 TFLOPS
A100 GPU fp32 performance: 77.6 TFLOPS
4× faster in bf16! ✅
```

## 5. Gradient Accumulation — Simulating Large Batches

```
THE PROBLEM:
Large batch sizes improve training stability.
But larger batches = more memory.
Limited GPU memory → can only fit small batches.

GRADIENT ACCUMULATION:
Instead of:
   Large batch → single update

Do this:
   Small batch 1 → compute gradients → DON'T update yet
   Small batch 2 → compute gradients → ADD to previous
   Small batch 3 → compute gradients → ADD to previous
   Small batch 4 → compute gradients → ADD to previous
   → NOW update weights (accumulated gradient from 4 batches)

RESULT:
4 small batches (batch_size=4) accumulated 4 times
= Equivalent to 1 large batch (batch_size=16)
= Same training dynamics as large batch training
= No extra memory needed!

IN CODE:
training_args = TrainingArguments(
    per_device_train_batch_size=4,   ← Small batch per GPU
    gradient_accumulation_steps=4,   ← Accumulate 4 times
    # Effective batch size = 4 × 4 = 16
)

TRADEOFF:
Memory:  Reduced (small batch) ✅
Speed:   Slightly slower (4 forward passes before update)
Quality: Same as large batch (equivalent optimization) ✅
```

## 3. LoRA Weight Merging — Zero Inference Latency

### This Is The Killer Feature of LoRA Over Adapters

```
THE PROBLEM WITH HOULSBY ADAPTERS:
During inference:
h = FFN(h) + Adapter(h)
→ Extra computation at every layer
→ Extra inference latency
→ For real-time applications: UNACCEPTABLE

LORA'S BRILLIANT SOLUTION:
Remember LoRA's formula:
h = Wx + BAx × α/r
h = (W + BA × α/r) × x
h = W_merged × x

WHERE:
W_merged = W + BA × α/r

The LoRA matrices can be MATHEMATICALLY MERGED
into the original weight matrices!

RESULT:
→ After merging: inference is IDENTICAL to original model
→ No extra layers → No extra computation → Zero latency penalty
→ The model "behaves" like it was fine-tuned from the start

MERGING PROCESS:
STEP 1: Compute ΔW = B × A × (α/r)
STEP 2: Add to original: W_new = W_frozen + ΔW
STEP 3: Replace W_frozen with W_new in the model
STEP 4: Delete the LoRA matrices (no longer needed)

RESULT: A new model where the LoRA knowledge is
        "baked into" the weights permanently.
        Inference speed = exactly the original model speed.
```

### The Merge vs. Keep Decision:

```
SHOULD YOU MERGE OR KEEP LORA SEPARATE?

KEEP LORA SEPARATE (adapter files):
✅ Can swap adapters for different tasks
✅ Can easily update or retrain just the adapter
✅ Can A/B test different adapters
✅ Base model and adapter are independent
❌ Slight inference overhead

MERGE LORA INTO WEIGHTS:
✅ Zero inference latency penalty
✅ Simpler deployment (just one model file)
✅ Can use standard inference engines
❌ Cannot swap adapters anymore
❌ Cannot easily update just the adapter
❌ Losing the modular flexibility

PRODUCTION DECISION:
Single task deployment → MERGE (zero latency) ✅
Multi-task system → KEEP SEPARATE (flexibility) ✅
A/B testing adapters → KEEP SEPARATE ✅
Serving to millions of users → MERGE (speed critical) ✅
```

## 4. Adapter Composition — Combining Multiple Adapters

### The Advanced Technique

```
WHAT IS ADAPTER COMPOSITION?
Combining MULTIPLE trained adapters to get
capabilities from BOTH without retraining.

EXAMPLE SCENARIO:
You have:
→ Medical-LoRA: Trained on medical Q&A
→ Safety-LoRA: Trained to refuse harmful content
→ Format-LoRA: Trained to output structured reports

Can you COMBINE all three for a medical assistant
that is safe AND formats well?

YES! Several methods exist:

METHOD 1: SEQUENTIAL COMPOSITION
──────────────────────────────────
Apply adapters one after another:

Input → [Base Model + Medical-LoRA] → intermediate
      → [Base Model + Safety-LoRA] → intermediate
      → [Base Model + Format-LoRA] → Output

Each adapter modifies the output of the previous.
Simple but can be unstable.

METHOD 2: LINEAR COMBINATION (LoRA SOUP)
─────────────────────────────────────────
Merge adapter weights with coefficients:

W_merged = W_base + λ₁(B₁A₁) + λ₂(B₂A₂) + λ₃(B₃A₃)

Where λ₁, λ₂, λ₃ are mixing coefficients (0 to 1).

This creates a single model that has all three capabilities.
λ values control how much each adapter contributes.

METHOD 3: TIES-MERGING (Task Interference Elimination)
────────────────────────────────────────────────────────
Advanced method that:
→ Identifies conflicting weight updates between adapters
→ Resolves conflicts by keeping only consistent changes
→ Merges remaining changes
→ Reduces interference between task-specific knowledge

METHOD 4: DARE (Drop And REscale)
───────────────────────────────────
Randomly drop a % of LoRA parameters before merging.
Reduces noise and task interference.
Surprisingly effective despite seeming random.
```

## 5. Continual Learning With Adapters

### Solving Catastrophic Forgetting At System Level

```
THE CONTINUAL LEARNING PROBLEM:
You want to keep adding new tasks to your system
without forgetting old tasks.

Traditional approach:
Learn Task A → Retrain on Tasks A+B → Retrain on A+B+C → ...
Each retraining risks forgetting previous tasks.

ADAPTER-BASED CONTINUAL LEARNING:
Learn Task A → Train Adapter A → FREEZE EVERYTHING
Learn Task B → Train Adapter B (on frozen base) → FREEZE
Learn Task C → Train Adapter C (on frozen base) → FREEZE

Each adapter is trained INDEPENDENTLY.
The base model NEVER CHANGES.
No task can affect any other task.

TASK ROUTING IN INFERENCE:
Input → Task Classifier → Select Adapter → Generate

VISUAL SYSTEM:
              ┌─────────────────┐
              │  BASE MODEL     │
              │   (FROZEN)      │
              └────────┬────────┘
                       │ (same base for all)
         ┌─────────────┼──────────────┐
         ↓             ↓              ↓
  [Adapter A]    [Adapter B]    [Adapter C]
  (Task A)       (Task B)       (Task C)
  Fine-tuned     Fine-tuned     Fine-tuned
  independently  independently  independently
         ↑             ↑              ↑
         └─────────────┼──────────────┘
                       ↑
               (selected at runtime
                by task router)

BENEFITS:
✅ No catastrophic forgetting (adapters are independent)
✅ Add new tasks without retraining old ones
✅ Can A/B test any adapter independently
✅ Remove a "bad" task adapter without affecting others
✅ Scales to hundreds of tasks efficiently
```

## 6. AdaLoRA — Adaptive Rank Distribution

```
THE PROBLEM LORA HAS:
You set the same rank r for ALL weight matrices.
But not all matrices are equally important.
W_Q might need rank 32 for this task.
W_V might only need rank 4.
W_gate might not need LoRA at all.

ADALORA'S INSIGHT:
"Let the training process DISCOVER which matrices
 need high rank and which need low rank."

HOW ADALORA WORKS:
1. Start with high rank for all matrices
2. During training, evaluate IMPORTANCE of each singular value
3. Prune (remove) low-importance singular values
4. High-importance matrices keep high effective rank
5. Low-importance matrices are compressed to low rank

MATHEMATICAL TOOL: SVD (Singular Value Decomposition)
ΔW = P × Λ × Q

Where:
P and Q = orthogonal matrices (like B and A in LoRA)
Λ = diagonal matrix of singular values (importance scores)

Training prunes small singular values (in Λ).
Large singular values = important → kept.
Small singular values = unimportant → pruned.

RESULT:
Same total parameter budget as LoRA.
But OPTIMALLY DISTRIBUTED across matrices.
Better performance than fixed-rank LoRA.
More complex to implement.
```

## 7. Failure Modes ⚠️

```
PEFT GENERAL FAILURE MODES:
─────────────────────────────

❌ FAILURE 1: RANK TOO LOW
What:  r is set too small. LoRA cannot capture needed changes.
Why:   The task requires high-rank weight changes.
       Low rank ≈ not enough expressiveness.
Signs: Training loss plateaus early. Validation loss stays high.
Fix:   Increase r. Try r=32, r=64, r=128. Monitor performance.

❌ FAILURE 2: RANK TOO HIGH
What:  r is set too large. LoRA overfits.
Why:   Too many parameters for the dataset size.
Signs: Train loss very low, val loss rising (overfitting).
Fix:   Decrease r. Add lora_dropout. Get more data.

❌ FAILURE 3: WRONG TARGET MODULES
What:  LoRA applied to wrong weight matrices.
Why:   Some matrices are more important for specific tasks.
Example: Code generation → attention matrices most important.
         Classification → might also need FFN matrices.
Fix:   Try different target_module combinations.
       Start with q,v then add k,o then add FFN.

❌ FAILURE 4: QUANTIZATION ACCURACY LOSS (QLoRA)
What:  4-bit quantization loses too much precision.
Why:   Some models or tasks are more sensitive to quantization.
Signs: QLoRA significantly underperforms LoRA on same task.
Fix:   Use 8-bit instead of 4-bit.
       Try different quantization schemes (NF4 vs INT4).
       Use larger r to compensate for quantization noise.

❌ FAILURE 5: ADAPTER INTERFERENCE (Composition)
What:  Combining two adapters makes performance worse.
Why:   Adapters trained on different tasks conflict.
       Their weight updates cancel each other out.
Signs: Combined adapter worse than either individual adapter.
Fix:   TIES-Merging instead of linear combination.
       Train adapters jointly on mixed data.
       Use DARE (random dropping before merge).

❌ FAILURE 6: LEARNING RATE TOO HIGH FOR PEFT
What:  Despite fewer parameters, using high LR destabilizes training.
Why:   The LoRA matrices control everything through their product B×A.
       High LR causes B×A to grow too large too fast.
Fix:   Start with LR = 2e-4 for LoRA (slightly higher than full FT).
       Use learning rate warmup (100-200 steps).
       Use cosine or linear decay schedule.

❌ FAILURE 7: CATASTROPHIC FORGETTING IN LORA (UNEXPECTED)
What:  Even with LoRA, model forgets general abilities.
Why:   If target modules include EVERYTHING and r is large,
       LoRA effectively becomes full fine-tuning.
Fix:   Limit target_modules to critical attention matrices.
       Use smaller r.
       Include general instruction examples in fine-tuning data.

❌ FAILURE 8: MERGING CAUSES DEGRADATION
What:  After merging LoRA into base model, performance drops.
Why:   Merging assumes W_merged = W + BA×α/r exactly.
       Quantization or numerical issues can corrupt the merge.
Fix:   Merge in bf16 or fp32, not int8.
       Verify merged model performance before deployment.
```

## 9. Interview Answers 💬

---

**Answer to Q5 (LoRA Math) — The Answer That Shows Deep Understanding:**

> *"LoRA is based on the observation that when fine-tuning a pretrained model, the required weight changes have low intrinsic rank. This means the weight update matrix ΔW doesn't need all d×d parameters — it can be approximated by a product of two smaller matrices: B (d×r) and A (r×d), where r is much smaller than d. During training, the model computes h = Wx + BAx × α/r, where W is the frozen original weight and BA×α/r is the low-rank adaptation. The original weights are never touched — only A and B are trained. The key initialization trick is that B starts at zero, so at the beginning of training, the LoRA contribution is exactly zero and the model behaves identically to the frozen base model, ensuring training stability."*

---

**Answer to Q14 (System Design — Single GPU Fine-Tuning):**

> *"For a 13B model on a 24GB RTX 4090, I would use QLoRA. First, quantize the base model to 4-bit NF4 precision — this brings the model size from ~26GB to ~6.5GB. Then configure LoRA adapters with r=16, targeting q_proj, k_proj, v_proj, and o_proj, keeping trainable parameters under 50M. Enable gradient checkpointing to reduce activation memory by 60-70%. Use mixed precision computation in bf16. Set batch size to 1-2 with gradient accumulation of 8-16 to achieve effective batch size of 16. Use paged AdamW optimizer for memory stability. Use Flash Attention 2 for further memory reduction. Total estimated memory: ~20-22GB, just fitting in 24GB. Training time for 10K examples: approximately 2-4 hours."*

---

**Answer to Q16 (Trap — Zero Latency):**

> *"This is only true AFTER merging the LoRA weights into the base model. Before merging, LoRA has a slight inference overhead because for each forward pass, you compute both Wx (through frozen weights) and BAx (through LoRA matrices) and sum them. This is slightly more computation than just Wx. The zero-latency claim applies only to the MERGED model, where W_merged = W + BA×α/r is computed once offline, and then inference is just W_merged × x — identical to the original model. However, merging eliminates adapter swappability. So in multi-task serving systems where adapters are swapped at runtime, there IS a small but measurable latency cost."*

---

**Answer to Q18 (Trap — Small LR vs LoRA):**

> *"No, they are NOT equivalent. A very small learning rate in full fine-tuning still updates ALL parameters — just by tiny amounts. This means gradients must be computed for all parameters (enormous memory), and optimizer states must be stored for all parameters (even more memory). The computational graph still includes all parameters. LoRA is fundamentally different: gradients are only computed for the LoRA matrices (0.1-1% of parameters), and optimizer states are only stored for those matrices. The memory savings come from the ABSENCE of gradients and optimizer states for frozen parameters — not from how small the updates are. A small LR helps with catastrophic forgetting but gives almost none of the memory benefits."*

## 10. Common Beginner Mistakes ❌

```
MISTAKE 1: Thinking frozen weights don't participate in computation
FIX: Frozen weights still process inputs in the forward pass.
     They just don't receive weight updates in backward pass.
     Their computation is essential — they provide the rich
     representations that adapters then modify.

MISTAKE 2: Setting r too small and expecting full fine-tuning quality
FIX: r=4 is very restrictive. r=8 to r=16 is the sweet spot.
     For complex tasks or larger models → r=32 or r=64.
     Always run on validation set to check if r is sufficient.

MISTAKE 3: Only targeting q and v projection matrices
FIX: This is the minimal configuration. For better performance:
     Also target k_proj and o_proj (attention output).
     For hard tasks: also target FFN layers (up_proj, down_proj).
     More target modules = better performance, more memory.

MISTAKE 4: Forgetting to use gradient checkpointing
FIX: Always enable it for sequence lengths > 512.
     It's free performance — slight speed cost, big memory gain.
     model.enable_input_require_grads() needed for some models.

MISTAKE 5: Thinking QLoRA is slower at inference
FIX: QLoRA's 4-bit quantization is during TRAINING only.
     At inference, you can use the merged model at full precision.
     Or deploy the 4-bit quantized model (faster inference too!).

MISTAKE 6: Merging LoRA into quantized (int8/int4) base model
FIX: Always dequantize to fp32 or bf16 BEFORE merging.
     Merging in quantized precision causes numerical errors.
     Merge → then optionally re-quantize for deployment.

MISTAKE 7: Thinking all PEFT methods are interchangeable
FIX: LoRA = matrix decomposition on weight matrices (generation)
     Prefix Tuning = trainable virtual tokens in attention
     Prompt Tuning = trainable input tokens only
     BitFit = only bias terms
     They suit different tasks, sizes, and compute budgets.

MISTAKE 8: Not tracking which layers are trainable
FIX: Always print trainable parameter count before training.
     In HuggingFace PEFT:
     model.print_trainable_parameters()
     If it shows 0 trainable params → something is wrong!

MISTAKE 9: Using same hyperparameters for different tasks
FIX: Classification → lower r is often enough (r=4 to r=8)
     Generation → higher r often needed (r=16 to r=64)
     Mathematical reasoning → highest r (r=64 to r=128)
     Always validate on task-specific benchmark.

MISTAKE 10: Not saving the adapter separately from base model
FIX: Save ONLY the adapter, not the full model.
     adapter_model.save_pretrained("./my_adapter")
     This saves ~16MB instead of ~14GB.
     Load with: model.load_adapter("./my_adapter")
```

```
WHEN AN ENGINEER DESIGNS A PEFT SYSTEM:

PHASE 1: HARDWARE ASSESSMENT
□ What GPU do I have? How much VRAM?
□ Use the table: What's the largest model I can run?
□ Do I need QLoRA (< 24GB GPU) or LoRA (24GB+ GPU)?

PHASE 2: MODEL SELECTION
□ Pick largest model that fits with QLoRA
□ Larger model + QLoRA often beats smaller model + full FT
□ Consider: Does base model's architecture match task?

PHASE 3: LORA CONFIGURATION
□ Start with r=16, target q,k,v,o projections
□ alpha = 2r = 32 (standard)
□ dropout = 0.05 (light regularization)
□ Adjust r based on task complexity and dataset size

PHASE 4: TRAINING SETUP
□ Enable gradient checkpointing (always!)
□ Use bf16 mixed precision (always!)
□ Set gradient accumulation for effective batch size 16-32
□ Use cosine LR schedule with warmup (100-200 steps)
□ Learning rate: 2e-4 to 5e-4 for LoRA (higher than full FT)

PHASE 5: VALIDATION STRATEGY
□ Print trainable parameters before starting
□ Monitor train AND validation loss
□ Check response quality with human spot-checks every epoch
□ Run task-specific benchmarks after each epoch

PHASE 6: DEPLOYMENT DECISION
□ Single task, speed critical → MERGE LoRA into base
□ Multi-task, flexibility needed → Keep adapters separate
□ Multi-client serving → Load-on-demand adapter system

PHASE 7: MONITORING IN PRODUCTION
□ Track response latency (watch for adapter loading overhead)
□ Track response quality (sample daily for human review)
□ Track memory usage (watch for memory leaks in adapter loading)
□ A/B test adapter versions (easy with separate adapter files)
```

## 13. LoRA Code Implementation

### What It Actually Looks Like In Practice

```python
# ============================================
# COMPLETE LORA FINE-TUNING SETUP
# (Using HuggingFace PEFT + TRL)
# ============================================

from transformers import AutoModelForCausalLM, AutoTokenizer
from peft import LoraConfig, get_peft_model, TaskType
from trl import SFTTrainer, TrainingArguments

# STEP 1: Load base model
model = AutoModelForCausalLM.from_pretrained(
    "meta-llama/Meta-Llama-3-8B",
    torch_dtype=torch.bfloat16,    # bf16 precision
    device_map="auto"               # auto GPU placement
)
tokenizer = AutoTokenizer.from_pretrained("meta-llama/Meta-Llama-3-8B")

# STEP 2: Configure LoRA
lora_config = LoraConfig(
    task_type=TaskType.CAUSAL_LM,  # We are fine-tuning a causal LM
    r=16,                           # Rank (bottleneck dimension)
    lora_alpha=32,                  # Alpha (scaling = alpha/r = 2)
    target_modules=[                # Which matrices to adapt
        "q_proj",
        "k_proj",
        "v_proj",
        "o_proj"
    ],
    lora_dropout=0.05,             # Light regularization
    bias="none"                     # Don't train bias terms
)

# STEP 3: Apply LoRA to model
model = get_peft_model(model, lora_config)

# STEP 4: Check trainable parameters
model.print_trainable_parameters()
# Output: trainable params: 41,943,040 || all params: 8,030,261,248
#         trainable%: 0.5224%
# ONLY 0.52% of parameters are trainable!

# STEP 5: Configure training
training_args = TrainingArguments(
    output_dir="./lora_output",
    num_train_epochs=3,
    per_device_train_batch_size=4,
    gradient_accumulation_steps=4,     # Effective batch size = 16
    warmup_steps=100,
    learning_rate=2e-4,                # Higher than full FT (1e-5)
    bf16=True,                          # Mixed precision
    gradient_checkpointing=True,        # Save activation memory
    logging_steps=50,
    evaluation_strategy="epoch",
    save_strategy="epoch",
    load_best_model_at_end=True,        # Early stopping
)

# STEP 6: Train
trainer = SFTTrainer(
    model=model,
    args=training_args,
    train_dataset=train_dataset,
    eval_dataset=val_dataset,
    tokenizer=tokenizer,
    dataset_text_field="text",
    max_seq_length=2048,
)
trainer.train()

# STEP 7: Save adapter (tiny file!)
model.save_pretrained("./my_lora_adapter")
# Saves only the LoRA matrices — ~16MB!

# STEP 8: Optional — merge into base model
merged_model = model.merge_and_unload()
merged_model.save_pretrained("./merged_model")
# Now zero extra inference cost!
```
