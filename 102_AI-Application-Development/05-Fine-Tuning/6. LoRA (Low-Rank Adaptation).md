## 1. What Is A Matrix? (Visual Foundation)

### Start From Zero — No Assumptions

```
A MATRIX is a rectangular grid of numbers.

Example — a 3×4 matrix:

     Column 1  Column 2  Column 3  Column 4
Row 1  [ 2.1     0.5     -1.3      3.7  ]
Row 2  [ 0.8    -2.4      1.1      0.3  ]
Row 3  [ 1.5     0.9     -0.7     -1.8  ]

DIMENSIONS: 3 rows × 4 columns = "3×4 matrix"

IN NEURAL NETWORKS:
Every weight matrix W transforms one vector into another.

Input vector x (4 dimensions)
↓
Matrix W (3 × 4)
↓
Output vector h (3 dimensions)

h = W × x
```

## 2. What Is Matrix Rank? — From Absolute Zero

### This Is The Foundation Of Everything

```
RANK = The number of TRULY INDEPENDENT pieces of information
       in the matrix.

Let me show what "independent" means:

EXAMPLE 1 — FULL RANK MATRIX (Rank = 3):
─────────────────────────────────────────
[  1   0   0  ]
[  0   1   0  ]
[  0   0   1  ]

→ Each row is completely different direction
→ No row can be "built from" other rows
→ 3 rows, all independent → Rank = 3 (full rank)

EXAMPLE 2 — RANK-1 MATRIX:
────────────────────────────
[  2   4   6   8  ]
[  1   2   3   4  ]
[  3   6   9  12  ]

Look carefully:
→ Row 1 = 2 × Row 2
→ Row 3 = 3 × Row 2
→ ALL rows are just multiples of Row 2!
→ Only ONE independent direction
→ Rank = 1

EXAMPLE 3 — RANK-2 MATRIX:
────────────────────────────
[  1   0   2   3  ]
[  0   1   1  -1  ]
[  2   3   7   3  ]

→ Row 3 = 2×Row1 + 3×Row2 (dependent!)
→ Only Rows 1 and 2 are truly independent
→ Rank = 2
```

### The Deep Intuition:

```
THINK OF RANK LIKE THIS:

A matrix with rank r contains information
that lives in an r-dimensional subspace.

HIGH RANK = Complex, diverse information
            Cannot be compressed much
            Needs many independent directions

LOW RANK = Simple, redundant information
           Can be compressed a lot
           Only a few truly independent directions

ANALOGY — RANK AS COLORS IN A PAINTING:
─────────────────────────────────────────
Full rank matrix = A detailed painting with 1000 unique colors
Low rank matrix  = A simple painting with only 3 colors
                   (all other "colors" are mixes of those 3)

You can describe a simple (low rank) painting
with just 3 base colors + mixing ratios.
Way less information needed.

LoRA says: "The CHANGE in weights when fine-tuning
            is a SIMPLE painting — low rank.
            We don't need to store the full expensive
            painting — just the 3 base colors."
```

## 3. Why Does Rank Matter In Neural Networks?

### The Critical Connection

```
WEIGHT MATRICES IN TRANSFORMERS:

LLaMA 3 8B example:
W_Q: 4096 × 4096 matrix
     = 16,777,216 parameters
     Theoretical maximum rank: 4096

IF W_Q WERE FULL RANK:
→ Would need all 4096 independent directions to describe it
→ Every fine-tuning update would change all 4096 directions
→ Extremely complex task-specific changes needed

THE RESEARCH FINDING:
When you fine-tune for a SPECIFIC DOWNSTREAM TASK:
"The fine-tuning update ΔW doesn't actually USE
 all 4096 directions.
 It mostly changes information in just 4-64 directions."

WHY?
A downstream task is SIMPLER than the full space of language.
"Answer medical questions" only uses a subset
of the full language representation space.
The required weight change lies in a low-dimensional subspace.

THIS IS THE INTRINSIC DIMENSIONALITY HYPOTHESIS:
Tasks have much lower intrinsic dimensionality
than the model parameter space suggests.
```

## 4. SVD — The Mathematical Tool Behind LoRA

### Singular Value Decomposition — From Zero

> **SVD** (Singular Value Decomposition) is a mathematical technique that **decomposes any matrix** into three simpler matrices — revealing its hidden structure and rank.

```
THE SVD DECOMPOSITION:

Any matrix M (m×n) can be written as:
M = U × Σ × V^T

WHERE:
U  = m×m orthogonal matrix (left singular vectors)
Σ  = m×n diagonal matrix (singular values, sorted largest→smallest)
V^T = n×n orthogonal matrix (right singular vectors, transposed)

WHAT ARE SINGULAR VALUES?
The diagonal of Σ: σ₁ ≥ σ₂ ≥ σ₃ ≥ ... ≥ σₙ ≥ 0

INTERPRETATION:
σ₁ = How much "energy" is in direction 1 (largest direction)
σ₂ = How much "energy" is in direction 2 (second largest)
...
σₙ = How much "energy" is in the smallest direction

SMALL σᵢ ≈ 0 → That direction carries VERY LITTLE information
LARGE σᵢ      → That direction carries LOTS of information
```

### Worked Example — SVD Step by Step:

```
SIMPLE 3×3 MATRIX:
M = [ 4   0   0 ]
    [ 0   2   0 ]
    [ 0   0  0.1]

SVD gives singular values: [4, 2, 0.1]

INTERPRETATION:
σ₁ = 4.0   → Direction 1 carries 4.0 units of energy
σ₂ = 2.0   → Direction 2 carries 2.0 units of energy
σ₃ = 0.1   → Direction 3 carries 0.1 units of energy

TOTAL ENERGY = 4.0 + 2.0 + 0.1 = 6.1

Direction 3 only contributes: 0.1/6.1 = 1.6% of energy

TRUNCATED SVD (RANK-2 APPROXIMATION):
"Keep only the top 2 singular values"

M_approx ≈ U[:,:2] × Σ[:2,:2] × V^T[:2,:]
         = rank-2 matrix

This approximation captures: (4.0+2.0)/6.1 = 98.4% of energy
Using only 2/3 = 67% of the directions.

THIS IS THE IDEA BEHIND LORA:
ΔW has many singular values.
Most are tiny (near zero).
We only keep the top r singular values.
This captures most of the information.
```

### SVD Connection To LoRA:

```
WHAT LORA IS DOING MATHEMATICALLY:

If we did FULL fine-tuning:
W_new = W_old + ΔW
ΔW is a full-rank d×d matrix (expensive!)

If we apply SVD to ΔW:
ΔW = U × Σ × V^T

Now keep only top r singular values:
ΔW_approx = U_r × Σ_r × V_r^T
           = (U_r × √Σ_r) × (√Σ_r × V_r^T)
           = B              × A

WHERE:
B = U_r × √Σ_r    is a (d × r) matrix
A = √Σ_r × V_r^T  is a (r × d) matrix

LoRA directly parameterizes B and A.
It LEARNS B and A from scratch.
The product B×A approximates ΔW.

KEY INSIGHT:
LoRA doesn't explicitly do SVD.
But it LEARNS the same low-rank structure implicitly
through gradient descent on B and A.
```

## 5. The Low-Rank Hypothesis — Evidence From Research

### Is This Actually Valid?

```
THE ORIGINAL EVIDENCE (from LoRA paper):

The authors measured the INTRINSIC DIMENSIONALITY
of fine-tuning on common NLP benchmarks.

EXPERIMENT:
Project the gradient updates to random subspaces
of different dimensionalities (r = 1, 2, 4, 8, ...)
Train a model in ONLY this r-dimensional subspace.
Measure: what is the minimum r to match full fine-tuning?

RESULTS ON BERT:
Task: MRPC (sentence pair classification)
Full fine-tuning (r = full) → 91.2% accuracy
r = 4                        → 90.8% accuracy  (only 0.4% drop!)
r = 1                        → 88.3% accuracy  (only 2.9% drop!)

Task: SST-2 (sentiment classification)
Full fine-tuning             → 95.1%
r = 4                        → 94.7%  (only 0.4% drop!)

CONCLUSION:
Most fine-tuning tasks have intrinsic dimensionality
much lower than the model parameter space.
Fine-tuning "lives" in a very small subspace.
LoRA exploits this structure.

FURTHER EVIDENCE (from follow-up research):

SVD Analysis of ΔW after full fine-tuning:
→ Top 10 singular values account for >90% of ΔW's norm
→ Remaining singular values are nearly zero
→ ΔW IS empirically low-rank after task-specific fine-tuning

This VALIDATES the low-rank hypothesis directly.
```

## 6. The Intrinsic Dimensionality Concept

```
INTRINSIC DIMENSIONALITY:
The minimum number of dimensions needed to express
a solution to a particular task.

ANALOGY — HIKING UP A MOUNTAIN:
────────────────────────────────
The mountain exists in 3D space (x, y, z).
But the path up the mountain is essentially 1D
(you just need to know: how far along the path are you?).
The path has intrinsic dimensionality = 1
even though it exists in 3D space.

FOR LLM FINE-TUNING:
The parameter space has billions of dimensions.
But the "path" from the general model to the task-specific model
might only need ~100-1000 dimensions.

The task has intrinsic dimensionality << model dimensionality.

LoRA WITH RANK r IS SAYING:
"I believe the path from base model to task-specific model
 can be described in r-dimensional space.
 Let me parameterize exactly that r-dimensional space."

WHEN DOES THIS BREAK DOWN?
→ When the task IS intrinsically high-dimensional
→ When the task requires changes that span
   many independent directions in weight space
→ Example: Learning a completely new language from scratch
   (might need higher rank to capture all new patterns)
→ Example: Multi-task fine-tuning across many diverse tasks
   (each task needs different directions → sum is high rank)
```

## 7. Mathematical Proof — Why B×A Can Approximate Any Low-Rank Matrix

```
THEOREM: Any rank-r matrix M (m×n) can be EXACTLY expressed
         as a product of two matrices: B (m×r) × A (r×n).

PROOF (conceptual):
If M has rank r, its SVD gives:
M = U_r Σ_r V_r^T

Let:
B = U_r Σ_r^(1/2)   [m×r matrix]
A = Σ_r^(1/2) V_r^T [r×n matrix]

Then:
B × A = U_r Σ_r^(1/2) × Σ_r^(1/2) V_r^T
      = U_r Σ_r V_r^T
      = M ✓ (exactly!)

CONCLUSION:
Any low-rank matrix can be exactly expressed as B×A.
LoRA simply LEARNS what B and A should be.
It never explicitly computes SVD.
Instead, gradient descent discovers the optimal B and A
that make B×A match the needed weight update ΔW.

THE FREEDOM IN B AND A:
Note: B×A is not unique!
If we multiply B by any invertible matrix P:
(BP)(P^{-1}A) = B(PP^{-1})A = BA ✓

Many different (B, A) pairs give the same product.
This means LoRA has redundancy in parameterization.
Training still works because gradient descent
finds a consistent solution.
```

## 1. Full Transformer Anatomy Review

### Every Component Before We Inject LoRA

```
TRANSFORMER BLOCK — COMPLETE ANATOMY:

INPUT (x): sequence of token embeddings
           shape: [batch_size × seq_len × d_model]

┌────────────────────────────────────────────────────────┐
│                  TRANSFORMER LAYER k                    │
│                                                         │
│  ┌──────────────────────────────────────────────────┐  │
│  │            MULTI-HEAD SELF-ATTENTION              │  │
│  │                                                   │  │
│  │  Input: x (batch × seq_len × d_model)            │  │
│  │                                                   │  │
│  │  Q = x @ W_Q^T    [d_model → d_model]           │  │
│  │  K = x @ W_K^T    [d_model → d_model]           │  │
│  │  V = x @ W_V^T    [d_model → d_model]           │  │
│  │                                                   │  │
│  │  Split into h heads:                             │  │
│  │  Each head: d_head = d_model / h                 │  │
│  │                                                   │  │
│  │  For each head i:                                │  │
│  │  scores_i = (Q_i @ K_i^T) / √d_head            │  │
│  │  attn_i   = softmax(scores_i) @ V_i             │  │
│  │                                                   │  │
│  │  Concatenate all heads → output [d_model]       │  │
│  │  output = concat(attn_1,...,attn_h) @ W_O       │  │
│  └──────────────────────────────────────────────────┘  │
│                         ↓                               │
│              Residual + LayerNorm                       │
│                         ↓                               │
│  ┌──────────────────────────────────────────────────┐  │
│  │         FEED-FORWARD NETWORK (FFN)               │  │
│  │                                                   │  │
│  │  h1 = GELU(x @ W_up^T + b_up)                   │  │
│  │  h2 = x @ W_gate^T (in Llama-style)              │  │
│  │  output = (h1 ⊙ h2) @ W_down^T                  │  │
│  │                                                   │  │
│  │  W_up:   d_model → d_ffn  (4× larger)            │  │
│  │  W_down: d_ffn → d_model  (compress back)        │  │
│  └──────────────────────────────────────────────────┘  │
│                         ↓                               │
│              Residual + LayerNorm                       │
└────────────────────────────────────────────────────────┘

OUTPUT: modified sequence embeddings [batch × seq_len × d_model]
```

## 2. The Four Attention Matrices — Deep Explanation

### Understanding What Each Matrix Actually Does

```
THE FOUR WEIGHT MATRICES IN ATTENTION:

┌──────────┬──────────────────────────────────────────────────────┐
│ MATRIX   │ WHAT IT ACTUALLY DOES                               │
├──────────┼──────────────────────────────────────────────────────┤
│          │ Transforms input into QUERY vectors.                │
│  W_Q     │ Queries ask: "What information am I looking for?"   │
│ (d × d)  │ Controls WHAT each token searches for in others.    │
│          │ Determines the "question" side of attention.        │
├──────────┼──────────────────────────────────────────────────────┤
│          │ Transforms input into KEY vectors.                  │
│  W_K     │ Keys say: "What information do I contain?"          │
│ (d × d)  │ Controls HOW each token presents itself to queries. │
│          │ Determines the "label" side of attention.           │
├──────────┼──────────────────────────────────────────────────────┤
│          │ Transforms input into VALUE vectors.                │
│  W_V     │ Values say: "What information do I share?"          │
│ (d × d)  │ Controls WHAT CONTENT is aggregated.               │
│          │ If attention score is high → this value is used.    │
├──────────┼──────────────────────────────────────────────────────┤
│          │ Transforms concatenated attention heads to output.  │
│  W_O     │ Projects multi-head output back to d_model space.   │
│ (d × d)  │ "Mixes" information from all heads.                 │
│          │ Final projection in attention block.                │
└──────────┴──────────────────────────────────────────────────────┘

ATTENTION COMPUTATION SUMMARY:
─────────────────────────────────
Q = x W_Q^T           → "What is each token looking for?"
K = x W_K^T           → "What does each token offer?"
V = x W_V^T           → "What does each token contain?"
Attn = softmax(QK^T/√d)V → Weighted combination of values
Out = Attn W_O^T      → Final projection
```

## 3. Exactly Where LoRA Is Injected — Visual + Math

### The Precise Injection Point

```
LORA INJECTION — DETAILED VISUAL:

STANDARD ATTENTION (no LoRA):
─────────────────────────────────
x (input)
    │

───────────────────────────────
x (input)
    │
    ├──── W_Q (frozen) ─────────────────────────────────┐
    │                                                     │
    ├──── A_Q (r×d, trainable) → B_Q (d×r, trainable) ─┤→ Q_total
    │         (parallel LoRA branch)                     │
    │                                                     │
    ├──── W_K (frozen) ─────────────────────────────────┐
    │                                                     │
    ├──── A_K (r×d, trainable) → B_K (d×r, trainable) ─┤→ K_total
    │                                                     │
    ├──── W_V (frozen) ─────────────────────────────────┐
    │                                                     │
    ├──── A_V (r×d, trainable) → B_V (d×r, trainable) ─┤→ V_total
    │                                                     │
    └──── [after attention] ─────────────────────────────→ W_O (frozen)
                                                           + LoRA_O
                                                           → output

FORMULA FOR EACH PROJECTION:
Q = x @ W_Q^T + x @ A_Q^T @ B_Q^T × (α/r)
  = x @ (W_Q + B_Q @ A_Q × α/r)^T
  = x @ W_Q_effective^T

The LoRA branch runs in PARALLEL with the frozen branch.
Outputs are ADDED together.
```

## 4. The Step-By-Step Math For One Attention Layer With LoRA

```
COMPLETE MATH — ONE ATTENTION PROJECTION WITH LORA:

INPUT: x of shape [seq_len × d_model]
       For LLaMA 8B: d_model = 4096

FROZEN WEIGHT MATRIX: W_Q of shape [d_model × d_model]
                       = [4096 × 4096]

LORA MATRICES: A of shape [r × d_model] = [16 × 4096]
               B of shape [d_model × r] = [4096 × 16]
               (with r = 16 as example)

─────────────────────────────────────────────────────────

FORWARD COMPUTATION:

STEP 1: Frozen branch
   output_frozen = x @ W_Q^T
   Shape: [seq_len × d_model] @ [d_model × d_model]
        = [seq_len × d_model]

STEP 2: LoRA branch — FIRST projection (down)
   x_down = x @ A^T
   Shape: [seq_len × d_model] @ [d_model × r]
        = [seq_len × r]
   (We compressed from 4096 → 16 dimensions!)

STEP 3: LoRA branch — SECOND projection (up)
   x_up = x_down @ B^T
   Shape: [seq_len × r] @ [r × d_model]
        = [seq_len × d_model]
   (We expanded from 16 → 4096 dimensions!)

STEP 4: Apply scaling
   lora_output = x_up × (α / r)
               = x_up × (32 / 16)     [if α=32, r=16]
               = x_up × 2.0

STEP 5: Combine frozen and LoRA outputs
   final_output = output_frozen + lora_output
   Shape: [seq_len × d_model]

STEP 6: This final_output IS the Q matrix
   (Identical computation for K, V, O with their own A, B)

─────────────────────────────────────────────────────────

DURING BACKWARD PASS:
Gradients flow to A and B (trainable).
Gradients are COMPUTED through W_Q (for gradient flow).
But W_Q weights are NOT updated (frozen, requires_grad=False).
Only A and B receive weight updates.
```

## 6. What Each LoRA Injection Actually Learns

### This Is The Deep Insight

```
WHAT LORA IN W_Q LEARNS:
────────────────────────────
W_Q controls what each token "searches for."
LoRA in W_Q teaches: "For this task, search for DIFFERENT things."

Example (Medical QA fine-tuning):
→ Before: W_Q causes tokens to search for general semantic meaning
→ After LoRA W_Q: Tokens now search for medical terminology,
  symptom patterns, drug names, clinical reasoning structure

WHAT LORA IN W_K LEARNS:
────────────────────────────
W_K controls how tokens present themselves to be found.
LoRA in W_K teaches: "For this task, present yourself differently."

Example:
→ Before: Token "fever" presents itself as general medical symptom
→ After LoRA W_K: "fever" now presents itself in context of
  diagnostic protocols, severity scales, differential diagnosis

WHAT LORA IN W_V LEARNS:
────────────────────────────
W_V controls what INFORMATION is aggregated when attention is high.
LoRA in W_V teaches: "What content to extract and mix."

Example:
→ Before: When attending to "fever," extract general description
→ After LoRA W_V: Extract clinical features, measurement values,
  associated symptoms, treatment protocols

WHAT LORA IN W_O LEARNS:
────────────────────────────
W_O mixes the multi-head outputs together.
LoRA in W_O teaches: "How to blend head outputs for this task."

Example:
→ Before: Mix heads equally based on general language structure
→ After LoRA W_O: Weight heads that captured medical terminology
  more heavily in final output

COMBINED:
LoRA in all 4 matrices gives task-specific control over:
→ WHAT to look for (Q)
→ HOW to present yourself (K)
→ WHAT to share (V)
→ HOW to combine what was found (O)

This is COMPLETE task-specific attention adaptation.
```

## 7. FFN Layers — Should You LoRA Them?

```
RESEARCH SAYS:

                     Good for: Style, format, behavior changes

For complex tasks (math, code, science):
Adding FFN LoRA gives 3-8% additional improvement

For simple tasks (classification, format change):
FFN LoRA gives minimal improvement (<1%)
Not worth the extra parameters.
```

## 8. Layer-Wise LoRA Strategy

```
NOT ALL TRANSFORMER LAYERS ARE EQUAL.
Should every layer get a LoRA adapter?

RESEARCH INSIGHT — WHAT DIFFERENT LAYERS LEARN:
─────────────────────────────────────────────────
Early layers (1-8 in a 32-layer model):
→ Learn syntactic patterns (grammar, punctuation)
→ Basic token relationships
→ Position and structural information
→ VERY GENERAL — changes rarely needed for tasks

Middle layers (9-24):
→ Learn semantic relationships
→ Entity properties and world knowledge
→ Cross-sentence reasoning patterns
→ MODERATELY GENERAL — sometimes need task adaptation

Late layers (25-32):
→ Learn task-specific prediction
→ Output format and style
→ Final token probability distribution shaping
→ VERY TASK-SPECIFIC — almost always benefit from LoRA

STRATEGIES:
───────────

STRATEGY 1: LoRA in ALL layers (most common)
→ Same r applied to every transformer block
→ Simple and effective
→ Standard practice, works well

STRATEGY 2: LoRA only in LATE layers
→ More efficient (fewer total parameters)
→ Works for tasks that mainly need output-style changes
→ Not effective for deep knowledge adaptation

STRATEGY 3: INCREASING RANK IN LATE LAYERS
→ Early layers: r=4 (small, they need little change)
→ Middle layers: r=8
→ Late layers: r=16 (larger, they need more adaptation)
→ Better parameter efficiency than uniform r

STRATEGY 4: SKIP EVERY OTHER LAYER
→ Apply LoRA to layers 1, 3, 5, 7, ... (odd only)
→ 50% fewer adapters, ~80-90% of the performance
→ Good for compute-constrained scenarios
```

## 2. Matrix A — The Down-Projection — Deep Dive

### What A Actually Does During Training

```
MATRIX A — COMPLETE ANALYSIS:

SHAPE: [r × d_model]
ROLE: First step of the LoRA branch — COMPRESS the input

OPERATION:
x_compressed = dropout(x) @ A^T
Shape: [seq_len × d_model] @ [d_model × r] = [seq_len × r]

WHAT THIS MEANS GEOMETRICALLY:
A projects the input from d_model-dimensional space
into r-dimensional space.

d_model = 4096 dimensions (LLaMA 8B)
r = 16 dimensions

We're compressing 4096 dimensions → 16 dimensions!
Only keeping the 16 most "useful" directions for this task.

INITIALIZATION: KAIMING UNIFORM (or Gaussian)
Formula: A ~ N(0, σ²) where σ = 1/√r

WHY KAIMING (not zeros like B)?
If A were also zeros: B×A = 0×0 = 0 ✓ (still zero start)
But during training, if A starts at zero:
→ Gradient of loss w.r.t. A depends on B
→ Gradient of loss w.r.t. B depends on A
→ If both zero: Both gradients are zero
→ DEAD NEURONS — neither A nor B can ever learn!

So A must start random to provide initial gradient signal.
B starts at zero to ensure zero initial LoRA contribution.
This combination is the correct initialization strategy.

WHAT A LEARNS:
A learns which DIRECTIONS in the input space are
most important for the task.
It is like learning a "task-relevant basis."
After training, A's rows point toward the most
task-discriminative features in the embedding space.
```

---

## 3. Matrix B — The Up-Projection — Deep Dive

### Why Zero Initialization Is The Key Insight

```
MATRIX B — COMPLETE ANALYSIS:

SHAPE: [d_model × r]
ROLE: Second step — EXPAND back to original dimension

OPERATION:
x_output = x_compressed @ B^T
Shape: [seq_len × r] @ [r × d_model] = [seq_len × d_model]

WHAT THIS MEANS GEOMETRICALLY:
B expands the r-dimensional compressed representation
back to d_model-dimensional space.
It decides HOW to "spread" the task-specific signal
across the full output dimensions.

INITIALIZATION: ALL ZEROS
B = np.zeros((d_model, r))   ← Every element is 0.0

WHY ZEROS — THE DEEP REASON:

Goal: At training start, model should behave
      IDENTICALLY to the base pretrained model.

LoRA contribution: B @ A × (α/r)
If B = 0: contribution = 0 @ A × (α/r) = 0

So at start:
total_output = W_frozen @ x + 0 = W_frozen @ x ✓

Model starts as the original pretrained model. ✓

AS TRAINING PROGRESSES:
Step 1: Forward pass uses B=0, so output is just W@x
Step 2: Gradient computed w.r.t. loss
Step 3: Gradient of loss w.r.t. B is computed:
        ∂L/∂B = ∂L/∂(BAx) × (Ax)^T ← Ax is non-zero (A is random)
Step 4: B gets its first update away from zero
Step 5: Now B is slightly non-zero
Step 6: LoRA contribution is now slightly non-zero
Step 7: Model starts adapting to the task

WHAT B LEARNS:
B learns how to "write" task-specific information
back into the full d_model-dimensional space.
B's columns define the output directions that
carry task-specific information.

AFTER TRAINING — B×A VISUALIZATION:
B × A creates a rank-r matrix (max rank = r).
This matrix captures the learned task-specific
weight adjustment ΔW that the model needs.
```

## 4. The α (Alpha) Scaling Parameter — Complete Analysis

### The Most Misunderstood LoRA Parameter

```
THE SCALING FORMULA:

LoRA output = B @ A @ x × (α / r)

WHERE:
α (alpha) = scaling hyperparameter (your choice)
r         = rank (your choice)
α/r       = the actual scaling factor applied

TYPICAL VALUES:
α = r:    scaling = 1.0   (no amplification)
α = 2r:   scaling = 2.0   (double the LoRA effect)
α = r/2:  scaling = 0.5   (half the LoRA effect)

WHY DOES α EXIST?

PROBLEM WITHOUT α:
When you change r, the magnitude of B@A changes.
→ Higher r → more parameters → potentially larger B@A outputs
→ To compensate, you'd need to change learning rate each time
→ Very inconvenient for experimenting with different r values

SOLUTION WITH α:
The scaling factor α/r normalizes the output.
When you change r but keep α fixed:
→ B@A is scaled by α/r
→ Higher r → smaller scaling → net effect stays similar
→ You can change r without re-tuning learning rate!

INTUITION BEHIND α/r:
Think of it like this:
If r=8, each of the 8 dimensions contributes (α/8) to the output
If r=16, each of the 16 dimensions contributes (α/16) to output
Total contribution per rank unit stays constant!

RECOMMENDED PRACTICE:
Set α = 2r as the default.
This gives a scaling of 2.0 regardless of r.
It slightly amplifies the LoRA contribution.
Works well across many tasks and model sizes.

ADVANCED INSIGHT:
α effectively controls the learning rate for LoRA.
Higher α → Stronger LoRA effect → Faster adaptation
Lower α → Weaker LoRA effect → Slower adaptation
α works with learning rate multiplicatively.
Effectively: LoRA_LR = optimizer_LR × α
```

## 6. LoRA Dropout — When and Why

```
LORA DROPOUT:

Applied TO THE INPUT of matrix A (before down-projection).

CODE:
x_after_dropout = lora_dropout(x)  ← dropout applied here
x_compressed = x_after_dropout @ A^T
x_output = x_compressed @ B^T × (α/r)

WHAT DROPOUT DOES:
Randomly zeros out some input dimensions during training.
Forces LoRA to learn ROBUST features, not just memorize inputs.

WHEN TO USE LORA DROPOUT:
──────────────────────────────────────────────────────────
SMALL DATASET (<5K examples) → dropout = 0.05 to 0.1
MEDIUM DATASET (5K-50K)      → dropout = 0.01 to 0.05
LARGE DATASET (>50K)         → dropout = 0.0 to 0.01
VERY LARGE (>500K)           → dropout = 0.0 (not needed)

WHY ZERO DROPOUT FOR LARGE DATASETS?
Large datasets naturally provide diverse training signal.
Dropout adds noise that slows convergence.
With abundant data, dropout hurts more than helps.

CAVEAT:
Dropout is NOT applied during INFERENCE.
Only active during TRAINING.
At inference, full input is used (all dimensions).

INTERACTION WITH MERGING:
Dropout is a TRAINING-ONLY operation.
When you merge LoRA into the base model:
W_merged = W + B@A×(α/r)
The dropout is NOT part of the merge.
Merged model inference has no dropout.
```

## 7. Gradient Flow Through LoRA Parameters

### The Complete Backward Pass

```
FORWARD PASS (what we already know):
x → [A] → x_down → [B] → x_up → × (α/r) → lora_out
                                              + W@x = total_out

BACKWARD PASS — HOW GRADIENTS FLOW:

STARTING POINT: Loss L is computed from model output.
∂L/∂total_out is computed (gradient w.r.t. final output).

STEP 1: Gradient w.r.t. the sum
∂L/∂lora_out = ∂L/∂total_out (because total_out = W@x + lora_out)
∂L/∂(W@x)   = ∂L/∂total_out (same gradient splits both ways)

STEP 2: Gradient flows through frozen W
∂L/∂(W@x) is computed but W is NOT updated.
It only flows through to give gradients w.r.t. x.
Gradients through W: ∂L/∂x = W^T @ ∂L/∂total_out

STEP 3: Gradient w.r.t. B
lora_out = B @ A @ x × (α/r)
∂L/∂B = ∂L/∂lora_out × (A@x)^T × (α/r)
       = ∂L/∂total_out × (A@x)^T × (α/r)
→ B receives gradient and gets UPDATED.

STEP 4: Gradient w.r.t. A
∂L/∂A = B^T @ ∂L/∂lora_out × x^T × (α/r)
       = B^T @ ∂L/∂total_out × x^T × (α/r)
→ A receives gradient and gets UPDATED.

KEY INSIGHT:
At start (B=0):
∂L/∂A = 0^T @ ∂L/∂total_out × x^T × (α/r) = 0

Initially A gets ZERO gradient too!
Is this a problem?

NO! Because:
1. B gets a gradient proportional to A@x (which is non-zero since A is random)
2. After B's first update, B is no longer zero
3. Now A starts receiving non-zero gradients
4. Both A and B update from this point forward

TYPICAL GRADIENT MAGNITUDES (first few steps):
A: 0 → 1e-8 → 1e-6 → stable learning
B: 1e-6 → 1e-5 → stable learning
(B learns faster initially; A catches up)
```

# 📦 TOPIC 4 — Adapter Merging vs Separate Deployment

## 1. The Mathematical Mechanics of Merging

### Proven Step By Step

```
THE MERGE OPERATION — MATHEMATICAL PROOF:

BEFORE MERGING:
Forward pass for one layer:
h = W_frozen @ x + (B @ A @ x) × (α/r)

Factor out x:
h = (W_frozen + B @ A × (α/r)) @ x

Define:
W_merged = W_frozen + B @ A × (α/r)

Then:
h = W_merged @ x

THIS IS IDENTICAL TO HAVING A SINGLE WEIGHT MATRIX W_merged!
No separate LoRA branches needed.
The computation reduces to a SINGLE matrix multiply.

THE MERGE IS EXACT — NOT AN APPROXIMATION.
There is zero quality loss from merging.
The merged model is mathematically identical to the LoRA model.
```

### The Merge Algorithm — Step By Step:

```
COMPLETE MERGE PROCEDURE:

INPUTS:
- W_frozen: Original frozen weight matrix [d × d]
- A: LoRA A matrix [r × d] (trained)
- B: LoRA B matrix [d × r] (trained)
- alpha: scaling factor (e.g., 32)
- r: rank (e.g., 16)

STEP 1: Compute the LoRA weight update
ΔW = B @ A
Shape: [d × r] @ [r × d] = [d × d]

STEP 2: Apply the scaling factor
ΔW_scaled = ΔW × (alpha / r)
           = ΔW × (32/16)
           = ΔW × 2.0

STEP 3: Ensure both matrices are same dtype
# W_frozen might be bf16 or fp16
# ΔW_scaled should be cast to match
ΔW_scaled = ΔW_scaled.to(W_frozen.dtype)

STEP 4: Add to frozen weights
W_merged = W_frozen + ΔW_scaled

STEP 5: Replace in model
model.W_Q = W_merged  (replaces frozen + LoRA with single matrix)
del model.lora_A_Q    (remove LoRA matrices)
del model.lora_B_Q    (remove LoRA matrices)

STEP 6: Repeat for ALL LoRA-targeted weight matrices

RESULT:
- Model has ONLY the original frozen matrices (now updated)
- No LoRA branches exist anymore
- Inference is identical to original base model
- But weights encode the task-specific adaptation

IN CODE (HuggingFace PEFT):
merged_model = peft_model.merge_and_unload()
# This does steps 1-6 automatically for all matrices
```

---

## 2. Why Merging Preserves Performance — The Proof

```
CONCERN: "Does merging lose quality compared to keeping LoRA separate?"

ANSWER: NO. Here is why:

MATHEMATICAL EQUIVALENCE THEOREM:

For any input x, the following are IDENTICAL:

SEPARATE LoRA:
output = W_frozen @ x + B @ A @ x × (α/r)

MERGED MODEL:
output = (W_frozen + B @ A × (α/r)) @ x
       = W_merged @ x

PROOF:
W_frozen @ x + B @ A @ x × (α/r)
= (W_frozen + B @ A × (α/r)) @ x    [distributivity of matrix multiply]
= W_merged @ x ✓

The two computations give EXACTLY the same output.
This is not an approximation.
It is an algebraic identity.

THEREFORE:
Merged model performance = LoRA model performance (exactly)
Any evaluation metric is identical before and after merging.

CAVEAT:
This holds in full precision (fp32 or bf16).
In integer quantization (int4, int8):
There can be tiny floating-point rounding differences.
But these are negligible (< 0.1% performance change).
```

## 3. Merging Multiple LoRA Adapters — LoRA Soup

### Advanced Composition Technique

```
SCENARIO:
You have trained 3 different LoRA adapters:

Adapter 1: Medical QA   → A₁, B₁ trained on medical data
Adapter 2: Safety        → A₂, B₂ trained to refuse harmful content
Adapter 3: Clinical Format → A₃, B₃ trained for structured output

CAN YOU MERGE ALL THREE?

YES! Linear Merging (LoRA Soup):

W_merged = W_frozen + λ₁(B₁A₁×α/r) + λ₂(B₂A₂×α/r) + λ₃(B₃A₃×α/r)

WHERE:
λ₁, λ₂, λ₃ = mixing coefficients (must sum to 1 or be tuned freely)

SIMPLE EXAMPLE (equal mixing):
λ₁ = λ₂ = λ₃ = 1/3

W_merged = W_frozen + (1/3)(B₁A₁×α/r) + (1/3)(B₂A₂×α/r) + (1/3)(B₃A₃×α/r)

INTUITION:
Each adapter's contribution is weighted by λ.
Higher λ = that adapter's behavior dominates.
Lower λ = that adapter's behavior is subtle.

CHALLENGE — TASK INTERFERENCE:
────────────────────────────────
What if two adapters conflict?

Medical adapter learned: "Give detailed clinical answers"
Safety adapter learned:  "Refuse detailed medical advice"

These directly CONFLICT.
Simple linear merging → both cancel each other out!
Merged model might give vague, uncommitted responses.

SOLUTION — TIES MERGING:
─────────────────────────
Algorithm:
STEP 1: For each weight in each adapter ΔWᵢ:
        Find sign (positive or negative)
STEP 2: For conflicting signs (medical says +0.3, safety says -0.2):
        Check majority vote among all adapters
STEP 3: Keep only weights with MAJORITY SIGN
        Zero out minority-signed weights (resolve conflict)
STEP 4: Scale remaining weights appropriately
STEP 5: Merge into base model

RESULT: Conflict-free merge that preserves non-conflicting knowledge.

MATHEMATICAL FORMULA:
ΔW_merged = γ × sign_majority(ΔW₁, ΔW₂, ΔW₃) × mean_magnitude

WHERE:
sign_majority = sign agreed upon by majority of adapters
mean_magnitude = average size of non-conflicting updates
γ = global scaling factor
```

## 4. DARE — Drop And REscale Before Merging

```
DARE (2024) — A CLEVER TRICK BEFORE MERGING:

THE OBSERVATION:
When you train a LoRA adapter, most parameters make
SMALL contributions to the adaptation.
A few parameters make LARGE contributions.

THE IDEA:
Before merging, randomly DROP p% of the smallest LoRA parameters.
Then RESCALE the remaining (1-p)% by 1/(1-p) to compensate.

ALGORITHM:
STEP 1: For each parameter θ in ΔW = B@A×(α/r):
        Generate random number u ~ Uniform(0,1)
STEP 2: If u < p (drop probability): set θ = 0
        If u ≥ p (keep): set θ = θ / (1-p)   [rescale]
STEP 3: Proceed with normal merging using modified ΔW

EXAMPLE (p=0.5, 50% dropout):
Original ΔW = [0.1, -0.3, 0.05, 0.8, -0.2, 0.15]
Random keep = [keep, drop, drop, keep, drop, keep]
After drop  = [0.1,  0.0,  0.0,  0.8,  0.0,  0.15]
After rescale = [0.2, 0.0, 0.0, 1.6, 0.0, 0.30]  (÷ 0.5)

WHY DOES THIS HELP?
→ Removes noise from smaller parameters
→ Reduces task interference when merging multiple adapters
→ More aggressive pruning = less interference
→ Rescaling preserves expected output magnitude

WHEN TO USE DARE:
→ Merging 3+ adapters (interference is real)
→ Adapters trained on very different tasks
→ When linear merging degrades performance

SURPRISING RESULT:
Even for SINGLE adapter merging, DARE sometimes helps.
Removing 90% of LoRA parameters with rescaling
often barely hurts performance!
```

## 6. Hot-Swapping Adapters at Inference Time

```
HOT-SWAPPING = Changing which adapter is active
               WITHOUT reloading the base model.

USE CASE:
Same user switches between tasks mid-conversation:
"Help me with Python code." → Code adapter active
"Now explain the medical concept in my code." → Medical adapter

HOW HOT-SWAPPING WORKS:

STEP 1: Base model ALWAYS in memory (never unloaded)
STEP 2: Active adapter: a set of (A, B) matrices per layer
STEP 3: To swap: remove old adapter matrices, load new ones
STEP 4: Next forward pass uses new adapter automatically
```

## 9. Advanced Scenario — LoRA Weight Space Analysis

```
AFTER TRAINING, WHAT DOES B@A LOOK LIKE?

ANALYSIS TECHNIQUE — Post-Training SVD:
Apply SVD to the trained ΔW = B@A:

ΔW = U Σ V^T

Examine the singular values Σ:

EXPECTED RESULT FOR WELL-TRAINED LORA:
σ₁ >> σ₂ >> ... >> σᵣ

The singular values should be concentrated in the first few.
This means the task truly uses fewer directions than r.
Even within the r-dimensional subspace, the actual information
might only need 2-4 dimensions!

WHAT THIS TELLS YOU:
If σ₁ ≫ all others: Task is very low-rank (could use smaller r)
If σ₁ ≈ σ₂ ≈ ... ≈ σᵣ: Task uses all r dimensions (r might be too small)

DIAGNOSTIC VALUE:
→ If r=16 but only top 3 singular values are significant:
  → You were wasteful. r=4 would have worked just as well.
  → Save parameters next time.

→ If all r=16 singular values are roughly equal:
  → Task is genuinely rank-16 or higher.
  → Try r=32 to see if performance improves.

THIS IS HOW RESEARCHERS DETERMINE THE RIGHT RANK
FOR A GIVEN TASK.
```

## 10. Failure Modes ⚠️ — Deep and Specific

```
FAILURE 1: LOSS OF BASE MODEL CAPABILITY AFTER MERGING
───────────────────────────────────────────────────────
What:  Merged model is worse than base model on unrelated tasks.
Why:   LoRA adapted the weights too aggressively.
       Merged ΔW is too large and corrupts general representations.
Signs: Base model MMLU: 70%. Merged model MMLU: 60%.
Fix:   Reduce α (lower scaling). Reduce r.
       Use smaller learning rate. Train fewer epochs.
       Add general instruction data to fine-tuning set.

FAILURE 2: RANK COLLAPSE
────────────────────────
What:  After training, the B@A matrix has effective rank << r.
       Most singular values are near zero.
Why:   Task is simpler than the rank r chosen.
       Gradient updates only push a few directions.
Signs: Post-training SVD shows 1-2 large σ, rest near zero.
Fix:   Use smaller r next time. Current model is fine but wasteful.

FAILURE 3: GRADIENT VANISHING THROUGH FROZEN LAYERS
────────────────────────────────────────────────────
What:  LoRA adapters in early layers barely learn anything.
Why:   Gradients must travel through many frozen layers.
       Each frozen layer potentially reduces gradient magnitude.
       By layer 1, gradient is tiny compared to layer 32.
Signs: A and B matrices in early layers stay near initialization.
       Later layers learn well, early layers barely change.
Fix:   Use different LR for different layers (layer-wise LR).
       Higher LR for early layers to compensate for vanishing.
       Or only apply LoRA to later layers.

FAILURE 4: ALPHA-RANK MISMATCH
────────────────────────────────
What:  Using α much larger than r causes instability.
Why:   Very high α/r ratio (e.g., α=128, r=4 → ratio=32!)
       Makes LoRA output 32x larger than expected.
       Overwhelms frozen weight contribution.
Signs: Loss diverges early. Very high learning needed to compensate.
Fix:   Keep α/r ratio between 0.5 and 4.
       α = r (ratio=1) or α = 2r (ratio=2) are safest defaults.

FAILURE 5: MERGE FAILURE FROM DTYPE MISMATCH
──────────────────────────────────────────────
What:  Merged model produces NaN or incorrect outputs.
Why:   W_frozen might be in int8 quantized format.
       B@A is in fp32.
       Adding fp32 to int8 → type mismatch → NaN.
Fix:   ALWAYS dequantize W_frozen to fp32 BEFORE merging.
       Then optionally re-quantize merged result.
       Never merge directly into quantized weights.

FAILURE 6: HOT-SWAP CACHE MEMORY LEAK
────────────────────────────────────────
What:  GPU memory grows over time as adapters are swapped.
Why:   Old adapter tensors not properly deleted after swap.
       Python garbage collector doesn't free GPU memory immediately.
Signs: GPU memory usage grows until OOM crash.
Fix:   Explicitly call torch.cuda.empty_cache() after unloading.
       Delete adapter tensors explicitly.
       Implement LRU (least recently used) eviction for adapter cache.

FAILURE 7: LORA DOUBLE COUNTING
─────────────────────────────────
What:  Accidentally applying LoRA twice to same matrix.
Why:   Re-loading an already-adapted model and adding LoRA again.
Signs: Extremely large outputs. Loss immediately diverges.
Fix:   Always check if model already has LoRA before adding.
       Use model.print_trainable_parameters() to verify state.
       Load BASE model (not adapted model) before adding LoRA.

FAILURE 8: TOO FEW STEPS FOR LoRA TO LEARN
────────────────────────────────────────────
What:  Training completes but B matrix barely moved from zero.
Why:   Not enough training steps. LR too low. Dataset too small.
Signs: model.lora_B weights are still very close to zero.
Fix:   Increase training epochs. Use higher LR.
       Check gradient magnitudes in first few steps.
       Ensure loss is actually decreasing.
```

## 12. Interview Answers 💬

---

**Answer to Q3 (B=0 initialization) — Impresses with depth:**

> *"B is initialized to zero to ensure that at the start of training, the LoRA contribution is exactly zero — meaning the model starts behaving identically to the pretrained base model. This is a form of residual learning with a stable starting point. A cannot also be zero because of a subtle gradient flow issue: the gradient of the loss with respect to A depends on B, and the gradient with respect to B depends on A. If both are zero, both gradients are zero, and neither can ever learn — a dead neuron problem. So A is initialized with small random Gaussian values to break symmetry and provide initial gradient signal to B, while B stays zero to guarantee a stable training start."*

---

**Answer to Q9 (SVD Connection) — The senior-level answer:**

> *"SVD tells us that any matrix can be written as U Σ V^T. If we truncate this to the top r singular values, we get U_r Σ_r V_r^T — a rank-r approximation. Setting B = U_r Σ_r^{1/2} and A = Σ_r^{1/2} V_r^T, we get B@A = U_r Σ_r V_r^T, which is exactly the truncated SVD. So LoRA's parameterization B@A is mathematically equivalent to truncated SVD of the weight update ΔW. However, LoRA does NOT explicitly compute SVD during training — it learns A and B directly through gradient descent. The key insight is that gradient descent on the unconstrained B and A matrices implicitly discovers the same low-rank structure that SVD would reveal. The B=0 initialization ensures training starts cleanly, and the optimization landscape guides A and B toward the optimal low-rank decomposition of ΔW."*

---

**Answer to Q15 (Trap — merge degrades performance):**

> *"False. Merging LoRA into the base model is mathematically exact — not an approximation. For any input x, the output of W@x + B@A@x × (α/r) is algebraically identical to (W + B@A×α/r)@x. This is simply the distributive property of matrix multiplication. There is zero quality degradation. The only exception is when merging into a quantized base model in integer precision — there can be tiny floating-point rounding artifacts. But if you dequantize to fp32 before merging, the merged model is exactly identical in all outputs to the separate LoRA model. This is one of LoRA's greatest engineering advantages — you can have the efficiency of a single matrix multiply at inference time with absolutely no performance penalty."*

---

**Answer to Q16 (Trap — higher r always better):**

> *"Disagree. Higher r gives more model capacity, but this is only beneficial if the task actually requires high-rank weight changes. If a task has low intrinsic dimensionality — for example, simple instruction following or style adaptation — rank 4 or 8 is often sufficient. Using rank 64 for such a task wastes parameters, increases training cost, and risks overfitting on small datasets. The right rank depends on the task. Post-training SVD analysis of ΔW can reveal the actual effective rank the task uses. Additionally, for a fixed parameter budget, spreading rank across more weight matrices often beats using higher rank on fewer matrices — showing that where you put LoRA matters as much as how much capacity it has."*

## 13. Common Beginner Mistakes ❌

```
MISTAKE 1: Not understanding that merging is mathematically exact
FIX: W_merged = W + B@A×(α/r) is not an approximation.
     It is algebraically identical. Zero performance loss.
     Test this: Run both before and after merging — outputs match exactly.

MISTAKE 2: Setting the same rank r for all tasks
FIX: Task complexity should determine r.
     Simple classification → r=4 is often more than enough.
     Complex reasoning → r=32 or higher.
     Always validate on your specific task benchmark.

MISTAKE 3: Thinking LoRA can only apply to attention matrices
FIX: LoRA can be applied to ANY weight matrix:
     → Attention Q, K, V, O ✅
     → FFN up, down, gate ✅
     → Even embedding matrices ✅ (though rare)
     → Any nn.Linear layer in any model ✅

MISTAKE 4: Not checking trainable parameter count before training
FIX: Always run model.print_trainable_parameters() first.
     If it shows 100% trainable → forgot to freeze base model!
     If it shows 0% trainable → forgot to add LoRA or wrong config.

MISTAKE 5: Loading adapted model, THEN adding LoRA again
FIX: Always start from BASE (pre-trained, not fine-tuned) model.
     Adding LoRA to an already-LoRA-merged model doubles the effect.
     Load: base model → add LoRA config → train.

MISTAKE 6: Confusing α (alpha) with learning rate
FIX: α is a FIXED scaling constant (not trained, not optimized).
     It multiplies the LoRA output: × (α/r).
     It works with learning rate multiplicatively.
     Higher α ≠ higher learning rate (they are independent).

MISTAKE 7: Applying dropout at inference time
FIX: LoRA dropout is training-only.
     During inference: model.eval() disables all dropout.
     This happens automatically in PyTorch.
     Never manually apply dropout during inference.

MISTAKE 8: Using too low learning rate with LoRA
FIX: LoRA needs HIGHER LR than full fine-tuning.
     Full FT: 1e-5 to 3e-5.
     LoRA: 1e-4 to 3e-4.
     Low LR with LoRA = B matrix barely moves from zero.
     = Adapter barely learns anything.

MISTAKE 9: Forgetting to save in correct format
FIX: Don't save peft_model as if it were a regular model.
     peft_model.save_pretrained() saves ONLY adapter weights.
     This is what you want (~16MB, not 14GB).
     To save merged: merged = model.merge_and_unload() then save.

MISTAKE 10: Applying LoRA with same config to different model sizes
FIX: r=16 on a 7B model ≈ 0.06% trainable params.
     r=16 on a 70B model (d=8192) ≈ larger % but fewer relative to need.
     Scale r with task complexity, not model size.
     Larger models generally need smaller r proportionally.
```

## 14. Practical Implementation — Complete Code

```python
# ================================================
# COMPLETE LORA IMPLEMENTATION — EVERY DETAIL
# ================================================

import torch
from transformers import (
    AutoModelForCausalLM,
    AutoTokenizer,
    TrainingArguments
)
from peft import (
    LoraConfig,
    get_peft_model,
    TaskType,
    PeftModel
)
from trl import SFTTrainer
from datasets import load_dataset

# ─────────────────────────────────────────────────
# STEP 1: LOAD BASE MODEL (not adapter, not merged)
# ─────────────────────────────────────────────────
model_name = "meta-llama/Meta-Llama-3-8B"

model = AutoModelForCausalLM.from_pretrained(
    model_name,
    torch_dtype=torch.bfloat16,    # bf16 for memory efficiency
    device_map="auto",              # auto-place on GPU(s)
    trust_remote_code=True,
)
tokenizer = AutoTokenizer.from_pretrained(model_name)
tokenizer.pad_token = tokenizer.eos_token   # For padding

# ─────────────────────────────────────────────────
# STEP 2: VERIFY BASE MODEL (no trainable params yet)
# ─────────────────────────────────────────────────
total_params = sum(p.numel() for p in model.parameters())
trainable_params = sum(p.numel() for p in model.parameters()
                       if p.requires_grad)
print(f"Total params: {total_params:,}")        # ~8 billion
print(f"Trainable params: {trainable_params:,}") # ~8 billion (all!)

# ─────────────────────────────────────────────────
# STEP 3: CONFIGURE LORA — EVERY PARAMETER EXPLAINED
# ─────────────────────────────────────────────────
lora_config = LoraConfig(
    # TASK TYPE
    task_type=TaskType.CAUSAL_LM,    # We're fine-tuning a causal LM

    # RANK — The bottleneck dimension
    r=16,                             # Try 8, 16, 32, 64

    # ALPHA — Scaling factor
    lora_alpha=32,                    # α/r = 32/16 = 2.0 scaling
                                      # Rule of thumb: α = 2r

    # TARGET MODULES — Which weight matrices to adapt
    target_modules=[
        "q_proj",   # Query projection (what to look for)
        "k_proj",   # Key projection (how to present)
        "v_proj",   # Value projection (what to share) ← most important
        "o_proj",   # Output projection (how to mix heads)
        # Optionally add FFN for complex tasks:
        # "gate_proj",
        # "up_proj",
        # "down_proj",
    ],

    # DROPOUT — Applied to input of A matrix
    lora_dropout=0.05,               # 5% for medium datasets

    # BIAS — Whether to also train bias terms
    bias="none",                      # Options: "none", "all", "lora_only"
                                      # "none" is most parameter-efficient

    # INFERENCE MODE — False during training, True for serving
    inference_mode=False,
)

# ─────────────────────────────────────────────────
# STEP 4: APPLY LORA TO MODEL
# ─────────────────────────────────────────────────
model = get_peft_model(model, lora_config)

# ─────────────────────────────────────────────────
# STEP 5: VERIFY LORA (should show ~0.1% trainable)
# ─────────────────────────────────────────────────
model.print_trainable_parameters()
# Expected output:
# trainable params: 41,943,040 || all params: 8,030,261,248
# trainable%: 0.5224%

# ─────────────────────────────────────────────────
# STEP 6: INSPECT A LORA LAYER
# ─────────────────────────────────────────────────
# Access LoRA matrices directly
layer = model.base_model.model.model.layers[0]
lora_q = layer.self_attn.q_proj

print(f"A matrix shape: {lora_q.lora_A.default.weight.shape}")
# [r, d_model] = [16, 4096]

print(f"B matrix shape: {lora_q.lora_B.default.weight.shape}")
# [d_model, r] = [4096, 16]

print(f"A matrix (random init): {lora_q.lora_A.default.weight[:2,:4]}")
# Should show small random values

print(f"B matrix (zero init): {lora_q.lora_B.default.weight[:2,:4]}")
# Should show all zeros [[0., 0., 0., 0.], [0., 0., 0., 0.]]

print(f"Scaling (α/r): {lora_q.scaling}")
# Should show: 2.0 (= 32/16)

# ─────────────────────────────────────────────────
# STEP 7: TRAIN
# ─────────────────────────────────────────────────
training_args = TrainingArguments(
    output_dir="./lora_checkpoints",
    num_train_epochs=3,
    per_device_train_batch_size=2,
    gradient_accumulation_steps=8,    # Effective batch = 16
    warmup_ratio=0.03,                # 3% warmup
    learning_rate=2e-4,               # Higher than full FT!
    bf16=True,
    gradient_checkpointing=True,      # Memory optimization
    logging_steps=25,
    evaluation_strategy="steps",
    eval_steps=100,
    save_strategy="steps",
    save_steps=100,
    load_best_model_at_end=True,
    metric_for_best_model="eval_loss",
    greater_is_better=False,
    lr_scheduler_type="cosine",
    optim="paged_adamw_32bit",       # Paged optimizer for stability
)

trainer = SFTTrainer(
    model=model,
    args=training_args,
    train_dataset=train_dataset,     # Your JSONL dataset
    eval_dataset=val_dataset,
    tokenizer=tokenizer,
    max_seq_length=2048,
)

trainer.train()

# ─────────────────────────────────────────────────
# STEP 8: SAVE ADAPTER (just the small files!)
# ─────────────────────────────────────────────────
model.save_pretrained("./my_lora_adapter")
tokenizer.save_pretrained("./my_lora_adapter")
# Creates: adapter_config.json (~1KB) + adapter_model.bin (~16MB)

# ─────────────────────────────────────────────────
# STEP 9: POST-TRAINING SVD ANALYSIS
# ─────────────────────────────────────────────────
# Analyze if we used the right rank
delta_W = (
    layer.self_attn.q_proj.lora_B.default.weight @
    layer.self_attn.q_proj.lora_A.default.weight
) * lora_q.scaling

U, S, Vh = torch.linalg.svd(delta_W.float())
print(f"Singular values of ΔW_Q (layer 0):")
print(S[:20])  # Show top 20 singular values
# If first 4 are big, rest near zero → r=4 was enough
# If all 16 are similar → task needs all dimensions → try r=32

# ─────────────────────────────────────────────────
# STEP 10A: MERGE FOR SINGLE-TASK DEPLOYMENT
# ─────────────────────────────────────────────────
merged_model = model.merge_and_unload()
# This computes W_merged = W_frozen + B@A×(α/r) for all matrices
# Returns a regular model with NO LoRA components

merged_model.save_pretrained("./merged_model")
# Saves the full model (~16GB for 8B model)
# But now: zero inference latency overhead!

# ─────────────────────────────────────────────────
```
