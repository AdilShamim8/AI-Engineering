## 1.1 The Fundamental Problem

### First Principles: What Actually Happens Inside Software

Every real software system works like this:

```
FUNCTION EXPECTS:       FUNCTION RECEIVES:
─────────────────       ──────────────────
An integer              ✅ 42
A list of strings       ✅ ["apple", "banana"]
A dictionary            ✅ {"name": "Rahim", "age": 25}
A boolean               ✅ True or False

NOT:                    NOT:
A human sentence        ❌ "The number is 42, which is..."
Ambiguous text          ❌ "The fruits include apple and banana"
Mixed format            ❌ "Name: Rahim. Age is 25 years old."
```

> **The core tension:**
> - Your **software** speaks structured data (types, schemas, contracts)
> - Your **LLM** speaks natural language (sentences, paragraphs, prose)
>
> **Structured Output = Translation layer between these two worlds.**

## 1.2 The Mental Model — "Contract Programming"

> 🤝 **Analogy: A Legal Contract**
>
> When two businesses work together, they sign a **contract** that says:
> - *"You will deliver X items"* (not "some items")
> - *"Payment is $Y on date Z"* (not "some money eventually")
> - *"Format of delivery is ABC"* (not "however you feel like")
>
> Without a contract, both parties might do something different.
> With a contract, both parties MUST follow the agreed format.
>
> **Structured Output = A contract between your LLM and your code.**
>
> Your code says: *"I expect this exact structure."*
> The LLM says: *"I will produce exactly that structure."*
> If the LLM breaks the contract → you handle it (validation + retry).

## 2.2 The 5 Levels of JSON Prompting

### LEVEL 1 — Simple Request (Weakest)

```python
# ❌ WEAK - Just asking nicely
prompt = """
Extract the name and age from this text.
Return it as JSON.

Text: "Hi, I'm Sara and I'm 28 years old"
"""

# LLM MIGHT RETURN (unpredictable):
# Option A: {"name": "Sara", "age": 28}           ← what we want
# Option B: {"name": "Sara", "age": "28"}         ← age is string, not int!
# Option C: Here is the JSON: {"name": "Sara"...} ← extra text!
# Option D: ```json\n{"name": "Sara"...}\n```     ← markdown wrapper!
# Option E: The name is Sara and age is 28        ← ignored instruction!
```

---

### LEVEL 2 — Example-Driven (Better)

```python
# ✅ BETTER - Show exact example
prompt = """
Extract the name and age from the text below.

Return ONLY this exact JSON format (no extra text):
{
  "name": "string",
  "age": number
}

EXAMPLE:
Text: "My name is Ali and I am 30 years old"
Output: {"name": "Ali", "age": 30}

Now extract from:
Text: "Hi, I'm Sara and I'm 28 years old"
Output:
"""

# LLM will usually return: {"name": "Sara", "age": 28}
# Much more consistent now. But still not 100% guaranteed.
```

---

### LEVEL 3 — Explicit Rules (Even Better)

```python
# ✅✅ GOOD - With explicit rules
prompt = """
Extract person information from the text below.

OUTPUT RULES (follow exactly):
1. Return ONLY valid JSON. No other text before or after.
2. Do NOT wrap in markdown (no backticks, no ```json)
3. Start your response with { and end with }
4. "age" must be a NUMBER (integer), NOT a string
5. If information is missing, use null
6. Keys must be exactly: "name", "age"

JSON SCHEMA:
{
  "name": string or null,
  "age": integer or null
}

Text: "Hi, I'm Sara and I'm 28 years old"
"""

# Now the LLM is much more constrained. Better reliability.
```

### LEVEL 4 — System Prompt Separation (Production Grade)

```python
# ✅✅✅ PRODUCTION - System + User separation
system_prompt = """

## 3.1 What Is a Schema?

### Simple English:
> **A schema = A blueprint that defines exactly what structure, types, and rules your data must follow.**
>
> It answers: *"What fields exist? What type is each field? Which are required? What are the allowed values?"*

```
REAL WORLD ANALOGY: A Form
━━━━━━━━━━━━━━━━━━━━━━━━━━

Think of a government application form:

[ First Name: ________ ]  ← required, text, max 50 chars
[ Last Name:  ________ ]  ← required, text
[ Age:        ________ ]  ← required, number, must be 18-120
[ Gender:     M / F / Other ]  ← required, must be one of these options
[ Email:      ________ ]  ← optional, must match email format

This FORM is a schema.
It says: "Your data MUST look exactly like this."
If you fill in wrong type → form rejects it.

A JSON SCHEMA does the same thing for data.
```

## 3.2 JSON Schema — The Language of Data Contracts

### JSON Schema Syntax from Scratch:

```json
// THE SIMPLEST POSSIBLE SCHEMA:
{
  "type": "object",
  "properties": {
    "name": {"type": "string"},
    "age":  {"type": "integer"}
  }
}

// This says:
// - The output must be an OBJECT (dictionary)
// - It must have "name" which is a STRING
// - It must have "age" which is an INTEGER
```

### Growing Complexity — Step by Step:

```json
// LEVEL 1: Basic types
{
  "type": "object",
  "properties": {
    "name":       {"type": "string"},
    "age":        {"type": "integer"},
    "score":      {"type": "number"},   // float or int
    "is_active":  {"type": "boolean"},
    "nickname":   {"type": ["string", "null"]}  // optional
  },
  "required": ["name", "age"]  // these MUST be present
}

// ─────────────────────────────────────────────────

// LEVEL 2: Adding constraints
{
  "type": "object",
  "properties": {
    "name": {
      "type": "string",
      "minLength": 1,      // Can't be empty string
      "maxLength": 100     // Can't be too long
    },
    "age": {
      "type": "integer",
      "minimum": 0,        // Can't be negative
      "maximum": 150       // Can't be unrealistic
    },
    "email": {
      "type": "string",
      "format": "email"    // Must look like an email
    },
    "status": {
      "type": "string",
      "enum": ["active", "inactive", "pending"]  // Must be ONE of these
    }
  },
  "required": ["name", "age", "email", "status"]
}

// ─────────────────────────────────────────────────

// LEVEL 3: Nested objects and arrays
{
  "type": "object",
  "properties": {
    "customer": {
      "type": "object",          // Nested object
      "properties": {
        "name": {"type": "string"},
        "email": {"type": "string"}
      },
      "required": ["name"]
    },
    "items": {
      "type": "array",           // Array of items
      "items": {                 // Schema for each array item
        "type": "object",
        "properties": {
          "product_id": {"type": "string"},
          "quantity":   {"type": "integer", "minimum": 1},
          "price":      {"type": "number",  "minimum": 0}
        },
        "required": ["product_id", "quantity", "price"]
      },
      "minItems": 1              // Array can't be empty
    },
    "total_amount": {"type": "number"}
  },
  "required": ["customer", "items", "total_amount"]
}

## 3.3 Schema-Constrained Prompting Pattern

```python
# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
# SCHEMA-CONSTRAINED OUTPUT PATTERN
# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

import json
import jsonschema  # pip install jsonschema

# DEFINE YOUR SCHEMA ONCE
ORDER_SCHEMA = {
    "type": "object",
    "properties": {
        "customer_name": {"type": "string"},
        "items": {
            "type": "array",
            "items": {
                "type": "object",
                "properties": {
                    "product":  {"type": "string"},
                    "quantity": {"type": "integer", "minimum": 1},
                    "color":    {"type": ["string", "null"]},
                    "size":     {"type": ["string", "null"]}
                },
                "required": ["product", "quantity"]
            }
        },
        "delivery_urgency": {
            "type": "string",
            "enum": ["standard", "express", "same_day"]
        }
    },
    "required": ["customer_name", "items", "delivery_urgency"]
}

def extract_order(customer_message: str, customer_name: str) -> dict:
    
    # BUILD PROMPT WITH SCHEMA EMBEDDED
    prompt = f"""
    Extract order details from this customer message.
    
    Customer name: {customer_name}
    
    You MUST return valid JSON matching this EXACT schema:
    {json.dumps(ORDER_SCHEMA, indent=2)}
    
    IMPORTANT RULES:
    - delivery_urgency must be EXACTLY one of: "standard", "express", "same_day"
    - quantity must be a positive INTEGER
    - If color/size not mentioned, use null
    - Return ONLY the JSON. Nothing else.
    
    Customer message: "{customer_message}"
    """
    
    raw_response = llm.call(prompt)
    
    # PARSE AND VALIDATE AGAINST SCHEMA
    try:
        parsed = json.loads(raw_response)
        jsonschema.validate(instance=parsed, schema=ORDER_SCHEMA)
        return parsed  # ✅ Valid!
        
    except json.JSONDecodeError as e:
        raise ValueError(f"LLM returned invalid JSON: {e}")
        
    except jsonschema.ValidationError as e:
        raise ValueError(f"JSON doesn't match schema: {e.message}")

# TEST:
result = extract_order(
    customer_message="I need 3 red Nike shoes size 10 urgently please!",
    customer_name="Rahim"
)

# RESULT:
# {
#   "customer_name": "Rahim",
#   "items": [
#     {"product": "Nike shoes", "quantity": 3, "color": "red", "size": "10"}
#   ],
#   "delivery_urgency": "express"
# }
```

## 4.1 What Is Pydantic?

### Simple English:
> **Pydantic = A Python library that lets you define data shapes as Python classes, and automatically validates + converts data to match that shape.**
>
> Instead of writing JSON schema by hand (verbose, error-prone), you write **Python classes** (clean, readable, type-safe).

```
WITHOUT PYDANTIC (raw dictionary approach):
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
# You get this from LLM:
data = {"name": "Sara", "age": "28", "email": "sara@test.com"}
#                              ↑ Problem: age is a STRING "28", not integer 28

# Your code expects:
process_age(data["age"] + 5)  # ← CRASH! "28" + 5 doesn't work
                               # String + Integer = TypeError ❌

WITH PYDANTIC:
━━━━━━━━━━━━━━
from pydantic import BaseModel

class Person(BaseModel):
    name: str
    age: int        # ← Pydantic automatically converts "28" → 28
    email: str

person = Person(**data)
# Pydantic: "age is '28' (string), but you want int. Let me convert: 28" ✅
process_age(person.age + 5)  # ← WORKS! person.age is now integer 28
```

## 4.2 Pydantic from First Principles

### Step 1: The Basic Class

```python
from pydantic import BaseModel
from typing import Optional, List

# STEP 1: Define your data shape as a class
class Product(BaseModel):
    name: str               # Required string
    price: float            # Required float
    quantity: int           # Required integer
    color: Optional[str]    # Optional string (can be None)
    in_stock: bool          # Required boolean

# STEP 2: Create an instance - Pydantic validates automatically
product = Product(
    name="Nike Shoes",
    price=99.99,
    quantity=5,
    color="red",
    in_stock=True
)

print(product.name)      # "Nike Shoes"
print(product.price)     # 99.99
print(product.quantity)  # 5

# STEP 3: Auto-conversion (Pydantic's magic)
product2 = Product(

## 4.4 Pydantic Schema Thinking — The Engineering Mindset

```
WHEN DESIGNING AN LLM OUTPUT SCHEMA, THINK THROUGH:

QUESTION 1: "What is the MINIMUM information I need?"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Don't ask for 20 fields when you only need 3.
More fields = more chances for the LLM to get something wrong.
Start minimal. Add fields only when needed.

QUESTION 2: "Which fields should be Optional vs Required?"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Required: The LLM will always fail if it can't fill this
Optional: If the information isn't in the input, None is fine
Wrong: Making everything required → LLM fabricates missing info ❌
Right: Make truly optional things Optional → LLM returns None safely ✅

QUESTION 3: "What TYPES make sense?"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Use enums/Literal for controlled vocabulary fields
  GOOD: status: Literal["active", "inactive"]  
  BAD:  status: str   ← LLM might say "currently active" instead of "active"

Use float for confidence/probability scores, not str
  GOOD: confidence: float  → 0.87
  BAD:  confidence: str    → "highly confident" (can't compare programmatically)

QUESTION 4: "What are my business rules?"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Encode business rules in validators:
  - price must be >= 0
  - quantity must be > 0
  - email must match pattern
  - date must be in the future
Don't check these in your application code AFTER parsing.
Catch them AT THE SCHEMA LEVEL.

QUESTION 5: "What do I do when validation fails?"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Always have a plan:
  Option A: Retry with stricter prompt
  Option B: Ask the LLM to fix the specific error
  Option C: Return safe default / fallback
  Option D: Escalate to human review
Never silently swallow validation errors.
```

## 5.1 What Is Function/Tool Calling?

### Simple English:
> **Function calling = Instead of asking the LLM to "write JSON that looks like a function call", you tell the LLM what functions/tools exist, and it CHOOSES which one to call and fills in the arguments.**

This is the **highest reliability** method for structured output because:
1. The LLM is **specifically trained** to use function calling
2. The structure is enforced **at the model level**, not just through prompting
3. Arguments are **automatically validated** against the function schema

---

### The Core Idea — Before vs After Function Calling

```
BEFORE FUNCTION CALLING (using prompts):
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

You: "If the user wants weather, respond with JSON:
      {'action': 'get_weather', 'city': '...', 'unit': 'celsius'}"

LLM: "I'll get the weather for you!"
     "Here is the JSON: {'action': 'get_weather', 'city': 'Dhaka'}"
     
Problems:
- LLM might not always include all fields
- Unit field might be missing
- Format might vary ("celsius" vs "Celsius" vs "c")
- LLM might add extra commentary

AFTER FUNCTION CALLING (native API feature):
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

You register a function:
  get_weather(city: str, unit: Literal["celsius", "fahrenheit"])

LLM: [calls get_weather with arguments: city="Dhaka", unit="celsius"]

What you get back from API:
{
  "name": "get_weather",
  "arguments": {
    "city": "Dhaka",
    "unit": "celsius"
  }
}

✅ Always valid JSON
✅ Always correct field names  
✅ Always correct types
✅ No extra commentary
✅ Guaranteed to match your function signature
```

## 5.2 How Function Calling Works — Step by Step

```
THE COMPLETE FLOW:

USER: "What's the weather in Dhaka?"

STEP 1: YOU define available functions for the LLM
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

tools = [
  {
    "type": "function",
    "function": {
      "name": "get_weather",
      "description": "Get current weather for a city",
      "parameters": {
        "type": "object",
        "properties": {
          "city": {
            "type": "string",
            "description": "City name to get weather for"
          },
          "unit": {
            "type": "string",
            "enum": ["celsius", "fahrenheit"],
            "description": "Temperature unit"
          }
        },
        "required": ["city", "unit"]
      }
    }
  }
]

STEP 2: LLM reads user message + function definitions
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
LLM thinks: "User wants weather. I have get_weather function. I'll call it."

STEP 3: LLM returns a TOOL CALL (not text)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
{
  "tool_calls": [{
    "function": {
      "name": "get_weather",
      "arguments": '{"city": "Dhaka", "unit": "celsius"}'
    }
  }]
}

STEP 4: YOUR CODE executes the actual function
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
# Parse the arguments
args = json.loads(tool_call["function"]["arguments"])
# Call your real function
weather_data = get_weather(city=args["city"], unit=args["unit"])
# Returns: {"temp": 32, "condition": "Sunny", "humidity": 78}

STEP 5: Feed result back to LLM for final response
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
LLM: "The current weather in Dhaka is 32°C and sunny with 78% humidity."

NOTICE: The LLM never actually got the weather. 
        YOUR CODE got the weather.
        The LLM only decided WHICH function to call and WITH WHAT ARGUMENTS.
```

## 5.3 Complete Function Calling Code

```python
# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
# COMPLETE FUNCTION CALLING IMPLEMENTATION
# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

from openai import OpenAI
import json

client = OpenAI()

# ─── DEFINE YOUR REAL FUNCTIONS ───
def get_weather(city: str, unit: str) -> dict:
    """Actually fetch weather from a real API"""
    # In reality: call weather API
    return {"city": city, "temp": 32, "unit": unit, "condition": "Sunny"}

def search_products(query: str, max_price: float = None) -> list:
    """Search product database"""
    # In reality: query database
    return [{"name": "Nike Shoes", "price": 89.99}]

def send_email(to: str, subject: str, body: str) -> dict:
    """Send an email"""
    # In reality: call email API
    return {"status": "sent", "message_id": "MSG_001"}

# ─── REGISTER FUNCTIONS FOR LLM ───
TOOLS = [
    {
        "type": "function",
        "function": {
            "name": "get_weather",
            "description": "Get current weather for any city in the world",
            "parameters": {
                "type": "object",
                "properties": {
                    "city": {
                        "type": "string",
                        "description": "The city name, e.g. 'Dhaka', 'London'"
                    },
                    "unit": {
                        "type": "string",
                        "enum": ["celsius", "fahrenheit"],
                        "description": "Temperature unit preference"
                    }
                },
                "required": ["city", "unit"]
            }
        }
    },
    {
        "type": "function",
        "function": {
            "name": "search_products",
            "description": "Search for products in our catalog",
            "parameters": {
                "type": "object",
                "properties": {
                    "query": {
                        "type": "string",
                        "description": "Product search query"
                    },
                    "max_price": {
                        "type": "number",
                        "description": "Maximum price filter (optional)"
                    }
                },
                "required": ["query"]
            }
        }
    },
    {
        "type": "function",
        "function": {
            "name": "send_email",
            "description": "Send an email to someone",
            "parameters": {
                "type": "object",
                "properties": {
                    "to":      {"type": "string", "description": "Recipient email"},
                    "subject": {"type": "string", "description": "Email subject"},
                    "body":    {"type": "string", "description": "Email body content"}
                },
                "required": ["to", "subject", "body"]
            }
        }
    }
]

# ─── FUNCTION REGISTRY (maps name → function) ───
FUNCTION_REGISTRY = {
    "get_weather":    get_weather,
    "search_products": search_products,
    "send_email":     send_email
}

# ─── THE COMPLETE AGENT LOOP ───
def run_with_tools(user_message: str) -> str:
    """Process user message, using tools as needed"""
    
    messages = [{"role": "user", "content": user_message}]
    
    while True:  # Loop until LLM stops calling tools
        
        # Send to LLM with tool definitions
        response = client.chat.completions.create(
            model="gpt-4o",
            messages=messages,
            tools=TOOLS,
            tool_choice="auto"  # LLM decides: use tool or respond directly
        )
        
        message = response.choices[0].message
        
        # ─── CASE 1: LLM wants to call a function ───
        if message.tool_calls:
            
            # Add LLM's response to conversation
            messages.append(message)
            
            # Process each tool call
            for tool_call in message.tool_calls:
                function_name = tool_call.function.name
                function_args = json.loads(tool_call.function.arguments)
                
                print(f"🔧 Calling: {function_name}({function_args})")
                
                # Execute the actual function
                if function_name in FUNCTION_REGISTRY:
                    result = FUNCTION_REGISTRY[function_name](**function_args)
                else:
                    result = {"error": f"Unknown function: {function_name}"}
                
                # Add tool result to conversation
                messages.append({
                    "role": "tool",
                    "tool_call_id": tool_call.id,
                    "content": json.dumps(result)
                })
        
        # ─── CASE 2: LLM is done, giving final answer ───
        else:
            return message.content  # ← Return the final text response
    
# USAGE EXAMPLES:
print(run_with_tools("What's the weather in Dhaka in celsius?"))
# 🔧 Calling: get_weather({'city': 'Dhaka', 'unit': 'celsius'})
# Output: "The current weather in Dhaka is 32°C and sunny."

print(run_with_tools("Find me Nike shoes under $100"))
# 🔧 Calling: search_products({'query': 'Nike shoes', 'max_price': 100})
# Output: "I found Nike Shoes for $89.99..."

print(run_with_tools("Send an email to boss@company.com about the meeting tomorrow"))
# 🔧 Calling: send_email({'to': 'boss@company.com', 'subject': '...', 'body': '...'})
# Output: "Email sent successfully to boss@company.com"
```

## 5.4 Function Calling vs JSON Prompting — When to Use Which

```
┌─────────────────────┬──────────────────────────┬──────────────────────────┐
│ DIMENSION           │ JSON PROMPTING           │ FUNCTION CALLING         │
├─────────────────────┼──────────────────────────┼──────────────────────────┤
│ Reliability         │ ⭐⭐⭐ Medium             │ ⭐⭐⭐⭐⭐ Very High      │
│ Setup complexity    │ Simple (just prompt)     │ More setup needed        │
│ Tool execution      │ ❌ You parse and call    │ ✅ Framework helps       │
│ Multiple tools      │ ❌ Complex to handle     │ ✅ Built-in support      │
│ Model compatibility │ ✅ Any model             │ ⚠️ Only supported models │
│ Argument validation │ Manual                   │ Automatic                │
│ Cost                │ Same                     │ Same                     │
│ Best for            │ Simple extraction        │ Agent systems, tools     │
└─────────────────────┴──────────────────────────┴──────────────────────────┘

USE JSON PROMPTING WHEN:
✅ Simple extraction tasks (get name, age from text)
✅ Model doesn't support function calling
✅ Output is data, not an action
✅ Quick prototyping

USE FUNCTION CALLING WHEN:
✅ LLM needs to take ACTIONS (search, email, database)
✅ Multiple possible tools to choose from
✅ Reliability is critical
✅ Building agent systems
✅ Tool selection logic is needed
```

## 6.2 Building the Complete Defense System

# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
# THE COMPLETE 5-LAYER ENFORCEMENT SYSTEM
# ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

from pydantic import BaseModel, Field, field_validator

import json
import re

# ─── YOUR DATA SCHEMA ───
class InvoiceItem(BaseModel):

    quantity:    int  = Field(..., gt=0)
    unit_price:  float = Field(..., ge=0)
    total:       float = Field(..., ge=0)

class Invoice(BaseModel):
    invoice_number: str   = Field(..., min_length=3)
    vendor_name:    str   = Field(..., min_length=1)
    invoice_date:   str   = Field(..., pattern=r'^\d{4}-\d{2}-\d{2}$')  # YYYY-MM-DD
    items:          List[InvoiceItem] = Field(..., min_length=1)
    subtotal:       float = Field(..., ge=0)
    tax_rate:       float = Field(..., ge=0, le=1)   # 0.0 to 1.0
    total_amount:   float = Field(..., ge=0)
    currency:       Literal["USD", "EUR", "GBP", "BDT"] = "USD"
    
    @field_validator('total_amount')
    @classmethod
    def validate_total_matches_items(cls, v, info):
        """BUSINESS RULE: total = subtotal + (subtotal × tax_rate)"""
        if 'subtotal' in info.data and 'tax_rate' in info.data:
            expected = info.data['subtotal'] * (1 + info.data['tax_rate'])
            if abs(v - expected) > 0.01:  # Allow $0.01 rounding difference
                raise ValueError(
                    f"total_amount {v} doesn't match "
                    f"subtotal×(1+tax) = {expected:.2f}"
                )
        return v

# ─── LAYER 1+2: PROMPT + API ENFORCEMENT ───
def build_invoice_prompt(raw_text: str) -> str:
    schema = Invoice.model_json_schema()
    return f"""
    Extract invoice information from the text below.
    
    Return ONLY valid JSON matching this schema:
    {json.dumps(schema, indent=2)}
    
    CRITICAL RULES:
    - invoice_date: MUST be in YYYY-MM-DD format
    - currency: MUST be exactly one of: USD, EUR, GBP, BDT
    - all amounts: MUST be numbers (not strings)
    - total_amount MUST equal subtotal × (1 + tax_rate)
    
    Invoice text:
    {raw_text}
    """

# ─── LAYER 3: JSON PARSING ───
def parse_json_safely(raw_response: str) -> dict:
    """Try multiple strategies to extract valid JSON"""
    
    # Strategy 1: Direct parse (ideal case)
    try:
        return json.loads(raw_response.strip())
    except json.JSONDecodeError:
        pass
    
    # Strategy 2: Find JSON block in markdown (```json ... ```)
    md_pattern = r'```(?:json)?\s*(\{.*?\})\s*```'
    match = re.search(md_pattern, raw_response, re.DOTALL)
    if match:
        try:
            return json.loads(match.group(1))
        except json.JSONDecodeError:
            pass
    
    # Strategy 3: Find first { to last } in the response
    start = raw_response.find('{')
    end = raw_response.rfind('}')
    if start != -1 and end != -1 and start < end:
        try:
            return json.loads(raw_response[start:end+1])
        except json.JSONDecodeError:
            pass
    
    # All strategies failed
    raise ValueError(f"Cannot extract valid JSON from response: {raw_response[:200]}...")

# ─── LAYER 4+5: SCHEMA + BUSINESS VALIDATION ───
def validate_invoice(data: dict) -> Invoice:
    """Pydantic validates types + business rules"""
    try:
        return Invoice(**data)
    except Exception as e:
        raise ValueError(f"Schema/business validation failed: {e}")

# ─── THE COMPLETE PIPELINE ───
def extract_invoice_with_enforcement(raw_text: str, max_retries: int = 3) -> Invoice:
    """
    Full 5-layer enforcement pipeline
    """
    
    last_error = None
    improvement_context = ""
    
    for attempt in range(max_retries):
        
        try:
            # LAYER 1+2: Prompt engineering + API call
            prompt = build_invoice_prompt(raw_text)
            if improvement_context:
                prompt += f"\n\nPREVIOUS ERROR (fix this): {improvement_context}"
            
            raw_response = llm.call(
                prompt,
                response_format={"type": "json_object"}  # Layer 2: API enforcement
            )
            
            # LAYER 3: Parse JSON
            data = parse_json_safely(raw_response)
            
            # LAYER 4+5: Schema + Business validation
            invoice = validate_invoice(data)
            
            # ✅ ALL LAYERS PASSED
            print(f"✅ Extraction successful on attempt {attempt + 1}")
            return invoice
            
        except ValueError as e:
            last_error = str(e)
            improvement_context = last_error
            print(f"⚠️ Attempt {attempt + 1} failed: {last_error[:100]}")
    
    raise Exception(f"Extraction failed after {max_retries} attempts. "
                   f"Last error: {last_error}")

### STRATEGY 2: Strip Markdown Code Blocks

def parse_strip_markdown(llm_response: str) -> dict:
    """
    Handle markdown-wrapped JSON (very common LLM behavior)
    LLMs trained on code often wrap JSON in ```json ... ```
    """
    # Remove ```json ... ``` or ``` ... ```
    cleaned = re.sub(
        r'^```(?:json)?\s*\n?',  # Remove opening ```json
        '',
        llm_response.strip(),
        flags=re.MULTILINE
    )
    cleaned = re.sub(
        r'\n?```\s*$',           # Remove closing ```
        '',
        cleaned.strip(),
        flags=re.MULTILINE
    )
    return json.loads(cleaned.strip())

# Works for:
# ```json
# {"name": "Sara", "age": 28}
# ```
```

### STRATEGY 3: Extract JSON from Text

```python
def parse_extract_from_text(llm_response: str) -> dict:
    """
    Extract JSON when it's buried in explanatory text.
    Common when LLM adds: "Here is the extracted data:" before JSON.
    """
    # Find first { and last } (handles simple single-object JSON)
    start_brace = llm_response.find('{')
    end_brace = llm_response.rfind('}')
    
    if start_brace != -1 and end_brace != -1 and start_brace < end_brace:
        json_str = llm_response[start_brace:end_brace + 1]
        return json.loads(json_str)
    
    raise ValueError("No JSON object found in response")

# Works for:
# "Here is the data: {"name": "Sara", "age": 28} Hope this helps!"
```

### STRATEGY 4: Fix Common JSON Errors

```python
def parse_fix_common_errors(llm_response: str) -> dict:
    """
    Fix common LLM JSON mistakes before parsing.
    LLMs sometimes produce ALMOST-valid JSON with small errors.
    """
    text = llm_response.strip()
    
    # Remove markdown wrappers
    text = re.sub(r'^```(?:json)?\s*\n?', '', text)
    text = re.sub(r'\n?```\s*$', '', text)
    text = text.strip()
    
    # Fix 1: Trailing commas (LLMs often add these)
    # {"name": "Sara", "age": 28,}  ← invalid
    text = re.sub(r',(\s*[}\]])', r'\1', text)
    
    # Fix 2: Single quotes instead of double quotes
    # {'name': 'Sara'}  ← invalid JSON, valid Python
    # This is tricky — only fix if json.loads fails
    
    # Fix 3: Unquoted keys
    # {name: "Sara"}  ← invalid JSON
    text = re.sub(r'(\w+)(?=\s*:)', r'"\1"', text)
    # Careful: this is aggressive, test thoroughly
    
    # Fix 4: Remove comments (// or /* */ not valid in JSON)
    text = re.sub(r'//.*?\n', '\n', text)  # Remove // comments
    
    try:
        return json.loads(text)
    except json.JSONDecodeError:
        # Try ast.literal_eval for Python-like dicts with single quotes
        import ast
        try:
            result = ast.literal_eval(text)
            if isinstance(result, dict):
                return result
        except:
            pass
        raise ValueError(f"Cannot fix JSON: {text[:200]}")
```

### STRATEGY 5: LLM Self-Repair

```python
def parse_with_llm_repair(llm_response: str, original_prompt: str) -> dict:
    """
    When all parsing fails, ask the LLM to fix its own output.
    Expensive but powerful last resort.
    """
    repair_prompt = f"""
    The following text should be valid JSON but has errors.
    Fix it so it becomes valid JSON and return ONLY the fixed JSON.
    
    Do NOT add explanations.
    Do NOT wrap in markdown.
    Return only the JSON starting with {{ and ending with }}.
    
    BROKEN JSON:
    {llm_response}
    
    WHAT IT SHOULD REPRESENT (context):
    {original_prompt[:200]}
    """
    
    repaired = llm.call(repair_prompt)
    return json.loads(repaired.strip())  # Try direct parse on repaired version
```

### STRATEGY 6: The Complete Cascade Parser (Production Ready)

```python
def parse_robust(
    llm_response: str,
    original_prompt: str = "",
    use_llm_repair: bool = True
) -> dict:
    """
    Try strategies in order of cost/complexity.
    Falls through to more aggressive strategies only when needed.
    """
    
    strategies = [
        ("direct",          lambda: json.loads(llm_response.strip())),
        ("strip_markdown",  lambda: parse_strip_markdown(llm_response)),
        ("extract_json",    lambda: parse_extract_from_text(llm_response)),
        ("fix_errors",      lambda: parse_fix_common_errors(llm_response)),
    ]
    
    if use_llm_repair:
        strategies.append(
            ("llm_repair", lambda: parse_with_llm_repair(llm_response, original_prompt))
        )
    
    for strategy_name, strategy_fn in strategies:
        try:
            result = strategy_fn()
            if isinstance(result, dict):
                print(f"✅ Parsed using strategy: {strategy_name}")
                return result
        except Exception as e:
            print(f"⚠️ Strategy '{strategy_name}' failed: {str(e)[:50]}")
            continue
    
    raise ValueError(
        f"All {len(strategies)} parsing strategies failed for response:\n"
        f"{llm_response[:300]}..."
    )

Why: LLM interprets instructions as guidelines, not hard constraints

# 📌 INTERVIEW QUESTIONS & ANSWERS

**❓ Q1: "What is structured output and why is it critical for AI applications?"**

> ✅ **Strong Answer:**
> "Structured output is the practice of constraining LLM responses to a specific data format — typically JSON — that can be programmatically processed. It's critical because LLMs naturally produce unstructured prose, but real applications need type-safe, predictable data structures. Without structured output, you can't reliably store data in databases, call downstream functions, or build multi-step workflows. I enforce it through layered strategies: prompt engineering, API-level JSON mode, Pydantic schema validation, and business logic checks."

---

**❓ Q2: "How would you use Pydantic to validate LLM output?"**

> ✅ **Strong Answer:**
> "I define the expected output as a Pydantic BaseModel with typed fields, validators, and constraints. I generate the JSON schema from the model and embed it in the prompt. After the LLM responds, I parse the JSON and instantiate the Pydantic model — which automatically validates types, converts compatible types, and runs custom validators. If validation fails, Pydantic gives me precise error messages I can use to improve the prompt in a retry. This approach gives me compile-time-like type safety on runtime LLM outputs."

---

**❓ Q3: "What's the difference between JSON mode and function calling?"**

> ✅ **Strong Answer:**
> "JSON mode guarantees the response is valid parseable JSON, but you still define the schema yourself in the prompt and validate it yourself in code. Function calling goes further — you define the function signatures with typed parameters, and the model selects which function to call and fills in validated arguments. Function calling is superior when the LLM needs to choose between multiple tools or actions, because the selection logic and argument structure are enforced at the model level, trained specifically for this purpose."

---

**❓ Q4: "Walk me through your parsing strategy when an LLM returns malformed JSON."**

> ✅ **Strong Answer:**
> "I use a cascade of strategies in order of cost. First, direct json.loads. If that fails, strip markdown code blocks — a very common LLM behavior. If still failing, find the first { to last } to extract JSON from surrounding text. Then try fixing common errors like trailing commas. As a last resort, ask the LLM to repair its own output — expensive but effective. Each strategy logs which one succeeded for monitoring. I track failure rates per strategy in production to identify when the LLM is consistently producing certain error patterns, which signals a need to improve the original prompt."

---

**❓ Q5: "How do you prevent LLMs from fabricating data for missing fields?"**

> ✅ **Strong Answer:**
> "Three approaches. First, make optional fields truly Optional in your schema — LLMs are trained to complete required fields and will fabricate if forced. Second, add explicit instruction in the prompt: 'If information is not present in the source text, use null. Never invent or assume data.' Third, add a source-grounding check as a post-validation step — for critical fields, verify the extracted value actually appears in the original text. For high-stakes applications like medical or financial data extraction, I add a confidence score field and flag any low-confidence extractions for human review."

# 📌 COMMON BEGINNER MISTAKES

```
MISTAKE 1: Trusting LLM Output Directly
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Wrong:  data = json.loads(llm.call(prompt))["name"]
Right:  data = extract_with_validation(prompt)
The LLM will eventually return something unexpected. Always validate.

MISTAKE 2: Using str Type for Everything
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Wrong:  class Output(BaseModel):
            amount: str   ← "99.99" or "$99.99" or "ninety-nine"?
Right:  class Output(BaseModel):
            amount: float  ← Forces numeric type, Pydantic converts
Numbers should always be numeric types, never strings.

MISTAKE 3: Making Everything Required
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Wrong:  All fields are required → LLM fabricates missing info
Right:  Optional[str] = None for fields that might not be in the input
Never force the LLM to invent data.

MISTAKE 4: No Fallback When Parsing Fails
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Wrong:  data = json.loads(response)  ← crashes the app on failure
Right:  data = parse_robust(response) with retry logic and fallbacks
Production systems must handle parsing failures gracefully.

MISTAKE 5: Giant Schemas on First Try
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Wrong:  Designing 20-field nested schema immediately
Right:  Start with 3-5 essential fields. Add fields one at a time.
        More fields = more failure points. Keep it minimal.

MISTAKE 6: Not Using JSON Mode When Available
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Wrong:  Relying only on prompt instructions to get JSON
Right:  response_format={"type": "json_object"} is a free reliability upgrade.
        Always use it when your endpoint supports it.

MISTAKE 7: Ignoring Pydantic's Auto-Conversion
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Wrong:  Manually converting types after parsing
Right:  Let Pydantic do it — it handles "28"→28, "true"→True, etc.
        Define types correctly in your model, not in post-processing code.
```

# 📌 ENGINEER MINDSET

```
QUESTION 1: "What is the MINIMUM schema needed?"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Every extra field is a new failure point.
Ask: "Does my downstream code actually USE this field?"
If no → remove it from the schema.
Minimal schemas are more reliable schemas.

QUESTION 2: "What is the failure recovery plan?"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Before writing the happy path, design the failure path:
- What happens when JSON is invalid? → Retry with repair
- What happens when schema fails? → Log + escalate
- What happens after max retries? → Fallback or human review
If you can't answer these, you're not production-ready.

QUESTION 3: "Are my enum values truly constrained?"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Never use free-text strings where you need controlled vocabulary.
"status": str        → Could be "Active", "active", "ACTIVE", "currently active"
"status": Literal["active", "inactive"] → Only two valid values
Use Literal or Enum for any field with a fixed set of options.

QUESTION 4: "What would I monitor in production?"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Track:
- JSON parse failure rate (should be <1% with JSON mode)
- Schema validation failure rate (tells you which fields fail most)
- Which parsing strategy wins most often (tells you LLM behavior)
- Retry rate (tells you prompt quality)
- Specific fields that fail validation most (target for prompt improvement)

QUESTION 5: "Can I auto-generate the schema?"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Yes! Pydantic model → JSON schema:
  MyModel.model_json_schema()
This means: define once in Pydantic, use everywhere:
  - In the LLM prompt (as the schema to follow)
  - In the validator (to check the response)
  - In the API docs (as the response schema)
  - In the database (as the document schema)
Single source of truth → no schema drift.
```

# 📌 THE ULTIMATE SUMMARY

## 🔑 The 10 Core Truths of Structured Output

```
TRUTH 1: LLMs speak human language. Your code speaks structured data.
         Structured output is the translation layer between them.

TRUTH 2: Never trust raw LLM output in production code.
         Always parse → validate → type-check.

TRUTH 3: Prompt engineering alone is insufficient.
         Use JSON mode + Pydantic + business validation.
         Defense in depth, not a single checkpoint.

TRUTH 4: Make optional fields Optional.
         Forcing required fields causes hallucination/fabrication.
         null is better than fabricated data.

TRUTH 5: Use Literal/Enum for controlled vocabulary.
         "status": str is a trap. "status": Literal["active","inactive"] is safe.

TRUTH 6: Function calling > JSON prompting for tool use.
         When LLMs need to take actions, function calling is the right tool.

TRUTH 7: Pydantic is your best friend.
         Define once → validate automatically → get helpful error messages.
         Use model_json_schema() to generate prompts automatically.

TRUTH 8: Build a cascade parser, not a single parse attempt.
         LLMs will produce messy output. Be ready for all variants.

TRUTH 9: Validation errors are INFORMATION, not just failures.
         Log which fields fail most → tells you exactly how to improve prompts.

TRUTH 10: Minimum viable schema is maximum reliable schema.
          Every field you add is a new failure point.
          Start minimal. Expand only with justification.
```
