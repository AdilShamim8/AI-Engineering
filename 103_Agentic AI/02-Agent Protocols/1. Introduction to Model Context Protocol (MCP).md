# 🧠 Agent Protocols — Deep Dive Session
## Topic: Introduction to Model Context Protocol (MCP)

> **"Before I explain — what do you think MCP is?"**
> A beginner might guess: *"It is some kind of chat protocol between AI models."*
> **Reality:** It is much bigger than that. It is about giving AI the ability to **connect to the entire world of tools and data** — in one universal, standard way.

Let's build this from absolute zero. 🧱

---

## 📌 SECTION 1 — What Is This?

### Simple English Definition

**MODEL** = A large language model (AI brain)
**CONTEXT** = The data or relevant information given to the AI
**PROTOCOL** = A set of rules or standards

So put them together:

> 🔵 **MCP = A set of standard rules that tell AI models HOW to receive information and USE external tools**

### Official Definition

The Model Context Protocol (MCP) is an open standard for connecting AI assistants to the systems where data lives, including content repositories, business tools, and development environments.

### One-Line Summary
> MCP is like a **universal language** that every AI model and every external tool agrees to speak — so they can talk to each other without anyone building a custom translator every time.

## 📌 SECTION 2 — Why Do We Need It? (The Problem)

### The World Before MCP — A Painful Reality

Imagine you are an AI Engineer. You are building an AI assistant.

Your AI needs to:
- 🔍 Search Google
- 📂 Read files from Google Drive
- 💬 Send Slack messages
- 🐙 Push code to GitHub
- 🗄️ Query a Postgres database

**What did you have to do before MCP?**

Before MCP, developers often had to build custom connectors for each data source or tool, resulting in what Anthropic described as an **"N×M" data integration problem.**

### The N×M Problem — Visualized

```
BEFORE MCP — Chaos 😱

         GPT-4    Claude    Gemini    LLaMA
           |        |         |        |
  Google ──┼────────┼─────────┼────────┤  ← 4 custom connectors
  Slack  ──┼────────┼─────────┼────────┤  ← 4 custom connectors
  GitHub ──┼────────┼─────────┼────────┤  ← 4 custom connectors
  Notion ──┼────────┼─────────┼────────┤  ← 4 custom connectors
  Postgres─┼────────┼─────────┼────────┤  ← 4 custom connectors

  4 AI Models × 5 Tools = 20 CUSTOM CONNECTORS! 😭
  (Each one different. Each one fragile. Each one expensive to build.)
```

```
AFTER MCP — Harmony ✅

         GPT-4    Claude    Gemini    LLaMA
              \      |      /      /
               [ MCP STANDARD ]
              /      |      \      \
  Google    Slack  GitHub  Notion  Postgres

  4 + 5 = 9 connectors only! 🎉
  (All built once. All reusable. All standard.)
```

Instead of every AI tool needing a unique, custom-built connection to every single data source — MCP creates one standard way for them to talk. This turns the **"M × N" problem into a simpler "M + N" setup.**

## 📌 SECTION 3 — First Principles Breakdown

Let's ask: **What are the smallest truths behind MCP?**

### Truth #1 — AI Models Are Isolated By Nature

As AI assistants gain mainstream adoption, the industry has invested heavily in model capabilities. Yet even the most sophisticated models are **constrained by their isolation from data** — trapped behind information silos and legacy systems. Every new data source requires its own custom implementation, making truly connected systems difficult to scale.

> 🔑 **Core Truth:** A powerful LLM that can't access data is like a genius locked in a room with no internet, no books, and no phone.

### Truth #2 — Tools Are Everywhere, But Unorganized

Before MCP:
- OpenAI had its own function-calling system
- LangChain had its own tool format
- Every company wrote their own tool connectors

Earlier stop-gap approaches — such as OpenAI's 2023 "function-calling" API and the ChatGPT plug-in framework — solved similar problems but **required vendor-specific connectors.**

> 🔑 **Core Truth:** Every company reinventing the wheel = massive waste of engineering effort.

### Truth #3 — Standards Create Power

Think of how the internet works:
- HTTP = how browsers and servers talk
- SMTP = how email systems talk
- USB-C = how hardware devices connect

MCP takes some inspiration from the **Language Server Protocol**, which standardizes how to add support for programming languages across a whole ecosystem of development tools. In a similar way, MCP standardizes how to integrate additional context and tools into the ecosystem of AI applications.

> 🔑 **Core Truth:** One standard protocol = every player builds once, and everything works together.

## 📌 SECTION 5 — Step-by-Step Example

Let's walk through a **real scenario** to make this concrete.

### 🎯 Scenario: You ask Claude, "What are the latest pull requests on my GitHub repo?"

#### WITHOUT MCP (Old Way):

```
Step 1: Developer writes custom Python code to call GitHub API
Step 2: Developer writes custom parser for the response
Step 3: Developer writes custom code to format it for Claude
Step 4: Claude gets the data and responds
Step 5: If you switch from Claude → GPT-4, you rewrite Steps 1-4 all over again 😭
```

#### WITH MCP (New Way):

```
Step 1: GitHub builds one MCP Server (following MCP rules)
Step 2: Claude connects to GitHub MCP Server (following MCP rules)
Step 3: You ask: "Show me latest pull requests"
Step 4: Claude → [MCP] → GitHub MCP Server → returns data
Step 5: Claude responds intelligently

✅ Switch to GPT-4? It also speaks MCP → connects to same GitHub MCP Server
✅ No rewriting. No custom code. Just plug and play!
```


The Model Context Protocol enables developers to build **secure, two-way connections** between their data sources and AI-powered tools. The architecture is straightforward: developers can either **expose their data through MCP servers** or **build AI applications (MCP clients)** that connect to these servers.

## 📌 SECTION 6 — The Three Core Building Blocks (MCP Primitives)

MCP standardizes what gets passed back and forth using **three main building blocks**, called "Primitives":

- **Resources:** Structured data that the server gives the AI — think code snippets, parts of a document, or database results — anything that adds factual context. Usually, the application controls when resources are provided.
- **Prompts:** Pre-made instructions or templates that the server can offer — saved prompts for summarizing text or generating code in a specific style. Often, the user chooses when to use these.
- **Tools:** Actual actions the AI can ask the server to perform (usually needing your approval first!).

### Visual Breakdown:
```
MCP SERVER
├── 📦 RESOURCES  → "Here is DATA for you to read"
│     (files, DB results, documents)
│
├── 📝 PROMPTS    → "Here are TEMPLATES for common tasks"
│     (pre-written instructions, workflow guides)
│
└── 🔧 TOOLS      → "Here are ACTIONS you can perform"
      (search web, send email, run code, query DB)
```

## 📌 SECTION 7 — How Does MCP Actually Communicate? (Tech Layer)

Don't worry — we'll keep this simple!

### The Language: JSON-RPC 2.0

These components talk using **JSON-RPC 2.0**, which is just a structured way to send messages back and forth using JSON. This keeps communication clear and consistent, no matter who built the Client or Server.

### Simple JSON Example:

```json
// AI Agent ASKS GitHub MCP Server for tools available:
{
  "jsonrpc": "2.0",
  "method": "tools/list",
  "id": 1
}

// GitHub MCP Server RESPONDS:
{
  "jsonrpc": "2.0",
  "result": {
    "tools": [
      {
        "name": "list_pull_requests",
        "description": "Get all open pull requests",
        "input_schema": { "repo": "string" }
      },
      {
        "name": "create_issue",
        "description": "Create a new GitHub issue",
        "input_schema": { "title": "string", "body": "string" }
      }
    ]
  }
}

// AI Agent CALLS a tool:
{
  "jsonrpc": "2.0",
  "method": "tools/call",
  "params": {
    "name": "list_pull_requests",
    "arguments": { "repo": "my-awesome-project" }
  }
}
```

### The Lifecycle of MCP Communication:

The protocol specifies a lifecycle with **initialization handshake, capability negotiation, and bidirectional communication** between clients (agents) and servers (tool providers).

```
Step 1: HANDSHAKE    → Client says "Hello! I speak MCP version X"
Step 2: NEGOTIATE    → Server says "I have these tools available"
Step 3: DISCOVER     → Agent learns what tools exist
Step 4: CALL         → Agent calls a tool
Step 5: RESPOND      → Server executes and returns result
Step 6: REASON       → LLM uses result to answer your question
```

## 📌 SECTION 8 — Decoupling Models From Tools (The Big Idea)

This is the **most important engineering concept** behind MCP.

### What Does "Decoupling" Mean?

**Coupling** = Two things are directly connected and depend on each other
**Decoupling** = Separating them so they don't need to know about each other

### Before MCP — Tightly Coupled:

```
Claude ←──────── (custom code) ──────── GitHub API
   │                                        │
   └── if GitHub changes API format         │
       Claude integration BREAKS ──────────┘
```

### After MCP — Decoupled:

```
Claude ←── MCP Standard ──► GitHub MCP Server ──► GitHub API

   Claude only needs to know MCP.
   GitHub MCP Server handles GitHub API details.
   If GitHub API changes → only MCP Server updates.
   Claude is untouched! ✅
```

MCP offers a new, standardized format for doing so, centered around the idea of tools being **self-contained, re-usable across systems, and standardized** in how they connect to the agent.

The MCP server interfaces with tools or data sources and exposes their capabilities through a standardized interface. **The agent does not require knowledge of the tool's internal workings** — only the capabilities the server provides.

### Engineer Mindset:
> This is exactly how great software is built:
> **Separate concerns. Define interfaces. Build independently. Connect through standards.**

## 📌 SECTION 10 — MCP Architecture: The Three Roles

```
┌─────────────────────────────────────────────────────────────┐
│                         MCP HOST                            │
│          (Your AI Application: Claude Desktop,              │
│           Cursor IDE, ChatGPT App)                          │
│                                                             │
│   ┌─────────────┐    ┌─────────────┐    ┌─────────────┐   │
│   │ MCP CLIENT  │    │ MCP CLIENT  │    │ MCP CLIENT  │   │
│   │  (talks to  │    │  (talks to  │    │  (talks to  │   │
│   │  Server 1)  │    │  Server 2)  │    │  Server 3)  │   │
│   └──────┬──────┘    └──────┬──────┘    └──────┬──────┘   │
└──────────┼─────────────────┼─────────────────┼────────────┘
           │ MCP Protocol    │ MCP Protocol    │ MCP Protocol
           ▼                 ▼                 ▼
    ┌────────────┐    ┌────────────┐    ┌────────────┐
    │ MCP SERVER │    │ MCP SERVER │    │ MCP SERVER │
    │  (GitHub)  │    │  (Slack)   │    │ (Postgres) │
    └─────┬──────┘    └─────┬──────┘    └─────┬──────┘
          │                 │                  │
    GitHub API         Slack API          DB Queries
```

**The Host** is your AI application (like Claude Desktop or VS Code with Cursor) — it is the manager, overseeing everything. **MCP Clients** live inside the Host — they are dedicated communication lines, where each Client connects to one specific MCP Server. **MCP Servers** are the gateways — a server sits before a specific data source or tool, and knows how to talk to that specific system and expose its capabilities using the MCP rules.

## 📌 SECTION 12 — Failure Modes (Where MCP Breaks)

> **A senior engineer always asks: "Where does this fail?"**

### ❌ Failure Mode 1: Security Vulnerabilities

In April 2025, security researchers released an analysis that concluded there are multiple outstanding security issues with MCP, including **prompt injection and poisoned tools** that allow for data exfiltration through other connected tools.

> **What this means:** A bad actor could create a malicious MCP server that tricks your AI agent into stealing data or doing harmful actions.

### ❌ Failure Mode 2: Authentication Gaps

Security researchers have documented multiple outstanding issues — **Authentication gaps**: the protocol provides minimal guidance on authentication, and many implementations default to **no auth at all.**

> **What this means:** Without proper authentication, anyone could potentially call your MCP server and run your tools.

### ❌ Failure Mode 3: Context Window Bloat

The MCP standardizes tool interfaces but does not specify how much metadata and output must be exposed to the model. In practice, existing implementations serialize full schemas and tool outputs in the context window. This means that **tool metadata, user input, intermediate reasoning, and tool outputs all compete for the same space** — referred to as a "context-coupled" execution model.

> **What this means:** Too many tools connected = context window gets full = AI performs worse.

### ❌ Failure Mode 4: Not Always Necessary

For less complex and more simple AI projects with clearly defined context — perhaps local-only or single-language deployment — an MCP server will likely be **overkill**; you could just use a direct API integration.

### ❌ Failure Mode 5: Still Doesn't Fully Solve N×M

If you have N agents and M tools, you potentially need N×M integrations. **MCP helps standardize the interface, but it doesn't eliminate the combinatorial problem** of connecting many agents to many services.

## 📌 SECTION 13 — Interview Questions & Answers

### 🎯 Interview Questions

---

**Q1: What is MCP and why was it created?**

> **Strong Answer:**
> MCP stands for Model Context Protocol. It is an open standard created by Anthropic to solve the **N×M integration problem** in AI systems. Before MCP, connecting M AI models to N tools required M×N custom integrations — each fragile, expensive, and not reusable. MCP defines one standard interface that any AI model and any tool can implement once, reducing M×N down to M+N. It decouples AI models from the tools they use, so they don't need to know each other's internals — only the MCP standard.

---

**Q2: What are the three components in MCP architecture?**

> **Strong Answer:**
> MCP has three roles:
> - **Host:** The AI application (like Claude Desktop or a VS Code extension) that the user interacts with
> - **Client:** Lives inside the Host; speaks MCP protocol; maintains one connection per server
> - **Server:** A lightweight program that wraps an external tool or data source (GitHub, Slack, Postgres) and exposes it through standardized MCP interfaces

---

**Q3: What are the three primitives of MCP?**

> **Strong Answer:**
> MCP servers expose three types of capabilities:
> - **Resources:** Data the AI can read (files, DB records, documents)
> - **Prompts:** Pre-built instruction templates for specific tasks
> - **Tools:** Actions the AI can execute (run queries, send messages, create issues)

---

**Q4: How is MCP different from OpenAI's function calling?**

> **Strong Answer:**
> Function calling is OpenAI-specific and requires vendor-specific integration — it works only inside OpenAI's ecosystem. MCP is model-agnostic and platform-neutral. Any model (GPT-4, Claude, Gemini, LLaMA) can speak MCP. Any tool built as an MCP server works with all of them. MCP is the open standard; function calling was a proprietary stop-gap solution.

---

**Q5: What are the security risks of MCP?**

> **Strong Answer:**
> Three key risks:
> 1. **Prompt Injection** — A malicious MCP server description could inject instructions that hijack the AI's behavior
> 2. **Tool Poisoning** — A compromised server could exfiltrate data or perform harmful actions
> 3. **Authentication Gaps** — Many MCP implementations default to no authentication, making servers open to unauthorized access

## 📌 SECTION 15 — Practical ML/AI Engineering Usage

### Where MCP Is Used Today:

Anthropic shares pre-built MCP servers for popular enterprise systems like **Google Drive, Slack, GitHub, Git, Postgres, and Puppeteer**.

**Code development and review:** MCP can power systems that fetch PR details from GitHub, analyze code changes, generate review summaries, and save reviews to platforms like Notion.

MCP enables AI agents to access real-time data and invoke external capabilities — such as **querying inventory databases, retrieving supplier catalogues, or submitting purchase orders** — in a modular and interoperable manner, without requiring custom integration code for each system connection.

## 📌 SECTION 16 — Engineer Mindset

### What a Real AI Engineer Thinks About MCP:

```
✅ THINK ABOUT:
   • Do I really need MCP or will a simple API call work?
   • How many tools does my agent actually need?
   • Am I handling authentication properly in my MCP server?
   • Is my context window getting bloated with too many tool descriptions?
   • Am I validating tool inputs and outputs?
```

It's not magic. It's **plumbing.** But great plumbing lets you build great buildings.
