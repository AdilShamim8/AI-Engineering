# 🧠 Other Relevant Protocols & Standards — Deep Dive Session
## Topic: A2A (Agent-to-Agent) Protocol

---

> **"Before I explain — what do you think A2A means in the context of AI agents?"**
>
> A beginner might guess: *"It's just two AI agents talking to each other somehow. Maybe using MCP?"*
>
> **Reality:** A2A is a completely different class of problem. MCP solved how agents talk to **tools**. A2A solves how agents talk to **other agents** — across different companies, different frameworks, different countries — as equals, as peers, as autonomous collaborators who each have their own intelligence, their own task state, and their own life cycle. This is the infrastructure layer that makes **true multi-agent systems** at enterprise scale finally possible.

Let's build this from absolute zero. 🧱

## 📌 SECTION 1 — What Is A2A?

### Simple English Definition

> **AGENT** = An autonomous AI system with its own brain, tools, memory, and goals
> **TO AGENT** = Peer-to-peer — two equals communicating directly
> **PROTOCOL** = A universal set of rules that both sides agree to follow

Put it together:

> 🔵 **A2A (Agent-to-Agent) Protocol = An open standard that defines HOW one AI agent can discover another agent, delegate tasks to it, track the work in progress, and receive structured results — regardless of which company built either agent, which framework runs them, or which AI model powers them**

### The One-Line Summary:

A2A defines a universal "language" for agents to talk to each other, just as HTTP does for computers.

### The Official History:

Google announced the Agent2Agent (A2A) protocol on April 9, 2025, at Google Cloud Next. It was developed by Google and launched in April 2025 with support from over 50 technology partners, including Atlassian, Salesforce, SAP, Workday, and ServiceNow.

The specification was released as open source under the Apache 2.0 license and was donated to the Linux Foundation in June 2025 for neutral governance.

By 2026: On April 9, 2026, the Linux Foundation announced A2A had crossed 150+ production organisations, 22,000+ GitHub stars, and SDKs in five production languages (Python, JavaScript, Java, Go, .NET).

## 📌 SECTION 2 — Why Do We Need A2A? (The Real Problem)

### The World Before A2A — Pure Integration Chaos

Before A2A, enterprise AI teams building multi-agent systems faced a fragmentation problem: agents from one vendor could not reliably hand off work to agents from another vendor using a shared, open standard. Teams could write custom API integrations between specific agents, but every new agent pair required a new bespoke connector.

Each framework had its own internal messaging format and task model, and there was no common discovery mechanism. A Salesforce agent could not delegate a sub-task to a ServiceNow agent without custom glue code; a Google Vertex agent could not coordinate with an AWS Bedrock agent without a hand-rolled bridge.

```
BEFORE A2A — The N×M Agent Integration Problem

           LangGraph    CrewAI    AutoGen    Vertex AI
           Agent        Agent     Agent      Agent
              │            │         │          │
  Claude ─────┼────────────┼─────────┼──────────┤ ← 4 custom connectors
  GPT-4  ─────┼────────────┼─────────┼──────────┤ ← 4 custom connectors
  Gemini ─────┼────────────┼─────────┼──────────┤ ← 4 custom connectors
  AWS    ─────┼────────────┼─────────┼──────────┤ ← 4 custom connectors

  4 agent types × 4 frameworks = 16 custom integrations! 😭
  Each one fragile. Each one expensive. Each one unique.

AFTER A2A — The N+M Solution

LangGraph  CrewAI  AutoGen  Vertex AI
    \         |       |       /
          [ A2A STANDARD ]
    /         |       |       \
Claude     GPT-4  Gemini    AWS

4 + 4 = 8 connectors only — all standard! 🎉
```

### The Research Evidence of the Problem:

Research analyzing multi-agent LLM system failures found step repetitions account for 15.7% of failures and failure to recognize task completion accounts for 12.4%, both attributed to ad-hoc coordination.

> 🔑 **Key Insight:** Almost 1 in 3 multi-agent failures happen because agents don't have a standard way to coordinate. A2A directly solves this.

## 📌 SECTION 3 — Real World Analogies

### 🌐 Analogy 1: HTTP for the Web

A2A aims to do for heterogeneous AI agents what protocols like HTTP did for heterogeneous web servers and clients.

```
WEB WORLD:                     AGENT WORLD:
Browser (Chrome)               AI Agent (LangGraph)
    │                               │
    │ HTTP Protocol                 │ A2A Protocol
    ▼                               ▼
Web Server (Apache/Nginx)      Remote AI Agent (CrewAI)

Chrome doesn't need to know     LangGraph agent doesn't need
how Apache works internally.    to know how CrewAI works.
They just both speak HTTP.      They just both speak A2A.
```

The analogy most people reach for is HTTP. HTTP does not care whether your backend is Rails, Django, or Go — it just defines the shape of requests and responses.

### 🏢 Analogy 2: The Corporate Staffing Agency

Imagine a large company that needs specialized work done:

```
CEO's AI Agent (Orchestrator)
│ "We need market analysis on 5 countries"
│
├──► Contracts A specialized Research Agent  ← A2A delegation
│    (Built by different company, runs on Azure)
│    │
│    └── Research Agent uses its own internal MCP tools
│        (web search, database, document reader)
│        This is INVISIBLE to the CEO's agent
│
├──► Contracts A specialized Translation Agent ← A2A delegation
│    (Built by SAP, runs on their infrastructure)
│
└──► Receives RESULTS from both agents
     (Structured artifacts — doesn't care how work was done)
```

> 🔑 **Key Insight:** A2A is an open specification that defines how autonomous AI agents from different vendors and frameworks can discover each other, delegate tasks, and coordinate work. Neither agent needs to expose its internal logic, memory, or implementation details.

### 🔌 Analogy 3: MCP is USB-C, A2A is the Internet

```
MCP = USB-C port
   One agent connects to many tools
   Vertical relationship (agent → tool)
   Tool has no intelligence of its own
   Tool just executes and returns

A2A = The Internet Protocol
   Agent connects to other agents (peers)
   Horizontal relationship (agent ↔ agent)
   Remote agent has its OWN intelligence
   Remote agent decides HOW to do the work
```

The A2A/MCP distinction is crisp: MCP is the "USB-C for tool connectivity" (vertical, agent → tool), while A2A is "HTTP for agent collaboration" (horizontal, agent → agent).

## 📌 SECTION 4 — A2A vs MCP: The Fundamental Difference

This is the MOST IMPORTANT concept to understand before going deeper:

```
═══════════════════════════════════════════════════════════════
         MCP                    vs              A2A
═══════════════════════════════════════════════════════════════

RELATIONSHIP:
  Agent → Tool                        Agent → Agent
  (Vertical: one has power)           (Horizontal: peers)

WHO IS ON THE OTHER SIDE?
  Passive tool                        Autonomous AI agent
  No intelligence                     Has its own LLM brain
  Does exactly what asked             May interpret & adapt
  Can't push back                     Can ask for clarification
  Can't refuse                        Can negotiate, fail gracefully

TASK MODEL:
  Request → Response (immediate)      Submit task → Track lifecycle
  Synchronous (mostly)                Async (long-running work)
  No state between calls              Stateful (tracked by task ID)
  Simple function call                Multi-turn conversation

WHAT IT EXPOSES:
  Tool schemas (what actions to call) Agent Card (what agent can do)
  Input/output contracts              Skills, modalities, auth methods

WHEN TO USE:
  Agent needs to use a tool/API       Agent needs help from another agent
  Simple action + result              Complex, delegated, multi-step work
  Milliseconds to execute            Seconds/minutes to execute

ANALOGY:
  Like calling a function             Like hiring a contractor
  Function does exactly what asked    Contractor uses own judgment
  You specify HOW                     You specify WHAT, they decide HOW
```

Each protocol effectively addresses a different layer of interoperability: MCP standardizes access to capabilities (how agents interact with the outside world), while A2A enables collaborative workflows (how AI agents work together).

### The Simple Rule:

If you want a simple rule for 2025 agent architecture, use this: MCP connects agents to tools. A2A connects agents to other agents.

## 📌 SECTION 5 — The Four Core Building Blocks of A2A

A2A is an agent communication protocol proposed by Google for enterprise-scale agent ecosystems. The following components constitute the fundamental elements of A2A: **Agent Card**, **Task**, **Message**, and **Artifact**.

```
A2A CORE COMPONENTS:
├── 🪪 Agent Card    → "Who am I? What can I do?"
├── 📋 Task          → "Here is a unit of work with a lifecycle"
├── 💬 Message       → "Let's communicate during the work"
└── 📦 Artifact      → "Here is the finished deliverable"
```

---

### 🪪 Component 1: The Agent Card

> **The Agent Card = An agent's professional business card + resume + capability catalog — all in one machine-readable JSON document**

**Agent Card** denotes a publicly accessible JSON document, typically hosted at a public URL, detailing the agent's operational scope, its specific functions, the designated endpoint URL, methods for authentication, and other relevant metadata.

Agent Cards serve as a discovery mechanism through which each agent publishes a machine-readable description of its capabilities, input and output modalities, and authentication requirements, analogous to a service descriptor in microservice architectures.

#### Where Is It Hosted?

Any A2A server publishes an AgentCard at `/.well-known/agent-card.json` declaring its skills, supported MIME types, transport bindings, and security schemes.

So if an agent is hosted at `https://research-agent.company.com`, its Agent Card lives at:
`https://research-agent.company.com/.well-known/agent-card.json`

This is like your resume always being at the same, predictable URL — anyone can find it!

#### A Complete Agent Card — Fully Annotated:

```json
// /.well-known/agent-card.json

{
  // ══════════════════════════════════════════
  // IDENTITY: Who am I?
  // ══════════════════════════════════════════
  "name": "Market Research Agent",
  //  ↑ Human-readable name

  "description": "Expert AI agent specializing in competitive market analysis,
                  industry research, and strategic insights. Produces structured
                  reports with citations for enterprise decision-making.",
  //  ↑ What this agent does — read by orchestrating agents to decide
  //  ↑ if THIS is the right agent for the job

  "version": "2.1.0",

  "url": "https://research-agent.company.com",
  //  ↑ Where to send A2A requests

  // ══════════════════════════════════════════
  // CAPABILITIES: What can I do?
  // ══════════════════════════════════════════
  "skills": [
    {
      "id": "competitive_analysis",
      "name": "Competitive Analysis",
      "description": "Analyze competitors in a given market segment",
      "inputModes":  ["text"],
      //  ↑ I accept text inputs
      "outputModes": ["text", "data"],
      //  ↑ I return both text reports and structured data
      "tags": ["research", "competitive-intelligence", "market-analysis"],
      "examples": [
        "Analyze the top 5 CRM software vendors in the SMB market"
      ]
    },
    {
      "id": "industry_report",
      "name": "Industry Report Generator",
      "description": "Generate comprehensive industry reports with trend analysis",
      "inputModes":  ["text"],
      "outputModes": ["text", "file"],
      //  ↑ Can return PDF files as output
      "tags": ["research", "reporting", "trends"]
    }
  ],

  // ══════════════════════════════════════════
  // CAPABILITIES FLAGS: What can this agent do?
  // ══════════════════════════════════════════
  "capabilities": {
    "streaming": true,
    //  ↑ I can stream progress updates (SSE)
    //  ↑ Long-running tasks send live status updates

    "pushNotifications": true,
    //  ↑ I can send webhook callbacks when done
    //  ↑ You don't need to poll me

    "stateTransitionHistory": true

    //  ↑ You can audit exactly what happened and when
  },

  // ══════════════════════════════════════════
  // SUPPORTED MODALITIES: What types of data?
  // ══════════════════════════════════════════
  "defaultInputModes":  ["text/plain", "application/json"],
  "defaultOutputModes": ["text/plain", "application/json", "application/pdf"],

  // ══════════════════════════════════════════
  // AUTHENTICATION: How do I authenticate callers?
  // ══════════════════════════════════════════
  "authentication": {
    "schemes": ["Bearer"]
    //  ↑ Requires Bearer token (OAuth 2.0 / JWT)
    //  ↑ No anonymous access
  },

  // ══════════════════════════════════════════
  // PROVIDER: Who built this agent?
  // ══════════════════════════════════════════
  "provider": {
    "organization": "Research Corp",

```

### 📋 Component 2: The Task

> **The Task = A structured, uniquely identified unit of work that has a full lifecycle — it can be submitted, tracked, paused, resumed, completed, or canceled**

Tasks represent units of work with a defined lifecycle, progressing through states such as submitted, working, input-required, completed, canceled, and failed, and carrying structured payloads that can include text, files, and structured data.

#### The Task State Machine:

Agents communicate via JSON-RPC 2.0 using an eight-state Task lifecycle: submitted, working, input_required, auth_required, completed, failed, canceled, rejected.

```
TASK LIFECYCLE STATE MACHINE:

                    ┌─────────────────┐
                    │    SUBMITTED    │  ← Client sends the task
                    └────────┬────────┘
                             │ Agent acknowledges receipt
                             ▼
                    ┌─────────────────┐
                    │    WORKING      │  ← Agent is actively processing
                    └────────┬────────┘
                             │
            ┌────────────────┼──────────────────────┐
            │                │                      │
            ▼                ▼                      ▼
  ┌──────────────────┐  ┌──────────────┐  ┌────────────────┐
  │  INPUT_REQUIRED  │  │AUTH_REQUIRED │  │    FAILED      │
  │ "I need more     │  │"Need your    │  │ "Something     │
  │  info from you"  │  │ permission"  │  │  went wrong"   │
  └────────┬─────────┘  └──────┬───────┘  └────────────────┘
           │ Client provides   │ Client
           │ more info         │ authenticates
           ▼                   ▼
  ┌─────────────────────────────────┐
  │            WORKING              │  ← Back to processing
  └────────────────┬────────────────┘
                   │
       ┌───────────┴──────────┐
       ▼                      ▼
  ┌──────────┐          ┌──────────┐
  │COMPLETED │          │CANCELED  │
  │ "Done!   │          │ "You     │
  │  Here's  │          │  stopped │
  │  result" │          │  me"     │
  └──────────┘          └──────────┘
```

#### What Each State Means — Real World:

```
STATE: submitted
→ Client: "Research agent, please analyze the EV market"
→ Agent: "Got it! Task ID: task_abc123. I'll start now."
→ Nothing is done yet. Just acknowledged.

STATE: working
→ Agent is actively running: searching web, reading reports,
  analyzing data, synthesizing insights
→ Client can subscribe to streaming updates
→ "Progress: Found 15 relevant reports... Analyzing..."

STATE: input_required
→ Agent: "I need clarification: Which geographic market?
  North America only? Or global? Also, what time period?"
→ Work is PAUSED. Agent is waiting for human input.
→ Client must send more information to continue.

STATE: auth_required
→ Agent: "I need access to your internal sales database
  to complete this analysis. Please authorize access."
→ Agent needs more permissions before proceeding.

STATE: completed
→ Agent: "Analysis complete! Here are the results:"
→ Artifact attached: full competitive analysis report
→ Task is done. Final state. No more changes.

STATE: failed
→ Agent: "I couldn't complete the analysis because the
  primary data source returned an error consistently."
→ Contains error details so caller can retry or adapt.

STATE: canceled
→ Client said "stop" during processing.
→ Agent stopped gracefully. Partial work discarded.
```

#### The Task Object Structure:

```json
{
  "id": "task_abc123",
  //  ↑ Unique identifier — used to track THIS specific task forever

  "status": {
    "state": "working",
    //  ↑ Current lifecycle state

    "message": {
      "role": "agent",
      "parts": [{"type": "text",
                 "text": "Analyzing 15 market reports... 45% complete"}]
    },
    //  ↑ What the agent wants to communicate right now

    "timestamp": "2025-04-09T10:30:00Z"
    //  ↑ When this state was entered
  },

  "artifacts": [],
  //  ↑ Empty while working.
  //  ↑ Filled with results when completed.

  "metadata": {
    "created_at": "2025-04-09T10:00:00Z",
    "updated_at": "2025-04-09T10:30:00Z"
  }
}
```

### 💬 Component 3: The Message

**Message** refers to a communication object exchanged among entities, usually attributed with either a "user" or "agent" role.

Agents can exchange contextual messages, intermediate responses, artifacts, and user instructions to keep alignment during task execution.

```json
// Message from client to agent (sending task):
{
  "role": "user",
  "parts": [
    {
      "type": "text",
      "text": "Please analyze the competitive landscape for EV batteries in Europe. Focus on 2023-2024."
    }
  ]
}

// Message from agent to client (asking for input):
{
  "role": "agent",
  "parts": [
    {
      "type": "text",
      "text": "I need clarification: Should I focus on cell manufacturers only, or also include system integrators?"
    }
  ]
}

// Message with multiple content types (multimodal):
{
  "role": "agent",
  "parts": [
    {
      "type": "text",
      "text": "Here is the preliminary market data:"
    },
    {
      "type": "data",
      "data": {
        "market_size_bn": 45.2,
        "growth_rate_pct": 28.5,
        "top_players": ["CATL", "LG Energy", "Panasonic"]
      }
    }
  ]
}
```

### 📦 Component 4: The Artifact

> **The Artifact = The finished deliverable that the remote agent produces — the actual RESULT of the completed work, packaged in a structured format**

```
ARTIFACT TYPES:

TEXT ARTIFACT → The result is a text document (report, summary)
DATA ARTIFACT → The result is structured data (JSON, CSV)
FILE ARTIFACT → The result is a file (PDF report, Excel spreadsheet, image)

Examples:
  "Here is your competitive analysis report" → TEXT ARTIFACT
  "Here are the market statistics"           → DATA ARTIFACT
  "Here is the PDF report you can share"     → FILE ARTIFACT
```

```json
// ARTIFACT — attached to completed task
{
  "id": "artifact_001",
  "name": "EV Battery Market Analysis 2024",
  "description": "Complete competitive analysis of European EV battery market",

  "parts": [
    // Part 1: Text summary
    {
      "type": "text",
      "text": "## Executive Summary\n\nThe European EV battery market..."
    },

    // Part 2: Structured data
    {
      "type": "data",
      "data": {
        "market_size_2024_bn_usd": 45.2,
        "cagr_2024_2028_pct": 28.5,
        "top_competitors": [
          {"name": "CATL", "market_share_pct": 34.2},
          {"name": "LG Energy Solution", "market_share_pct": 21.1}
        ]
      }
    },

    // Part 3: File (PDF)
    {
      "type": "file",
      "file": {
        "name": "ev_battery_analysis.pdf",
        "mimeType": "application/pdf",
        "uri": "https://research-agent.company.com/artifacts/ev_analysis.pdf"
      }
    }
  ],

  "index": 0,      // Order in multi-artifact responses
  "lastChunk": true // Is this the final part?
}
```

## 📌 SECTION 6 — How A2A Communication Works End-to-End

Let's walk through a complete real-world A2A interaction step by step:

### The Scenario:
> An **HR Orchestrator Agent** needs to schedule a technical interview and asks a specialized **Calendar Agent** to do the scheduling.

```
═══════════════════════════════════════════════════════════════
COMPLETE A2A INTERACTION — HR Orchestrator + Calendar Agent
═══════════════════════════════════════════════════════════════

PHASE 1: DISCOVERY
──────────────────

HR Agent: "I need a calendar agent"
          → Looks up /.well-known/agent-card.json on calendar-agent.company.com
          ← Receives Agent Card: "I can schedule meetings, check availability, create events"
          → HR Agent decides: "Yes, this agent can help with scheduling"

PHASE 2: TASK SUBMISSION
─────────────────────────

HR Agent sends A2A request:
{
  "jsonrpc": "2.0",
  "method": "tasks/send",
  "id": 1,
  "params": {
    "id": "task_hr_001",
    "message": {
      "role": "user",
      "parts": [{
        "type": "text",
        "text": "Schedule a 1-hour technical interview for
                 John Smith (john@candidate.com) with
                 our engineering team (eng@company.com).
                 Needs to happen this week, preferably Tuesday
                 or Wednesday 2-5pm PST."
      }]
    }
  }
}

PHASE 3: AGENT ACKNOWLEDGMENT
──────────────────────────────

Calendar Agent responds immediately:
{
  "result": {
    "id": "task_hr_001",
    "status": {
      "state": "submitted",
      //  ↑ Immediately acknowledged
      "timestamp": "2025-04-09T10:00:00Z"
    }
  }
}

PHASE 4: STREAMING PROGRESS (SSE)
───────────────────────────────────

HR Agent subscribed to updates. Calendar Agent streams:

Update 1 (T+2s):
event: task_status_update
data: {"id":"task_hr_001", "status":{"state":"working",
       "message":{"role":"agent","parts":[{"type":"text",
       "text":"Checking engineering team calendar availability..."}]}}}

Update 2 (T+8s):
event: task_status_update
data: {"id":"task_hr_001", "status":{"state":"working",
       "message":{"role":"agent","parts":[{"type":"text",
       "text":"Found 3 available slots. Sending invite to candidate..."}]}}}

PHASE 5: INPUT REQUIRED (agent asks for more info)
────────────────────────────────────────────────────

Update 3 (T+12s):
event: task_status_update
data: {
  "id": "task_hr_001",
  "status": {
    "state": "input_required",
    "message": {
      "role": "agent",
      "parts": [{"type": "text",
                 "text": "I found 2 slots: Tuesday 3pm or Wednesday 4pm.
                          Which do you prefer? Or should I auto-select the earliest?"}]
    }
  }
}

HR Agent (or human) responds:
{
  "method": "tasks/send",
  "params": {
    "id": "task_hr_001",
    "message": {
      "role": "user",
      "parts": [{"type":"text", "text":"Auto-select Tuesday 3pm."}]
    }
  }
}

PHASE 6: COMPLETION WITH ARTIFACT
───────────────────────────────────

Final update (T+18s):
{
  "id": "task_hr_001",
  "status": {
    "state": "completed",
    "timestamp": "2025-04-09T10:00:18Z"
  },
  "artifacts": [
    {
      "name": "Interview Scheduled",
      "parts": [
        {"type": "text", "text": "Technical interview scheduled successfully!"},
        {
          "type": "data",
          "data": {
            "event_id": "cal_789xyz",
            "date": "2025-04-15",
            "time": "15:00 PST",
            "duration_mins": 60,
            "attendees": ["john@candidate.com", "eng@company.com"],
            "meeting_link": "https://meet.company.com/interview-001",
            "calendar_link": "https://calendar.company.com/event/cal_789xyz"
          }
        }
      ]
    }
  ]
}

HR Orchestrator receives artifact:
→ Knows interview is scheduled
→ Can now continue its workflow: send prep materials, notify recruiter, etc.
→ Used Calendar Agent's result without ever knowing how Calendar Agent works internally!
```

An A2A "HR Agent" receives a request to schedule a technical interview and delegates the scheduling task via A2A to a specialized "Calendar Agent." The Calendar Agent receives the A2A message, understands the intent, and uses MCP locally to call its calendar tool to query open slots. Once it has a slot, the Calendar Agent finalizes the booking and transmits the completed artifact back to the HR Agent over the A2A channel.

## 📌 SECTION 7 — The Technical Stack of A2A

### What Technologies Does A2A Use?

A2A is built on existing common standards, including Server-Sent Events (SSE), HTTP(S), and JSON-RPC, and OAuth 2.0 for mutual agent authentication and access to resources without sharing credentials; it also uses JSON Web Tokens (JWTs) for compacting and signing tokens.

```
A2A TECHNOLOGY STACK:

TRANSPORT LAYER:
  HTTP/HTTPS
  └── Standard web protocol everyone knows
  └── No proprietary transport needed

MESSAGE FORMAT:
  JSON-RPC 2.0
  └── Same as MCP! Structured request/response
  └── Method names: tasks/send, tasks/get, tasks/cancel

STREAMING:
  Server-Sent Events (SSE)
  └── Server pushes updates to client
  └── Perfect for long-running tasks
  └── One-way stream (server → client)

AUTHENTICATION:
  OAuth 2.0 + JWT
  └── Industry standard for enterprise
  └── Mutual agent authentication
  └── No credential sharing between agents
```

### The Three Layers of A2A Architecture:

The specification is organized into three layers: Layer 1 (Data Model): Core objects including AgentCard, AgentSkill, Task, Message, Part, Artifact, and Extension, specified in Protocol Buffers and published as JSON Schema 2020-12.

```
A2A THREE-LAYER ARCHITECTURE:

LAYER 1: DATA MODEL
├── AgentCard (who/what I am)
├── AgentSkill (specific capability)
├── Task (unit of work + lifecycle)
├── Message (communication)
├── Part (content piece: text/data/file)
├── Artifact (finished deliverable)
└── Extension (plugins like AP2 payments)

LAYER 2: OPERATIONS
├── tasks/send        → Submit new task / send follow-up message
├── tasks/get         → Check task status
├── tasks/cancel      → Cancel in-progress task
├── tasks/sendSubscribe → Submit + subscribe to streaming updates
└── tasks/pushNotification/set → Register webhook for callbacks

LAYER 3: TRANSPORT BINDINGS
├── HTTP + JSON-RPC 2.0  → Standard web (synchronous)
├── HTTP + SSE           → Streaming updates (async)
└── Webhooks             → Push notifications (callback)
```

### The A2A Endpoints:

```
ENDPOINT 1: /.well-known/agent-card.json
  Method: GET
  Purpose: Discover agent capabilities
  Who calls it: Any agent wanting to discover capabilities
  Response: Agent Card JSON

ENDPOINT 2: /                (root A2A endpoint, or configured URL)
  Method: POST
  Purpose: Submit tasks, get status, cancel, send messages
  Who calls it: Client agents (orchestrators)
  Body: JSON-RPC request

ENDPOINT 3: SSE stream (on task submission)
```

## 📌 SECTION 10 — The Five Core Requirements of A2A

Core requirements for A2A communication:
1. **Discoverability**: Agents must be able to find other agents and understand their capabilities.
2. **Interoperability**: Agents built by different teams or vendors must speak a common protocol.
3. **Asynchrony**: Long-running tasks must not block the caller; results arrive via callbacks or polling.
4. **Security**: Agents must authenticate each other and enforce authorization boundaries.
5. **Observability**: Every message exchange must be traceable for debugging and auditing.

```
REQUIREMENT 1: DISCOVERABILITY
   Problem: How does my agent find other agents?
   Solution: Agent Card at /.well-known/agent-card.json
   Analogy: DNS for people (find anyone by domain → find agent card)

REQUIREMENT 2: INTEROPERABILITY
   Problem: LangGraph agent needs to talk to CrewAI agent
   Solution: Both implement A2A — common JSON-RPC format
   Analogy: HTTP made all web frameworks interoperable

REQUIREMENT 3: ASYNCHRONY
   Problem: Research task takes 10 minutes. Client can't wait!
   Solution: Submit task → get task_id → subscribe to SSE → receive artifact
   Analogy: Restaurant order system (take order → ticket number → food arrives)

REQUIREMENT 4: SECURITY
   Problem: How do agents know they're talking to trusted agents?
   Solution: OAuth 2.0 + JWT — industry-standard mutual authentication
   Analogy: Two companies exchanging signed contracts

REQUIREMENT 5: OBSERVABILITY
   Problem: Agent delegated work to 5 sub-agents. Something failed. Where?
   Solution: Every state transition logged with timestamps + task IDs
   Analogy: Package tracking — see exactly where delivery is at all times
```

```python
from enum import Enum

app = FastAPI()

# ─────────────────────────────────────────

    "name": "Research Specialist Agent",
    "description": "Expert AI agent for deep market research and competitive analysis. Produces structured reports with citations.",
    "version": "1.0.0",

    "defaultOutputModes": ["text/plain", "application/json"],

        "schemes": ["Bearer"]
    }
}

tasks = {}

# STEP 2: Expose the Agent Card endpoint
# ─────────────────────────────────────────
@app.get("/.well-known/agent-card.json")
async def get_agent_card():
    """
    Any agent can discover this agent's capabilities by calling this URL.
    Standard A2A discovery endpoint.
    """
    return JSONResponse(AGENT_CARD)


# ─────────────────────────────────────────
# STEP 3: Handle A2A JSON-RPC requests
# ─────────────────────────────────────────
@app.post("/")
async def handle_a2a_request(request: Request):
    """
    Main A2A endpoint. Handles all JSON-RPC 2.0 method calls.
    """
    body = await request.json()
    method = body.get("method")
    params = body.get("params", {})
    request_id = body.get("id")

    # ─────────────────────────────────
    # METHOD: tasks/send
    # Submit a new task or send a follow-up message
    # ─────────────────────────────────
    if method == "tasks/send":
        task_id = params.get("id") or str(uuid.uuid4())
        message = params.get("message", {})

        if task_id not in tasks:
            # New task
            tasks[task_id] = {
                "id": task_id,
                "status": {
                    "state": "submitted",
                    "timestamp": datetime.utcnow().isoformat()
                },
                "messages": [message],
                "artifacts": []
            }

            # Start processing asynchronously
            asyncio.create_task(process_task(task_id))

        else:
            # Follow-up message to existing task (e.g., after input_required)
            tasks[task_id]["messages"].append(message)
            tasks[task_id]["status"]["state"] = "working"
            # Resume processing
            asyncio.create_task(resume_task(task_id))

        return JSONResponse({
            "jsonrpc": "2.0",
            "id": request_id,
            "result": tasks[task_id]
        })

    # ─────────────────────────────────
    # METHOD: tasks/get
    # Get current status of a task
    # ─────────────────────────────────
    elif method == "tasks/get":
        task_id = params.get("id")
        if task_id not in tasks:
            raise HTTPException(status_code=404, detail="Task not found")

        return JSONResponse({
            "jsonrpc": "2.0",
            "id": request_id,
            "result": tasks[task_id]
        })

    # ─────────────────────────────────
    # METHOD: tasks/cancel
    # Cancel an in-progress task
    # ─────────────────────────────────
    elif method == "tasks/cancel":
        task_id = params.get("id")
        if task_id in tasks:
            tasks[task_id]["status"]["state"] = "canceled"
            tasks[task_id]["status"]["timestamp"] = datetime.utcnow().isoformat()

        return JSONResponse({
            "jsonrpc": "2.0",
            "id": request_id,
            "result": tasks.get(task_id, {})
        })


# ─────────────────────────────────────────
# STEP 4: SSE Streaming endpoint
# ─────────────────────────────────────────
@app.get("/stream/{task_id}")
async def stream_task_updates(task_id: str):
    """
    Client subscribes to this endpoint to receive
    real-time Server-Sent Events for task progress.
    """
    async def event_generator():
        """Generate SSE events for task state changes"""
        last_state = None

        while True:
            task = tasks.get(task_id)
            if not task:
                yield f"event: error\ndata: Task not found\n\n"
                break

            current_state = task["status"]["state"]

            # Send update when state changes
            if current_state != last_state:
                event_data = json.dumps({
                    "id": task_id,
                    "status": task["status"],
                    "artifacts": task.get("artifacts", [])
                })
                yield f"event: task_status_update\ndata: {event_data}\n\n"
                last_state = current_state

                # Stop streaming when task reaches terminal state
                if current_state in ["completed", "failed", "canceled"]:
                    break

            await asyncio.sleep(0.5)  # Poll every 500ms

    return StreamingResponse(
        event_generator(),
        media_type="text/event-stream",
        headers={"Cache-Control": "no-cache", "Connection": "keep-alive"}
    )

# STEP 6: A2A CLIENT — Calling Another Agent

import httpx

class A2AClient:
    """
    Client for calling remote A2A agents.
    Use this in your orchestrator agent.
    """

    def __init__(self, agent_url: str, auth_token: str):
        self.agent_url = agent_url
        self.auth_token = auth_token
        self.headers = {
            "Authorization": f"Bearer {auth_token}",
            "Content-Type": "application/json"
        }

    async def discover_capabilities(self) -> dict:
        """Read remote agent's Agent Card"""
        async with httpx.AsyncClient() as client:
            response = await client.get(
                f"{self.agent_url}/.well-known/agent-card.json"
            )
            return response.json()

    async def send_task(self, task_message: str) -> dict:
        """Submit a task to the remote agent"""
        task_id = str(uuid.uuid4())

        async with httpx.AsyncClient() as client:
            response = await client.post(
                self.agent_url,
                headers=self.headers,
                json={
                    "jsonrpc": "2.0",
                    "method": "tasks/send",
                    "id": 1,
                    "params": {
                        "id": task_id,
                        "message": {
                            "role": "user",
                            "parts": [{"type": "text", "text": task_message}]
                        }
                    }
                }
            )
            return response.json()["result"]

    async def get_task_status(self, task_id: str) -> dict:
        """Poll for task status"""
        async with httpx.AsyncClient() as client:
            response = await client.post(
                self.agent_url,
                headers=self.headers,
                json={
                    "jsonrpc": "2.0",
                    "method": "tasks/get",
                    "id": 2,
                    "params": {"id": task_id}
                }
            )
            return response.json()["result"]

    async def wait_for_completion(self, task_id: str) -> dict:
        """
        Poll until task reaches terminal state.
        In production: use SSE streaming instead of polling!
        """
        terminal_states = {"completed", "failed", "canceled", "rejected"}

        while True:
            task = await self.get_task_status(task_id)
            state = task["status"]["state"]

            print(f"Task {task_id}: {state}")

            if state in terminal_states:
                return task

            await asyncio.sleep(2)  # Poll every 2 seconds
```

## 📌 SECTION 12 — A2A Security Model

A2A was designed with security as a first-class concern from day one:

```
A2A SECURITY ARCHITECTURE:

1. AUTHENTICATION (Who are you?)
   ├── OAuth 2.0 Bearer tokens
   ├── JWT with expiry and signing
   ├── Agent Card declares what auth schemes it requires
   └── Client must authenticate before EVERY task call

2. MUTUAL AUTHENTICATION (Prove BOTH sides are real)
   ├── Client authenticates TO server (standard)
   ├── Server identity verified by TLS certificate
   └── Signed Agent Cards (v1.0 feature) — verifiable provenance

3. AUTHORIZATION (What can you do?)
   ├── Each agent enforces its own RBAC
   ├── Agent Card declares required scopes
   └── Scoped API tokens per delegating agent

4. DATA ISOLATION (Can you see my internal state?)
   ├── Remote agents NEVER expose internal logic
   ├── Only Task artifacts are shared
   ├── Agent Card hides implementation details
   └── Each agent has its own isolated data store

5. AUDIT TRAIL
   ├── Every task has unique ID (traceable)
   ├── Every state transition has timestamp
   ├── Full message history stored per task
   └── Cross-agent audit log via task IDs
```

A2A's stateful task model introduces its own attack surface: multi-turn session manipulation allows an attacker to refine prompt injections across successive task interactions in ways that MCP's stateless tool-call model does not permit.

This means A2A has a **unique security consideration**: because tasks are multi-turn (agent asks follow-up questions, client responds), an attacker can craft a slowly escalating prompt injection attack across multiple turns. Mitigation:

```
MULTI-TURN INJECTION DEFENSE:

PROBLEM:
Turn 1: Innocent message ← normal
Turn 2: Slightly suspicious ← agent allows
Turn 3: "Ignore previous..." ← by this point, agent is manipulated!

DEFENSE:
✅ Scan ALL messages in a task for injection — not just the first
✅ Limit number of input_required turns per task (max 5)
✅ Re-validate intent alignment before each turn
✅ Timeout tasks that remain in input_required too long
✅ Rate limit per source agent
```

## 📌 SECTION 13 — Failure Modes

### ❌ Failure Mode 1: Using A2A When MCP Is Enough

We built a simple "weather to calendar" agent using A2A. Two agents. One registry. Two task queues. It took three days. MCP would have taken three hours.

```
SYMPTOM: You're implementing A2A for a simple tool call
RESULT:  Massive over-engineering. Weeks of extra work.

DIAGNOSIS TEST:
  Does the "remote agent" have its OWN intelligence?
  Does it make its own decisions about HOW to do the work?
  Does it run for more than 5 seconds?
  
  If ALL answers are NO → use MCP (it's just a tool)
  If ANY answer is YES → A2A makes sense

RULE: "When your 'tool' starts looking like another autonomous 
       specialist with its own task lifecycle, it is probably 
       not just a tool anymore — that is when A2A becomes interesting."
```

### ❌ Failure Mode 2: No Task State Persistence

```
PROBLEM:
Task submitted → Server restarts → Task ID is gone
Client asks for update → "Task not found" error

RESULT:
Lost work. Confused clients. Unrecoverable state.

FIX:
Store tasks in persistent storage (PostgreSQL, Redis)
NOT in memory variables (they die with the process)
Task IDs must be queryable ACROSS server restarts
```

### ❌ Failure Mode 3: Blocking on Long-Running Tasks

```
PROBLEM:
Client submits task → waits synchronously → connection times out
Research task takes 8 minutes. HTTP timeout = 30 seconds.

RESULT:
Client thinks task failed. Re-submits. Duplicate tasks!

FIX:
Submit task → receive task_id IMMEDIATELY (within seconds)
Subscribe to SSE stream for updates (async)
Use webhooks for even longer tasks (callback URL)
NEVER block synchronously on task completion
```

### ❌ Failure Mode 4: No Agent Card Validation

```
PROBLEM:
Client discovers agent card from unknown server.
Agent card says: "I can do anything" (overpromises)
OR Agent card is malicious (contains injection instructions)

RESULT:
Orchestrator sends sensitive data to wrong/malicious agent.

FIX:
v1.0 Signed Agent Cards — verify cryptographic signature
Maintain allowlist of trusted agent registries
Validate agent card schema before trusting it
Never send sensitive data to agents from unknown sources
```

### ❌ Failure Mode 5: Step Repetition from Bad Coordination

Research analyzing multi-agent LLM system failures found step repetitions account for 15.7% of failures and failure to recognize task completion accounts for 12.4%, both attributed to ad-hoc coordination.

```
PROBLEM:
Orchestrator not sure if sub-agent completed its task.
Orchestrator re-submits same task to same agent.
Same work done twice. Inconsistent results. Wasted resources.

FIX:
Always check task state before re-submitting
Idempotency: use the SAME task_id for retry (server detects duplicate)
Set clear completion criteria in the original task message
Use task state history to understand exactly what happened
```

### ❌ Failure Mode 6: Context Window Leakage Across Agents

```
PROBLEM:
Orchestrator agent has sensitive information in its context.
Orchestrator delegates to research agent.
Orchestrator accidentally includes full context in task message.

RESULT:
Research agent (potentially untrusted, third-party)
receives ALL internal conversation data!

FIX:
Craft task messages carefully — include ONLY what's needed
Don't send system prompts, user histories, credentials
Use scoped messages: "Research X" NOT "My full context is: [...]"
Principle of minimum necessary disclosure
```

## 📌 SECTION 15 — Interview Questions & Answers

### 🎯 Interview Questions:

---

**Q1: What is the A2A protocol and what problem does it solve?**

> **Strong Answer:**
> A2A (Agent-to-Agent) is an open protocol released by Google in April 2025 that standardizes how autonomous AI agents from different vendors and frameworks can discover each other, delegate tasks, track work in progress, and exchange structured results.
>
> The problem it solves is the N×M agent integration problem: before A2A, connecting agents from different frameworks (LangGraph, CrewAI, AutoGen) or different companies (Salesforce, ServiceNow) required custom integration code for every pair. 4 agent types × 5 frameworks = 20 custom connectors. With A2A, everyone implements one standard — reducing this to N+M connections.
>
> The key insight is that A2A is NOT a replacement for MCP. MCP connects agents to tools (vertical). A2A connects agents to other agents (horizontal). Real production systems use both together.

---

**Q2: What are the four core components of A2A and what does each do?**

> **Strong Answer:**
> 1. **Agent Card**: A JSON document published at `/.well-known/agent-card.json`. It describes the agent's identity, skills, supported modalities, endpoint URL, and authentication requirements. It's how other agents discover what this agent can do — like a business card + capability catalog.
>
> 2. **Task**: The unit of work. Has a unique ID and follows an eight-state lifecycle: submitted → working → (input_required / auth_required) → completed / failed / canceled / rejected. Tasks are tracked across time — unlike stateless MCP tool calls.
>
> 3. **Message**: Communication objects exchanged during the task lifecycle. Can have role "user" or "agent." Used for initial request, progress updates, clarifying questions, and responses to those questions.
>
> 4. **Artifact**: The finished deliverable when the task completes. Can be text, structured data, or files. This is what the orchestrating agent actually uses.

---

**Q3: How does A2A handle long-running tasks? Why is this important?**

> **Strong Answer:**
> A2A uses three mechanisms for long-running tasks:
>
> 1. **Immediate task_id**: Client submits task and receives a task_id immediately — within milliseconds. The client does NOT block waiting for completion.
>
> 2. **SSE Streaming**: Client subscribes to an SSE stream for the task. Server pushes state change events (working → input_required → completed) in real-time without polling.
>
> 3. **Webhooks**: For very long tasks (hours), the client registers a callback URL. Server pushes a notification to that URL when the task reaches a terminal state.
>
> This is critical because real AI agent work takes time. Research tasks, document generation, complex analysis — these can take minutes. HTTP has timeout limits. You cannot block synchronously on a 10-minute AI operation. The async task model is what makes A2A suitable for real enterprise workloads.

---

**Q4: How does A2A's security model differ from MCP's?**

> **Strong Answer:**
> A2A treats authentication as a first-class concern — Agent Cards explicitly declare which authentication schemes they require (typically OAuth 2.0 Bearer tokens with JWT). MCP's original design had weaker authentication guidance, which led to security vulnerabilities.
>
> A2A has a unique security challenge MCP doesn't: multi-turn session manipulation. Because A2A tasks can involve multiple rounds of back-and-forth (input_required states), an attacker can craft a slowly escalating prompt injection attack across successive turns — each turn looking innocent individually but collectively achieving agent manipulation.
>
> Defense requires: scanning ALL messages in a task lifecycle (not just the first), limiting maximum input_required rounds, validating intent alignment at each turn, and using Signed Agent Cards (v1.0 feature) to cryptographically verify the identity of remote agents.

---

**Q5: When would you choose A2A over MCP for a specific capability?**

> **Strong Answer:**
> I use a decision framework based on the nature of the "other side":
>
> **Use MCP when:**
> - The capability is a passive tool (no own intelligence)
> - It executes in milliseconds to seconds
> - It does exactly what you specify, no interpretation
> - Simple request → response pattern
> - Examples: read a file, query a database, call a weather API
>
> **Use A2A when:**
> - The capability requires an autonomous AI agent with its own reasoning
> - The work takes more than a few seconds (often minutes)
> - The remote side may ask for clarification or make decisions about HOW to do the work
> - You need to delegate to a specialist agent from a different company/framework
> - Examples: research analysis, legal document review, complex data science task
>
> If the "tool" has its own LLM brain and task lifecycle → it's an agent → use A2A. If it's just a function that executes and returns → use MCP.

## 📌 SECTION 16 — Common Beginner Mistakes

| ❌ Mistake | ✅ Correct Understanding |
|-----------|------------------------|
| "A2A replaces MCP" | They are complementary. Use BOTH in production systems |
| "Use A2A for everything" | Major over-engineering — simple tools don't need A2A |
| "A2A tasks are synchronous" | Always async — submit → track → receive artifact |
| "Store tasks in memory" | Must persist in DB — tasks survive server restarts |
| "Agent Cards are optional" | They are the discovery mechanism — required for A2A |
| "A2A is just API calling" | No — it's autonomous delegation with lifecycle tracking |
| "Trust all Agent Cards" | Verify signatures — Agent Cards can be malicious |
| "Only scan first turn for injection" | Multi-turn tasks need scanning on EVERY message |
| "A2A is production-ready now" | v1.0 is stable, but security patterns still maturing |
| "A2A requires new protocols" | Built on HTTP + SSE + JSON-RPC 2.0 — all web standards |

## 📌 SECTION 17 — Engineer Mindset

```
BEFORE USING A2A — Ask These Questions:

ARCHITECTURE DECISIONS:
✅ Is the "agent" I'm calling truly autonomous (has its own LLM brain)?
   → YES: A2A appropriate
   → NO: Use MCP (it's just a tool)

✅ Does the work take more than ~5 seconds?
   → YES: Need async task model → A2A
   → NO: Synchronous MCP tool call is fine

✅ Is this agent from a different company or framework?
   → YES: A2A provides standard interoperability
   → NO: Consider in-framework orchestration (LangGraph, CrewAI)

✅ Do I need to track task progress over time?
   → YES: A2A task lifecycle is perfect
   → NO: Simple MCP call works

SECURITY DECISIONS:
✅ Am I verifying the Agent Card signature before trusting it?
✅ Am I scanning ALL message turns for injection — not just the first?
✅ Am I limiting what context I share in task messages?
✅ Am I using OAuth 2.0 with proper token expiry?
✅ Am I persisting tasks in a real database (not memory)?

PERFORMANCE DECISIONS:
✅ Am I using SSE streaming (not polling) for updates?
✅ Am I starting with MCP and graduating to A2A when complexity warrants?
✅ Am I limiting the number of concurrent A2A delegations per orchestrator?

THE SENIOR ENGINEER MINDSET:
"MCP is how my agent gets things done.
 A2A is how my agent gets help from other agents.
 The boundary is: does the other side have its own intelligence?
 Tool = no intelligence → MCP
 Agent = has intelligence → A2A
 Use both. Master the boundary between them."
```

## 🎯 Session Summary — What You Learned Today

```
✅ WHAT A2A IS:
   ↳ Open protocol for agent-to-agent (PEER) communication
   ↳ Launched by Google, April 2025 → now Linux Foundation
   ↳ 150+ orgs, 22K+ GitHub stars, v1.0 stable (2026)
   ↳ "HTTP for agents" — defines universal agent language

✅ WHY IT EXISTS:
   ↳ N×M agent integration problem (like MCP solved for tools)
   ↳ LangGraph can't talk to CrewAI without custom code
   ↳ A2A makes any A2A agent talk to any other A2A agent

✅ FOUR CORE COMPONENTS:
   ↳ Agent Card → /.well-known/agent-card.json (discovery)
   ↳ Task → Unit of work with 8-state lifecycle
   ↳ Message → Multi-turn communication objects
   ↳ Artifact → Finished deliverable (text/data/file)

✅ TASK LIFECYCLE (8 states):
   submitted → working → input_required / auth_required
   → completed / failed / canceled / rejected

✅ TECHNICAL STACK:
   ↳ HTTP + JSON-RPC 2.0 (standard web)
   ↳ SSE streaming (real-time progress)
   ↳ OAuth 2.0 + JWT (auth)
   ↳ Webhooks (long-task callbacks)

✅ A2A vs MCP THE SIMPLE RULE:
   ↳ MCP = agent to TOOL (vertical, passive, instant)
   ↳ A2A = agent to AGENT (horizontal, autonomous, async)
   ↳ Use BOTH in production — they're complementary layers

✅ UNIQUE SECURITY RISK:
   ↳ Multi-turn prompt injection (attacks escalate across turns)
   ↳ Scan EVERY message, not just the first
   ↳ Verify Agent Card signatures before trusting

✅ WHEN TO USE:
   ↳ A2A: other side has own LLM + intelligence + task lifecycle
   ↳ MCP: other side is a passive tool/function
   ↳ Start with MCP — graduate to A2A when complexity warrants
```
