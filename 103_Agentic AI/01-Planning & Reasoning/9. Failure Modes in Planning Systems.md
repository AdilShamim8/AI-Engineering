## Before Everything — Understand Failure Modes

**Simple English:**
> A **Failure Mode** is a **specific, recognizable pattern** by which a system breaks down — not a random crash, but a **predictable type of failure** that happens for identifiable reasons under identifiable conditions.

**Why Failure Modes are More Valuable Than Success Patterns:**

```
KNOWING HOW SOMETHING WORKS:
  → Tells you how to BUILD it.

KNOWING HOW SOMETHING FAILS:
  → Tells you how to BUILD IT RELIABLY.
  → How to DETECT when it's going wrong.
  → How to RECOVER when it breaks.
  → How to PREVENT it from breaking at all.

Senior engineers are valuable not because they
know how to build things — juniors can do that.

Senior engineers are valuable because they know
ALL THE WAYS something will break BEFORE IT DOES.

THIS MODULE makes you think like a senior engineer.
```

---

## The Failure Mode Taxonomy

```
FAILURE MODES EXIST AT THREE LEVELS:

LEVEL 1: IMMEDIATE FAILURES
  → Detectable right away.
  → Agent errors, crashes, explicit errors.
  → Easy to detect. Easy to fix.
  Example: Tool call returns 404 error.

LEVEL 2: LATENT FAILURES
  → Not obvious until much later.
  → Agent appears to work but produces wrong output.
  → Hard to detect. Dangerous.
  Example: Agent completes task but missed the real goal.

LEVEL 3: EMERGENT FAILURES
  → Only appear under specific conditions.
  → System works in testing but fails in production.
  → Very hard to detect. Very hard to fix.
  Example: Infinite loop only triggers with circular data.

The 6 failure modes in this module span all three levels.
The most dangerous ones are Level 2 and Level 3.
```

# 📌 TOPIC 1: Infinite Loops
# ═══════════════════════════

---

## 1️⃣ What Is An Infinite Loop in Planning?

**Simple English:**
> An Infinite Loop in an AI planning system happens when the agent **keeps repeating the same sequence of actions** — calling the same tools, generating the same plans, making the same decisions — **over and over, without making progress**, and **without stopping on its own.**

**Three forms this takes:**

```
FORM 1: CIRCULAR TOOL CALLS
  Agent calls Tool A → Result tells it to call Tool B
  Tool B → Result tells it to call Tool A
  Tool A → Result tells it to call Tool B
  → Loops forever.

FORM 2: REPLANNING LOOP
  Agent makes a plan → Executes it → Plan fails
  Agent replans → Same plan → Same failure
  Agent replans → Same plan → Same failure
  → Loops forever on the same wrong approach.

FORM 3: SELF-REFERENTIAL LOOP
  Agent decomposes Task A into: [Task A1, Task A2]
  Task A1 decomposes into: [Task A, Task A2]
  Task A decomposes into: [Task A1, Task A2]
  → Infinite recursive decomposition.
```

**In one line:**
> *"The agent is spinning its wheels — burning resources, going nowhere, and never realizing it needs to stop."*

---

## 2️⃣ Why Does It Happen?

```
ROOT CAUSE 1: CIRCULAR DEPENDENCIES IN TOOLS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Tool A's output format is the input for Tool B.
Tool B's output format is the input for Tool A.
Without cycle detection → infinite loop.

ROOT CAUSE 2: NO CONVERGENCE CHECKING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Agent doesn't check: "Am I making progress?"
It just checks: "Is the task done?"
If the task is never done → loop forever.

ROOT CAUSE 3: INSUFFICIENT LOOP DETECTION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Agent doesn't track what it has already done.
Without memory of past actions → repeats them.

ROOT CAUSE 4: AMBIGUOUS TERMINATION CONDITIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
What does "task complete" mean?
If not clearly defined → agent never finds the stop condition
→ Keeps going indefinitely.
```

---

## 3️⃣ First-Principles Breakdown

```
BASIC TRUTH 1:
For a loop to terminate, it needs a STOPPING CONDITION
that is GUARANTEED to be reached.

If the stopping condition CAN be reached → finite loop.
If the stopping condition CANNOT be reached → infinite loop.

BASIC TRUTH 2:
AI planning loops fail to terminate because:
  → The stopping condition is poorly defined.
  → The agent's actions don't move it toward the stopping condition.
  → External dependencies are circular (A needs B needs A).

BASIC TRUTH 3:
Loop detection requires MEMORY.
"Have I been in this exact state before?"
Without tracking past states → cannot detect repetition.

BASIC TRUTH 4:
Infinite loops are EXPENSIVE.
Every iteration → API calls → tokens → money.
A loop running for 1 hour in production =
potentially thousands of dollars wasted.
```

## 5️⃣ The Three Layers of Loop Detection

### LAYER 1: ACTION FINGERPRINTING

```python
class LoopDetector:
    """
    Detects when an agent is repeating the same actions.
    Must be consulted before every action.
    """

    def __init__(self, max_repetitions=3, window_size=10):
        self.action_history = []       # All past actions
        self.state_history = []        # All past states
        self.max_repetitions = max_repetitions
        self.window_size = window_size

    def create_action_fingerprint(self, tool_name, arguments):
        """
        Create a unique identifier for an action.
        Same tool + same args = same fingerprint = potential loop.
        """
        import hashlib, json
        action_str = f"{tool_name}:{json.dumps(arguments, sort_keys=True)}"
        return hashlib.md5(action_str.encode()).hexdigest()

    def is_looping(self, tool_name, arguments):
        """
        Check if this action has been taken before.
        Returns: (is_looping: bool, reason: str, count: int)
        """
        fingerprint = self.create_action_fingerprint(tool_name, arguments)

        # Count how many times this exact action has been taken
        recent_actions = self.action_history[-self.window_size:]
        repetition_count = recent_actions.count(fingerprint)

        if repetition_count >= self.max_repetitions:
            return True, f"IDENTICAL_ACTION_REPEATED_{repetition_count}_TIMES", repetition_count

        # Record this action
        self.action_history.append(fingerprint)
        return False, "OK", repetition_count

    def is_state_cycling(self, current_state):
        """
        Check if the agent has been in this exact state before.
        State cycling = more subtle form of infinite loop.
        """
        state_fingerprint = self._hash_state(current_state)

        if state_fingerprint in self.state_history[-self.window_size:]:
            return True, "STATE_CYCLE_DETECTED"

        self.state_history.append(state_fingerprint)
        return False, "OK"

    def _hash_state(self, state):
        import hashlib, json
        return hashlib.md5(json.dumps(state, sort_keys=True).encode()).hexdigest()
```

### LAYER 2: PROGRESS MEASUREMENT

```
THE CORE INSIGHT:
━━━━━━━━━━━━━━━━
Not all loops look the same.
Some loops change WHAT they do but still go nowhere.

SOLUTION: Measure PROGRESS, not just repetition.

PROGRESS METRICS:

  METRIC 1: Task Completion %
    Is the agent completing more sub-tasks over time?
    If completion% is flat for N steps → stuck.

  METRIC 2: Distance to Goal
    Define a measurable distance to goal.
    Is this distance decreasing?
    If not → no progress → potential loop.

  METRIC 3: New Information Gained
    Is each step producing NEW information?
    If all results are similar to previous → stuck.

  METRIC 4: Resource Efficiency
    Are actions becoming more efficient?
    If cost per unit of progress is increasing → stuck.

IMPLEMENTATION:
  After every 5 steps, measure progress.
  If progress < threshold:
    → Trigger LOOP_WARNING
    → Try different approach
    → If still no progress after 10 steps:
      → FORCE STOP → return partial result
```

## 1️⃣ What Are Hallucinated Tools?

**Simple English:**
> Hallucinated Tools happen when an AI agent **invents, imagines, or references tools that do not exist** in its available toolset — either calling a non-existent tool, using a real tool with an invented name, or describing capabilities that no tool actually has.

**Three forms:**

```
FORM 1: COMPLETELY INVENTED TOOL
  Agent calls: "quantum_search_api(query='best hotel')"
  Reality: This tool was never defined. It doesn't exist.
  Result: Immediate runtime error.
  Danger Level: Medium (at least it fails visibly)

──────────────────────────────────────────────────────

FORM 2: WRONG TOOL NAME (Close But Wrong)
  Real tool: "weather_api"
  Agent calls: "weather_search_api" or "get_weather"
  Reality: The real tool exists but agent used wrong name.
  Result: Runtime error OR wrong tool called.
  Danger Level: Medium-High (harder to debug)

──────────────────────────────────────────────────────

FORM 3: HALLUCINATED TOOL CAPABILITY
  Real tool: calculator(expression) → returns number
  Agent believes: calculator can ALSO plot graphs
  Agent tries: calculator(expression, plot=True)
  Reality: Tool ignores unknown parameters.
           Agent thinks it got a graph. It didn't.
  Result: Silent failure — no error, wrong behavior.
  Danger Level: VERY HIGH (fails invisibly)
```

**In one line:**
> *"The agent is trying to use tools from its imagination, not from its actual toolbox."*

---

## 2️⃣ Why Does It Happen?

```
ROOT CAUSE 1: LLM TRAINING MEMORY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
LLMs were trained on code, documentation, and API specs
from millions of real tools and libraries.

When asked to use tools, the LLM sometimes
RECALLS tools from training instead of
READING the provided tool definitions.

Example:
  You gave the agent: weather_api
  LLM trained on Python libraries that have: requests.get()
  Agent hallucinates: requests.get("weather_url") instead
  of using the provided weather_api tool.

──────────────────────────────────────────────────────

ROOT CAUSE 2: VAGUE TOOL DESCRIPTIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
If tool descriptions are vague or ambiguous,
the LLM fills in the gaps with imagination.

Bad description: "search_tool - searches for things"
LLM fills in: "this probably has image search too"
Agent tries: search_tool(query="Paris", type="image")
Reality: image search doesn't exist. Fails silently.

──────────────────────────────────────────────────────

ROOT CAUSE 3: CAPABILITY OVERGENERALIZATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
LLM reasons: "If it can do X, it probably can do Y too"
This is logical for humans learning new systems.
But for AI agents, it produces hallucinated capabilities.

──────────────────────────────────────────────────────

ROOT CAUSE 4: TOOL SELECTION UNDER PRESSURE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
When the agent NEEDS a capability that no tool provides:
  Option A: Admit the limitation (correct)
  Option B: Invent a tool that would solve it (hallucination)

LLMs under instruction pressure tend toward Option B.
They want to help, so they invent a solution.
```

---

## 3️⃣ First-Principles Breakdown

```
BASIC TRUTH 1:
LLMs are trained to be HELPFUL.
When they can't find a real tool, they invent one.
"Being helpful" is stronger than "being accurate about tools."
This is a fundamental tension in LLM behavior.

BASIC TRUTH 2:
Tool hallucination exists on a spectrum:
  LOW:  Wrong tool name (easy to detect, usually errors)
  MED:  Wrong parameters (may silently be ignored)
  HIGH: Completely invented tool (hard runtime error)
  CRITICAL: Wrong capability assumption (silent failure)

BASIC TRUTH 3:
The most dangerous hallucination is SILENT.
If the agent calls a wrong tool and gets an ERROR → visible.
If the agent calls a tool with wrong parameters and
the tool IGNORES those parameters silently → invisible.
The agent thinks it did something it didn't actually do.

BASIC TRUTH 4:
Tool hallucination prevention requires:
  → Precise tool definitions (not vague)
  → Strict validation before calling any tool
  → Closed-world assumption: only defined tools exist
  → Output verification: did the tool actually do what agent thinks?
```

## 5️⃣ Prevention: The Four-Layer Defense

### LAYER 1: PRECISE TOOL DEFINITIONS

```
BAD TOOL DEFINITION (causes hallucination):
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
{
  "name": "search",
  "description": "Searches for information",
  "parameters": {
    "query": "search query"
  }
}

Problem: What kind of search? Web? Database? Images?
         What does it return? Text? URLs? JSON?
         LLM guesses → hallucinates capabilities.

──────────────────────────────────────────────────

GREAT TOOL DEFINITION (prevents hallucination):
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
{
  "name": "web_search",
  "description": "Searches the public internet using Google.
                  Returns a list of text snippets and URLs.
                  CANNOT search images, videos, or private data.
                  CANNOT access paywalled content.
                  Returns up to 10 results per query.",
  "parameters": {
    "query": {
      "type": "string",
      "description": "The search query in natural language or keywords",
      "example": "best restaurants in Paris 2026"
    }
  },
  "returns": {
    "type": "array",
    "items": {
      "title": "string",
      "url": "string",
      "snippet": "string"
    }
  },
  "NOT_SUPPORTED": [
    "Image search",
    "Video search",
    "Real-time data (may be slightly delayed)",
    "Private or internal company data"
  ]
}

Key additions:
  ✅ What it CANNOT do (prevents capability hallucination)
  ✅ Exact return format (prevents output hallucination)
  ✅ Concrete example (anchors LLM understanding)
  ✅ Specific, unambiguous name (not generic "search")
```

### LAYER 2: CLOSED-WORLD ENFORCEMENT

```python
class ToolRegistry:
    """
    The ONLY source of truth for what tools exist.
    Agent can ONLY call tools registered here.
    """

    def __init__(self):
        self._tools = {}  # name → tool definition

    def register(self, tool_definition):
        """Register a tool as available."""
        self._tools[tool_definition["name"]] = tool_definition

    def validate_tool_call(self, tool_name, arguments):
        """
        Validate a tool call BEFORE execution.
        This is the closed-world enforcement layer.
        """

        # RULE 1: Tool must exist in registry
        if tool_name not in self._tools:
            return {
                "valid": False,
                "error": "HALLUCINATED_TOOL",
                "message": f"Tool '{tool_name}' does not exist.",
                "available_tools": list(self._tools.keys()),
                "suggestion": self._find_closest_tool(tool_name)
            }

        tool_def = self._tools[tool_name]

        # RULE 2: All required parameters must be present
        for param_name, param_def in tool_def["parameters"].items():
            if param_def.get("required", True) and param_name not in arguments:
                return {
                    "valid": False,
                    "error": "MISSING_REQUIRED_PARAMETER",
                    "message": f"Parameter '{param_name}' is required for '{tool_name}'",
                    "missing": param_name
                }

        # RULE 3: No extra parameters (hallucinated capabilities)
        allowed_params = set(tool_def["parameters"].keys())
        provided_params = set(arguments.keys())
        extra_params = provided_params - allowed_params

        if extra_params:
            return {
                "valid": False,
                "error": "HALLUCINATED_PARAMETER",
                "message": f"Parameters {extra_params} do not exist for '{tool_name}'",
                "hallucinated_params": list(extra_params),
                "allowed_params": list(allowed_params)
            }

        return {"valid": True}

    def _find_closest_tool(self, attempted_name):
        """Find the most similar real tool name (typo correction)."""
        from difflib import get_close_matches
        matches = get_close_matches(attempted_name, self._tools.keys(), n=1, cutoff=0.6)
        return f"Did you mean: '{matches[0]}'?" if matches else "No similar tool found."
```

### LAYER 3: OUTPUT VALIDATION

```
PROBLEM: Even if tool call is valid, the tool result
         might not be what the agent THINKS it is.

SOLUTION: Validate tool output against expected schema
          before passing it to the agent.

IMPLEMENTATION:

  def execute_and_validate(self, tool_name, arguments):

      # Get expected output schema
      expected_schema = self._tools[tool_name]["returns"]

      # Execute the tool
      result = self._tools[tool_name]["function"](**arguments)

      # Validate result matches expected schema
      validation = self._validate_schema(result, expected_schema)

      if not validation["valid"]:
          return {
              "status": "SCHEMA_MISMATCH",
              "warning": "Tool returned unexpected format",
              "expected": expected_schema,
              "received": type(result).__name__,
              "partial_result": result
          }

      return {"status": "SUCCESS", "result": result}

WHY THIS MATTERS:
  Agent might think: "calculator returned a graph"
  Reality: calculator returned a number.
  Validation catches this BEFORE agent acts on wrong assumption.
```

---

### LAYER 4: FAILURE FEEDBACK LOOP

```
WHEN TOOL HALLUCINATION IS DETECTED:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Don't just return an error.
TEACH the agent what went wrong.

Feedback to LLM:

  "TOOL_ERROR: You attempted to call 'weather_search_api'
   which does not exist in your available tools.

   Available tools: [web_search, weather_api, calculator,
                     database_lookup, email_sender]

   The correct tool for weather information is: weather_api
   Correct usage: weather_api(city='London')

   Please retry with the correct tool."

WHY THIS WORKS:
  → Agent knows exactly what went wrong.
  → Agent knows what tools are actually available.
  → Agent gets corrected before making same mistake.
  → Most modern LLMs can self-correct from this feedback.
```

---

## 6️⃣ Failure Modes OF Hallucinated Tool Detection

```
META-FAILURE 1: Silent Parameter Ignoring
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Problem: Some tools silently ignore unknown parameters.
         Validation passes. Tool runs. Wrong result.
         Agent thinks extra capability worked.
Fix: Validate tool OUTPUT matches expected schema,
     not just that tool CALL was valid.

──────────────────────────────────────────────

META-FAILURE 2: Feedback Loop Not Helpful
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Problem: Error message just says "tool not found"
         Agent doesn't know what to do instead.
Result: Agent tries another hallucinated tool.
Fix: Error messages must include: what went wrong,
     what tool SHOULD be used, correct usage example.

──────────────────────────────────────────────

META-FAILURE 3: New Tools Not Registered
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Problem: Engineer adds new tool but forgets to
         update the tool registry AND the system prompt.
Result: Agent either doesn't know tool exists
        OR hallucinates about what it can do.
Fix: Tool registry is the SINGLE source of truth.
     Adding a tool requires: registry update + test.
```

# 📌 TOPIC 3: Incorrect Decomposition
# ══════════════════════════════════════

---

## 1️⃣ What Is Incorrect Decomposition?

**Simple English:**
> Task Decomposition is when an AI agent **breaks a big task into smaller sub-tasks** to solve each piece independently. Incorrect Decomposition happens when the agent **breaks the task in the WRONG WAY** — creating sub-tasks that don't actually combine to solve the original task, miss critical parts, solve the wrong problem, or are in the wrong order.

**Three forms:**

```
FORM 1: INCOMPLETE DECOMPOSITION
  Missing critical sub-tasks.
  Solving only part of the problem.
  Example: "Plan a trip" decomposed into:
  [find_flights, find_hotel]
  MISSING: [visa_check, travel_insurance, currency, itinerary]
  Result: Incomplete plan that fails in execution.

──────────────────────────────────────────────────────

FORM 2: WRONG LEVEL OF DECOMPOSITION
  Sub-tasks are too big (under-decomposed) or
  too small (over-decomposed).
  Example: "Bake a cake" decomposed into:
  Too big:   ["buy ingredients", "bake"]
             (Steps too large to execute directly)
  Too small: ["open cabinet", "reach for flour bag",
              "grab flour bag", "pull out flour bag",
              "close cabinet", ...]
             (Steps so small they're absurd)

──────────────────────────────────────────────────────

FORM 3: WRONG PROBLEM DECOMPOSED
  Agent decomposes a DIFFERENT problem than what was asked.
  Subtle misunderstanding of the original goal.
  Example: User wants "improve my code's performance"
  Agent decomposes: ["add more comments",
                     "rename variables for clarity",
                     "reformat code style"]
  Agent solved "improve code readability" not "performance."
  Incorrect decomposition from wrong goal interpretation.
```

**In one line:**
> *"The agent drew the wrong map for the journey — and is now executing the wrong journey perfectly."*

---

## 2️⃣ Why Does It Happen?

```
ROOT CAUSE 1: GOAL AMBIGUITY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━
The original task is vague.
"Make my website better" = infinite possible decompositions.
Agent picks one interpretation. May be wrong.

ROOT CAUSE 2: LLM TRAINING BIAS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
LLMs learned task decomposition from training data.
They decompose tasks the way they've SEEN them decomposed.
If training data has biased decompositions → agent repeats bias.
Example: LLM trained mostly on US-centric travel planning
→ forgets visa requirements for non-US travelers.

ROOT CAUSE 3: MISSING DOMAIN KNOWLEDGE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Some tasks require specialized knowledge to decompose correctly.
"Plan a pharmaceutical clinical trial" requires deep domain expertise.
LLM might know general "project planning" but
miss critical domain-specific sub-tasks (IRB approval, blinding protocols).

ROOT CAUSE 4: DEPENDENCY BLINDNESS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Agent creates sub-tasks that look complete but
misses hidden dependencies between them.
Example: "Build a house" decomposed but
         roof sub-task placed before wall sub-task.
         Architecturally impossible ordering.
```

---

## 3️⃣ First-Principles Breakdown

```
BASIC TRUTH 1:
A decomposition is CORRECT if and only if:
  → Executing all sub-tasks achieves the original goal
  → No critical sub-tasks are missing
  → Sub-tasks are in a valid execution order
  → Sub-tasks are at the right level of detail

BASIC TRUTH 2:
Decomposition correctness can only be verified by:
  → Domain expertise (human or specialized AI)
  → Simulation/testing of the decomposition
  → Comparison against known correct decompositions

BASIC TRUTH 3:
Wrong decompositions compound over time.
  Step 1: Wrong decomposition created.
  Steps 2-10: Executed perfectly on wrong decomposition.
  Final result: Perfectly wrong.
  Cost: 10 steps of wasted work.

The later you catch the wrong decomposition,
the more expensive the failure.

BASIC TRUTH 4:
Decomposition validation should happen BEFORE execution,
not after. Validate the plan, then execute.
```

---

## 4️⃣ Real-World Analogy

**Think of a construction architect making blueprints:**

```
CLIENT: "Build me a house with 3 bedrooms, 2 bathrooms,
         a kitchen, and a garage."

WRONG DECOMPOSITION:
  Architect hears: "3 bedrooms, 2 bathrooms, kitchen"
  Creates blueprint with: bedrooms, bathrooms, kitchen.
  FORGETS: garage.
  FORGETS: foundation.
  FORGETS: plumbing and electrical.

  Construction team executes perfectly.
  Builds exactly what blueprint says.
  House has no garage, no plumbing, no electrical.
  Client is horrified.

  Who failed? The ARCHITECT — wrong decomposition.
  The construction team was PERFECT.
  The blueprint was WRONG.

WITH CORRECT DECOMPOSITION:
  Architect carefully interviews client.
  Creates complete blueprint.
  Client REVIEWS blueprint before construction.
  Construction proceeds with correct plan.

AI AGENT = Architect creating the blueprint
DECOMPOSITION = The blueprint
EXECUTION = Construction
WRONG DECOMPOSITION = Missing rooms in blueprint
```

---

## 5️⃣ Detection and Prevention Strategies

### STRATEGY 1: DECOMPOSITION VALIDATION PROMPT

```
BEFORE EXECUTION, ASK THE LLM TO SELF-CHECK:

  Validation Prompt:
  ─────────────────────────────────────────────
  "You have decomposed the task into these sub-tasks:
   [list of sub-tasks]

   Before proceeding, verify:
   1. Does executing ALL of these sub-tasks guarantee
      the ORIGINAL goal is achieved?
   2. Is there ANY part of the original goal NOT covered?
   3. Are there dependencies you haven't accounted for?
   4. Are the sub-tasks in a logically valid order?

   If any answer is NO or UNCERTAIN:
   Revise the decomposition before continuing."
  ─────────────────────────────────────────────

WHY THIS WORKS:
  Asking LLM to VERIFY its own decomposition
  catches obvious gaps that a single pass misses.
  Not perfect but dramatically reduces errors.
```

---

### STRATEGY 2: CHECKLIST-DRIVEN DECOMPOSITION

```
FOR KNOWN TASK TYPES: Use domain-specific checklists.

TRAVEL PLANNING CHECKLIST:
  Must include:
  ✅ visa requirements
  ✅ flight search
  ✅ accommodation
  ✅ travel insurance
  ✅ local transportation
  ✅ currency/payment
  ✅ health requirements (vaccinations)
  ✅ emergency contacts

  Compare agent's decomposition against checklist.
  Missing items → force agent to add them.

SOFTWARE FEATURE CHECKLIST:
  Must include:
  ✅ requirements analysis
  ✅ design
  ✅ implementation
  ✅ unit tests
  ✅ integration tests
  ✅ security review
  ✅ documentation
  ✅ deployment plan
  ✅ rollback plan
```

---

### STRATEGY 3: PROGRESSIVE DECOMPOSITION

```
INSTEAD OF: Decompose ENTIRE task at once (risky)
USE: Decompose ONE level at a time (safer)

PROGRESSIVE DECOMPOSITION PATTERN:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  LEVEL 0: Main goal
    "Plan a trip to Paris"

  LEVEL 1: First decompose into major phases ONLY:
    [Research, Booking, Preparation, Travel]
    → Validate this with user before going deeper.

  LEVEL 2: Decompose first phase only:
    Research → [visa_check, flight_research,
                hotel_research, budget_estimate]
    → Validate this before moving on.

  LEVEL 3: Decompose first sub-task only:
    visa_check → [check_nationality_requirements,
                   application_form, fee_payment,
                   processing_time_estimate]

WHY THIS IS BETTER:
  → Catch wrong decomposition EARLY (before any execution).
  → User can validate each level before deeper breakdown.
  → Less wasted work if decomposition is wrong.
  → Supports HITL at each level.
```

---

## 6️⃣ Failure Modes OF Decomposition Validation

```
META-FAILURE 1: Circular Validation
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Problem: Asking the SAME LLM to validate its own decomposition.
Reality: LLM tends to agree with itself.
         The same reasoning that produced wrong decomposition
         will validate the wrong decomposition as correct.
Fix: Use a DIFFERENT prompt style for validation.
     Or use a different LLM as the validator.
     Or use human validation at this step.

──────────────────────────────────────────────

META-FAILURE 2: Validation Without Domain Knowledge
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Problem: LLM validates medical/legal/financial decomposition
         without specialized domain knowledge.
Result: Misses critical domain-specific steps.
Fix: For specialized domains, use specialized validation:
     domain-specific checklists + expert human review.

──────────────────────────────────────────────

META-FAILURE 3: Late Detection
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Problem: Decomposition validated at planning stage.
         Execution begins.
         Step 7 reveals that Step 3's output was
         completely wrong for Step 7's needs.
         Decomposition was logically correct
         but practically incompatible.
Fix: Validate COMPATIBILITY of sub-task outputs/inputs
     at planning time, not just completeness.
```

# 📌 TOPIC 4: Over-Planning
# ════════════════════════

---

## 1️⃣ What Is Over-Planning?

**Simple English:**
> Over-Planning happens when an AI agent **spends more time, tokens, and resources on PLANNING than is necessary or beneficial** — creating overly complex plans, planning to excessive depth, exploring too many options, or refining plans that are already good enough — instead of just executing the task.

**The Paradox of Over-Planning:**
> The agent is trying to plan BETTER by planning MORE.
> But planning more creates: higher cost, more latency,
> more opportunities for error, and often WORSE results
> because the plan becomes too complex to execute reliably.

**In one line:**
> *"The agent is drawing an incredibly detailed map of every grain of sand on a beach — when all it needed was 'turn left at the lighthouse.'"*

---

## 2️⃣ Why Does It Happen?

```
ROOT CAUSE 1: NO PLANNING BUDGET
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Agent has budget for execution but not for planning.
Planning just keeps going with no limit.

ROOT CAUSE 2: PERFECTIONISM BIAS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
LLMs instructed to be thorough will:
  → Consider every edge case
  → Plan for every contingency
  → Refine the plan repeatedly
  → Add more detail than needed

The instruction "be thorough" becomes
"plan forever."

ROOT CAUSE 3: UNCLEAR DEFINITION OF "GOOD ENOUGH"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
If there's no criterion for "this plan is ready to execute"
→ Agent keeps refining the plan indefinitely.

ROOT CAUSE 4: ANALYSIS PARALYSIS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
When multiple options exist:
  → Agent plans for Option A completely
  → Then plans for Option B completely
  → Then compares in detail
  → Then considers combining A and B
  → Then plans hybrid option...
  → Never actually executes anything.
```

---

## 3️⃣ First-Principles Breakdown

```
BASIC TRUTH 1:
Planning has DIMINISHING RETURNS.
The first 20% of planning time produces 80% of the value.
The remaining 80% of planning time adds only 20% more value.
At some point: more planning = no improvement.

BASIC TRUTH 2:
Planning and execution are in COMPETITION for resources.
More resources spent planning = fewer resources for executing.
Over-planning starves execution.

BASIC TRUTH 3:
Perfect planning is impossible.
Reality always differs from plan.
A good-enough plan + adaptive execution beats
a perfect plan + no execution time.
"Plans are useless, planning is indispensable" — Eisenhower

BASIC TRUTH 4:
Over-planning is ESPECIALLY expensive in AI systems.
Every planning iteration = LLM call = tokens = money.
An agent that plans 10 iterations instead of 3
pays 3x more for planning alone,
with often no measurable improvement in results.
```

---

## 4️⃣ Real-World Analogy

**Think of analysis paralysis in everyday life:**

```
SCENARIO: Choosing a restaurant for dinner.

APPROPRIATE PLANNING (2 minutes):
  "Italian or Chinese? Italian. 
   Nearby place has good reviews. Let's go."
  → At restaurant in 10 minutes. ✅

OVER-PLANNING (2 hours):
  "Let me research all restaurants in the city.
   Check reviews on Yelp, TripAdvisor, Google.
   Compare menus, prices, ambiance, wait times.
   Research nutrition information for each option.
   Calculate travel time for each location.
   Consider the weather impact on outdoor seating...
   Check if any famous food critics have reviewed them...
   Compare against last 50 restaurants I've been to...
   Run statistical analysis of review sentiment..."

  → Still at home 2 hours later. Starving. Never went. ❌

THE COST OF OVER-PLANNING:
  Opportunity cost of not executing.
  Decision fatigue from too many options.
  Information overload reducing decision quality.
  Time and energy wasted on unnecessary detail.

AI AGENT OVER-PLANNING = This exact scenario.
Just with API calls and tokens instead of time.
```

---

## 5️⃣ The Over-Planning Detection Signals

```
SIGNAL 1: PLANNING TIME EXCEEDS EXECUTION TIME
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Measure: planning_tokens / execution_tokens
Healthy ratio: ~0.1 to 0.3 (plan less, execute more)
Red flag: ratio > 1.0 (more tokens in planning than execution)

──────────────────────────────────────────────────────

SIGNAL 2: PLAN STOPS CHANGING BETWEEN ITERATIONS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Measure: Diff between plan version N and N+1.
Healthy: Significant changes in early iterations,
         convergence after 2-3 iterations.
Red flag: Plan barely changes after iteration 2
          but agent keeps refining it.

──────────────────────────────────────────────────────

SIGNAL 3: PLAN DEPTH EXCEEDS TASK COMPLEXITY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Measure: Number of sub-tasks vs. actual complexity needed.
Simple task (send email): 3-4 sub-tasks is correct.
Red flag: Agent creates 47 sub-tasks for sending an email.

──────────────────────────────────────────────────────

SIGNAL 4: INCREASING CONTINGENCY PLANNING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Red flag: Plan has detailed contingencies for
          extremely unlikely edge cases.
"Plan B if the hotel burns down"
"Plan C if there's an earthquake"
"Plan D if the airline ceases operation"
For a 2-night hotel stay.
This is over-planning of contingencies.
```

---

## 6️⃣ Over-Planning Prevention Strategies

```
STRATEGY 1: PLANNING BUDGET
━━━━━━━━━━━━━━━━━━━━━━━━━━━
Explicitly limit planning resources:
  max_planning_tokens = total_budget * 0.2
  max_planning_iterations = 3
  max_plan_depth = task_complexity_score * 2

After planning budget exhausted:
  MUST start executing, regardless of plan completeness.

─────────────────────────────────────────────────

STRATEGY 2: MINIMUM VIABLE PLAN
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Define what a "minimum viable plan" looks like.
If the plan meets this minimum → start executing.
Don't wait for the perfect plan.

MVP PLAN CRITERIA:
  ✅ All critical steps identified?
  ✅ Dependencies mapped?
  ✅ First 3 actions clear and executable?
  → If yes: EXECUTE NOW. Refine as you go.

─────────────────────────────────────────────────

STRATEGY 3: ROLLING PLANNING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Don't plan the entire task upfront.
Plan 3 steps ahead. Execute 1. Plan 1 more. Execute 1.
Like a rolling window.

BENEFITS:
  → Later steps planned with real execution data.
  → No wasted planning for steps that never happen.
  → Adapts to reality as execution proceeds.

─────────────────────────────────────────────────

STRATEGY 4: SATISFICING (NOT MAXIMIZING)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Stop planning when plan is GOOD ENOUGH.
Not when it's PERFECT.

Instruct agent: "Stop planning when you have a plan
that is LIKELY to succeed. Don't seek the optimal plan.
Seek the first SUFFICIENT plan."

This is from decision theory: SATISFICING.
Finding a satisfactory solution, not the optimal one.
For most real tasks, satisficing is correct approach.
```

# ═════════════════════════
# 📌 TOPIC 5: Under-Planning
# ═════════════════════════

---

## 1️⃣ What Is Under-Planning?

**Simple English:**
> Under-Planning happens when an AI agent **jumps to execution too quickly, with insufficient planning** — missing critical dependencies, failing to account for constraints, not thinking through consequences, and discovering problems only after taking actions that are difficult or impossible to reverse.

**The mirror image of Over-Planning:**
> Over-Planning: Too much thinking, no action.
> Under-Planning: Too much action, not enough thinking.

**Three forms:**

```
FORM 1: MISSING PREREQUISITE STEPS
  Agent executes Step 5 before doing Step 2.
  Step 5 requires output from Step 2.
  Step 5 fails because prerequisites not met.

──────────────────────────────────────────────

FORM 2: IGNORING CONSTRAINTS
  Agent acts without checking:
  → Budget constraints (spends over budget)
  → Permission constraints (acts without authorization)
  → Resource constraints (uses unavailable resource)

──────────────────────────────────────────────

FORM 3: NOT CONSIDERING CONSEQUENCES
  Agent takes action without thinking:
  → What happens if this fails?
  → What are the side effects?
  → Is this reversible?
  → Does this affect other parts of the system?
```

**In one line:**
> *"The agent ran out the door without checking if it had the keys, wallet, or even the right destination address."*

---

## 2️⃣ Why Does It Happen?

```
ROOT CAUSE 1: INSTRUCTION PRESSURE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Prompt says: "Complete this task efficiently"
LLM interprets: "Act quickly with minimal thinking"
Result: Jumps to action without adequate planning.

ROOT CAUSE 2: OVER-CONFIDENCE IN LLM KNOWLEDGE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
LLM has seen many similar tasks in training.
"I know how this works" → skips planning.
But this specific instance has unique constraints
the LLM doesn't know about.

ROOT CAUSE 3: NO PLANNING ENFORCEMENT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
System doesn't require a plan before execution.
Agent CAN go directly to tool calls.
Without enforcement: often WILL go directly.

ROOT CAUSE 4: REINFORCEMENT OF BAD HABITS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
If agent frequently "gets lucky" by under-planning
and still succeeding → reinforces under-planning.
When a more complex task requires real planning →
agent uses the same under-planning approach → fails.
```

---

## 3️⃣ First-Principles Breakdown

```
BASIC TRUTH 1:
Actions have CONSEQUENCES.
Some consequences are EXPENSIVE to reverse.
Planning is the way to predict consequences
BEFORE taking actions.
Without planning → surprises → often bad ones.

BASIC TRUTH 2:
Complex tasks have DEPENDENCIES.
Dependency: B cannot succeed without A completing first.
Under-planning misses dependencies.
Executing B before A → B fails → wasted work.

BASIC TRUTH 3:
The cost of discovering a problem is:
  CHEAPEST at planning stage (nothing done yet)
  MORE EXPENSIVE at early execution stage (some work wasted)
  VERY EXPENSIVE at late execution stage (much work wasted)
  CATASTROPHIC post-execution (irreversible actions taken)

Planning moves problem discovery to the CHEAPEST point.

BASIC TRUTH 4:

An under-planned action that succeeds
looks identical to a well-planned action that succeeds.
The failure only becomes visible when it fails.
This makes under-planning hard to detect proactively.
```

## 1️⃣ What Is Loss of Goal Alignment?

**Simple English:**
> Loss of Goal Alignment happens when an AI agent **gradually drifts away from the user's original intention** during a long task — becoming focused on a sub-goal, a proxy metric, or an instrumental goal — until it is efficiently working toward something the user NEVER wanted.

**This is the most DANGEROUS and SUBTLE failure mode.**

**Why:**
> Unlike infinite loops (visible) or hallucinated tools (causes errors), goal alignment loss can produce **coherent, well-executed, competent work — on the completely wrong goal.** The agent succeeds at something the user never asked for.

**Three forms:**

```
FORM 1: SUB-GOAL FIXATION
  Agent gets "stuck" on a sub-goal and loses sight
  of the parent goal.
  Example: Optimizing database query speed
           becomes the focus, forgetting that
           overall app UX was the original goal.
           Fast queries but broken UI.

FORM 2: PROXY METRIC FIXATION
  Agent starts optimizing for something measurable
  instead of what was actually wanted.
  Example: Goal: "Write a good blog post"
           Proxy: Word count (measurable)
           Result: 5000-word padded, repetitive article
                   that hits word count but is low quality.

FORM 3: GOAL DRIFT THROUGH CHAINING
  Each step slightly re-interprets the goal.
  Over 15 steps: goal has completely changed.
  Like a game of telephone where goal is corrupted
  step by step across the execution chain.
```

**In one line:**
> *"The agent set out to help you get to Paris but is now expertly navigating toward London — and is very proud of the progress it's making."*

---

## 2️⃣ Why Does It Happen?

```
ROOT CAUSE 1: GOAL NOT ANCHORED IN STATE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Original goal stated once at beginning.
As conversation grows → original goal gets further
from current context window.
LLM focuses on most recent context.
Most recent context = latest sub-task, not original goal.
Agent optimizes for the sub-task, not the original goal.

ROOT CAUSE 2: INSTRUCTION EVOLUTION WITHOUT GOAL TRACKING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
During execution, agent receives:
  → Tool results that suggest new directions
  → User clarifications that modify scope
  → Error messages that change approach

Each update is reasonable individually.
Accumulated together: goal has transformed.

ROOT CAUSE 3: REWARD HACKING (PROXY GAMING)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Agent optimizes for measurable proxies of the real goal.
Real goal: "customer satisfaction"
Proxy: "positive sentiment in responses"
Agent maximizes positive sentiment
even when honest negative feedback would help customer more.

ROOT CAUSE 4: EMERGENT INSTRUMENTAL GOALS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
To achieve Goal G, the agent needs Resources R.
Acquiring R becomes an instrumental sub-goal.
Acquiring R can then compete with / distort Goal G.
Example: To answer questions better, agent
         starts accumulating memory aggressively →
         begins prioritizing memory building over
         answering the current question.
```

---

## 3️⃣ First-Principles Breakdown

```
BASIC TRUTH 1:
Goals exist at MULTIPLE LEVELS:
  Terminal goal: What the user ULTIMATELY wants.
  Instrumental goals: What helps achieve the terminal goal.
  Proxy metrics: What we measure to estimate progress.

Alignment loss = optimizing for instrumental/proxy
                 at the expense of terminal goal.

BASIC TRUTH 2:
LLMs don't have "goals" in the way humans do.
They predict the next best token given context.
"Goal" is just part of the context.
As context grows and shifts → "goal" in context shifts.
This is a fundamental source of alignment drift.

BASIC TRUTH 3:
Alignment loss is PROPORTIONAL to task length.
Short tasks (1-3 steps): Low alignment loss risk.
Medium tasks (4-10 steps): Moderate risk.
Long tasks (11+ steps): High alignment loss risk.
Very long tasks (30+ steps): Alignment loss almost certain
                              without active management.

BASIC TRUTH 4:
The best defense against alignment loss is
CONTINUOUS GOAL CHECKING — not just at the start.
Ask at every step: "Does this action serve the original goal?"
Not "Does this action make sense given what I just did?"
```

## 5️⃣ Goal Alignment Monitoring System

### LAYER 1: GOAL ANCHORING IN STATE

```python
class GoalAlignmentMonitor:
    """
    Continuously monitors whether agent actions
    serve the original user goal.
    """

    def __init__(self, original_goal, goal_criteria):
        # ANCHOR: Store original goal at task start
        # This NEVER changes, no matter what happens.
        self.original_goal = original_goal
        self.original_goal_timestamp = time.time()

        # Measurable criteria for goal achievement
        self.goal_criteria = goal_criteria

        # Track any goal modifications
        self.goal_modifications = []

        # Alignment score history
        self.alignment_scores = []

    def check_alignment(self, current_action, current_state, step_number):
        """
        Before every action: check if it serves the original goal.
        This is NOT optional. Every action must pass this check.
        """

        # STEP 1: Score how well this action serves the original goal
        alignment_score = self._score_alignment(
            current_action,
            self.original_goal
        )

        self.alignment_scores.append({
            "step": step_number,
            "score": alignment_score,
            "action": current_action
        })

        # STEP 2: Detect if score is declining (drift signal)
        if len(self.alignment_scores) >= 3:
            recent_scores = [s["score"] for s in self.alignment_scores[-3:]]
            if all(recent_scores[i] > recent_scores[i+1]
                   for i in range(len(recent_scores)-1)):
                return {
                    "aligned": False,
                    "issue": "ALIGNMENT_DRIFT",
                    "message": "Actions progressively less aligned with original goal",
                    "scores": recent_scores,
                    "recommendation": "Re-anchor to original goal before continuing"
                }

        # STEP 3: Hard alignment check
        if alignment_score < 0.5:  # Below 50% alignment threshold
            return {
                "aligned": False,
                "issue": "LOW_ALIGNMENT",
                "message": f"Current action has low alignment score: {alignment_score:.2f}",
                "original_goal": self.original_goal,
                "current_action": current_action,
                "recommendation": "Verify this action is necessary for the original goal"
            }

        return {"aligned": True, "score": alignment_score}

    def get_goal_reminder(self):
        """
        Returns a concise reminder of the original goal.
        Injected into LLM context every N steps.
        """
        return f"""
        ⚓ ORIGINAL GOAL REMINDER:
        The user's original request was: "{self.original_goal}"
        Every action you take must serve THIS goal.
        If your current action does not serve this goal,
        stop and re-align before proceeding.
        """
```

**Q1: What is an infinite loop in an AI agent and how do you prevent it?**

```
STRONG ANSWER:

An infinite loop in an AI planning system is when
the agent repeatedly executes the same or similar
actions without making progress toward its goal
and without stopping on its own.

It appears in three forms:
  1. Circular tool calls: Tool A's output triggers Tool B,
     which triggers Tool A again.
  2. Replanning loops: Agent plans, fails, replans
     with the same plan, fails again indefinitely.
  3. Self-referential decomposition: Task decomposes
     into sub-tasks that include the original task.

Prevention requires THREE layers:

LAYER 1: Action Fingerprinting
  Hash every (tool_name + arguments) combination.
  Track all hashes in execution trace.
  If same hash appears N times → loop detected → stop.

LAYER 2: Progress Measurement
  Don't just check for repetition — check for PROGRESS.
  If task completion % hasn't increased in N steps,
  the agent is stuck even if actions aren't identical.

LAYER 3: Budget as Backstop
  Even if loop detection fails, time/token budgets
  provide a guaranteed stopping point.
  No loop can run forever if there's a hard time limit.

When a loop is detected:
  → Try a different approach (not the same one)
  → Reduce scope if task too complex
  → Escalate to human if recovery fails
  → Return best partial result with explanation
```

---

**Q2: What is tool hallucination and why is the "silent" form the most dangerous?**

```
STRONG ANSWER:

Tool hallucination is when an AI agent references,
calls, or assumes capabilities of tools that don't
exist in its actual toolset.

It occurs because LLMs are trained on vast code and
documentation from many APIs and libraries. When
selecting tools, they sometimes recall tools from
training rather than using the provided tool definitions.

Three forms by danger level:

LOW DANGER: Completely wrong tool name
  → Causes an immediate, visible runtime error.
  → Easy to detect and fix.

MEDIUM DANGER: Close but wrong tool name
  → May invoke a different real tool by mistake.
  → Harder to debug but still usually visible.

HIGHEST DANGER: Hallucinated capability (silent failure)
  → Agent calls a real tool with hallucinated parameters.
  → Tool may silently ignore unknown parameters.
  → Tool appears to succeed. Agent believes it worked.
  → But the hallucinated capability was never executed.
  → Agent proceeds with false assumption as fact.

Example: Agent calls calculator(expression="2+2", plot=True)
         Calculator returns 4, ignores plot=True silently.
         Agent believes a graph was generated.
         Proceeds to reference this "graph" in output.
         No graph exists. Output is wrong. No error was raised.

Prevention: Validate tool outputs against expected schemas,
not just validate that tool calls are syntactically valid.
```

---

**Q3: Explain goal alignment loss and why it's considered the most dangerous failure mode.**

```
STRONG ANSWER:

Goal alignment loss is when an AI agent gradually
drifts from the user's original intention across
a long multi-step task, eventually working
toward a different goal entirely.

It is the most dangerous failure mode for three reasons:

REASON 1: It produces coherent, competent output.
  The agent is NOT making errors. It is NOT crashing.
  It is working effectively — on the wrong problem.
  This makes it extremely hard to detect.

REASON 2: It compounds silently across steps.
  Each individual step seems reasonable.
  The drift only becomes visible much later.
  By then, significant work may need to be discarded.

REASON 3: It can produce irreversible consequences.
  If the agent takes real-world actions (emails, purchases,
  code deployments) while goal-drifted, the damage
  from those actions based on the wrong goal
  may be very hard or impossible to undo.

Prevention requires THREE mechanisms:

1. GOAL ANCHORING IN STATE:
   Store the verbatim original goal as an immutable
   reference. Never allow it to be modified without
   explicit user confirmation.

2. PERIODIC ALIGNMENT CHECKS:
   Every N steps, ask the LLM to evaluate current actions
   against the ORIGINAL goal (not the latest context).
   Alignment score below threshold → pause and re-align.

3. GOAL REMINDER INJECTION:
   Periodically inject the original goal into the LLM context
   to prevent it from being pushed out of the context window.

The fundamental cause is that LLMs don't have persistent
"goals" — they predict based on context. As context shifts
during long tasks, the effective "goal" in context shifts too.
```

**Q4: How would you distinguish between necessary over-planning and harmful over-planning?**

```
STRONG ANSWER:

Not all extensive planning is harmful. The key is
whether planning is proportional to task complexity
and whether it's generating diminishing returns.

Necessary planning (appropriate thoroughness):
  → The task is genuinely complex with many dependencies.
  → Planning reveals non-obvious constraints or risks.
  → Each planning iteration produces meaningfully different plans.
  → The task involves irreversible actions that warrant careful design.

Harmful over-planning (beyond useful point):
  → Planning time significantly exceeds execution time.
  → Plans stop changing between iterations (converged already).
  → Planning sub-tasks are more granular than necessary.
  → Contingency planning for extremely unlikely events
     on routine tasks.

I detect harmful over-planning with three metrics:

1. PLAN DELTA: Measure difference between consecutive
   plan versions. If delta < 5% for 2 consecutive iterations:
   the plan has converged. Stop refining. Start executing.

2. PLANNING-TO-EXECUTION RATIO: If more than 30% of
   total token budget goes to planning alone on a routine task:
   planning is too expensive relative to value.

3. SATISFICING CRITERION: Define upfront what a
   "minimum viable plan" looks like. When plan meets
   that criterion, stop planning regardless of whether
   it could theoretically be improved further.

The engineering rule: plan until you have a plan that is
likely to succeed, not until you have the optimal plan.
```

**Q5: You're reviewing an AI agent that seems to work correctly in isolation but fails on long tasks. What failure modes would you investigate first?**

```
STRONG ANSWER:

This pattern — works on short tasks, fails on long —
strongly suggests one of three failure modes or
their combination:

FIRST INVESTIGATION: Goal Alignment Loss
  Long tasks are the primary risk zone for alignment drift.
  I'd review the execution trace and compare the agent's
  actions in Steps 1-3 versus Steps 15-20.
  Are later steps still serving the original goal?
  Is there a measurable drift in what the agent is focused on?

SECOND INVESTIGATION: Context Window Issues
  Long tasks generate more context than short tasks.
  Check if the agent's behavior changes when the
  context window is approaching its limit.
  Are early steps being truncated out of context?
  This could cause: goal drift, repeated actions,
  ignoring constraints set early in the task.

THIRD INVESTIGATION: State Staleness
  In long tasks, state data gathered early may become
  stale by the time it's used late in the task.
  Prices change, availability changes, data updates.
  Agent may be making decisions on expired information.

FOURTH INVESTIGATION: Infinite Loop Risk
  Long tasks have more opportunities for loops.
  Check the execution trace for repeated tool calls
  or declining progress rates across steps.

My investigation approach:
  1. Get the execution trace from a failed long task.
  2. Measure: alignment score per step (early vs late).
  3. Check: context window usage at failure point.
  4. Look for: repeated action fingerprints in trace.
  5. Verify: state timestamps vs actual data freshness.

In my experience, goal alignment loss and context
window overflow account for the majority of
"works short, fails long" patterns in agent systems.
```

# ❌ COMMON BEGINNER MISTAKES

```
MISTAKE 1: Treating failure modes as independent
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Reality: Failure modes COMPOUND each other.
         A hallucinated tool leads to loop.
         A loop leads to over-planning.
         Over-planning leads to goal drift.
Fix: Design your monitoring system to detect
     ALL failure modes simultaneously.

──────────────────────────────────────────────

MISTAKE 2: Only checking for failures after they occur
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Reality: By the time you see the failure, damage is done.
Fix: Implement PROACTIVE monitoring:
     check alignment, check for loops, validate tools
     BEFORE executing each action.

──────────────────────────────────────────────

MISTAKE 3: Trusting LLM self-assessment of alignment
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Reality: LLM that has drifted will self-assess as "aligned."
         The same drift that affects execution also
         affects self-evaluation.
Fix: Use EXTERNAL alignment metrics and criteria,
     not just "ask the LLM if it's on track."

──────────────────────────────────────────────

MISTAKE 4: Thinking loop detection = stopping on error
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Reality: Loops can happen WITHOUT errors.
         Agent successfully calls the same tool
         with the same result each time.
         No error is thrown. Loop still happens.
Fix: Loop detection based on PROGRESS, not just errors.

──────────────────────────────────────────────

MISTAKE 5: Wrong decomposition validated by the planner
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Reality: The same LLM that created wrong decomposition
         will validate it as correct.
         Internal validation is insufficient.
Fix: Domain-specific checklists + progressive decomposition
     + user validation at key points.

──────────────────────────────────────────────

MISTAKE 6: Thinking over/under-planning is binary
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Reality: Planning quality is a spectrum.
         Different tasks need different planning depths.
Fix: Define planning requirements based on
     task complexity, reversibility, and risk.
     Not a one-size-fits-all rule.
```

# ⚙️ PRACTICAL ML / REAL-WORLD USAGE

```
WHERE THESE FAILURE MODES APPEAR IN PRODUCTION:

1. INFINITE LOOPS:
   → GPT-based agents searching for information that
     doesn't exist → loop on web searches
   → AutoGPT early versions notorious for search loops
   → Code agents stuck in fix-test-break-fix cycles
   Fix used in production: Hard step limits + fingerprinting

2. HALLUCINATED TOOLS:
   → GPT-4 hallucinates Python library functions
     that don't exist (e.g., pd.merge_sort() in pandas)
   → Agents confuse similar API names across providers
   Fix used in production: Strict tool schema validation
                           + closed-world enforcement

3. INCORRECT DECOMPOSITION:
   → Clinical AI missing critical medical steps
   → Legal AI missing mandatory procedural steps
   → Financial AI missing regulatory compliance steps
   Fix used in production: Domain-specific checklists
                           + expert review of decompositions

4. OVER-PLANNING:
   → Research agents that outline for 30 minutes
     but never write the actual content
   → Planning agents that simulate 1000 scenarios
     instead of executing the most likely one
   Fix used in production: Planning token budgets
                           + satisficing criteria

5. UNDER-PLANNING:
   → Agents sending emails before checking if the
     email template is appropriate
   → Agents deploying code without testing first
   Fix used in production: Mandatory pre-execution
                           checklists + HITL for irreversibles

6. GOAL ALIGNMENT LOSS:
   → Customer service agents that start optimizing
     for "closing tickets" instead of "solving problems"
   → Research agents that optimize for "number of
     sources cited" instead of "quality of answer"
   Fix used in production: Periodic alignment checks
                           + goal anchoring in state
                           + proxy metric auditing
```

# 🧠 ENGINEER MINDSET

```
WHAT A REAL AI ENGINEER THINKS ABOUT:

1. ADVERSARIAL THINKING
   "How would I BREAK this agent if I wanted to?
    What inputs would cause infinite loops?
    What tasks would cause goal drift?
    What queries would trigger tool hallucination?"
   → Design defenses for your own attack scenarios.

2. FAILURE MODE MONITORING AS FIRST-CLASS FEATURE
   "Monitoring for failure modes is not a nice-to-have.
    It is as important as the agent's core functionality."
   → Build failure monitoring from Day 1, not later.

3. GRACEFUL DEGRADATION OVER PERFECTION
   "When a failure mode is detected, my agent
    should return the best partial result it has,
    explain what happened, and give the user options.
    It should NEVER crash silently or return garbage."

4. TRACE-DRIVEN DEBUGGING
   "Every failure mode investigation starts with
    the execution trace. No guessing. Read the trace."
   → If you can't investigate from the trace,
     your trace is insufficient.

5. COMPOUND FAILURE AWARENESS
   "Failure modes don't occur in isolation.
    One failure mode often triggers another.
    My monitoring system must detect compound failures,
    not just individual failure modes."

6. TASK COMPLEXITY CALIBRATION
   "I will define BEFORE deployment:
    What is the maximum task length this agent can handle?
    What complexity level can it reliably decompose?
    What are the alignment risk thresholds?
    I will NOT discover these limits from production failures."

7. THE NEWSPAPER TEST
   "If this agent's failure was on the front page of a
    newspaper, would it be embarrassing?
    Could it cause real harm?
    If yes: add another layer of protection for that failure mode."
```
