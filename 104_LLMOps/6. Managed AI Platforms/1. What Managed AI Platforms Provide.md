# 🏗️ PILLAR 1: Data Sourcing Policies

## What Is It?

**Simple English:**
Data Sourcing Policy = **The rules about WHERE your data comes from and WHETHER you are allowed to use it.**

Before a single byte of data enters your LLM pipeline, you must answer:

```
✅ Did users CONSENT to this data being used?
✅ Is the source LEGAL to use? (No copyright violations)
✅ Is the data ACCURATE and TRUSTWORTHY?
✅ Does the data have KNOWN BIASES we must document?
✅ Is there a DATA LINEAGE trail? (Where did it come from?)
```

---

## 🔍 First Principles — Why Does This Matter?

```
Basic Truth:
Garbage In → Garbage Out

Biased Data In → Biased AI Out
Private Data In → Privacy Violation Out
Illegal Data In → Legal Liability Out
```

---

## 🌍 Real-World Analogy

Think of your data like **ingredients in a restaurant kitchen**:

- You need to know WHERE every ingredient came from
- You need to know it is SAFE (no contamination)
- You need to know you have PERMISSION to use it (no stolen goods)
- You need to track it if there's a RECALL (data breach)

This is exactly what **Data Sourcing Policy** does — it's the **food safety certification for your AI's data**.

---

## 📋 The 5 Key Components of Data Sourcing Policy

### Component 1: Consent & Legal Basis

```
Before using ANY user data, you must have ONE of:

✅ Explicit Consent → "I agree to share my data"
✅ Contractual Need → "We need this to provide the service"
✅ Legal Obligation → "Law requires us to process this"
✅ Legitimate Interest → (Rare, must be documented carefully)
```

> 🔑 GDPR requires you to document the **legal basis** for processing EVERY type of data.

---

### Component 2: Data Classification

Use data discovery and classification tools to scan repositories for sensitive information like PII or financial data, automating the initial and ongoing classification effort.

```
Data Classification Levels:

🔴 RESTRICTED   → Medical records, SSN, passwords
                  (Highest protection, limited access)

🟠 CONFIDENTIAL → User emails, IP addresses, usage logs
                  (Strong protection, role-based access)

🟡 INTERNAL     → Product documentation, model configs
                  (Standard protection, employee access)

🟢 PUBLIC       → Marketing content, public FAQs
                  (Minimal protection, open access)
```

---

### Component 3: Data Lineage

**What is Data Lineage?**
It is a **complete family tree** of your data — tracking exactly where it came from, how it was transformed, and where it went.

```
DATA LINEAGE EXAMPLE:

Source: Customer Support Chat Logs
    ↓ [Collected via API]
Raw Storage: S3 Bucket (encrypted)
    ↓ [PII Removed by Presidio]
Cleaned Dataset: Training Database
    ↓ [Fine-tuned]
Model: LLaMA-3-Customer-Support-v2
    ↓ [Deployed]
Production API: chatbot.company.com

Each step → LOGGED with timestamp + who approved
```

> 🧠 Why does this matter? If a **data breach** happens, you can immediately trace which model was trained on which data — and who is at risk.

---

### Component 4: Third-Party Data Contracts

If you use **external data sources** (APIs, scraped web data, purchased datasets):

```
✅ Review Terms of Service — can you use it for AI training?
✅ Sign Data Processing Agreements (DPAs)
✅ Verify data quality and bias levels
✅ Document the data source in model card
```

> ⚠️ **Real Example:** Many companies scraped Common Crawl data to train LLMs without checking copyright — now facing lawsuits. **Data sourcing policy prevents this.**

---

### Component 5: Ongoing Review

Data's context and sensitivity can change. Schedule annual or semi-annual reviews to update classifications and ensure the policy remains aligned with business needs and regulatory requirements.

# 🏗️ PILLAR 2: Data Retention Rules

## What Is It?

**Simple English:**
Data Retention = **How long you keep different types of data — and what you do with it after that time expires.**

The rule is simple:
```
Keep data ONLY as long as you NEED it.
Delete it when you DON'T.
```

Retention policies define how long data is stored, managed, and securely disposed of.

---

## 🌍 Real-World Analogy

Think of data retention like **food expiration dates in a fridge**:

- Milk expires in 7 days → throw it out
- Frozen beef can last 6 months → keep it
- Leftovers after 3 days → dangerous, must go

Similarly, different types of data have different "expiration dates" based on **legal requirements** and **business needs**.

---

## 📋 Retention Schedule — Real Example

A practical retention schedule looks like this:

| Data Category | Active Retention | Archive Retention | Total |
|---------------|-----------------|-------------------|-------|
| Financial Transactions | 3 years | 4 years | 7 years (SOX, FINRA) |
| Customer PII | Relationship duration | +6 years | Relationship + 6 years (GDPR) |
| System Logs | 90 days | N/A | 90 days (Operational) |
| Marketing Data | 1 year | 2 years | 3 years |


---

## ⚖️ Regulations That Dictate Retention Rules

Key regulations include SOX (7 years), GDPR, PCI DSS, Dodd-Frank, GLBA, and SEC rule 17a-4.

```
For AI/LLM Systems specifically:

🏥 HIPAA (Healthcare)    → 6 years minimum
💰 SOX (Finance)         → 7 years
🇪🇺 GDPR (Europe)        → Only as long as needed
🛒 PCI DSS (Payments)    → 1-3 years depending on data type
🤖 EU AI Act             → Training data must be documented
```

---

## 🏗️ How to Build a Retention Policy — Step by Step

```
STEP 1: CLASSIFY
  → What type of data is this?
  → Is it PII? Financial? System logs?

STEP 2: FIND THE LAW
  → What regulation applies?
  → What's the minimum required retention?

STEP 3: SET THE SCHEDULE
  → Active retention period (hot storage)
  → Archive period (cold storage)
  → Deletion trigger date

STEP 4: AUTOMATE
  → Set automatic expiration on S3 buckets
  → Database TTL (Time To Live) fields
  → Automated deletion jobs

STEP 5: AUDIT
  → Regularly check compliance
  → Log all deletions with who approved
```

> 🚨 **Real Consequence:** IDDesign was fined DKK 1.5M for failing to delete personal data of 385,000 customers under GDPR.

---

## ⚠️ Failure Modes in Retention

No automation means manual deletion doesn't scale and creates compliance gaps. Ignoring legal holds means destroying data under legal hold creates massive liability.

```
COMMON MISTAKES:
❌ Keeping data "forever, just in case"
❌ Deleting data that is under legal hold (lawsuit)
❌ No automated process → humans forget
❌ Deleting backups but not primary copies
❌ Not documenting WHO approved the deletion
```

# 🏗️ PILLAR 3: PII Handling Policies

## What Is PII?

**PII = Personally Identifiable Information**
Any data that can identify a specific real person.

```
DIRECT PII (Strongly Identifies):
  👤 Full Name
  📧 Email Address
  📞 Phone Number
  🪪 Social Security Number (SSN)
  🆔 Passport / Driver's License
  💳 Credit Card Number

INDIRECT PII (Identifies When Combined):
  📍 ZIP Code + Age + Gender → Can identify a person
  🌐 IP Address
  🍪 Cookie / Session ID
  💻 Device Fingerprint
  📍 Location Data

SENSITIVE CATEGORY PII (Extra Protection):
  🏥 Health/Medical Data
  🧬 Biometric Data
  ⚖️ Criminal Records
  🛐 Religious Beliefs
  🏳️‍🌈 Sexual Orientation
```

---

## 🌍 Analogy — Why PII Is Dangerous in LLMs

Every time you paste a corporate document into ChatGPT or Claude to summarize a contract, that text may hide names, email addresses, phone numbers, government IDs, and credit card details. Those data leave your computer and end up on a third-party vendor's servers, often outside your own jurisdiction. That is exactly the problem Microsoft Presidio tries to solve: an open-source framework that spots personal information in a text and replaces it before the model ever sees it.

---

## 📋 PII Handling Policy — 4 Core Rules

### Rule 1: MINIMIZE
```
Collect ONLY the PII you absolutely need.
Ask yourself: "Do I REALLY need the user's 
full name to answer this question?"
If NO → don't collect it.
```

### Rule 2: ANONYMIZE / PSEUDONYMIZE
```
Before data enters the LLM:
  "John Doe, aged 45, living in New York"
       ↓ Presidio PII Removal
  "<PERSON>, aged <AGE>, living in <LOCATION>"

The LLM NEVER sees the real person's details.
```

### Rule 3: ENCRYPT
```
All PII must be encrypted:
  - At rest (stored in database) → AES-256
  - In transit (moving over network) → TLS 1.3
  - In use (in memory during processing) → Secure enclaves
```

### Rule 4: ACCESS CONTROL
```
Only people who NEED PII can SEE PII.
  - Doctor → Can see patient medical data
  - Customer service rep → Can see contact info
  - Data scientist → Cannot see raw PII (anonymized data only)
  - External vendor → Cannot see any PII
```

## 🔧 TOOL DEEP DIVE: Microsoft Presidio

### What Is Presidio?

Microsoft Presidio is an open-source framework that provides context-aware PII detection and anonymization for text, images, and other modalities.

Microsoft Presidio is an open-source framework that detects and anonymizes PII in text, images, and structured data. It has been around since 2019 and is actively maintained.

---

### 🔬 How Presidio Works — First Principles

Presidio has **TWO main engines**:

```
ENGINE 1: ANALYZER (Finds PII)
    ↓
ENGINE 2: ANONYMIZER (Removes/Masks PII)
```

The Analyzer finds PII. It combines named entity recognition (NER) from spaCy or Hugging Face transformers with regex pattern matching and contextual scoring. When you feed it text, it returns a list of detected entities with types, confidence scores, and character positions. It doesn't modify the text. It just tells you what it found.

The Anonymizer takes the analyzer's output and does something with it — replace detected names with `<PERSON>`, redact phone numbers entirely, mask credit card numbers with asterisks, hash emails, or encrypt values you need to reverse later.

---

### 🔬 Presidio Architecture — Deep Dive

Microsoft Presidio represents the current state of practice for enterprise PII detection. It combines regex-based recognisers with a spaCy NER backend, supporting configurable entity types through a plugin architecture. Its anonymiser module offers redaction, hashing, and masking.

```
TEXT INPUT:
"My name is John Smith, email: john@gmail.com,
 SSN: 123-45-6789, DOB: 01/15/1985"

     ↓ PRESIDIO ANALYZER

DETECTED ENTITIES:
[
  {entity: "PERSON",        text: "John Smith",     confidence: 0.97},
  {entity: "EMAIL_ADDRESS", text: "john@gmail.com", confidence: 0.99},
  {entity: "US_SSN",        text: "123-45-6789",    confidence: 0.98},
  {entity: "DATE_TIME",     text: "01/15/1985",      confidence: 0.91}
]

     ↓ PRESIDIO ANONYMIZER

ANONYMIZED OUTPUT:
"My name is <PERSON>, email: <EMAIL_ADDRESS>,
 SSN: <US_SSN>, DOB: <DATE_TIME>"
```

---

### 🔧 Presidio Anonymization Strategies

```
STRATEGY 1: REPLACE
  "John Smith" → "<PERSON>"
  (Simplest. Good for logging.)

STRATEGY 2: REDACT
  "John Smith" → ""
  (Removes entirely. Loss of context.)

STRATEGY 3: MASK
  "john@gmail.com" → "jo**@*****.com"
  (Partial hiding. Shows format only.)

STRATEGY 4: HASH
  "123-45-6789" → "a3f7d92bc1..."
  (One-way. Cannot reverse. Good for IDs.)

STRATEGY 5: ENCRYPT
  "John Smith" → "EncryptedValue_xyz"
  (Two-way. Can decrypt with key. Good for retrieval.)

STRATEGY 6: SYNTHETIC REPLACEMENT
  "John Smith" → "Robert Johnson"
  (Replace with fake but realistic data.)
```

---

### 💻 Presidio Code — Step by Step

```python
# Step 1: Install
# pip install presidio-analyzer presidio-anonymizer
# python -m spacy download en_core_web_lg

from presidio_analyzer import AnalyzerEngine
from presidio_anonymizer import AnonymizerEngine

# Step 2: Initialize Engines
analyzer = AnalyzerEngine()
anonymizer = AnonymizerEngine()

# Step 3: Your text with PII
text = """
Hi, my name is Sarah Johnson. 
My email is sarah.johnson@company.com 
and my phone is +1-555-234-5678.
My SSN is 456-78-9012.
"""

# Step 4: Detect PII
results = analyzer.analyze(
    text=text,
    language="en"
)

print("DETECTED PII:")
for result in results:
    print(f"  Type: {result.entity_type}")
    print(f"  Text: {text[result.start:result.end]}")
    print(f"  Confidence: {result.score}")
    print()

# Step 5: Anonymize
anonymized_text = anonymizer.anonymize(
    text=text,
    analyzer_results=results
)

print("ANONYMIZED TEXT:")
print(anonymized_text.text)

# OUTPUT:
# ANONYMIZED TEXT:
# Hi, my name is <PERSON>.
# My email is <EMAIL_ADDRESS>
# and my phone is <PHONE_NUMBER>.
# My SSN is <US_SSN>.
```

---

### ⚠️ Presidio Failure Modes

Presidio's synthetic generation capability does not guarantee type-consistency, does not maintain cross-session uniqueness, and does not address the semantic coherence of the resulting text.

```
WHEN PRESIDIO FAILS:

❌ Unusual name formats → "O'Brien-McKenzie" might be missed
❌ Non-English languages → Weaker NER coverage
❌ Contextual PII → "She lives near the stadium" 
                    (location implied, not stated)
❌ Domain-specific IDs → Medical record numbers 
                         (needs custom recognizer)
❌ Indirect PII combinations → ZIP + Age + Gender combined
```

Presidio works best as a building block, not a standalone compliance solution.

# 🏗️ PILLAR 4: User Data Isolation

## What Is It?

**Simple English:**
User Data Isolation = **Making sure one user's data NEVER leaks into another user's context, memory, or responses.**

This is critical in **multi-tenant LLM systems** — where many different users or companies use the SAME AI system.

---

## 🌍 Analogy — Apartment Building

Think of a multi-tenant AI system like an **apartment building**:

```
🏢 APARTMENT BUILDING = Your LLM Platform

🏠 Apartment 1A = Company A (Tenant 1)
   └── Their data, their conversations

🏠 Apartment 1B = Company B (Tenant 2)
   └── Their data, their conversations

🏠 Apartment 1C = Company C (Tenant 3)
   └── Their data, their conversations

KEY RULE:
Tenant 1A can NEVER walk into Tenant 1B's apartment.
Company A can NEVER see Company B's conversations.
```

---

## 🔬 How Data Leaks Between Users — The Real Risk

**Scenario 1: Shared Vector Database (RAG system)**
```
❌ BAD DESIGN:
User A uploads: "My salary is $150,000"
     ↓ Stored in shared vector DB
User B asks: "What do people earn here?"
     ↓ RAG retrieves User A's document
AI replies: "Based on documents, $150,000"

User B just learned User A's private salary!
```

**Scenario 2: Shared Conversation Memory**
```
❌ BAD DESIGN:
Session memory not scoped to user_id
User A says: "My password is abc123"
Memory stored globally
User B's session → sees User A's memory
```

---

## 🔧 Data Isolation Techniques

### Technique 1: Tenant-Scoped Vector Databases

```python
# BAD: No isolation
results = vectordb.query(
    query="salary information",
    top_k=5
)

# GOOD: Tenant isolation with metadata filter
results = vectordb.query(
    query="salary information",
    top_k=5,
    filter={"tenant_id": current_user.tenant_id}  # ← KEY!
)
```

### Technique 2: Session-Scoped Memory

```python
# Each conversation MUST have unique session_id

from langchain.memory import ConversationBufferMemory

memory = ConversationBufferMemory(
    memory_key=f"chat_history_{user_id}_{session_id}",
    # Unique key per user per session
    # NEVER share memory objects between users
)
```

### Technique 3: Row-Level Security (Database)

```sql
-- PostgreSQL Row Level Security Example
-- Each row tagged with tenant_id

ALTER TABLE conversation_logs 
ENABLE ROW LEVEL SECURITY;

CREATE POLICY user_isolation ON conversation_logs
    USING (tenant_id = current_setting('app.current_tenant'));

-- Now User A CANNOT query User B's rows
-- Even if they try direct SQL injection
```

### Technique 4: Namespace Isolation (Vector DB)

```python
# Pinecone example - one namespace per tenant
import pinecone

# User A's documents go into their namespace
index.upsert(
    vectors=user_a_embeddings,
    namespace=f"tenant_{user_a.id}"  # ← Isolated!
)

# User B can ONLY query their namespace
index.query(
    vector=query_embedding,
    namespace=f"tenant_{user_b.id}",  # ← Their data only
    top_k=5
)
```

## 🔧 TOOL DEEP DIVE: IAM (Identity and Access Management)

### What Is IAM?

IAM = **The bouncer system** for your cloud infrastructure.
It controls:
- WHO can access WHAT resources
- With WHAT level of permission
- UNDER WHAT conditions

Enforcing strong access controls is one of the most effective ways to protect LLMs and sensitive data. Role-based access control (RBAC), multi-factor authentication (MFA), and proper API key management are essential components of LLMOps security.

---

### 🔬 IAM Across Cloud Providers

AWS uses IAM policies, SCPs, and Security Hub. Azure uses Azure AD, Conditional Access, and Defender for Cloud. GCP uses Cloud IAM, Organization Policies, and Security Command Center.

---

### AWS IAM — Deep Dive

```
AWS IAM CORE CONCEPTS:

👤 USER    → A person (has credentials: username + password)
🤖 ROLE    → A temporary identity (for services, not humans)
👥 GROUP   → A collection of users with shared policies
📋 POLICY  → A JSON document defining permissions

EXAMPLE POLICY:
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject"
      ],
      "Resource": "arn:aws:s3:::my-llm-data-bucket/*",
      "Condition": {
        "StringEquals": {
          "s3:prefix": "${aws:PrincipalTag/TenantID}/"
        }
      }
    }
  ]
}

TRANSLATION:
"Allow this role to GET and PUT objects in S3,
 BUT ONLY in the folder matching their TenantID"
```

---

### Principle of Least Privilege

```
GOLDEN RULE OF IAM:

Give every user/service ONLY the 
minimum permissions they need.
Nothing more.

❌ BAD:  Data Scientist has ADMIN access
✅ GOOD: Data Scientist can only READ training data

❌ BAD:  LLM service can DELETE any database
✅ GOOD: LLM service can only READ from specific tables

❌ BAD:  "Use long-lived access keys"
✅ GOOD: "Use short-lived role-based tokens"
```

Prefer IAM roles for workloads instead of long-lived access keys.

---

### IAM for LLM Systems — Practical Setup

Best practice AWS AI security starts with: AWS Nitro System for hardware-enforced isolation, AWS IAM for access control, AWS Key Management Service (KMS) for encryption, Amazon Bedrock Guardrails for prompt injection and PII filtering, and AWS CloudTrail for audit logging.

```python
# Example: Role-based access in your LLM API

        raise HTTPException(
            status_code=403,
            detail=f"Role {user_role.value} cannot perform: {action}"
        )
```

# 🏗️ PILLAR 5: Data Deletion Workflows

## What Is It?

**Simple English:**
Data Deletion Workflow = **A formal, documented, automated process to completely erase data — so it is permanently unrecoverable.**

This is NOT just pressing delete.

Using safeguards such as encryption can protect data whether it is in transit or at rest. Cloned data should be securely erased from all storage locations and backups.

---

## 🌍 Analogy — Destroying a Classified Document

Imagine a spy agency destroying a classified file:

```
❌ BAD WAY (Regular Delete):
  → Put file in recycling bin
  → Empty recycling bin
  → File still exists on disk as unallocated space
  → Anyone with recovery software can get it back

✅ GOOD WAY (Secure Delete):
  → Overwrite file 7 times with random data
  → Shred the physical paper
  → Burn the shreds
  → Log WHO destroyed it, WHEN, and WHY
  → Get signature from witness
```

Data deletion in LLMOps follows the same logic — but digitally.

---

## ⚖️ When Must You Delete? (The Triggers)

```
DELETION TRIGGERS:

1. 📋 USER REQUESTS IT (GDPR "Right to be Forgotten")
   → User clicks "Delete my account"
   → You have 30 days to delete ALL their data

2. ⏰ RETENTION PERIOD EXPIRES
   → System logs older than 90 days → auto-delete

3. 🏛️ LEGAL HOLD LIFTED
   → Data held for lawsuit → case closes → delete

4. 🤝 CONTRACT ENDS
   → B2B customer leaves → delete their data
   → Usually within 30-90 days of contract end

5. 🔒 SECURITY INCIDENT
   → Compromised data → delete and notify
```

---

## 🔬 The Complete Deletion Workflow — Step by Step

```
TRIGGER → User requests account deletion

STEP 1: VERIFY IDENTITY
  → Confirm it's really the user
  → Check for legal holds (active lawsuit?)
  → Log request with timestamp

STEP 2: LOCATE ALL DATA
  → Primary database (user profile)
  → Conversation history table
  → Vector database (user's embeddings)
  → Audit logs (anonymize, don't delete)
  → Backup systems
  → Third-party systems (analytics, CRM)
  → LLM fine-tuning datasets (if user data used)

STEP 3: EXECUTE DELETION
  → Delete primary records
  → Delete vector embeddings
  → Overwrite backups
  → Revoke API keys and tokens
  → Clear cached data (Redis/Memcached)

STEP 4: VERIFY DELETION
  → Query all systems to confirm data is gone
  → Check backup snapshots
  → Verify no cached copies remain

STEP 5: NOTIFY & LOG
  → Send confirmation email to user
  → Log: who deleted, what, when, how, verified by
  → Store deletion receipt (proof of compliance)
```

## 💻 Deletion Code Example

```python
import boto3
import psycopg2
from datetime import datetime

class DataDeletionWorkflow:
    
    def __init__(self, user_id: str):
        self.user_id = user_id
        self.deletion_log = []
    
    def delete_user_data(self):
        """
        Complete GDPR-compliant data deletion workflow
        """
        print(f"Starting deletion for user: {self.user_id}")
        
        # STEP 1: Check for legal holds
        if self._has_legal_hold():
            raise Exception("Cannot delete: Active legal hold")
        
        # STEP 2: Delete from PostgreSQL
        self._delete_from_database()
        
        # STEP 3: Delete from Vector DB (Pinecone)
        self._delete_from_vector_db()
        
        # STEP 4: Delete from S3 (uploaded files)
        self._delete_from_s3()
        
        # STEP 5: Clear cache (Redis)
        self._clear_cache()
        
        # STEP 6: Revoke API keys
        self._revoke_api_tokens()
        
        # STEP 7: Anonymize audit logs (don't delete)
        self._anonymize_audit_logs()
        
        # STEP 8: Log the deletion
        self._record_deletion_completion()
        
        return {
            "status": "deleted",
            "user_id": self.user_id,
            "timestamp": datetime.utcnow().isoformat(),
            "systems_cleaned": self.deletion_log
        }
    
    def _delete_from_database(self):
        conn = psycopg2.connect(DATABASE_URL)
        cursor = conn.cursor()
        
        # Delete in correct order (foreign keys!)
        cursor.execute("DELETE FROM conversation_messages WHERE user_id = %s", 
                      (self.user_id,))
        cursor.execute("DELETE FROM conversation_sessions WHERE user_id = %s", 
                      (self.user_id,))
        cursor.execute("DELETE FROM user_preferences WHERE user_id = %s", 
                      (self.user_id,))
        cursor.execute("DELETE FROM users WHERE id = %s", 
                      (self.user_id,))
        
        conn.commit()
        self.deletion_log.append("postgresql: deleted")
    
    def _delete_from_vector_db(self):
        # Delete user's embeddings from Pinecone
        import pinecone
        index = pinecone.Index("my-llm-index")
        
        # Delete all vectors in user's namespace
        index.delete(
            delete_all=True,
            namespace=f"user_{self.user_id}"
        )
        self.deletion_log.append("vector_db: deleted")
    
    def _delete_from_s3(self):
        s3 = boto3.client("s3")
        
        # List all objects with user's prefix
        response = s3.list_objects_v2(
            Bucket="user-uploads-bucket",
            Prefix=f"users/{self.user_id}/"
        )
        
        # Delete each object
        if "Contents" in response:
            for obj in response["Contents"]:
                s3.delete_object(
                    Bucket="user-uploads-bucket",
                    Key=obj["Key"]
                )
        
        self.deletion_log.append("s3: deleted")
    
    def _anonymize_audit_logs(self):
        # NOTE: We CANNOT delete audit logs (compliance)
        # We ANONYMIZE them instead
        conn = psycopg2.connect(DATABASE_URL)
        cursor = conn.cursor()
        
        cursor.execute("""
            UPDATE audit_logs 
            SET user_id = 'DELETED_USER',
                ip_address = 'ANONYMIZED',
                user_email = 'ANONYMIZED'
            WHERE user_id = %s
        """, (self.user_id,))
        
        conn.commit()
        self.deletion_log.append("audit_logs: anonymized (kept for compliance)")
```

## 🔧 TOOL DEEP DIVE: KMS (Key Management Service)

### What Is KMS?

**Simple English:**
KMS = **A secure safe that holds the secret keys used to lock and unlock your encrypted data.**

Think of it like this:

```
Your Data = A secret document
Encryption Key = The padlock
KMS = A bank vault where padlocks are stored

Even if someone STEALS your encrypted data,
they CANNOT read it without the key.
The key is safely stored in KMS.
```

---

### 🔬 How KMS Works — First Principles

```
ENCRYPTION FLOW:

PLAIN TEXT DATA: "John Smith, SSN: 123-45-6789"
        ↓
[KMS GENERATES ENCRYPTION KEY]
        ↓
ENCRYPTED DATA: "xKd92pLm4nR8..."
        ↓
Store encrypted data in S3/Database
Store encryption key in KMS (NOT with data!)

DECRYPTION FLOW:

Request: "I need to decrypt this"
        ↓
[IAM CHECK: Do you have permission to use this key?]
        ↓
YES → KMS releases key temporarily
        ↓
Data decrypted in memory
        ↓
Key never leaves KMS permanently
```

---

### Three Cloud KMS Options

Encryption for data at rest and in transit is vital. AWS provides services such as AWS Key Management Service (KMS) and CloudHSM to help manage cryptographic keys effectively.

GCP takes encryption seriously with its default encryption at rest and offers robust services like Cloud Key Management Service (KMS) to manage cryptographic keys, helping ensure data confidentiality and integrity throughout its lifecycle.

```
┌──────────────┬────────────────────┬──────────────────┐
│ Provider     │ Service Name       │ Key Feature      │
├──────────────┼────────────────────┼──────────────────┤
│ AWS          │ AWS KMS            │ Deep AWS         │
│              │                    │ integration +    │
│              │                    │ CloudTrail logs  │
├──────────────┼────────────────────┼──────────────────┤
│ Google Cloud │ Cloud KMS          │ CMEK for         │
│              │                    │ all GCP services │
├──────────────┼────────────────────┼──────────────────┤
│ Azure        │ Azure Key Vault    │ Secrets +        │
│              │                    │ Certificates     │
│              │                    │ + Keys together  │
└──────────────┴────────────────────┴──────────────────┘
```

Data at rest is encrypted with AES-256, data in transit with TLS 1.2 or higher, with optional customer-managed keys (CMKs) in AWS KMS.

---

### KMS Best Practices

Use customer-managed keys where required, rotate keys on schedule, and restrict key usage with least privilege policies.

```
KMS GOLDEN RULES:

✅ Rule 1: ROTATE KEYS REGULARLY
   → Set automatic key rotation (every 90-365 days)
   → Old data re-encrypted with new key

✅ Rule 2: SEPARATE KEYS BY PURPOSE
   → One key for user PII
   → One key for system logs
   → One key for model weights
   (If one key compromised → limited blast radius)

✅ Rule 3: LOG ALL KEY USAGE
   → Every time a key is used → log it
   → Who used it, when, for what data

✅ Rule 4: NEVER HARDCODE KEYS IN CODE
   ❌ BAD:  API_KEY = "sk-abc123xyz"  (in code!)
   ✅ GOOD: API_KEY = os.getenv("API_KEY")
            Or: aws_secrets_manager.get_secret("api_key")

✅ Rule 5: ENCRYPT EVERYTHING
   → Data at rest (S3, databases)
   → Data in transit (TLS/HTTPS)
   → Data in use (secure enclaves where possible)
```

### 💻 KMS Code Example — AWS

```python
import boto3
import json
import base64

# Initialize KMS client
kms_client = boto3.client('kms', region_name='us-east-1')

# Your KMS key ID (stored in environment variable!)
KEY_ID = os.getenv('KMS_KEY_ID')  # Never hardcode!

def encrypt_pii(plaintext_data: str) -> str:
    """
    Encrypt sensitive PII using AWS KMS
    """
    response = kms_client.encrypt(
        KeyId=KEY_ID,
        Plaintext=plaintext_data.encode('utf-8')
    )
    
    # Return base64 encoded encrypted bytes
    encrypted = base64.b64encode(
        response['CiphertextBlob']
    ).decode('utf-8')
    
    return encrypted

def decrypt_pii(encrypted_data: str) -> str:
    """
    Decrypt PII - only roles with KMS:Decrypt permission can do this
    """
    ciphertext = base64.b64decode(encrypted_data)
    
    response = kms_client.decrypt(
        CiphertextBlob=ciphertext
    )
    
    return response['Plaintext'].decode('utf-8')

# Usage Example:
user_ssn = "123-45-6789"

# Encrypt before storing
encrypted_ssn = encrypt_pii(user_ssn)
print(f"Stored in DB: {encrypted_ssn}")  
# → "AQICAHh23..."

# Only authorized roles can decrypt
decrypted_ssn = decrypt_pii(encrypted_ssn)
print(f"Decrypted: {decrypted_ssn}")  
# → "123-45-6789"
```

## 🔧 TOOL DEEP DIVE: DLP (Data Loss Prevention)

### What Is DLP?

**Simple English:**
DLP = **A security system that watches all data movement and STOPS sensitive data from going where it shouldn't.**

```
WHAT DLP MONITORS:

📤 Data going OUT:
  → Emails leaving the company
  → Files uploaded to cloud
  → API responses to users
  → Copy-paste in browsers

📥 Data coming IN:
  → Files uploaded by users (malware + PII check)
  → Prompt injection attempts

🔄 Data moving INSIDE:
  → Data moving between systems
  → Database queries
  → Log exports
```

---

### DLP in LLM Systems — Specific Use Cases

```
USE CASE 1: Pre-LLM Input Scan
  User types prompt → DLP scans it
  → Credit card found → BLOCK + ALERT
  → Confidential doc pasted → WARN + LOG

USE CASE 2: LLM Output Scan
  LLM generates response → DLP scans it
  → Response contains employee salary → REDACT
  → Response contains source code → BLOCK

USE CASE 3: Training Data Scan
  Before fine-tuning → DLP scans all training data
  → PII found → Remove or pseudonymize
  → Copyright content found → Flag for review

USE CASE 4: Log Export Control
  Engineer exports logs → DLP checks
  → Log contains user conversations → BLOCK
  → Require anonymization first
```

> 🧠 **Key Insight:** Cloud DLP sends your text to the cloud for scanning — which can itself be a privacy risk for ultra-sensitive data. In those cases, use **on-premise tools like Presidio**.

# ⚠️ FAILURE MODES — Complete Summary

| Failure | Cause | Prevention |
|---------|-------|-----------|
| PII leaks into LLM | No pre-prompt scan | Presidio before LLM call |
| Cross-user data leak | No tenant isolation | Namespace + row-level security |
| Data over-retained | No retention policy | Automated TTL jobs |
| Key compromise | Long-lived keys, no rotation | KMS + auto-rotation |
| Audit gaps | Incomplete logging | Log every API call |
| GDPR violation | No deletion workflow | Automated deletion pipeline |
| Training data PII | Raw data used | DLP scan before fine-tuning |
| Access escalation | Too many permissions | Least privilege IAM |

There is a need to regularly audit the data pipelines and model outputs for privacy risks. Though most issues can be picked up in an automated way, occasionally a human has to review the case for records when sensitive data is embedded in unstructured forms such as text or images.

# 💬 Strong Interview Answers

### Q: "How do you handle PII in an LLM pipeline?"

✅ **Strong Answer:**
> "I implement PII protection at three layers. First, at the INPUT layer — I use Microsoft Presidio before every LLM call to detect and anonymize PII in user prompts. Second, at the STORAGE layer — all data containing PII is encrypted with KMS customer-managed keys, with separate keys per data category. Third, at the OUTPUT layer — I run Presidio again on LLM responses to catch any PII that appears in the output. Beyond that, I implement strict data retention policies with automated deletion, role-based IAM controls so only authorized roles can decrypt PII, and comprehensive audit logs for every data access event."

---

### Q: "How do you implement user data isolation in a RAG system?"

✅ **Strong Answer:**
> "I implement isolation at three levels. At the vector database level, I use namespace partitioning — each tenant gets their own isolated namespace, and all queries are scoped with a mandatory tenant_id filter. At the application level, all session memory is keyed by user_id plus session_id, preventing any shared state between users. At the database level, I use Row Level Security in PostgreSQL with tenant_id policies so even raw queries can never retrieve another tenant's rows. Finally, I enforce this with IAM policies that give each tenant service account access only to their own S3 prefix and database schema."

# ⚠️ Common Beginner Mistakes

| Mistake | Why It's Wrong | Correct Approach |
|---------|---------------|-----------------|
| "I'll just delete from the main table" | Copies exist in backups, logs, caches | Delete from ALL systems + verify |
| "Encryption is enough for compliance" | Also need access control + audit | Encrypt + IAM + Audit = Compliance |
| "Presidio catches all PII" | It misses contextual and indirect PII | Presidio + human review + DLP |
| "One KMS key for everything" | Large blast radius if compromised | Separate keys per data type |
| "Users in same vector DB namespace" | Cross-tenant leakage risk | One namespace per tenant |
| "Delete means DELETE button" | File still recoverable on disk | Cryptographic erasure / overwrite |

# 🧑‍💻 Engineer Mindset — Senior AI Engineer Checklist

```
🧠 Before Every Data Decision, Ask:

□ "What is the minimum data I need?" (Minimize)
□ "Who has access to this data?" (Least privilege IAM)
□ "Is PII being stripped before the LLM sees it?" (Presidio)
□ "Is this encrypted at rest AND in transit?" (KMS + TLS)
□ "How long are we keeping this?" (Retention policy)
□ "Can user A accidentally see user B's data?" (Isolation)
□ "Can we delete this fully if asked?" (Deletion workflow)
□ "Is every data access logged?" (Audit trail)
□ "What law applies to this data?" (GDPR/HIPAA/etc.)
□ "What happens if we're breached?" (Incident response)
```

Cloud security for LLMs depends on architecture and governance as much as platform choice. You need private endpoints, least-privilege IAM, strong encryption, careful logging, and a plan for prompt injection and data leakage.
