## 🤔 Before I Explain — Let Me Ask You First

> **"What do you think 'Request & Trace Logging' means in an LLM system?"**

A beginner might say:
> *"It's just saving the user's question and the AI's answer to a database, right?"*

That is **5% of the truth.**

Here's the **reality:**

When a user sends one message to your AI app, what actually happens is NOT one simple step. It's a **chain of 10–20 hidden operations** happening inside your system — retrieving documents, building prompts, calling tools, calling models, formatting outputs — and **every single step can silently fail or produce garbage.**

Request & Trace Logging is the system that **captures every single one of those hidden steps** — in real time — so you can debug, improve, and trust your AI.

Let's build this from absolute zero. 🏗️

## 📦 SECTION 1: What Is Request & Trace Logging?

### 🇬🇧 Simple English

| Term | Simple Meaning |
|---|---|
| **Request** | One user interaction — a question sent to your AI |
| **Log** | A permanent record of something that happened |
| **Trace** | The complete journey of ONE request through your entire system |
| **Request Logging** | Recording what came IN and what went OUT |
| **Trace Logging** | Recording every hidden step IN BETWEEN |

```
WITHOUT Logging:          WITH Logging:
```

With Request & Trace Logging:

**This is why logging is not optional — it is the foundation of everything.**

## 🔬 SECTION 3: First-Principles Breakdown

### 🧱 Building Block 1: What is a "Request" in an LLM system?

A request is not just `user_message → AI_response`. In a real system, one user message triggers a **tree of operations:**

```
User Message: "What is the refund policy for order #1234?"
│
├── [Auth Check] — Is this user logged in?
├── [Prompt Builder] — Build system prompt + user message
├── [Retriever] — Search knowledge base for "refund policy"
│   ├── [Embedding model called]
│   └── [Vector DB queried]
├── [Context Builder] — Combine retrieved docs + user message
├── [LLM Call] — Send to GPT-4
│   ├── [Tokens counted]
│   ├── [Temperature set]
│   └── [Response streamed]
├── [Tool Call] — Look up order #1234 in database
├── [Output Parser] — Format the response
└── [Final Response] — Sent back to user
```

**Every single arrow above** is something that can fail, be slow, be wrong, or cost money.

**Request & Trace Logging captures all of it.**

---

### 🧱 Building Block 2: What is a Trace?

A **Trace** is the complete record of one request's journey from start to finish.

Think of it as a **story with chapters:**
- The whole story = **Trace**
- Each chapter = **Span**
- Details inside a chapter = **Attributes / Tags**

```
TRACE: user_request_abc123
├── SPAN: prompt_builder (duration: 12ms)
│   ├── attribute: system_prompt_length = 450 tokens
│   └── attribute: user_message = "What is the refund..."
│
├── SPAN: retrieval (duration: 234ms)
│   ├── attribute: query = "refund policy"
│   ├── attribute: docs_retrieved = 3
│   └── attribute: top_score = 0.87
│
├── SPAN: llm_call (duration: 1200ms)
│   ├── attribute: model = "gpt-4-turbo"
│   ├── attribute: input_tokens = 890
│   ├── attribute: output_tokens = 245
│   └── attribute: cost = $0.034
│
└── SPAN: output_parser (duration: 5ms)
    └── attribute: response_length = 180 chars
```

---

### 🧱 Building Block 3: Spans are the atoms of tracing

| Property | What it is | Example |
|---|---|---|
| **Name** | What step this is | `"llm_call"` |
| **Start time** | When step started | `14:32:01.234` |
| **End time** | When step ended | `14:32:02.456` |
| **Duration** | How long it took | `1222ms` |
| **Status** | Success or error | `OK` / `ERROR` |
| **Attributes** | Key-value data | `model="gpt-4"` |
| **Parent span** | Which step created this | `retrieval_span` |
| **Trace ID** | Which trace it belongs to | `abc123` |

## 🏛️ COMPONENT 1: Full Prompt Logging

### What Is It?

Full prompt logging means recording **the complete text** that was sent to the LLM model — not just the user's question, but the **entire input including:**

```
┌─────────────────────────────────────────────────┐
│             FULL PROMPT (What LLM Sees)          │
│                                                  │
│  SYSTEM PROMPT:                                  │
│  "You are a helpful customer service agent       │
│   for TechCorp. Be concise. Do not make up       │
│   information. Use only the provided context."   │
│                                                  │
│  RETRIEVED CONTEXT:                              │
│  "Our refund policy states: Items can be         │
│   returned within 30 days with receipt..."       │
│                                                  │
│  CONVERSATION HISTORY:                           │
│  User: "I bought something last week"            │
│  AI: "I can help with that!"                     │
│                                                  │
│  CURRENT USER MESSAGE:                           │
│  "What is the refund policy for order #1234?"    │
└─────────────────────────────────────────────────┘
```

**This complete thing is the prompt. This is what you MUST log.**

---

### Why Log the Full Prompt?

| Scenario | Without Full Prompt Log | With Full Prompt Log |
|---|---|---|
| AI gives wrong answer | No idea why | See that system prompt had wrong instructions |
| AI ignores user | Don't know what it "saw" | See that user message was truncated |
| AI hallucinates | Can't trace root cause | See that retrieved context was empty |
| Prompt injection attack | Don't know what happened | See malicious input clearly |

### ⚠️ Critical Issue: Privacy in Prompt Logging

**Big problem:** Prompts often contain sensitive user data.

```
User types: "My name is John Smith, SSN 123-45-6789.
             What is my account balance?"
```

**You CANNOT log this raw.** Legal risk (GDPR, HIPAA, etc.)

**Solutions:**

```
Strategy 1: PII Detection + Masking
"My name is [NAME], SSN [REDACTED]. What is my balance?"

Strategy 2: Hashing sensitive fields
user_id: hash("John Smith SSN 123-45-6789")

Strategy 3: Selective logging
Only log non-sensitive portions of prompts

Strategy 4: Encryption at rest
All logs encrypted, access-controlled
```

### 🔢 Math: Token Counting in Prompt Logging

Why do you count tokens in logs?

**Because tokens = money.**

```
Token calculation (approximate):
1 token ≈ 4 characters ≈ 0.75 words

"Hello, how are you today?" = 6 tokens

GPT-4 Turbo pricing:
  Input:  $0.01  per 1,000 tokens
  Output: $0.03  per 1,000 tokens

Example calculation:
  Input tokens:  800  → cost = 800/1000 × $0.01 = $0.008
  Output tokens: 300  → cost = 300/1000 × $0.03 = $0.009
  ─────────────────────────────────────────────────────
  Total per call:                              = $0.017

Daily: 10,000 calls × $0.017 = $170/day
Monthly:                      = $5,100/month
```

**Logging token counts lets you see cost per user, per feature, per prompt version.**

## 🏛️ COMPONENT 2: Context Inspection

### What Is "Context" in an LLM?

Context = **everything the LLM knows about the current situation** when generating a response.

Think of it like working memory. The LLM can only "think" with what's inside its context window at that moment.

```
┌──────────────────────────────────────────┐
│           CONTEXT WINDOW                  │
│  (LLM's entire working memory)           │
│                                          │
│  ┌──────────────────┐                   │
│  │  System Prompt   │ ← Instructions    │
│  │  (500 tokens)    │                   │
│  └──────────────────┘                   │
│  ┌──────────────────┐                   │
│  │ Retrieved Docs   │ ← RAG results     │
│  │  (2000 tokens)   │                   │
│  └──────────────────┘                   │
│  ┌──────────────────┐                   │
│  │ Chat History     │ ← Memory          │
│  │  (800 tokens)    │                   │
│  └──────────────────┘                   │
│  ┌──────────────────┐                   │
│  │ Current Message  │ ← Now             │
│  │  (50 tokens)     │                   │
│  └──────────────────┘                   │
│  Total: 3,350 / 128,000 tokens used     │
└──────────────────────────────────────────┘
```

---

### What to Inspect in Context Logging?

| Inspection Point | What You're Checking | Why It Matters |
|---|---|---|
| **Context utilization** | How full is the window? | If >90% full = truncation risk |
| **Retrieved doc quality** | Are the right docs retrieved? | Bad docs = hallucination |
| **Retrieved doc relevance scores** | How relevant are the docs? | Low score = wrong retrieval |
| **Context window overflow** | Did anything get cut off? | Truncation causes silent failures |
| **History length** | Is chat history too long? | Costs money, may confuse model |
| **Instruction clarity** | Is system prompt contradictory? | Confusing prompts = weird outputs |

---

### Context Window Overflow — A Nasty Hidden Bug

```
Context Window Limit: 8,000 tokens

Your prompt builds to:
  System prompt:   500 tokens
  Retrieved docs: 5,000 tokens
  Chat history:   3,000 tokens
  User message:     200 tokens
  ─────────────────────────────
  Total:          8,700 tokens ← OVERFLOW!

What happens?
  → The OLDEST parts of the conversation get silently cut off
  → The model loses context
  → Answers become inconsistent
  → No error is thrown — it just silently fails
```

**Context inspection logging catches this before users notice.**

---

### Context Inspection Code Pattern

```python
def log_context_inspection(context_window):
    """Inspect and log the context before sending to LLM"""
    
    inspection = {
        # Token counts per section
        "system_prompt_tokens": count_tokens(context_window["system"]),
        "retrieved_docs_tokens": count_tokens(context_window["context"]),
        "history_tokens": count_tokens(context_window["history"]),
        "user_message_tokens": count_tokens(context_window["message"]),
        
        # Total usage
        "total_tokens": sum_all_tokens(context_window),
        "max_context_window": 128000,  # GPT-4 Turbo
        "utilization_percent": (total / 128000) * 100,
        
        # Danger flags
        "overflow_risk": total > (128000 * 0.9),  # >90% full
        "history_truncated": was_history_truncated,
        
        # RAG quality signals
        "top_doc_relevance_score": retrieved_docs[0]["score"],
        "avg_relevance_score": avg([d["score"] for d in retrieved_docs]),
        "docs_below_threshold": count(d for d in docs if d["score"] < 0.7),
    }
    
    # Alert if context is dangerously full
    if inspection["utilization_percent"] > 90:
        send_alert("⚠️ Context window near limit!")
    
    return inspection
```

## 🏛️ COMPONENT 3: Tool Call Tracing

### What are "Tool Calls" in LLMs?

Modern LLMs don't just generate text — they can **call external tools:**

```
Tools an LLM Agent might use:
├── 🔍 Search — "Search the web for latest prices"
├── 📊 Calculator — "Calculate 15% discount on $450"
├── 🗄️ Database Query — "Look up user account #1234"
├── 📧 Email Sender — "Send confirmation to user@email.com"
├── 🌐 API Call — "Get current weather in New York"
├── 📁 File Reader — "Read document from S3"
└── 🔧 Code Executor — "Run this Python script"
```

Each tool call is a **separate operation** that must be traced independently.

---

### Why Is Tool Call Tracing Critical?

```
Without tool call tracing:

User: "What's the weather in Paris and book me a hotel?"
AI: "The weather is nice, I booked the hotel!"
You: "Did it actually call the weather API? 
      Did the hotel booking succeed? 
      Did it charge the right card?
      Was there an error that got hidden?"
→ You have NO idea. This is dangerous.

With tool call tracing:

TRACE: user_request_xyz
├── SPAN: llm_reasoning (model decides to use tools)
│   └── tool_calls_decided: ["get_weather", "book_hotel"]
│
├── SPAN: tool_call: get_weather
│   ├── input: {"city": "Paris", "date": "2025-07-22"}
│   ├── output: {"temp": "22°C", "condition": "sunny"}
│   ├── duration: 340ms
│   └── status: SUCCESS ✅
│
├── SPAN: tool_call: book_hotel
│   ├── input: {"city": "Paris", "checkin": "2025-07-25", "nights": 3}
│   ├── output: ERROR: "No availability found"
│   ├── duration: 890ms
│   └── status: ERROR ❌
│
└── SPAN: final_response
    └── NOTE: Did the AI tell user about the hotel failure?
```

**You can now see EXACTLY what happened.**

---

### What to Log for Each Tool Call

```python
# Every single tool call must log:
tool_call_log = {
    "trace_id": "parent_trace_id",
    "span_id": "unique_span_id",
    "tool_name": "get_weather",
    "tool_version": "v2.1",
    
    # What the LLM decided to send
    "input_arguments": {
        "city": "Paris",
        "date": "2025-07-22"
    },
    
    # What came back
    "output": {"temp": "22°C", "condition": "sunny"},
    "output_tokens": 45,  # if tool returns text
    
    # Performance
    "start_time": "14:32:01.234",
    "end_time": "14:32:01.574",
    "duration_ms": 340,
    
    # Status
    "status": "success",  # or "error", "timeout"
    "error_message": None,
    "retry_count": 0,
    
    # Cost (if external API)
    "api_cost": 0.001,
    "api_provider": "OpenWeatherMap"
}
```

---

### Tool Call Tracing — Failure Modes

| Failure | What Happens | How Logging Catches It |
|---|---|---|
| Tool returns wrong data | LLM uses bad data confidently | Log shows tool output was incorrect |
| Tool times out | LLM hallucinates a response | Log shows timeout, no real output |
| Tool called in loop | Infinite loop, cost explosion | Log shows same tool called 100x |
| Tool error hidden | LLM pretends success | Log shows ERROR status |
| Wrong tool selected | LLM calls wrong API | Log shows tool_name mismatch |
| Tool called with wrong args | API rejects or returns garbage | Log shows malformed input_arguments |

---

### The Dangerous "Hidden Error" Pattern

```
What user sees:
User: "Book me a flight to Tokyo"
AI: "I've found some great options for your Tokyo trip!"

What actually happened (only visible in trace logs):
├── SPAN: search_flights
│   ├── status: ERROR ❌
│   └── error: "API rate limit exceeded"
│
└── SPAN: llm_response
    └── Model hallucinated a response
        instead of admitting tool failure
```

**Without tool call tracing, this hallucination is invisible.**

## 🏛️ COMPONENT 4: Multi-Step Workflow Visibility

### What Is a Multi-Step Workflow?

Modern AI applications are NOT simple `input → LLM → output`.
They are **complex chains and graphs** of operations:

```
Simple App (2020 thinking):
User → LLM → Answer

Real Production App (2025):
User
  ↓
[Step 1] Intent Classification
  ↓
[Step 2] Route to appropriate agent
  ↓          ↓           ↓
[Agent A] [Agent B]  [Agent C]
  ↓          ↓           ↓
[Tool calls] [RAG] [Calculator]
  ↓          ↓           ↓
[Merge results]
  ↓
[Safety check]
  ↓
[Format output]
  ↓
User
```

**Every single step above must be visible and traceable.**

---

### The 3 Types of Multi-Step Workflows

#### Type 1: Sequential Chain
```
Step 1 → Step 2 → Step 3 → Step 4

Example: Customer support
Classify intent → Retrieve docs → Generate answer → Format response

All steps happen in order.
If Step 2 fails, Steps 3 and 4 also fail.
```

#### Type 2: Parallel Workflow
```
          ┌→ Step A ─┐
Step 1 ──→│→ Step B ─│→ Merge → Step 5
          └→ Step C ─┘

Example: Research assistant
Classify question → [Search web] + [Search DB] + [Search docs] → Merge → Answer

Steps A, B, C run at the same time.
Total time = slowest of A, B, C (not their sum)
```

#### Type 3: Recursive/Agent Loop
```
Step 1 → Think → Act → Observe → Think again → Act again → ...
                  ↑                    |
                  └────────────────────┘
                      (loop until done)

Example: ReAct agent pattern
Think → Search → Think → Search → Think → Answer
```

---

### Parent-Child Span Relationships

This is how multi-step workflows maintain structure in logs:

```python
# How spans nest to show workflow structure:

trace_id = "abc123"

# Level 0: The whole request
root_span = {
    "span_id": "span_001",
    "parent_span_id": None,  # ← root, no parent
    "name": "handle_user_request",
    "trace_id": "abc123"
}

# Level 1: Major steps
intent_span = {
    "span_id": "span_002",
    "parent_span_id": "span_001",  # ← child of root
    "name": "classify_intent",
    "trace_id": "abc123"
}

retrieval_span = {
    "span_id": "span_003",
    "parent_span_id": "span_001",  # ← child of root
    "name": "retrieve_documents",
    "trace_id": "abc123"
}

# Level 2: Steps within retrieval
embedding_span = {
    "span_id": "span_004",
    "parent_span_id": "span_003",  # ← child of retrieval
    "name": "create_embedding",
    "trace_id": "abc123"
}

vector_search_span = {
    "span_id": "span_005",
    "parent_span_id": "span_003",  # ← child of retrieval
    "name": "vector_db_search",
    "trace_id": "abc123"
}
```

**When visualized, this creates a tree:**
```
handle_user_request (3,400ms)
├── classify_intent (45ms)
├── retrieve_documents (234ms)
│   ├── create_embedding (67ms)
│   └── vector_db_search (167ms)
├── llm_call (1,200ms)
├── tool_call: database (180ms)
├── safety_filter (67ms)
└── format_output (23ms)
```

### Distributed Tracing in Multi-Agent Systems

This is the hardest part. When Agent A calls Agent B across services:

```
Service 1 (Orchestrator)          Service 2 (Research Agent)
────────────────────────          ────────────────────────
User Request (trace: abc123)
       ↓
Orchestrator Span (abc123)
       ↓
HTTP call to Agent B  ────────→   Agent B receives request
  [passes trace_id: abc123]       Agent B Span (abc123) ← same trace!
                                         ↓
                                  LLM Call Span (abc123)
                                         ↓
                                  Tool Call Span (abc123)
                                         ↓
                      ←────────   Returns result
       ↓
Merge results Span (abc123)
       ↓
Final Response
```

**The trace_id travels across service boundaries.** This is called **trace propagation** using HTTP headers (W3C TraceContext standard):

```
HTTP Header: traceparent: 00-abc123-span_001-01
```

This is how distributed systems are traced end-to-end.

#### Level 2: Async Logging Pipeline

```python
import asyncio
from collections import deque
import aiohttp

class AsyncLLMLogger:
    """
    Don't slow down your app with synchronous logging!
    Log asynchronously in the background.
    """
    
    def __init__(self):
        self.queue = deque()
        self.batch_size = 100
        
    async def log(self, log_data: dict):
        """Non-blocking: add to queue and return immediately"""
        self.queue.append(log_data)
        
        # Don't wait for flush — app continues immediately
        if len(self.queue) >= self.batch_size:
            asyncio.create_task(self.flush())  # Background task
    
    async def flush(self):
        """Send batch of logs to your storage"""
        if not self.queue:
            return
            
        batch = []
        while self.queue and len(batch) < self.batch_size:
            batch.append(self.queue.popleft())
        
        # Send batch to your logging backend
        async with aiohttp.ClientSession() as session:
            await session.post(
                "https://your-logging-service.com/ingest",
                json={"logs": batch}
            )
```

## 📐 SECTION 7: Math Intuition — Key Calculations

### Latency Percentiles (P50, P95, P99)

This is extremely common in interviews. Let me explain simply.

**Imagine 100 user requests. We measure latency for each:**

```
Sorted latencies (milliseconds):
100, 120, 150, ..., 800, 900, 1200, 1500, 5000

P50 (Median):  50th value = 350ms   ← "Typical user experience"
P95:           95th value = 1200ms  ← "Slow user experience"
P99:           99th value = 3000ms  ← "Very bad user experience"
P99.9:         99.9th value = 5000ms ← "The worst of the worst"
```

**Why not just use average?**

```
10 requests: 100, 100, 100, 100, 100, 100, 100, 100, 100, 10,000ms

Average = (900 + 10,000) / 10 = 1,090ms → misleadingly high
P99     = 10,000ms → shows the real tail problem
P50     = 100ms    → shows typical experience
```

**The average lies. Percentiles tell the truth.**

```python
import numpy as np

def calculate_latency_percentiles(latencies: list):
    return {
        "p50": np.percentile(latencies, 50),
        "p90": np.percentile(latencies, 90),
        "p95": np.percentile(latencies, 95),
        "p99": np.percentile(latencies, 99),
        "p99_9": np.percentile(latencies, 99.9),
        "max": max(latencies),
        "mean": np.mean(latencies)
    }

# Example output:
# p50: 340ms, p95: 1,200ms, p99: 3,400ms, max: 12,000ms
# → You'd say "Most users (P50) get 340ms, 
#   but 1% of users wait over 3.4 seconds"
```

---

### Cost Formula in Logging

```
Per-request cost formula:
cost = (input_tokens × input_price_per_token) 
     + (output_tokens × output_price_per_token)

For GPT-4 Turbo:
cost = (input_tokens × $0.00001) 
     + (output_tokens × $0.00003)

Example request:
input_tokens = 890   → 890 × $0.00001 = $0.0089
output_tokens = 245  → 245 × $0.00003 = $0.0074
                       ────────────────────────
total_cost per call  = $0.0163

Daily tracking:
daily_cost = Σ(cost_i for all requests today)

Cost per user:
user_cost = Σ(cost_i for all requests by user_x)
```

## 💥 SECTION 8: Failure Modes

| # | Failure | Root Cause | How to Detect | How to Fix |
|---|---|---|---|---|
| 1 | **Over-logging** | Logging every token of every prompt | Storage costs explode | Sample 1-10% of requests; log metadata always, content selectively |
| 2 | **Under-logging** | Only logging final input/output | Can't debug intermediate failures | Instrument every step with spans |
| 3 | **Synchronous logging** | Logging blocks the main thread | App becomes slow | Always log asynchronously |
| 4 | **PII in logs** | User data stored unprotected | Legal violations (GDPR, HIPAA) | PII detection + masking before logging |
| 5 | **Missing trace IDs** | Each span doesn't know its parent | Traces are fragments, not trees | Generate and propagate trace_id from day 1 |
| 6 | **Log schema drift** | Different services log different fields | Can't query or join logs | Define and enforce a standard log schema |
| 7 | **No sampling strategy** | Log 100% of traffic | Costs too much at scale | Use head-based or tail-based sampling |
| 8 | **Logging in loops** | Agent loops same tool 100× | Logs fill with duplicates | Detect and alert on repeated span patterns |

---

### Sampling Strategies Explained

```
Problem: You have 1 million requests/day.
Logging every single one costs too much.
Solution: Sample intelligently.

Strategy 1: Head-based Sampling
→ Randomly decide to log 5% of requests at the start
→ Simple but might miss rare important cases

Strategy 2: Tail-based Sampling
→ Log ALL requests temporarily
→ After the request finishes, KEEP only:
   - All errors
   - All requests with latency > 3s
   - All requests with quality score < 0.5
   - 1% of normal requests
→ Expensive temporarily, but smart filtering

Strategy 3: Priority Sampling
→ Always log:
   - All errors (100%)
   - High-value users (100%)
   - Slow requests > P99 (100%)
   - Random 1% of normal requests
→ Best balance of cost and coverage
```

## 💬 SECTION 10: Strong Interview Answers

### Answer Q1: Log vs Metric vs Trace

> *"These are the three pillars of observability. A **log** is an immutable timestamped record of a specific event — like 'LLM call failed at 14:32:01 with error: timeout.' A **metric** is a numerical measurement aggregated over time — like 'average latency is 1.8s' or 'token cost this hour is $12.34.' A **trace** is the complete journey of one request through your system, showing every step, their timing, and their relationships. In LLM systems, traces are the most powerful because they show exactly what happened inside one user interaction, step by step."*

---

### Answer Q5: P50 vs P95 vs P99

> *"Percentile latencies tell you about the distribution of user experiences, not just the average. P50, or median, represents the typical user — 50% of requests are faster than this number. P95 means 95% of requests are faster — this is what most users experience including slow ones. P99 means 99% are faster — this is the 'tail' — representing worst-case scenarios that still affect 1 in 100 users. The average is misleading because one 10-second request can make 99 fast requests look slow. For LLM systems, I'd set alerts at P95 and P99 because even 1% of users having 5-second waits is unacceptable."*

---

### Answer Q9: Trace Correlation in Multi-Agent Systems

> *"We use distributed trace propagation. When Service A makes a call to Service B, it passes the trace_id and parent_span_id in the HTTP headers using the W3C TraceContext standard — specifically the traceparent header. Service B reads this header and creates a new span with the same trace_id but a new span_id, using Service A's span as the parent. This way, even though the two services are completely separate, all their spans belong to the same trace and appear together in the observability tool's trace view. You can follow one user request across 5 different microservices all in one unified trace timeline."*

## ⚠️ SECTION 11: Common Mistakes

| Mistake | Why Wrong | Right Approach |
|---|---|---|
| Only logging errors | You miss successful but bad responses | Log everything, then filter |
| Using print() for logging | Can't query, filter, or structure | Use structured JSON logging |
| Not logging tool call inputs/outputs | Can't debug agent failures | Log both IN and OUT for every tool |
| No trace IDs | Logs are disconnected fragments | Generate UUID trace_id for every request |
| Logging the full response always | Storage explosion | Log response preview + quality scores |
| Ignoring latency percentiles | Average hides tail problems | Always monitor P95 and P99 |
| Missing user context in logs | Can't debug user-specific issues | Always include user_id (hashed) |
| No async logging | Adds latency to user requests | Always log in background |

## 🏭 SECTION 12: Putting It All Together — Complete System

```python
"""
Complete Request & Trace Logging System
for a Production RAG Chatbot
"""

import uuid
import time
import hashlib
from opentelemetry import trace
from langfuse import Langfuse

# Initialize tools
tracer = trace.get_tracer("rag_chatbot")
langfuse = Langfuse()

class ProductionRAGChatbot:
    
    def handle_request(self, user_message: str, user_id: str):
        
        # STEP 1: Create a unique trace ID for this entire request
        trace_id = str(uuid.uuid4())
        start_time = time.time()
        
        # STEP 2: Start Langfuse trace for quality monitoring
        lf_trace = langfuse.trace(
            name="rag_request",
            user_id=hashlib.sha256(user_id.encode()).hexdigest(),  # Anonymized
            metadata={"trace_id": trace_id}
        )
        
        # STEP 3: Start OpenTelemetry root span for infrastructure
        with tracer.start_as_current_span("handle_request") as root_span:
            root_span.set_attribute("trace.id", trace_id)
            root_span.set_attribute("user.id_hash", hashlib.md5(user_id.encode()).hexdigest())
            root_span.set_attribute("request.message_length", len(user_message))
            
            try:
                # STEP 4: Retrieval with its own span
                with tracer.start_as_current_span("document_retrieval") as ret_span:
                    retrieval_span = lf_trace.span(name="retrieval")
                    
                    docs = self.retrieve_documents(user_message)
                    
                    ret_span.set_attribute("retrieval.doc_count", len(docs))
                    ret_span.set_attribute("retrieval.top_score", docs[0]["score"] if docs else 0)
                    
                    retrieval_span.end(
                        output={
                            "doc_count": len(docs),
                            "top_score": docs[0]["score"] if docs else 0
                        }
                    )
                
                # STEP 5: LLM call with full logging
                with tracer.start_as_current_span("llm_call") as llm_span:
                    llm_generation = lf_trace.generation(
                        name="gpt4_call",
                        model="gpt-4-turbo",
                        input={"user_message": user_message, "context_docs": len(docs)}
                    )
                    
                    prompt = self.build_prompt(user_message, docs)
                    llm_response = self.call_openai(prompt)
                    
                    # Log all LLM metrics
                    input_tokens = llm_response.usage.prompt_tokens
                    output_tokens = llm_response.usage.completion_tokens
                    cost = (input_tokens * 0.00001) + (output_tokens * 0.00003)
                    
                    llm_span.set_attribute("llm.model", "gpt-4-turbo")
                    llm_span.set_attribute("llm.input_tokens", input_tokens)
                    llm_span.set_attribute("llm.output_tokens", output_tokens)
                    llm_span.set_attribute("llm.cost_usd", cost)
                    
                    llm_generation.end(
                        output=llm_response.choices[0].message.content,
                        usage={"input": input_tokens, "output": output_tokens}
                    )
                
                # STEP 6: Log final request summary
                total_time_ms = (time.time() - start_time) * 1000
                root_span.set_attribute("request.total_latency_ms", total_time_ms)
                root_span.set_attribute("request.status", "success")
                root_span.set_attribute("request.total_cost_usd", cost)
                
                # STEP 7: Score quality (async, doesn't slow response)
                self.score_quality_async(
                    trace_id=trace_id,
                    lf_trace=lf_trace,
                    question=user_message,
                    answer=llm_response.choices[0].message.content,
                    context=docs
                )
                
                return llm_response.choices[0].message.content
                
            except Exception as e:
                root_span.set_attribute("request.status", "error")
                root_span.set_attribute("error.message", str(e))
                root_span.record_exception(e)
                lf_trace.update(metadata={"error": str(e)})
                raise
```

**How a senior AI engineer thinks about logging:**

```
Day 1 of a new LLM project, I ask myself:

✅ "What is the minimal logging I need to debug any future issue?"
   → trace_id, user_message, prompt, response, tokens, latency, errors

✅ "What is sensitive and must be protected or redacted?"
   → PII in messages, user IDs, confidential business data

✅ "What metrics do I need to measure business success?"
   → Quality scores, user satisfaction, task completion rate

✅ "What metrics do I need to control costs?"
   → Tokens per session, cost per user, cost per feature

✅ "What will I look at during an incident at 3am?"
   → Error rate, latency spike, quality score drop

✅ "How do I scale this logging system as I go from 
    100 to 1 million users?"
   → Sampling strategy, async pipeline, indexed storage

I instrument these from day 1, not as an afterthought.
Observability is not a feature — it's the foundation.
```

## 🎓 Final Summary — The 20% That Gives 80% Understanding

| Core Concept | One Sentence |
|---|---|
| **What trace logging is** | Recording every hidden step inside your LLM system — not just input and output |
| **Why it matters** | LLM apps can be "running" but silently producing garbage — only traces reveal this |
| **Full prompt logging** | Log the complete prompt the LLM received, not just the user's question |
| **Context inspection** | Monitor what's inside the context window — overflow kills quality silently |
| **Tool call tracing** | Every tool call is a span with its own inputs, outputs, timing, and status |
| **Multi-step visibility** | Traces show the full tree of operations, making root cause analysis possible |
| **The right tool stack** | OTel for standard instrumentation → LangSmith/Langfuse for LLM-specific UI |
| **Engineer mindset** | Instrument first, build features second — you can't improve what you can't see |
