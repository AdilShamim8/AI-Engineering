## 📌 SECTION 1: The Big Picture — What Is Backend Deployment?

### Simple English Definition:

> **Backend Deployment = Setting up the server-side system that receives user requests, runs your AI model, and sends back responses — reliably, securely, and at scale.**

Think of it like a **restaurant kitchen system:**

## 📌 SECTION 3: REST APIs For AI Services

### 3.1 — What Is a REST API?

> **REST API = A standardized way for two computers to talk to each other over the internet using HTTP.**

#### First Principles Breakdown:

```
REST = Representational State Transfer
API  = Application Programming Interface
HTTP = The language of the internet (same as websites)
```

#### Real-Life Analogy:

> Think of a **USB standard.**
>
> Every USB device uses the same plug shape.
> Your phone charger, mouse, keyboard — all same plug.
> This standard means any device works with any computer.
>
> REST API = **The USB standard for software communication**
> Every client (phone app, web app, other servers)
> can talk to your backend using the same standard rules.

### 3.2 — The 5 HTTP Methods (The Verbs of REST)

```
GET     → "Give me data"         (Reading)
POST    → "Here is new data"     (Creating)
PUT     → "Replace this data"    (Full update)
PATCH   → "Change part of data"  (Partial update)
DELETE  → "Remove this data"     (Deleting)
```

#### For AI Apps, You Mostly Use:

```
POST /chat          → Send message, get AI response
POST /analyze       → Send document, get analysis
POST /embed         → Send text, get embeddings
GET  /history       → Get conversation history
GET  /status/{id}   → Check if background job is done
DELETE /session     → Clear conversation memory
```

### 3.3 — Anatomy of an HTTP Request & Response

```
HTTP REQUEST (What your app sends to backend)
─────────────────────────────────────────────
POST /api/chat HTTP/1.1
Host: api.yourai.com
Authorization: Bearer eyJhbGc...    ← Your identity token
Content-Type: application/json      ← Data format
X-Rate-Limit-Key: user_123          ← For rate limiting

{
    "message": "Explain LLMOps",
    "session_id": "sess_abc123",
    "model": "gpt-4o"
}

─────────────────────────────────────────────
HTTP RESPONSE (What backend sends back)
─────────────────────────────────────────────
HTTP/1.1 200 OK
Content-Type: application/json
X-Request-Id: req_xyz789
X-Tokens-Used: 342

{
    "response": "LLMOps is...",
    "tokens_used": 342,
    "model": "gpt-4o",
    "session_id": "sess_abc123",
    "cost_usd": 0.0034
}
```

### 3.4 — HTTP Status Codes (Every AI Engineer Must Know)

```
2xx = ✅ Success
───────────────────────────────────────
200 OK              → Request succeeded
201 Created         → New resource created
202 Accepted        → Request accepted (processing in background)

4xx = ❌ Client Error (User's fault)
───────────────────────────────────────
400 Bad Request     → You sent invalid data
401 Unauthorized    → You are not logged in
403 Forbidden       → You don't have permission
404 Not Found       → This endpoint doesn't exist
422 Unprocessable   → Data format is wrong (FastAPI uses this a lot)
429 Too Many Req    → You hit the rate limit ← Very common in AI APIs

5xx = 💥 Server Error (Our fault)
───────────────────────────────────────
500 Internal Error  → Something broke in our backend
502 Bad Gateway     → AI provider is down
503 Service Unavail → Our server is overloaded
504 Gateway Timeout → AI model took too long to respond
```

```python
# ── MIDDLEWARE ──────────────────────────────────────────
# Middleware = Code that runs on EVERY request automatically
# Like airport security — every passenger goes through it

# 1. CORS — Allow frontend to call this API
app.add_middleware(
    CORSMiddleware,
    allow_origins=["https://yourapp.com"],  # Only YOUR frontend
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)

# 2. Request ID — Give every request a unique ID (for debugging)
@app.middleware("http")
async def add_request_id(request: Request, call_next):
    request_id = str(uuid.uuid4())
    request.state.request_id = request_id
    
    start_time = time.time()
    response = await call_next(request)
    process_time = (time.time() - start_time) * 1000  # in ms
    
    # Add useful headers to every response
    response.headers["X-Request-ID"] = request_id
    response.headers["X-Process-Time-ms"] = str(round(process_time, 2))
    
    return response

# ── ROUTERS ──────────────────────────────────────────────

    return {

        "version": "1.0.0",
```

#### Step 5: Build Chat Router

```python
# routers/chat.py
from fastapi import APIRouter, Depends, HTTPException, Request
from models.request import ChatRequest
from models.response import APIResponse
from services.llm_service import LLMService
import uuid
import time

router = APIRouter()
llm_service = LLMService()

@router.post("/chat", response_model=APIResponse)
async def chat(
    request_body: ChatRequest,
    request: Request,
    # user = Depends(get_current_user)  ← We'll add auth later
):
    """
    Main chat endpoint.
    
    What happens here step by step:
    1. FastAPI validates request_body shape automatically
    2. We call the LLM service
    3. We return structured response
    """
    
    start_time = time.time()
    
    try:
        # Generate session ID if not provided
        session_id = request_body.session_id or str(uuid.uuid4())
        
        # Call LLM
        result = await llm_service.chat(
            message=request_body.message,
            session_id=session_id,
            model=request_body.model,
            temperature=request_body.temperature
        )
        
        processing_time = int((time.time() - start_time) * 1000)
        
        return APIResponse(
            success=True,
            data={
                "response": result["text"],
                "session_id": session_id,
                "model_used": result["model"],
                "tokens_used": result["tokens"],
                "cost_usd": result["cost"],
                "processing_time_ms": processing_time
            },
            request_id=request.state.request_id
        )
    
    except ValueError as e:
        # User error (bad input)
        raise HTTPException(status_code=400, detail=str(e))
    
    except Exception as e:
        # Server error
        raise HTTPException(status_code=500, detail="AI service error")
```

#### Step 6: LLM Service Layer

```python
# services/llm_service.py
from openai import AsyncOpenAI
import os
import time

class LLMService:
    """
    All LLM logic lives here.
    This separates business logic from API routing.
    
    Why separate? 
    - Easy to test independently
    - Easy to swap providers
    - Easy to add caching, logging, fallbacks
    """
    
    def __init__(self):
        self.openai_client = AsyncOpenAI(
            api_key=os.getenv("OPENAI_API_KEY")
        )
        
        # Token pricing (per 1000 tokens)
        self.pricing = {
            "gpt-4o":      {"input": 0.005,  "output": 0.015},
            "gpt-4o-mini": {"input": 0.00015, "output": 0.0006},
        }
    
    async def chat(
        self,
        message: str,
        session_id: str,
        model: str = "gpt-4o-mini",
        temperature: float = 0.7
    ) -> dict:
        """Call LLM and return structured result"""
        
        response = await self.openai_client.chat.completions.create(
            model=model,
            messages=[{"role": "user", "content": message}],
            temperature=temperature
        )
        
        # Extract usage stats
        usage = response.usage
        
        # Calculate cost
        model_pricing = self.pricing.get(model, {"input": 0, "output": 0})
        cost = (
            (usage.prompt_tokens / 1000 * model_pricing["input"]) +
            (usage.completion_tokens / 1000 * model_pricing["output"])
        )
        
        return {
            "text": response.choices[0].message.content,
            "model": model,
            "tokens": usage.total_tokens,
            "prompt_tokens": usage.prompt_tokens,
            "completion_tokens": usage.completion_tokens,
            "cost": round(cost, 6)
        }
```

## 📌 SECTION 5: Async Processing — The Most Important Concept

### 5.1 — What Is The Problem?

```
SYNCHRONOUS (Blocking):
────────────────────────
Request 1 arrives → Process → Done (10s)
Request 2 waits...
Request 3 waits...
Request 4 waits...

Server handles ONE thing at a time.
Like a single cashier in a busy supermarket.
Everyone queues up. Slow and frustrating.
```

```
ASYNCHRONOUS (Non-Blocking):
──────────────────────────────
Request 1 arrives → Start processing (waiting for AI response)
Request 2 arrives → Start processing (while #1 is waiting)
Request 3 arrives → Start processing (while #1, #2 waiting)
Request 4 arrives → Start processing (while all waiting)

AI response for #2 ready → Return it
AI response for #1 ready → Return it
AI response for #4 ready → Return it
AI response for #3 ready → Return it

Server handles MANY things at same time.
Like a chef who starts all dishes simultaneously.
```

### 5.2 — Real-Life Analogy for Async:

> **Think of a waiter at a restaurant:**
>
> **Synchronous Waiter (BAD):**
> Takes order from Table 1 → Stands in kitchen and WAITS for food → Brings it → THEN goes to Table 2
> Table 2, 3, 4 all waiting 20 minutes before even giving their order!
>
> **Asynchronous Waiter (GOOD):**
> Takes order from Table 1 → Goes to Table 2 while kitchen cooks → Takes order from Table 3 → Food ready at Table 1 → Delivers it → Checks Table 4 → ...
>
> **Same one waiter. 4x more tables served. No extra staff.**
>
> `async/await` = **The restaurant waiter pattern for code**

### 5.3 — Sync vs Async Code (Side by Side)

```python
# ❌ SYNCHRONOUS — Blocks everything
import time
import requests  # Regular (blocking) HTTP library

def sync_call_ai(message: str):
    print("Starting AI call...")
    
    # This BLOCKS the entire server for 5 seconds!
    # No other request can be handled during this time
    response = requests.post(
        "https://api.openai.com/v1/chat/completions",
        json={...}
    )
    
    print("AI call done!")
    return response.json()

# If 100 users hit this at same time:
# User 1: waits 5s
# User 2: waits 10s (waits for user 1)
# User 3: waits 15s
# User 100: waits 500s = 8+ minutes! 😱
```

```python
# ✅ ASYNCHRONOUS — Handles multiple requests
import asyncio
import httpx  # Async HTTP library

async def async_call_ai(message: str):
    print("Starting AI call...")
    
    async with httpx.AsyncClient() as client:
        # While waiting for AI response,
        # Python handles OTHER requests!
        response = await client.post(
            "https://api.openai.com/v1/chat/completions",
            json={...}
        )
    
    print("AI call done!")
    return response.json()

# If 100 users hit this at same time:
# All 100 start processing "simultaneously"
# Each waits ~5s for their own AI response
# Total time ≈ 5s for everyone! ✅
```

### 5.4 — How Async Works Under The Hood

```
WHAT ACTUALLY HAPPENS WITH async/await:
────────────────────────────────────────

Time →   0s    1s    2s    3s    4s    5s
         │     │     │     │     │     │
User1:   START ──── WAIT FOR AI ──── DONE
                │                    
User2:          START ── WAIT FOR AI ─── DONE
                     │                    
User3:               START ─ WAIT FOR AI ── DONE

KEY INSIGHT:
"WAIT FOR AI" phase = Network I/O
During network I/O, your CPU is 100% free
Async Python uses that free time to start other requests

It's NOT true parallelism (not multiple CPUs)
It's CONCURRENCY (smartly filling the gaps)
```

### 5.5 — Complete Async FastAPI Example

```python
# Complete async endpoint with proper patterns
import asyncio
from fastapi import APIRouter
from openai import AsyncOpenAI
from fastapi.responses import StreamingResponse
import json

router = APIRouter()
client = AsyncOpenAI()

# Pattern 1: Basic Async Endpoint
@router.post("/chat")
async def chat(request: ChatRequest):
    # await means "start this, come back when done"
    # While waiting, FastAPI handles other requests
    response = await client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user", "content": request.message}]
    )
    return {"response": response.choices[0].message.content}


# Pattern 2: Parallel API Calls (Advanced)
@router.post("/analyze-parallel")
async def analyze_with_multiple_models(text: str):
    """
    Call GPT-4 AND Claude AT THE SAME TIME
    Instead of: GPT-4 (5s) THEN Claude (5s) = 10s total
    We get:     GPT-4 (5s) + Claude (5s) simultaneously = 5s total!
    """
    
    # asyncio.gather = Run multiple async tasks simultaneously
    gpt4_response, claude_response = await asyncio.gather(
        call_openai(text),
        call_claude(text)
    )
    
    return {
        "gpt4_analysis": gpt4_response,
        "claude_analysis": claude_response,
        # Both completed in ~5s instead of ~10s!
    }


# Pattern 3: Streaming Response (Users see text as it generates)
@router.post("/chat/stream")
async def chat_stream(request: ChatRequest):
    """
    Instead of waiting 10s for full response,
    user sees words appearing one by one (like ChatGPT!)
    """
    
    async def generate():
        stream = await client.chat.completions.create(
            model="gpt-4o-mini",
            messages=[{"role": "user", "content": request.message}],
            stream=True  # ← This enables streaming!
        )
        
        async for chunk in stream:
            if chunk.choices[0].delta.content is not None:
                # Send each word/token as it arrives
                word = chunk.choices[0].delta.content
                yield f"data: {json.dumps({'token': word})}\n\n"
        
        yield "data: [DONE]\n\n"
    
    # Server-Sent Events (SSE) = Standard for streaming
    return StreamingResponse(
        generate(),
        media_type="text/event-stream",
        headers={
            "Cache-Control": "no-cache",
            "X-Accel-Buffering": "no"
        }
    )
```

## 📌 SECTION 6: Background Task Workers

### 6.1 — What Problem Do They Solve?

```
SCENARIO: User uploads a 200-page PDF
"Analyze this entire document and give me insights"

NAIVE APPROACH (Bad):
─────────────────────
User uploads PDF
    ↓
Server starts processing (5 minutes)
    ↓
HTTP connection stays open for 5 minutes
    ↓
User's browser TIMES OUT after 30-60 seconds!
    ↓
Error! User frustrated. Work lost. 😤

BACKGROUND WORKER APPROACH (Good):
────────────────────────────────────
User uploads PDF
    ↓
Server immediately returns: "Job ID: abc123, Processing..."
(Response in < 1 second) ✅
    ↓
Background worker processes PDF for 5 minutes
(User can close browser, it still runs!)
    ↓
User checks status: GET /status/abc123
    ↓
"Status: Complete! Here are your insights."
```

### 6.2 — Real-Life Analogy:

> **Think of a DRY CLEANING shop:**
>
> You drop off your clothes (Submit job).
> They give you a TICKET (Job ID).
> You go home. They clean clothes in background.
> You come back later with ticket (Poll status).
> Pick up your clean clothes (Get result).
>
> You don't stand in the shop for 3 hours watching them clean!
>
> Background Workers = **The dry cleaning shop model**

### 6.4 — FastAPI BackgroundTasks (Simple, Built-in)

```python
# For SIMPLE background tasks (same server)
from fastapi import BackgroundTasks
import asyncio

@router.post("/analyze")
async def start_analysis(
    file_url: str,
    background_tasks: BackgroundTasks  # FastAPI injects this
):
    """
    Start analysis in background.
    Return immediately to user.
    """
    
    job_id = str(uuid.uuid4())
    
    # Store initial status
    await redis_client.set(
        f"job:{job_id}",
        json.dumps({"status": "processing", "progress": 0}),
        ex=3600  # Expire in 1 hour
    )
```

### 7.2 — JWT Authentication (Industry Standard)

#### What is JWT?

> **JWT = JSON Web Token = A secure digital ID card for your users**

```
JWT Structure (3 parts separated by dots):
──────────────────────────────────────────
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9    ← Header (algorithm used)
.
eyJ1c2VyX2lkIjoiMTIzIiwidXNlcm5hbWUiOiJqb2huIiwiZXhwIjoxNzA5MDAwMDAwfQ==
                                          ← Payload (user data)

                                          ← Signature (tamper-proof)
```

```
DECODED PAYLOAD (what's inside):
{
    "user_id": "123",
    "username": "john",
    "plan": "pro",
    "exp": 1709000000    ← Expiry timestamp
}
```

#### How JWT Auth Works:

```
1. User logs in with username/password
        │
        ▼
2. Server verifies credentials
        │
        ▼
3. Server creates JWT token (signed with secret key)
   "Here is your ID card"
        │
        ▼
4. User stores token (in browser/app)
        │
        ▼
5. Every API request includes token:
   Authorization: Bearer eyJhbGc...
        │
        ▼
6. Server verifies token signature
   "Is this ID card genuine? Not expired?"
        │
        ▼
7. If valid → Process request
   If invalid → Return 401 Unauthorized
```

#### Complete JWT Implementation:

```python
# pip install python-jose[cryptography] passlib bcrypt
# services/auth_service.py

from jose import JWTError, jwt
from passlib.context import CryptContext
from datetime import datetime, timedelta
import os

SECRET_KEY = os.getenv("JWT_SECRET_KEY")
ALGORITHM = "HS256"
TOKEN_EXPIRE_MINUTES = 60 * 24  # 24 hours

pwd_context = CryptContext(schemes=["bcrypt"])

class AuthService:
    
    def create_access_token(self, user_data: dict) -> str:
        """Create JWT token for user"""
        
        payload = user_data.copy()
        
        # Add expiry time
        expire = datetime.utcnow() + timedelta(minutes=TOKEN_EXPIRE_MINUTES)
        payload.update({"exp": expire})
        
        # Sign the token with our secret key
        token = jwt.encode(payload, SECRET_KEY, algorithm=ALGORITHM)
        return token
    
    def verify_token(self, token: str) -> dict:
        """Verify JWT token and extract user data"""
        
        try:
            # Decode and verify signature
            payload = jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM])
            
            user_id = payload.get("user_id")
            if user_id is None:
                raise ValueError("Invalid token: no user_id")
            
            return payload
            
        except JWTError:
            raise ValueError("Invalid or expired token")
    
    def hash_password(self, password: str) -> str:
        return pwd_context.hash(password)
    
    def verify_password(self, plain: str, hashed: str) -> bool:
        return pwd_context.verify(plain, hashed)
```

### 7.3 — Rate Limiting

#### What Is Rate Limiting?

> **Rate Limiting = Setting a maximum number of requests a user can make in a time window.**

#### Real-Life Analogy:

> **Think of an ATM:**
>
> ATM lets you withdraw money — but not unlimited.
> You can withdraw max $500/day.
> After that → "Limit reached, try tomorrow."
>
> This protects the bank from fraud.
>
> Rate Limiting = **The $500/day ATM rule for your API**

#### Types of Rate Limits For AI APIs:

```
RATE LIMIT TYPE 1: Requests per minute
────────────────────────────────────────
Free plan:   10 requests/minute
Pro plan:    100 requests/minute
Enterprise:  1000 requests/minute

RATE LIMIT TYPE 2: Tokens per day
───────────────────────────────────
Free plan:   10,000 tokens/day  (~$0.01 cost)
Pro plan:    1,000,000 tokens/day
Enterprise:  Unlimited

RATE LIMIT TYPE 3: Concurrent requests
────────────────────────────────────────
Free plan:   2 simultaneous requests
Pro plan:    20 simultaneous requests
```

#### Rate Limiting With Redis (Sliding Window Algorithm):

```
SLIDING WINDOW explained simply:
─────────────────────────────────
Imagine a 60-second window that's always moving:
Current time: 12:00:45
Window covers: 11:59:45 → 12:00:45 (last 60 seconds)

User made requests at:
  11:59:50 → Inside window ✅
  12:00:10 → Inside window ✅
  12:00:30 → Inside window ✅
  12:00:45 → NEW REQUEST (3 in window so far)

If limit = 5/minute → Allow ✅
If limit = 3/minute → Deny ❌ (already at 3)

As time passes (12:00:46):
  11:59:50 request slides OUT of window
  Now only 2 requests in window
  Next request allowed again ✅
```

```python
# middleware/rate_limit.py
import redis.asyncio as redis
import time
from fastapi import HTTPException, Request

redis_client = redis.from_url("redis://localhost:6379")

class RateLimiter:
    
    async def check_rate_limit(
        self,
        user_id: str,
        limit: int,          # Max requests allowed
        window_seconds: int  # Time window
    ) -> dict:
        """
        Sliding window rate limiter using Redis.
        
        HOW IT WORKS:
        - Store each request timestamp in a Redis sorted set
        - Key = "rate:{user_id}"
        - Score = timestamp
        - Count requests in last `window_seconds`
        """
        
        now = time.time()
        window_start = now - window_seconds
        key = f"rate:{user_id}"
        
        # Use Redis pipeline (atomic operation — all or nothing)
        pipe = redis_client.pipeline()
        
        # 1. Remove timestamps OLDER than window
        pipe.zremrangebyscore(key, 0, window_start)
        
        # 2. Add current timestamp
        pipe.zadd(key, {str(now): now})
        
        # 3. Count requests in current window
        pipe.zcard(key)
        
        # 4. Set key expiry
        pipe.expire(key, window_seconds)
        
        results = await pipe.execute()
        current_count = results[2]  # Result from zcard
        
        # Check if limit exceeded
        if current_count > limit:
            # Calculate when limit resets
            oldest_request = await redis_client.zrange(key, 0, 0, withscores=True)
            if oldest_request:
                reset_time = oldest_request[0][1] + window_seconds
                retry_after = int(reset_time - now)
            else:
                retry_after = window_seconds
            
            raise HTTPException(
                status_code=429,
                detail={
                    "error": "Rate limit exceeded",
                    "limit": limit,
                    "window": f"{window_seconds}s",
                    "retry_after_seconds": retry_after
                },
                headers={"Retry-After": str(retry_after)}
            )
        
        return {
            "requests_made": current_count,
            "requests_remaining": limit - current_count,
            "limit": limit
        }
```

```python
# services/cache_service.py
import redis.asyncio as redis
import json
import hashlib
from typing import Optional

redis_client = redis.from_url("redis://localhost:6379", decode_responses=True)

class CacheService:
    
    def _make_cache_key(self, prompt: str, model: str) -> str:
        """
        Create unique cache key for this exact prompt+model combo.
        We hash it so long prompts become short keys.
        """
        content = f"{model}:{prompt}"
        return f"response:{hashlib.md5(content.encode()).hexdigest()}"
    
    async def get_cached_response(
        self, 
        prompt: str, 
        model: str
    ) -> Optional[dict]:
        """Try to get response from cache"""
        
        key = self._make_cache_key(prompt, model)
        cached = await redis_client.get(key)
        
        if cached:
            print(f"🎯 CACHE HIT! Saved API call!")
            return json.loads(cached)
        
        print("💸 Cache miss — calling API")
        return None
    
    async def cache_response(
        self,
        prompt: str,
        model: str,
        response: dict,
        ttl_seconds: int = 3600  # Cache for 1 hour
    ):
        """Store response in cache"""
        
        key = self._make_cache_key(prompt, model)
        await redis_client.setex(
            key,
            ttl_seconds,
            json.dumps(response)
        )
    
    async def store_conversation(
        self,
        session_id: str,
        message: dict,
        max_messages: int = 20
    ):
        """Store conversation history in Redis"""
        
        key = f"conversation:{session_id}"
        
        # Add message to list
        await redis_client.rpush(key, json.dumps(message))
        
        # Keep only last N messages (sliding window)
        await redis_client.ltrim(key, -max_messages, -1)
        
        # Auto-expire conversation after 24 hours of inactivity
        await redis_client.expire(key, 86400)
    
    async def get_conversation(self, session_id: str) -> list:
        """Retrieve conversation history"""
        
        key = f"conversation:{session_id}"
        messages = await redis_client.lrange(key, 0, -1)
        return [json.loads(m) for m in messages]
```

```
         All see "cache miss" at the same moment
         → API overload, costs spike, failures

Fix: Cache Stampede Prevention
─────────────────────────────
async def get_with_lock(key, fetch_fn):
    result = await cache.get(key)
    if result: return result
    
    # Only ONE request fetches, others wait
    async with distributed_lock(key):
        result = await cache.get(key)  # Check again
        if not result:
            result = await fetch_fn()
            await cache.set(key, result)
    return result
```

### ⚠️ Failure 2: JWT Token Never Expires
```
Problem: Set token expiry = None or very long (1 year)
         User account compromised → Attacker has access forever
         Can't revoke without invalidating ALL tokens

Fix: Short expiry + refresh tokens
──────────────────────────────────
Access Token:  15 minutes expiry (short-lived)
Refresh Token: 30 days expiry (stored in HTTP-only cookie)

User stays logged in via refresh tokens.
Compromised access token = only 15 min of damage.
```

### ⚠️ Failure 3: Rate Limiting Too Aggressive
```
Problem: 10 requests/minute limit
         User sends legitimate batch of 12 messages
         Gets 429 error, thinks app is broken
         User leaves, bad review

Fix: Tiered limits + clear error messages
──────────────────────────────────────────
Return: {
    "error": "Rate limit exceeded",
    "limit": 10,
    "retry_after_seconds": 23,
    "upgrade_url": "/pricing"
}
Also: Implement burst allowance (allow 15 for brief spikes)
```

### ⚠️ Failure 4: Sync Endpoint Killing Server
```
Problem: Used regular def instead of async def
         Each AI request blocks one thread
         10 concurrent users → 10 threads blocked
         Server out of threads → New requests fail

Fix: ALWAYS use async def for AI endpoints
─────────────────────────────────────────
# WRONG
@app.post("/chat")
def chat(request):           # Sync = blocking!
    response = openai.chat() # Blocks thread
    return response

# RIGHT
@app.post("/chat")
async def chat(request):           # Async = non-blocking
    response = await openai.chat() # Releases thread while waiting
    return response
```

### ⚠️ Failure 5: Redis Connection Pool Exhaustion
```
Problem: Every request creates new Redis connection
         1000 concurrent users = 1000 Redis connections
         Redis max connections = 100 → Errors!

Fix: Connection pooling
───────────────────────
# Create ONE connection pool at startup
redis_pool = redis.ConnectionPool.from_url(
    "redis://localhost:6379",
    max_connections=50  # Shared pool of 50 connections
)
redis_client = redis.Redis(connection_pool=redis_pool)
# Now all requests share 50 connections efficiently
```

## 📌 SECTION 12: Interview Questions & Answers

### Q1: "What is the difference between sync and async in FastAPI?"

**Strong Answer:**
> *"Synchronous functions block the thread while waiting for I/O operations like API calls. With AI apps making 5-10 second LLM calls, sync endpoints mean one thread handles one user at a time. Async functions using async/await yield control back to the event loop during I/O waits, allowing FastAPI to handle thousands of concurrent requests with a single thread. For AI backends where most time is spent waiting for LLM responses, async is essential for scalability."*

---

### Q2: "When would you use background tasks vs synchronous endpoints?"

**Strong Answer:**
> *"I use synchronous endpoints for fast AI tasks under 10-15 seconds where users expect immediate responses — like chat completions. Background tasks are for long-running jobs: analyzing entire documents, processing audio, generating reports, or bulk operations. I return a job_id immediately with 202 Accepted, store progress in Redis, and provide a status endpoint users can poll. This prevents HTTP timeouts and gives better UX through progress tracking."*

---

### Q3: "How does rate limiting work and why is Redis used for it?"

**Strong Answer:**
> *"Rate limiting counts user requests within a time window and rejects excess requests with 429. Redis is ideal because: it's in-memory so checks are sub-millisecond, it supports atomic operations preventing race conditions, and it has built-in TTL so expired records clean themselves. I implement a sliding window algorithm — storing request timestamps in a sorted set, removing timestamps outside the window, and counting remaining. This is more accurate than fixed windows that allow bursts at window boundaries."*

---

### Q4: "How would you implement caching to reduce LLM API costs?"

**Strong Answer:**
> *"For deterministic queries — classification, structured extraction, factual lookups — I cache responses in Redis with a TTL. The cache key is an MD5 hash of the prompt plus model name. Important caveats: only cache when temperature=0 since higher temperatures produce varied outputs. Implement cache warming for common queries. Use semantic caching with embeddings to also catch near-duplicate questions. In production, this reduced our API costs by 60-70% for a FAQ chatbot."*

## 📌 SECTION 13: Common Mistakes

```
❌ Mistake 1: Not validating input size
   User sends 100,000 word prompt
   Your backend sends it all to OpenAI → huge token bill
   
   Fix: Always enforce max_length in Pydantic models
   max_length=4000 on message field

❌ Mistake 2: Exposing stack traces to users
   except Exception as e:
       return {"error": str(e)}  # WRONG! Shows internal code paths
   
   Fix: Log full error internally, return generic message
   Log the error → return "Internal server error"

❌ Mistake 3: Storing JWT in localStorage
   localStorage is accessible to JavaScript
   XSS attack can steal tokens
   
   Fix: Store in HTTP-only cookies (JavaScript can't access)

❌ Mistake 4: No timeout on LLM calls
   LLM hangs → Your endpoint hangs forever
   
   Fix: Always set timeout
   await asyncio.wait_for(llm_call(), timeout=30.0)

❌ Mistake 5: One Redis key for all users' rate limits
   key = "rate_limit" (same for everyone!)
   User A's requests count against User B
   
   Fix: Always include user_id in key
   key = f"rate:{user_id}"

❌ Mistake 6: Forgetting to handle Redis connection failures
   Redis goes down → Rate limiter crashes → Entire API crashes!
   
   Fix: Fail open on cache/rate limit errors
   try: check_rate_limit()
   except RedisError: pass  # Redis down → allow request through
```
