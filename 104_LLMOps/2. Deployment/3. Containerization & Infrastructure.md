## 📌 SECTION 1: What Is Containerization?

### Simple English Definition:

> **Containerization = Packaging your entire application — code, dependencies, environment settings, system libraries — into one portable box that runs IDENTICALLY everywhere.**

### The Core Idea In One Sentence:

> *"Don't ship code. Ship the entire environment that runs the code."*

### Real-Life Analogy:

> **Think about shipping physical goods.**
>
> **Before shipping containers (1950s):**
> Ships carried loose cargo — boxes, barrels, bags.
> Each port had different equipment.
> Loading/unloading took weeks.
> Things got lost, damaged, mixed up.
>
> **After shipping containers (1956):**
> Everything goes into a standard steel box.
> Same box. Any ship. Any port. Any crane.
> Load in New York → Unload in Shanghai → Same box, same contents.
> Time reduced from weeks to hours.
>
> **Docker Container = The shipping container of software.**
>
> Build once on your laptop.
> Run on any server, any cloud, any country.
> Exactly the same behavior. Every time.

```
│                                                                 │
```

### 3.2 — Your First Dockerfile For An AI App

#### Step by Step — Building Layer By Layer

```dockerfile
# ============================================================
# Dockerfile for Production AI API (FastAPI + LLM)
# ============================================================

# ── LAYER 1: BASE IMAGE ──────────────────────────────────────
# Start from an official Python image
# python:3.11-slim = Python 3.11 on minimal Linux (Debian)
# "slim" = smaller than full image, no unnecessary tools
# Always pin exact version! Never use "latest" in production
FROM python:3.11-slim

# WHY slim and not full?
# python:3.11         = 1.01 GB
# python:3.11-slim    = 125 MB
# Smaller = faster to pull, less attack surface, cheaper storage


# ── LAYER 2: SYSTEM DEPENDENCIES ─────────────────────────────
# Install system-level packages your app needs
# These are OS packages, not Python packages
RUN apt-get update && apt-get install -y \
    # For downloading files (health checks, file downloads)
    curl \
    # For C extensions that some Python packages need
    gcc \
    # git needed if installing packages from git repos
    git \
    # Clean up apt cache to keep image small
    && rm -rf /var/lib/apt/lists/*

# WHY && rm -rf /var/lib/apt/lists/* ?
# apt-get downloads package lists (big files)
# After install, we don't need them anymore
# Removing them = smaller final image


# ── LAYER 3: WORKING DIRECTORY ───────────────────────────────
# Set the working directory inside the container
# All subsequent commands run from here
# Like cd /app in terminal
WORKDIR /app


# ── LAYER 4: DEPENDENCIES (Smart Caching Trick!) ─────────────
# CRITICAL PATTERN: Copy requirements FIRST, then install
# BEFORE copying your actual code

# Why? Docker caches each layer.
# If requirements.txt didn't change → reuse cached layer
# If you changed your code but NOT requirements →
#   Python packages DON'T reinstall (saves 2-5 minutes!)

COPY requirements.txt .

RUN pip install --no-cache-dir --upgrade pip && \
    pip install --no-cache-dir -r requirements.txt

# --no-cache-dir = don't store pip cache (smaller image)
# --upgrade pip = get latest pip (avoids some install errors)


# ── LAYER 5: APPLICATION CODE ────────────────────────────────
# NOW copy your actual code
# This layer changes every time you change code
# But layer 4 (packages) is cached! Fast rebuilds.

COPY . .

# What does COPY . . mean?
# First . = source (your current directory on host machine)
# Second . = destination (WORKDIR = /app inside container)


# ── LAYER 6: SECURITY - NON-ROOT USER ────────────────────────
# By default, Docker runs as root (like admin)
# Running as root = security risk
# If container is compromised, attacker has root access
# Solution: Create a normal user

RUN adduser --disabled-password --gecos "" appuser
USER appuser

# Now container runs as "appuser" — limited permissions


# ── LAYER 7: EXPOSE PORT ─────────────────────────────────────
# Document which port this app uses
# This is just DOCUMENTATION — doesn't actually open port
# You still need to publish port with docker run -p

EXPOSE 8000


# ── LAYER 8: HEALTH CHECK ────────────────────────────────────
# Docker will call this to check if container is healthy
# If it fails repeatedly → container marked as "unhealthy"
# Load balancers stop sending traffic to unhealthy containers

HEALTHCHECK --interval=30s --timeout=10s --start-period=5s --retries=3 \
    CMD curl -f http://localhost:8000/health || exit 1

# --interval=30s   → Check every 30 seconds
# --timeout=10s    → Give 10 seconds to respond
# --start-period=5s → Wait 5s after start before first check
# --retries=3      → 3 failures = unhealthy


# ── LAYER 9: START COMMAND ───────────────────────────────────
# The command that runs when container starts

CMD ["uvicorn", "main:app", \
     "--host", "0.0.0.0", \    # Listen on all interfaces (not just localhost)
     "--port", "8000", \
     "--workers", "1"]          # 1 worker (Async handles concurrency)

# WHY --host 0.0.0.0 ?
# Without it → only localhost traffic reaches it
# Inside Docker, "localhost" is the container itself
# 0.0.0.0 = accept traffic from outside the container
```

### 3.4 — Docker Layer Caching (Understand This Deeply)

```
HOW DOCKER BUILDS WORK:
────────────────────────

Every instruction in Dockerfile = One LAYER

Layer 1: FROM python:3.11-slim          ← Cached after first build
Layer 2: RUN apt-get install...         ← Cached if unchanged
Layer 3: COPY requirements.txt .        ← Cached if file unchanged
Layer 4: RUN pip install...             ← Cached if layer 3 unchanged
Layer 5: COPY . .                       ← Changes on every code change
Layer 6: CMD uvicorn...                 ← Changes if CMD changes

SMART PATTERN (Fast Rebuilds):
────────────────────────────────

When you change ONLY your Python code:
✅ Layer 1: FROM → Cached (skip)
✅ Layer 2: apt-get → Cached (skip)
✅ Layer 3: COPY requirements.txt → Cached (skip)
✅ Layer 4: pip install → Cached (skip) ← HUGE TIME SAVER!
🔄 Layer 5: COPY . . → Rebuild (code changed)
🔄 Layer 6: CMD → Rebuild

Total rebuild time: 3 seconds (not 5 minutes)

WRONG PATTERN (Slow Rebuilds):
────────────────────────────────
# If you wrote this:
COPY . .                  ← Copies everything first
RUN pip install...        ← Re-runs EVERY time code changes!

Every single code change = Full pip install = 5+ minutes
This is the most common Docker beginner mistake!
```

### 3.5 — Docker Commands Cheatsheet

```bash
# ═══════════════════════════════════════════════
#          BUILDING IMAGES
# ═══════════════════════════════════════════════

# Build image from Dockerfile in current directory
# -t = tag (name:version)
docker build -t my-ai-app:1.0 .

# Build with specific Dockerfile
docker build -f Dockerfile.prod -t my-ai-app:prod .

# Build without cache (clean build)
docker build --no-cache -t my-ai-app:1.0 .

# See all built images
docker images
# or
docker image ls


# ═══════════════════════════════════════════════
#          RUNNING CONTAINERS
# ═══════════════════════════════════════════════

# Run container
# -d = detached (background)
# -p = port mapping HOST:CONTAINER
# --name = give it a friendly name
docker run -d -p 8000:8000 --name ai-api my-ai-app:1.0

# Run with environment variables (NEVER put secrets in Dockerfile!)
docker run -d \
  -p 8000:8000 \
  -e OPENAI_API_KEY=sk-... \
  -e REDIS_URL=redis://localhost:6379 \
  --name ai-api \
  my-ai-app:1.0

# Run with .env file (BETTER - don't expose secrets in terminal history)
docker run -d \
  -p 8000:8000 \
  --env-file .env \
  --name ai-api \
  my-ai-app:1.0

# Run with volume (persistent storage)
docker run -d \
  -p 8000:8000 \
  -v /host/data:/app/data \
  --name ai-api \
  my-ai-app:1.0


# ═══════════════════════════════════════════════
#          MANAGING CONTAINERS
# ═══════════════════════════════════════════════

# See running containers
docker ps

# See ALL containers (including stopped)
docker ps -a

# See container logs (crucial for debugging)
docker logs ai-api

# Follow logs in real-time (like tail -f)
docker logs -f ai-api

# See last 100 lines
docker logs --tail 100 ai-api

# Get container stats (CPU, memory, network)
docker stats ai-api

# Execute command inside running container
# (Like SSH into container)
docker exec -it ai-api bash

# Stop container gracefully
docker stop ai-api

# Kill container immediately
docker kill ai-api

# Remove container
docker rm ai-api

# Stop and remove in one command
docker rm -f ai-api


# ═══════════════════════════════════════════════
#          DEBUGGING TRICKS
# ═══════════════════════════════════════════════

# Run container interactively (don't use CMD, open terminal instead)
docker run -it --entrypoint bash my-ai-app:1.0

# Check what's inside the image
docker run -it my-ai-app:1.0 ls -la

# Inspect container configuration
docker inspect ai-api

# Check container resource usage
docker stats --no-stream ai-api
```

### 3.6 — Multi-Stage Builds (Production Best Practice)

```dockerfile
# Multi-stage build = Build in stages, keep only what's needed
# Result: Much smaller final image (important for fast deploys)

# ═══════════════════════════════════════════
# STAGE 1: BUILDER
# Install everything needed to BUILD the app
# ═══════════════════════════════════════════
FROM python:3.11-slim AS builder

WORKDIR /build

# Install build tools (only needed during build)
RUN apt-get update && apt-get install -y gcc curl

# Install dependencies
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt --target /build/packages


# ═══════════════════════════════════════════
# STAGE 2: PRODUCTION IMAGE
# Copy only what's needed to RUN the app
# Build tools, compilers → NOT included
# ═══════════════════════════════════════════
FROM python:3.11-slim AS production

WORKDIR /app

# Copy installed packages from builder stage
COPY --from=builder /build/packages /usr/local/lib/python3.11/site-packages/

# Copy only application code
COPY main.py .
COPY routers/ ./routers/
COPY services/ ./services/
COPY models/ ./models/

# Security: non-root user
RUN adduser --disabled-password appuser
USER appuser

EXPOSE 8000

HEALTHCHECK --interval=30s --timeout=10s --retries=3 \
    CMD curl -f http://localhost:8000/health || exit 1

CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]


# RESULT:
# Single-stage build:    ~800MB image
# Multi-stage build:     ~180MB image
# 4.4x smaller! Faster deploys, less storage cost, less attack surface
```

## 📌 SECTION 4: Environment Management

### 4.1 — The Problem With Secrets In Containers

```
THE WRONG WAY (NEVER DO THIS):
────────────────────────────────

# Dockerfile - NEVER embed secrets!
ENV OPENAI_API_KEY=sk-abc123   # 🚨 DANGEROUS!

# Why dangerous?
# 1. Image is stored in registry (could be public)
# 2. docker history shows all ENV values
# 3. Anyone with image access has your API key
# 4. Costs you money if key is stolen!


THE RIGHT WAY:
───────────────
Secrets → Injected at RUNTIME, not build time
Never baked into the image
```

### 4.2 — Environment Variable Strategies

```
STRATEGY 1: Direct injection (Development only)
────────────────────────────────────────────────
docker run -e OPENAI_API_KEY=sk-... my-ai-app

Problem: Visible in terminal history, ps aux output


STRATEGY 2: .env file (Development + Small teams)
───────────────────────────────────────────────────
# .env file (NEVER commit to git!)
OPENAI_API_KEY=sk-abc123
REDIS_URL=redis://localhost:6379
DATABASE_URL=postgresql://user:pass@localhost/db
JWT_SECRET=super-secret-key-change-in-production

docker run --env-file .env my-ai-app

Better: Not in terminal history
Still risky: .env file on disk


STRATEGY 3: Docker Secrets (Production)
─────────────────────────────────────────
# Create secret (encrypted, only accessible to authorized containers)
echo "sk-abc123" | docker secret create openai_key -

# Use in service
docker service create \
  --secret openai_key \
  my-ai-app

# In code:
with open('/run/secrets/openai_key', 'r') as f:
    OPENAI_API_KEY = f.read().strip()


STRATEGY 4: AWS Secrets Manager / HashiCorp Vault (Enterprise)
────────────────────────────────────────────────────────────────
# Secrets stored in dedicated secure system
# Fetched at runtime over encrypted connection
# Automatic rotation
# Audit logs of who accessed what secret
```

```python
# config.py — Environment-aware configuration
import os
from enum import Enum

class Environment(str, Enum):
    DEVELOPMENT = "development"
    STAGING = "staging"
    PRODUCTION = "production"

class Config:
    """
    Configuration loaded from environment variables.
    Never hardcode values here!
    """
    
    # Environment
    ENV: Environment = Environment(os.getenv("ENV", "development"))
    
    # AI Models
    if ENV == Environment.PRODUCTION:
        DEFAULT_MODEL = os.getenv("DEFAULT_MODEL", "gpt-4o")
    elif ENV == Environment.STAGING:
        DEFAULT_MODEL = os.getenv("DEFAULT_MODEL", "gpt-4o-mini")
    else:
        DEFAULT_MODEL = os.getenv("DEFAULT_MODEL", "local")  # Ollama
    
    # API Keys
    OPENAI_API_KEY: str = os.getenv("OPENAI_API_KEY", "")
    
    # Database
    REDIS_URL: str = os.getenv("REDIS_URL", "redis://localhost:6379")
    DATABASE_URL: str = os.getenv("DATABASE_URL", "")
    
    # Security
    JWT_SECRET_KEY: str = os.getenv("JWT_SECRET_KEY", "")
    
    # Performance
    WORKERS: int = int(os.getenv("WORKERS", "1"))
    MAX_TOKENS: int = int(os.getenv("MAX_TOKENS", "2000"))
    
    # Feature flags
    CACHE_ENABLED: bool = os.getenv("CACHE_ENABLED", "true").lower() == "true"
    DEBUG: bool = ENV == Environment.DEVELOPMENT
    
    def validate(self):
        """Crash at startup if required config is missing"""
        if self.ENV != Environment.DEVELOPMENT:
            assert self.OPENAI_API_KEY, "OPENAI_API_KEY is required!"
            assert self.JWT_SECRET_KEY, "JWT_SECRET_KEY is required!"
            assert self.DATABASE_URL, "DATABASE_URL is required!"
        return self

config = Config().validate()
```

## 📌 SECTION 5: Docker Compose — Running Multiple Services Together

### 5.1 — What Problem Does Compose Solve?

```
YOUR AI APP NEEDS MULTIPLE SERVICES:
──────────────────────────────────────

Without Compose (Manual Hell):
Terminal 1: docker run redis
Terminal 2: docker run chromadb
Terminal 3: docker run -p 8000:8000 my-ai-api
Terminal 4: docker run my-celery-worker
Terminal 5: docker run my-celery-worker
Terminal 6: docker run -p 80:80 nginx

6 separate commands!
They don't know about each other's IPs.
If Redis starts before your app is ready → crash.
To stop everything → kill each manually.
CHAOS.


With Docker Compose (One Command):
docker compose up

ONE command starts ALL services.
They share a network automatically.
Dependencies controlled (Redis starts before app).
docker compose down stops everything.
HARMONY. ✅
```

### 5.2 — Complete Docker Compose For AI App

```yaml
# docker-compose.yml
# Everything your AI application needs to run

version: "3.9"

# ═══════════════════════════════════════════════════════════════
#  NETWORKS — How services talk to each other
# ═══════════════════════════════════════════════════════════════
networks:
  ai_network:
    driver: bridge
    # All services on this network can reach each other by NAME
    # e.g., your app connects to Redis using hostname "redis"
    # Not IP address (IPs change!) — Service discovery by name


# ═══════════════════════════════════════════════════════════════
#  VOLUMES — Persistent data storage
# ═══════════════════════════════════════════════════════════════
volumes:
  redis_data:       # Redis data survives container restarts
  chromadb_data:    # Vector database data
  postgres_data:    # PostgreSQL data


# ═══════════════════════════════════════════════════════════════
#  SERVICES
# ═══════════════════════════════════════════════════════════════
services:

  # ─────────────────────────────────────────────────────────────
  # SERVICE 1: MAIN AI API (FastAPI)
  # ─────────────────────────────────────────────────────────────
  api:
    build:
      context: .            # Build from current directory
      dockerfile: Dockerfile
      target: production    # Use production stage (multi-stage)
    
    image: my-ai-app:latest
    container_name: ai_api
    
    ports:
      - "8000:8000"         # HOST_PORT:CONTAINER_PORT
    
    environment:
      - ENV=development
      - REDIS_URL=redis://redis:6379      # "redis" = service name
      - CHROMADB_URL=http://chromadb:8001
      - DATABASE_URL=postgresql://user:password@postgres:5432/aidb
    
    env_file:
      - .env                # Load secrets from .env file
    
    depends_on:
      redis:
        condition: service_healthy    # Wait for Redis health check
      postgres:
        condition: service_healthy
      chromadb:
        condition: service_started
    
    networks:
      - ai_network
    
    volumes:
      - ./logs:/app/logs    # Mount logs to host for debugging
    
    restart: unless-stopped  # Restart if crashes, unless manually stopped
    
    # Resource limits (prevent one service consuming everything)
    deploy:
      resources:
        limits:
          cpus: '2.0'       # Max 2 CPU cores
          memory: 2G        # Max 2GB RAM
        reservations:
          memory: 512M      # Guaranteed 512MB


  # ─────────────────────────────────────────────────────────────
  # SERVICE 2: CELERY WORKER (Background Tasks)
  # ─────────────────────────────────────────────────────────────
  worker:
    build:
      context: .
      dockerfile: Dockerfile
    
    # Override the CMD to run Celery instead of uvicorn
    command: celery -A celery_app worker --loglevel=info --concurrency=4
    
    environment:
      - ENV=development
      - REDIS_URL=redis://redis:6379
    
    env_file:
      - .env
    
    depends_on:
      redis:
        condition: service_healthy
    
    networks:
      - ai_network
    
    restart: unless-stopped
    
    deploy:
      resources:
        limits:
          cpus: '2.0'
          memory: 4G        # Workers need more RAM for AI models
    
    # Scale to multiple workers:
    # docker compose up --scale worker=3


  # ─────────────────────────────────────────────────────────────
  # SERVICE 3: REDIS (Cache + Queue)
  # ─────────────────────────────────────────────────────────────
  redis:
    image: redis:7-alpine   # Alpine = minimal Linux, smaller image
    container_name: ai_redis
    
    ports:
      - "6379:6379"         # Expose for local debugging
    
    command: >
      redis-server
      --maxmemory 512mb
      --maxmemory-policy allkeys-lru
      --appendonly yes
    
    # --maxmemory = Max RAM Redis uses
    # --maxmemory-policy allkeys-lru = When full, evict least recently used
    # --appendonly yes = Persist data to disk
    
    volumes:
      - redis_data:/data    # Persist Redis data
    
    networks:
      - ai_network
    
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 5s
      retries: 5
      start_period: 5s
    
    restart: unless-stopped


  # ─────────────────────────────────────────────────────────────
```

## 📌 SECTION 6: Nginx — The Reverse Proxy

### 6.1 — What Is Nginx And Why Do We Need It?

```
WITHOUT NGINX (Direct Access):
──────────────────────────────
User → http://yourserver.com:8000  ← Port exposed directly
                                      Ugly URL!
                                      No HTTPS!
                                      No load balancing!
                                      No rate limiting!
                                      One server = single point of failure


WITH NGINX (Reverse Proxy):
────────────────────────────
User → https://yourserver.com  ← Clean URL, HTTPS, port 443
             │
             ▼
           NGINX                ← The "front door"
             │
    ─────────┼─────────
    │         │         │
    ▼         ▼         ▼
  API:8000  API:8001  API:8002   ← Multiple app instances
```

### What Is A Reverse Proxy?

> **Reverse Proxy = A server that sits in front of your application servers and forwards requests to them.**

#### Real-Life Analogy:

> **Think of a hotel reception desk:**
>
> Guests don't go directly to hotel rooms.
> They go to reception first.
> Reception directs them: "Room 301, Room 205..."
> Reception also handles: Check-in (auth), "Do not disturb" (rate limiting), directing VIP guests (routing)
>
> **Nginx = The hotel reception desk for your servers**

### 6.2 — Complete Nginx Config For AI App

```nginx
# nginx/nginx.conf

# ═══════════════════════════════════════════════════════════════
# GLOBAL SETTINGS
# ═══════════════════════════════════════════════════════════════

# Number of worker processes
# Rule: Set to number of CPU cores
worker_processes auto;

# Max open file descriptors per worker
worker_rlimit_nofile 65535;

events {
    # Max concurrent connections per worker
    worker_connections 1024;
    
    # Accept multiple connections at once
    multi_accept on;
}


http {
    # ═══════════════════════════════════════════════════════════
    # BASIC SETTINGS
    # ═══════════════════════════════════════════════════════════
    
    # Don't show Nginx version in error pages (security!)
    server_tokens off;
    
    # Efficient file serving
    sendfile on;
    tcp_nopush on;
    tcp_nodelay on;
    
    # How long to keep connection alive (saves TCP handshake overhead)
    keepalive_timeout 65;
    
    # Max request body size (important for file upload AI apps!)
    client_max_body_size 50M;
    
    
    # ═══════════════════════════════════════════════════════════
    # LOGGING
    # ═══════════════════════════════════════════════════════════
    
    # Log format includes timing info (crucial for AI latency monitoring)
    log_format main '$remote_addr - $remote_user [$time_local] '
                    '"$request" $status $body_bytes_sent '
                    '"$http_referer" "$http_user_agent" '
                    'rt=$request_time';    # request_time = how long it took
    
    access_log /var/log/nginx/access.log main;
    error_log  /var/log/nginx/error.log warn;
    
    
    # ═══════════════════════════════════════════════════════════
    # UPSTREAM — Your Backend Servers
    # This is where load balancing happens!
    # ═══════════════════════════════════════════════════════════
    
    upstream ai_api {
        # Load balancing algorithm choices:
        # (default)  = round robin (request 1→server1, req2→server2...)
        # least_conn = send to server with fewest connections
        # ip_hash    = same user always goes to same server
        
        least_conn;   # Best for AI (some requests take longer)
        
        # List of backend servers
        # "api" = Docker service name (resolves to container IP)
        server api:8000 weight=1;
        
        # If you scale to multiple instances:
        # server api:8000 weight=2;   ← Twice as much traffic
        # server api:8001 weight=1;
        # server api:8002 weight=1;
        
        # Health checking
        # If server fails, temporarily remove it
        server api:8000 max_fails=3 fail_timeout=30s;
        
        # Keep connections alive to backend (performance!)
        keepalive 32;
    }
    
    
    # ═══════════════════════════════════════════════════════════
    # RATE LIMITING (Nginx-level, before app even sees request)
    # ═══════════════════════════════════════════════════════════
    
    # Define rate limit zone
    # $binary_remote_addr = User's IP address
    # zone=api_limit:10m  = 10MB memory for tracking IPs
    # rate=10r/s          = Max 10 requests per second per IP
    
    limit_req_zone $binary_remote_addr zone=api_limit:10m rate=10r/s;
    
    # Stricter limit for AI endpoints (expensive)
    limit_req_zone $binary_remote_addr zone=ai_limit:10m rate=2r/s;
    
    
    # ═══════════════════════════════════════════════════════════
    # SERVER BLOCK (HTTP → HTTPS redirect)
    # ═══════════════════════════════════════════════════════════
    
    server {
        listen 80;
        server_name yourdomain.com www.yourdomain.com;
        
        # Redirect all HTTP to HTTPS
        return 301 https://$host$request_uri;
    }
    
    
    # ═══════════════════════════════════════════════════════════
    # SERVER BLOCK (HTTPS — Main Server)
    # ═══════════════════════════════════════════════════════════
    
    server {
        listen 443 ssl http2;
        server_name yourdomain.com www.yourdomain.com;
        
        
        # ─────────────────────────────────────────────────────
        # SSL CONFIGURATION
        # ─────────────────────────────────────────────────────
        
        ssl_certificate     /etc/nginx/ssl/cert.pem;
        ssl_certificate_key /etc/nginx/ssl/key.pem;
        
        # Modern SSL settings (secure but compatible)
        ssl_protocols TLSv1.2 TLSv1.3;
        ssl_ciphers ECDHE-RSA-AES256-GCM-SHA512:DHE-RSA-AES256-GCM-SHA512;
        ssl_prefer_server_ciphers on;
        ssl_session_cache shared:SSL:10m;
        ssl_session_timeout 10m;
        
        
        # ─────────────────────────────────────────────────────
        # SECURITY HEADERS
        # ─────────────────────────────────────────────────────
        
        # Prevent clickjacking
        add_header X-Frame-Options "SAMEORIGIN" always;
        
        # Prevent MIME sniffing
        add_header X-Content-Type-Options "nosniff" always;
        
        # Force HTTPS (tell browser to always use HTTPS)
        add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
        
        # XSS Protection
        add_header X-XSS-Protection "1; mode=block" always;
        
        
        # ─────────────────────────────────────────────────────
        # CORS HEADERS (if not handled in FastAPI)
        # ─────────────────────────────────────────────────────
        
        add_header 'Access-Control-Allow-Origin' 'https://yourfrontend.com';
        add_header 'Access-Control-Allow-Methods' 'GET, POST, OPTIONS';
        add_header 'Access-Control-Allow-Headers' 'Authorization, Content-Type';
        
        
        # ─────────────────────────────────────────────────────
        # API ROUTING
        # ─────────────────────────────────────────────────────
        
        # Health check — no rate limiting, no auth
        location /health {
            proxy_pass http://ai_api;
            proxy_set_header Host $host;
        }
        
        # AI Chat endpoint — strict rate limiting
        location /api/v1/chat {
            # Apply strict rate limit (2 req/sec)
            limit_req zone=ai_limit burst=5 nodelay;
            limit_req_status 429;
            
            proxy_pass http://ai_api;
            
            # Pass important headers to backend
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
            
            # Timeouts (AI can be slow!)
            proxy_connect_timeout 10s;
            proxy_send_timeout 120s;     # 2 minutes for AI response
            proxy_read_timeout 120s;     # 2 minutes to read response
            
            # Streaming support (for SSE)
            proxy_buffering off;          # Don't buffer — stream immediately
            proxy_cache off;
            chunked_transfer_encoding on;
        }
        
        # General API — moderate rate limiting
        location /api/ {
            # Apply moderate rate limit
            limit_req zone=api_limit burst=20 nodelay;
            limit_req_status 429;
            
            proxy_pass http://ai_api;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            
            # Timeouts
            proxy_connect_timeout 10s;
            proxy_send_timeout 60s;
            proxy_read_timeout 60s;
        }
        
        
        # ─────────────────────────────────────────────────────
        # GZIP COMPRESSION (Faster responses!)
        # ─────────────────────────────────────────────────────
        
        gzip on;
        gzip_vary on;
        gzip_min_length 1000;
        gzip_types
            text/plain
            text/css
            application/json
            application/javascript
            text/xml;
        
        # DON'T gzip AI streaming responses
        # Compression + streaming = problems
        
        
        # ─────────────────────────────────────────────────────
        # CUSTOM ERROR PAGES
        # ─────────────────────────────────────────────────────
        
        error_page 429 /errors/rate_limit.json;
        error_page 502 503 504 /errors/service_unavailable.json;
        
        location /errors/ {
            internal;
            root /etc/nginx;
        }
    }
}
```

## 📌 SECTION 7: Scaling Replicas & Load Balancing

### 7.1 — Why Scale?

```
SCENARIO: Your AI app goes viral
─────────────────────────────────

Before viral moment:
100 users/hour → 1 server handles easily ✅

After viral moment:
10,000 users/hour → 1 server is overwhelmed ❌
- High latency (5s → 45s)
- Errors (500, 502)
- Users leave, don't come back
- Revenue lost

SOLUTION: Horizontal Scaling
───────────────────────────────
Add more servers (replicas) = Handle more users

1 server  → 100 users/hour
2 servers → 200 users/hour
10 servers → 1,000 users/hour
100 servers → 10,000 users/hour

THIS is why containerization matters:
Containers make it trivial to add replicas instantly.
```

### 7.2 — Vertical vs Horizontal Scaling

```
VERTICAL SCALING (Scale Up):
──────────────────────────────
Make existing server BIGGER
1 server: 4 CPU, 8GB RAM
→   1 server: 16 CPU, 64GB RAM

Pros:  Simple, no code changes
Cons:  Expensive, has a hard limit
       If this ONE server fails → complete outage!


HORIZONTAL SCALING (Scale Out):
─────────────────────────────────
Add MORE servers
1 server: 4 CPU, 8GB RAM
→   5 servers: 4 CPU, 8GB RAM each

Pros:  Cheaper at scale
       No single point of failure
       Theoretically unlimited scale
Cons:  App must be stateless (no local state)
       Need load balancer
       More complex
```

### 7.3 — Making AI Apps Stateless (Required For Scaling)

```
STATEFUL APP (Can't Scale Horizontally):
──────────────────────────────────────────
User conversation stored in SERVER MEMORY

Server 1 memory: User123's chat history = ["Hello", "How are you"]

Request 1 → Server 1 (stores memory)
Request 2 → Server 2 (no memory!) → AI forgets conversation!
Request 3 → Server 1 (has memory) → Works!

UNPREDICTABLE! Load balancer might route anywhere!


STATELESS APP (Scales Perfectly):
───────────────────────────────────
User conversation stored in SHARED REDIS (external)

Server 1, 2, 3 all connect to SAME Redis
All servers see SAME conversation history

Request 1 → Server 1 → Reads from Redis → Writes to Redis
Request 2 → Server 2 → Reads from Redis → Same history!
Request 3 → Server 3 → Reads from Redis → Same history!

CONSISTENT! Any server can handle any request!
```

```python
# WRONG: Stateful (can't scale)
class ChatBot:
    def __init__(self):
        self.conversations = {}  # Stored in SERVER MEMORY!
    
    async def chat(self, user_id: str, message: str):
        history = self.conversations.get(user_id, [])
        # If different server handles next request → history gone!


# RIGHT: Stateless (scales perfectly)
class ChatBot:
    def __init__(self, redis_client):
        self.redis = redis_client  # SHARED external storage
    
    async def chat(self, user_id: str, message: str):
        # Fetch from shared Redis (any server can fetch this)
        history_json = await self.redis.get(f"chat:{user_id}")
        history = json.loads(history_json) if history_json else []
        
        # Add new message
        history.append({"role": "user", "content": message})
        
        # Call AI
        response = await call_llm(history)
        
        # Save back to shared Redis
        history.append({"role": "assistant", "content": response})
        await self.redis.set(f"chat:{user_id}", json.dumps(history))
        
        return response
        # Now ANY server can handle next request! ✅
```

### 8.3 — Kubernetes YAML Files For AI App

#### Deployment (How to run your app):

```yaml
# k8s/api-deployment.yaml
apiVersion: apps/v1
kind: Deployment

metadata:
  name: ai-api
  namespace: production
  labels:
    app: ai-api
    version: "1.0"

spec:
  # ──────────────────────────────────────────
  # HOW MANY REPLICAS TO RUN
  # ──────────────────────────────────────────
  replicas: 3   # Always run 3 instances
  
  # Which pods does this deployment manage?
  selector:
    matchLabels:
      app: ai-api
  
  # ──────────────────────────────────────────
  # ROLLING UPDATE STRATEGY (Zero downtime!)
  # ──────────────────────────────────────────
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1         # Max extra pods during update
      maxUnavailable: 0   # Never have 0 running pods
  
  # HOW ROLLING UPDATE WORKS:
  # Old version: pod1, pod2, pod3  (all running)
  # Start update:
  #   1. Start new pod4 (surge)
  #   2. Wait for pod4 to be healthy
  #   3. Remove pod1
  #   4. Start pod5, remove pod2
  #   5. Start pod6, remove pod3
  # End: pod4, pod5, pod6 (all new version)
  # ZERO DOWNTIME! Users never see interruption.
  
  
  # ──────────────────────────────────────────
  # POD TEMPLATE (What each replica looks like)
  # ──────────────────────────────────────────
  template:
    metadata:
      labels:
        app: ai-api
    
    spec:
      containers:
        - name: ai-api
          image: your-registry/ai-api:1.0.0  # Exact version tag!
          
          ports:
            - containerPort: 8000
          
          # ────────────────────────────────
          # ENVIRONMENT VARIABLES
          # ────────────────────────────────
          env:
            - name: ENV
              value: "production"
            
            - name: REDIS_URL
              valueFrom:
                secretKeyRef:          # From Kubernetes Secret
                  name: ai-secrets
                  key: redis_url
            
            - name: OPENAI_API_KEY
              valueFrom:
                secretKeyRef:
                  name: ai-secrets
                  key: openai_api_key
          
          # ────────────────────────────────
          # RESOURCE LIMITS
          # ────────────────────────────────
          resources:
            requests:                  # Minimum guaranteed
              memory: "512Mi"
              cpu: "250m"              # 250 millicores = 0.25 CPU
            limits:                    # Maximum allowed
              memory: "2Gi"
              cpu: "2000m"             # 2000 millicores = 2 CPU
          
          # ────────────────────────────────
          # HEALTH CHECKS
          # ────────────────────────────────
          
          # LIVENESS PROBE: Is the container alive?
          # If this fails → Kubernetes RESTARTS the container
          livenessProbe:
            httpGet:
              path: /health
              port: 8000
            initialDelaySeconds: 30    # Wait 30s before first check
            periodSeconds: 10          # Check every 10 seconds
            failureThreshold: 3        # 3 failures = restart
          
          # READINESS PROBE: Is container ready to receive traffic?
          # If this fails → Kubernetes STOPS sending traffic (but doesn't restart)
          readinessProbe:
            httpGet:
              path: /health
              port: 8000
            initialDelaySeconds: 10
            periodSeconds: 5
            failureThreshold: 3
          
          # STARTUP PROBE: For slow-starting containers
          # Disables liveness probe until startup completes
          startupProbe:
            httpGet:
              path: /health
              port: 8000
            failureThreshold: 30
            periodSeconds: 10
            # Gives 5 minutes (30×10s) for startup
```

```yaml
        name: memory
        target:
          type: Utilization
          averageUtilization: 80    # Scale up if memory > 80%
  
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 60     # Wait 60s before scaling up
      policies:
        - type: Pods
          value: 2                       # Add max 2 pods at a time
          periodSeconds: 60
    
    scaleDown:
      stabilizationWindowSeconds: 300    # Wait 5 min before scaling DOWN
      # Don't scale down too fast — AI requests take time to finish!


# HOW AUTO-SCALING WORKS:
# 9 AM  - Traffic low   - 2 replicas running
# 10 AM - Traffic spikes - CPU hits 70%
# 10:01 - K8s adds 2 more replicas (now 4)
# 10:02 - Still high, adds 2 more (now 6)
# 12 PM - Traffic normal - K8s waits 5 min
# 12:05 - K8s removes 2 replicas (now 4)
# 1 PM  - Traffic low again - reduces to 2
# AUTOMATIC! No human intervention!
```

## 📌 SECTION 9: AWS ECS — Managed Containers Without Kubernetes Complexity

### 9.1 — What Is AWS ECS?

```
The Problem With Kubernetes:
──────────────────────────────
Kubernetes is POWERFUL but COMPLEX.
You need to:
- Manage the control plane
- Update Kubernetes version
- Configure networking (very complex!)
- Manage certificate rotation
- Learn 50+ YAML configurations

For many teams: Over-engineering!


AWS ECS (Elastic Container Service):
──────────────────────────────────────
AWS manages the complexity.
You just define: "Run these containers. Here's how many."
AWS handles: Scheduling, health checks, scaling, networking.
You focus on: Your AI application.

ECS = Kubernetes for teams who don't want to manage Kubernetes
```

### 9.2 — ECS Core Concepts

```
ECS ARCHITECTURE:
──────────────────

CLUSTER
│  (Group of compute resources)
│
├── TASK DEFINITION (like a Docker Compose file for one service)
│   "Run container with this image, this CPU, this memory,
│    these environment variables, these ports"
│
├── SERVICE
│   "Keep 3 tasks of this definition running at all times.
│    Auto-restart if any fail.
│    Load balance between them."
│
└── TASK
    "One running instance of a task definition"
    = One container (or group of containers)


LAUNCH TYPES:

ECS on EC2:
├── You manage EC2 servers
├── More control
└── More responsibility

ECS on FARGATE (Serverless):
├── AWS manages servers
├── You just define CPU + memory
├── Pay per task run time
└── RECOMMENDED for AI apps
```

### 9.4 — Deploying To ECS (Step by Step)

```bash
# STEP 1: Build and push image to ECR (AWS's Docker registry)
# ──────────────────────────────────────────────────────────

# Login to ECR
aws ecr get-login-password --region us-east-1 | \
  docker login --username AWS \
  --password-stdin ACCOUNT.dkr.ecr.us-east-1.amazonaws.com

# Build image
docker build -t ai-api:1.0.0 .

# Tag for ECR
docker tag ai-api:1.0.0 \
  ACCOUNT.dkr.ecr.us-east-1.amazonaws.com/ai-api:1.0.0

# Push to ECR
docker push ACCOUNT.dkr.ecr.us-east-1.amazonaws.com/ai-api:1.0.0


# STEP 2: Register Task Definition
# ──────────────────────────────────
aws ecs register-task-definition \
  --cli-input-json file://task-definition.json


# STEP 3: Create/Update ECS Service
# ───────────────────────────────────
aws ecs update-service \
  --cluster production-cluster \
  --service ai-api-service \
  --task-definition ai-api-task:2 \  # New version
  --desired-count 3 \                  # 3 replicas
  --deployment-configuration \
    "minimumHealthyPercent=100,maximumPercent=200"

# minimumHealthyPercent=100 = Never go below 3 running tasks
# maximumPercent=200 = Can go up to 6 during deployment (rolling)


# STEP 4: Watch deployment
# ──────────────────────────
aws ecs describe-services \
  --cluster production-cluster \
  --services ai-api-service
```

## 📌 SECTION 11: Failure Modes (Critical!)

### ⚠️ Failure 1: Image Size Explosion

```
Problem:
You put everything in your image including:
- Downloaded model weights (5GB for Mistral!)
- Entire Python venv
- Build tools left behind
Result: 8GB Docker image
       - Takes 15 minutes to pull in production
       - Costs $50/month just for image storage

Fix:
- Multi-stage builds (remove build tools)
- Never put model weights in images
  → Download them at startup from S3
- Use .dockerignore aggressively
- Use slim base images
- Target: < 500MB for most AI API apps
```

### ⚠️ Failure 2: Container Starts But App Doesn't

```
Problem:
Container shows as "running"
But application inside crashed on startup
Users see 502 Bad Gateway

Why it's hard to debug:
Container is "running" (process 1 is alive)
But your Python app crashed immediately
No health check catches this!

Fix:
Always configure proper health checks
livenessProbe:
  httpGet:
    path: /health     # Your app must respond here
    port: 8000
  initialDelaySeconds: 30    # Critical! App needs time to start
  failureThreshold: 3

And make /health truly verify the app is ready:
@app.get("/health")
async def health():
    # Verify database connection
    await db.execute("SELECT 1")
    # Verify Redis connection
    await redis.ping()
    # Verify LLM service accessible
    return {"status": "healthy"}
```

### ⚠️ Failure 3: OOMKilled (Out of Memory)

```
Problem:
Kubernetes sets memory limit = 1GB
Your app loads LLM → Uses 3GB RAM
Container KILLED by Kubernetes!
Pod restarts in a loop → CrashLoopBackOff

This is VERY common with self-hosted LLMs!

Fix:
1. Profile actual memory usage first:
   docker stats your-container

2. Set realistic limits:
   LLM 7B model = needs 8GB+ RAM minimum!
   
3. Use right-sized instances:
   CPU inference = 16GB RAM nodes
   GPU inference = GPU instances

4. Use quantized models (smaller memory):
   Mistral 7B FP16 = 14GB
   Mistral 7B INT4  = 4GB  ← 3.5x smaller!
```

### ⚠️ Failure 4: Secrets In Docker History

```
Problem:
ENV OPENAI_API_KEY=sk-abc123   ← IN DOCKERFILE

Even if you "remove" it later:
docker history my-ai-app --no-trunc

Shows EVERY command including ENV with the key!
Anyone with image access has your key!

Fix:
NEVER use ENV for secrets in Dockerfile.
Inject at runtime:
docker run --env-file .env my-ai-app

Or use Docker secrets / K8s secrets.
```

### ⚠️ Failure 5: Shared State Between Replicas

```
Problem:
User's conversation stored in container memory
2 replicas running
Request 1 → Replica 1 (stores conversation)
Request 2 → Replica 2 (no conversation!) 
AI says "Hello, I'm new here!" even mid-conversation

Fix:
Store ALL shared state in external Redis
Every piece of state that must persist across requests
MUST be in Redis, not in-memory variables
Test by running 2 replicas locally and checking consistency
```

## 📌 SECTION 12: Interview Questions & Answers

### Q1: "What is the difference between Docker image and container?"

**Strong Answer:**
> *"An image is an immutable, read-only template — like a class in programming. A container is a running instance of that image — like an object. You can run multiple containers from one image simultaneously. Images are stored in registries and pulled to servers. Containers are ephemeral — they start, run, and stop. This is why we never store important data inside containers; it disappears when the container stops."*

---

### Q2: "Why is Docker layer caching important for AI projects?"

**Strong Answer:**
> *"AI apps have heavy dependencies — sometimes 2-5GB of Python packages. Without proper layer caching, every code change rebuilds all packages from scratch, taking 10-15 minutes per build. The pattern is: copy requirements.txt first, run pip install, then copy application code. Since requirements rarely change but code changes constantly, pip install stays cached. This reduces rebuild time from 10 minutes to 30 seconds."*

---

### Q3: "When would you choose Kubernetes over ECS?"

**Strong Answer:**
> *"I'd choose ECS for AWS-focused teams who want managed infrastructure, faster time-to-production, and are comfortable with vendor lock-in. ECS handles scheduling and scaling without the operational burden of managing Kubernetes. I'd choose Kubernetes when we need multi-cloud portability, more sophisticated deployment patterns like canary releases, custom resource definitions, or when running on-premises alongside cloud. For most AI startups under 50 engineers, ECS Fargate hits the sweet spot of power versus operational complexity."*

---

### Q4: "How do you ensure zero-downtime deployments for an AI API?"

**Strong Answer:**
> *"Several strategies work together: Rolling updates ensure new pods are healthy before old ones are removed. Readiness probes prevent traffic from reaching pods that aren't ready — crucial for AI apps with slow startup times. Resource limits prevent one deployment from starving others. For database migrations, I use blue-green deployments — spin up entirely new environment, run migrations, test, then switch traffic. For LLM model updates specifically, I'd overlap old and new model loading since loading can take 30+ seconds."*

## 📌 SECTION 13: Common Beginner Mistakes

```
❌ Mistake 1: Using :latest tag in production
   docker pull my-app:latest
   "latest" changes meaning → unpredictable deployments
   Fix: Always use specific version tags: my-app:1.2.3

❌ Mistake 2: Running as root in containers
   Default = root user
   Security breach in container = root access to host!
   Fix: Always add non-root user in Dockerfile

❌ Mistake 3: Not setting resource limits
   One AI model loads 8GB RAM → starves other containers
   Fix: Always set memory and CPU limits

❌ Mistake 4: Storing important data in container filesystem
   Container crashes → data is lost forever
   Fix: Use volumes for any data that must persist

❌ Mistake 5: One giant container for everything
   Put FastAPI + Redis + Celery + Nginx all in one container
   If anything fails → everything fails
   Can't scale components independently
   Fix: One process per container (microservices)

❌ Mistake 6: Ignoring .dockerignore
   Copying .env, node_modules, .git into container
   Slow builds, huge images, security leaks
   Fix: Create comprehensive .dockerignore before first build

❌ Mistake 7: Hard-coding health check path
   /health returns 200 even when database is down
   Load balancer sends traffic to broken container
   Fix: Health check must verify all critical dependencies
```
