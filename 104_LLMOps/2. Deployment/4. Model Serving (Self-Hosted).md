## 📌 SECTION 2: GPU Inference — Understanding The Hardware

#### What a CPU Does:

```
────────────────────────────────

Very smart. Very fast at complex tasks.

Excellent at branching logic (if/else)

For AI: Must multiply millions of numbers
CPU core: "I'll multiply number 1, then number 2, then number 3..."
Very sequential → SLOW for AI
```

#### What a GPU Does:

```
GPU (Graphics Processing Unit):
─────────────────────────────────
Think of a GPU as a CLASSROOM OF STUDENTS.

Each student is NOT as smart as the professor.
But there are 10,000 students working simultaneously.
ALL can do simple math at the exact same moment.

NVIDIA A100: 6,912 CUDA cores
NVIDIA H100: 16,896 CUDA cores

For AI: "Multiply ALL these numbers simultaneously"
GPU cores: [×] [×] [×] [×] ... 10,000 multiplications AT ONCE

```

#### Why This Matters For LLMs:

```
Transformer Model (LLM) Math:
──────────────────────────────
Every single token generation requires:
- Matrix multiplications: billions of operations
- Each operation: simple multiply + add
- All can be done IN PARALLEL

- ~14 billion multiply-add operations
- CPU: 14B operations ÷ (64 cores × 1B ops/s) ≈ 220 seconds!
- GPU: 14B operations ÷ (6912 cores × 10B ops/s) ≈ 0.2 seconds

```

```
The model weights must be read from memory for EVERY token.
Faster memory reads = faster token generation.
VRAM is 40x faster than RAM → GPU wins completely.
```

### 2.3 — The KV Cache — The Secret Sauce of Fast LLM Serving

This is the concept that separates junior from senior AI engineers:

#### What Is The KV Cache?

```
UNDERSTANDING TOKEN GENERATION:
─────────────────────────────────

When LLM generates "Hello world how are you":

Step 1: Generate "Hello"
        Process: [nothing] → "Hello"
        
Step 2: Generate "world"
        Process: ["Hello"] → "Hello world"
        ← Must re-read "Hello" again!

Step 3: Generate "how"
        Process: ["Hello", "world"] → "Hello world how"
        ← Must re-read "Hello" AND "world" again!

Step 4: Generate "are"
        Process: ["Hello", "world", "how"] → ...
        ← Re-reads "Hello", "world", "how" AGAIN!

PROBLEM: Each new token requires re-reading ALL previous tokens!
         For a 1000 token response: token 1000 reads 999 tokens first!
         Computation grows: O(n²) — catastrophically slow!
```

```
KV CACHE SOLUTION:
───────────────────

"Key-Value" Cache stores intermediate computations.

Step 1: Generate "Hello"
        Compute K,V for "Hello" → STORE in cache
        
Step 2: Generate "world"
        REUSE cached K,V for "Hello" ← Don't recompute!
        Just compute new K,V for "world" → STORE
        
Step 3: Generate "how"
        REUSE cached K,V for "Hello", "world"
        Just compute new K,V for "how" → STORE

RESULT:
→ Each new token = O(n) instead of O(n²)
→ 10x-100x faster generation for long sequences!

BUT: KV Cache takes GPU MEMORY!
Long conversations = More KV cache = Less memory for more users
This creates a TENSION: quality vs throughput
```

## 📌 SECTION 3: Quantized Inference — Serving Bigger Models

### 3.1 — What Is Quantization?

> **Quantization = Representing model weights with FEWER bits — making the model smaller and faster, with acceptable quality loss.**

#### Real-Life Analogy:

> **Think of music audio quality:**
>
> **WAV file (uncompressed) = 1,411 kbps**
> Perfect quality. Huge file (50MB for 5 min song).
>
> **MP3 (192kbps) = 192 kbps**
> 93% smaller. Human ear can barely tell the difference.
>
> **MP3 (64kbps) = 64 kbps**
> Tiny file. Noticeable quality loss.
>
> **LLM Quantization = MP3 compression for AI model weights**

### 3.2 — Quantization Types Explained From Zero

#### First: What Are "Bits" and "Precision"?

```
Computer stores numbers in binary (0s and 1s = "bits")

FP32 (32-bit Float):
────────────────────
32 bits per number
Example: 3.14159265358979... (very precise)
Range: Can represent -3.4×10³⁸ to +3.4×10³⁸
Memory: 4 bytes per weight

FP16 (16-bit Float):
─────────────────────
16 bits per number
Example: 3.140625 (less precise)
Range: -65504 to +65504
Memory: 2 bytes per weight (50% smaller!)

INT8 (8-bit Integer):
──────────────────────
8 bits per number
Example: 3 (integer only, no decimals!)
Range: -128 to 127
Memory: 1 byte per weight (75% smaller than FP32!)

INT4 (4-bit Integer):
──────────────────────
4 bits per number
Range: -8 to 7 (only 16 possible values!)
Memory: 0.5 bytes per weight (87.5% smaller!)
```

#### Visual Comparison:

```
ORIGINAL WEIGHT VALUE: 3.14159265

FP32:   [1][01000000][10010000111111001110110]  = 3.14159265 (exact)
        32 bits                                   4 bytes

FP16:   [0][10000][0010010]                     = 3.140625  (close)
        16 bits                                   2 bytes

INT8:   [00000011]                              = 3          (rough)
        8 bits                                    1 byte

INT4:   [0011]                                  = 3          (roughest)
        4 bits                                    0.5 byte
```

### 3.3 — Quantization Methods (From Simple to Advanced)

#### Method 1: Post-Training Quantization (PTQ)

```
CONCEPT: Take already-trained FP16 model → Convert to INT8/INT4
         No retraining needed!
         Fast. Easy. Some quality loss.

POPULAR FORMATS:

GGUF (used by Ollama, llama.cpp):
──────────────────────────────────
Created by Georgi Gerganov
GGUF = GPT-Generated Unified Format
Can run on CPU too! (slower but no GPU needed)

Variants:
Q2_K   = 2-bit  (smallest, worst quality)
Q4_0   = 4-bit  (sweet spot for most use cases)
Q4_K_M = 4-bit  (better quality, slightly larger)
Q5_K_M = 5-bit  (great quality, medium size)
Q6_K   = 6-bit  (very close to original quality)
Q8_0   = 8-bit  (almost identical to FP16, 50% smaller)
F16    = 16-bit (original, no quantization)


GPTQ (used by vLLM, HuggingFace):
───────────────────────────────────
More GPU-optimized than GGUF
Better quality than naive INT8
Designed specifically for GPU inference

AWQ (Activation-Aware Weight Quantization):
─────────────────────────────────────────────
2023 method from MIT
Smarter: finds which weights MATTER most
Protects important weights, aggressively quantizes unimportant ones
Result: Better quality than GPTQ at same bit-width
```

#### Method 2: BitsAndBytes (bitsandbytes library)

```python
# Easy quantization with HuggingFace + bitsandbytes
# pip install bitsandbytes transformers accelerate

from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig
import torch

# ── INT8 Quantization (8-bit) ─────────────────────────────
quantization_config_int8 = BitsAndBytesConfig(
    load_in_8bit=True,           # Enable 8-bit quantization
    llm_int8_threshold=6.0,      # Threshold for outlier handling
    llm_int8_skip_modules=None   # Which layers to NOT quantize
)

# ── INT4 Quantization (4-bit, most aggressive) ────────────
quantization_config_int4 = BitsAndBytesConfig(
    load_in_4bit=True,               # Enable 4-bit quantization
    bnb_4bit_compute_dtype=torch.float16,  # Compute in FP16 during inference
    bnb_4bit_quant_type="nf4",       # NormalFloat4 (best quality INT4)
    bnb_4bit_use_double_quant=True   # Quantize the quantization constants too!
    # "Double quantization" = extra 15% memory savings
)

# Load model with quantization
model_name = "meta-llama/Meta-Llama-3-8B-Instruct"

tokenizer = AutoTokenizer.from_pretrained(model_name)

model = AutoModelForCausalLM.from_pretrained(
    model_name,
    quantization_config=quantization_config_int4,
    device_map="auto",          # Automatically place on GPU/CPU
    torch_dtype=torch.float16
)

# Check actual memory usage
print(f"Model memory: {model.get_memory_footprint() / 1e9:.2f} GB")
# LLaMA 8B FP16: 16.0 GB
# LLaMA 8B INT4: ~4.5 GB  ← 3.5x smaller!
```

## 📌 SECTION 4: Batch vs Real-Time Serving

### 4.1 — What Is Batching?

> **Batching = Processing MULTIPLE requests TOGETHER in one GPU pass, instead of one at a time.**

#### Real-Life Analogy:

> **Think of a taxi vs a bus:**
>
> **Taxi (No batching):**
> Takes Person A to downtown. Returns.
> Takes Person B to downtown. Returns.
> 10 trips for 10 people → 10 × 10 minutes = 100 minutes
>
> **Bus (Batching):**
> Picks up all 10 people.
> ONE trip downtown.
> 10 people → 10 minutes total!
>
> **BUT:** Bus has a schedule (must wait for enough passengers).
> **Batch inference = Bus model for GPU computation**

### 4.2 — Why Batching Matters For GPU Utilization

```
GPU UTILIZATION WITHOUT BATCHING:
───────────────────────────────────

GPU has 6,912 CUDA cores.
1 request uses maybe 100-200 cores.
Other 6,712 cores sit IDLE.
GPU utilization: 3%

You paid $2,000/month for 3% utilization!

GPU UTILIZATION WITH BATCHING:
────────────────────────────────

Group 32 requests together.
Send all 32 through GPU simultaneously.
6,912 cores now actually busy.
GPU utilization: 80-90%

Same hardware → 30x more throughput!
Same cost → 30x more users served.
```

### 4.3 — Types of Batching

#### Static Batching (Simple, Old Way):

```
STATIC BATCHING:
──────────────────
Wait for N requests to arrive
Bundle them together
Process as one batch
Return results

PROBLEM 1: You must WAIT for batch to fill
           If batch size = 8 and only 3 users are waiting...
           3 users wait until 5 more arrive!
           Adds latency for users.

PROBLEM 2: All sequences must be SAME LENGTH
           Request A: "Hi" → padded to: "Hi [PAD] [PAD] [PAD] [PAD]"
           Request B: "Tell me the history of..."
           Padding wastes computation!
```

#### Continuous Batching (Modern, Smart Way):

```
CONTINUOUS BATCHING (used by vLLM, TGI):
──────────────────────────────────────────

No waiting for batch to fill!
New requests JOIN the batch as they arrive.
Completed requests LEAVE the batch immediately.
Batch size is always optimally full.

TIMELINE:
─────────────────────────────────────────────────
Time 0: [RequestA]                     ← Start
Time 1: [RequestA, RequestB]           ← B joins
Time 2: [RequestA, RequestB, RequestC] ← C joins
Time 3: [RequestA_DONE, RequestB, RequestC, RequestD] 
         ↑ A finished! D takes A's slot immediately
Time 4: [RequestB, RequestC, RequestD, RequestE]
         ↑ B finished! E takes B's slot
...

RESULT:
→ GPU never goes idle between requests
→ No padding waste
→ New requests start immediately
→ 2-10x higher throughput vs static batching!
```

### 4.4 — Real-Time vs Batch Serving

```
REAL-TIME SERVING:
───────────────────
User types message → Immediate response needed
Target latency: < 5 seconds
Examples: Chatbot, code completion, Q&A

Requirements:
- Continuous batching (for throughput)
- Streaming (token by token, feels faster)
- Low latency optimization
- Always-on server


BATCH SERVING (Offline Processing):
────────────────────────────────────
No user waiting! Background processing.
Target latency: Minutes to hours is fine
Examples:
- "Summarize 10,000 news articles overnight"
- "Generate product descriptions for entire catalog"
- "Analyze all customer reviews from last month"
- Embedding generation for vector database

Requirements:
- Maximum throughput (process as many as possible)
- Can use largest possible batch sizes
- Can run on spot/preemptible instances (cheaper!)
- Doesn't matter if it takes 2 hours instead of 1


COMPARISON:
────────────────────────────────────────────────────
Feature          Real-Time          Batch
────────────────────────────────────────────────────
Latency          Milliseconds       Minutes-Hours
Throughput       Medium             Maximum
Cost             Higher (always on) Lower (spot instances)
User experience  Interactive        Not real-time
GPU optimization Continuous batch   Largest possible batch
Examples         Chatbot, Search    Reports, ETL, Embeddings
```

## 📌 SECTION 5: vLLM — The Industry Standard

### 5.1 — What Is vLLM?

```
vLLM = "Virtual Large Language Model"

Created by: UC Berkeley Sky Computing Lab (2023)
Used by:    OpenAI, Anthropic, Google (for serving)
GitHub:     50,000+ stars

THE KEY INNOVATION: PagedAttention

Before vLLM:
─────────────
GPU memory allocated statically for KV cache
Every request = reserved maximum possible memory
Mostly wasted! 80% of allocated memory = empty

vLLM's PagedAttention:
────────────────────────
Borrows from Operating System memory management
"Virtual Memory" for KV cache
Memory allocated in small pages, only when needed
Result: 3-10x more requests fit in same GPU!
```

### 5.2 — PagedAttention — The Core Innovation

#### How Operating System Virtual Memory Works:

```
OS VIRTUAL MEMORY (The inspiration):
──────────────────────────────────────
Program needs 1GB RAM
But RAM only has 256MB free

OS solution:
- Allocates memory in small "pages" (4KB each)
- Only loads pages that are ACTUALLY NEEDED
- Stores less-used pages on disk
- Program thinks it has 1GB, actually uses 256MB smartly


PAGEATTENTION (Same idea for KV cache):
──────────────────────────────────────────
Old approach:
Each request pre-allocated 2048 tokens × memory
Request uses only 50 tokens → 97.5% wasted!

PagedAttention approach:
- KV cache divided into small "blocks" (16-32 tokens each)
- Memory allocated per block, only when needed
- Blocks NOT contiguous in memory (virtual addressing)
- SHARE blocks between requests with same prefix!
```

#### Prefix Sharing (Bonus Feature):

```
PREFIX SHARING EXAMPLE:
────────────────────────

10 users all send:
"You are a helpful AI assistant. User: [different questions]"

Old approach: All 10 requests compute KV cache for
              "You are a helpful AI assistant." independently
              10 × (system prompt computation) = wasted!

PagedAttention: 
System prompt = computed ONCE → SHARED between all 10 requests
              = 10x less computation for the common prefix!
              = More users served for same cost

This is why vLLM is dramatically more efficient.
```

#### Method 2: Use vLLM in Python Code

```python
# Direct Python usage
from vllm import LLM, SamplingParams
from vllm.entrypoints.openai.api_server import run_server

# ── BASIC INFERENCE ────────────────────────────────────────
llm = LLM(
    model="meta-llama/Meta-Llama-3-8B-Instruct",
    
    # Memory settings
    gpu_memory_utilization=0.9,    # Use 90% VRAM for KV cache
    max_model_len=8192,            # Max sequence length
    
    # Parallelism
    tensor_parallel_size=1,        # Number of GPUs
    pipeline_parallel_size=1,      # Pipeline stages
    
    # Quantization
    dtype="float16",               # or "bfloat16", "auto"
    # quantization="awq",          # Enable for AWQ models
    
    # Performance
    enable_prefix_caching=True,    # Cache common prefixes!
    
    # Batch settings
    max_num_batched_tokens=4096,   # Max tokens in one batch
    max_num_seqs=256,              # Max concurrent sequences
)

# Define sampling parameters
sampling_params = SamplingParams(
    temperature=0.7,        # Randomness (0=deterministic, 1=creative)
    top_p=0.9,              # Nucleus sampling
    top_k=50,               # Top-k sampling
    max_tokens=512,         # Max response length
    stop=["</s>", "[INST]"] # Stop generation at these tokens
)

# ── BATCH INFERENCE (Most Efficient!) ─────────────────────
prompts = [
    "Explain quantum computing in simple terms",
    "What is the capital of France?",
    "Write a Python function to sort a list",
    "Translate 'Hello world' to Spanish",
    # ... can be hundreds of prompts
]

# Process ALL prompts at once - maximum GPU efficiency!
outputs = llm.generate(prompts, sampling_params)

for output in outputs:
    prompt = output.prompt
    generated_text = output.outputs[0].text
    tokens_generated = len(output.outputs[0].token_ids)
    
    print(f"Prompt: {prompt[:50]}...")
    print(f"Response: {generated_text}")
    print(f"Tokens: {tokens_generated}")
    print("─" * 50)
```

```python
# ── Configuration ─────────────────────────────────────────
class Config:

    api_key="ollama"

# ── Request Models ─────────────────────────────────────────
class ChatRequest(BaseModel):
    message: str = Field(..., min_length=1, max_length=8000)
    system_prompt: Optional[str] = "You are a helpful AI assistant."
    temperature: float = Field(default=0.7, ge=0.0, le=2.0)
    max_tokens: int = Field(default=500, ge=1, le=4096)
    stream: bool = False


# ── Chat Endpoint ──────────────────────────────────────────
@app.post("/chat")
async def chat(request: ChatRequest):
    """Chat with self-hosted LLM"""
    
    if request.stream:
        return StreamingResponse(
            stream_response(request),
            media_type="text/event-stream"
        )
    
    return await generate_response(request)


async def generate_response(request: ChatRequest) -> dict:
    """Try vLLM first, fallback to Ollama"""
    
    start_time = time.time()
    
    messages = [
        {"role": "system", "content": request.system_prompt},
        {"role": "user", "content": request.message}
    ]
    
    try:
        # Try vLLM (primary)
        response = await asyncio.wait_for(
            vllm_client.chat.completions.create(
                model=config.MODEL_NAME,
                messages=messages,
                temperature=request.temperature,
                max_tokens=request.max_tokens
            ),
            timeout=30.0
        )
        
        return {
            "response": response.choices[0].message.content,
            "model": config.MODEL_NAME,
            "server": "vllm",
            "tokens_used": response.usage.total_tokens,
            "latency_ms": int((time.time() - start_time) * 1000)
        }
    
    except Exception as e:
        print(f"vLLM failed: {e}. Trying Ollama fallback...")
        
        try:
            # Fallback to Ollama
            response = await asyncio.wait_for(
                ollama_client.chat.completions.create(
                    model=config.FALLBACK_MODEL,
                    messages=messages,
                    temperature=request.temperature,
                    max_tokens=request.max_tokens
                ),
                timeout=60.0  # Ollama is slower
            ),
            timeout=60.0
        )
        
        return {
            "response": response[0].choices[0].message.content,
            "model": config.FALLBACK_MODEL,
            "server": "ollama_fallback",
            "latency_ms": int((time.time() - start_time) * 1000)
        }
        
        except Exception as e2:
            raise HTTPException(
                status_code=503,
                detail=f"All LLM servers unavailable: {str(e2)}"
            )


async def stream_response(request: ChatRequest) -> AsyncIterator[str]:
    """Stream tokens from vLLM"""
    
    messages = [
        {"role": "system", "content": request.system_prompt},
        {"role": "user", "content": request.message}
    ]
    
    try:
        stream = await vllm_client.chat.completions.create(
            model=config.MODEL_NAME,
            messages=messages,
            temperature=request.temperature,
            max_tokens=request.max_tokens,
            stream=True
        )
        
        async for chunk in stream:
            if chunk.choices[0].delta.content:
                token = chunk.choices[0].delta.content
                yield f"data: {json.dumps({'token': token})}\n\n"
        
        yield "data: [DONE]\n\n"
    
    except Exception as e:
        yield f"data: {json.dumps({'error': str(e)})}\n\n"


# ── Batch Endpoint ─────────────────────────────────────────
class BatchRequest(BaseModel):
    prompts: list[str] = Field(..., min_length=1, max_length=100)
    max_tokens: int = Field(default=200, ge=1, le=2048)
    temperature: float = Field(default=0.3, ge=0.0, le=2.0)

@app.post("/batch")
async def batch_generate(request: BatchRequest):
    """Process multiple prompts simultaneously"""
    
    start_time = time.time()
    
    # Send all prompts concurrently to vLLM
    tasks = [
        vllm_client.chat.completions.create(
            model=config.MODEL_NAME,
            messages=[{"role": "user", "content": prompt}],
            temperature=request.temperature,
            max_tokens=request.max_tokens
        )
        for prompt in request.prompts
    ]
    
    responses = await asyncio.gather(*tasks, return_exceptions=True)
    
    results = []
    for i, response in enumerate(responses):
        if isinstance(response, Exception):
            results.append({"prompt": request.prompts[i], "error": str(response)})
        else:
            results.append({
                "prompt": request.prompts[i],
                "response": response.choices[0].message.content,
                "tokens": response.usage.total_tokens
            })
    
    total_time = int((time.time() - start_time) * 1000)
    
    return {
        "results": results,
        "total_prompts": len(request.prompts),
        "total_time_ms": total_time,
        "avg_time_per_prompt_ms": total_time // len(request.prompts)
    }
```

## 📌 SECTION 11: Failure Modes (Critical!)

### ⚠️ Failure 1: CUDA Out of Memory (OOM)

```
SYMPTOM:
RuntimeError: CUDA out of memory.
Tried to allocate X.XX GiB but only X.XX GiB free.

WHY IT HAPPENS:
────────────────
1. Model too large for GPU
2. KV cache fills up (too many concurrent users)
3. Memory leak (model reloaded multiple times)
4. Batch size too large

DEBUGGING STEPS:
─────────────────
# See GPU memory usage in real-time
watch -n 1 nvidia-smi

# Check allocated vs reserved memory in Python
import torch
print(f"Allocated: {torch.cuda.memory_allocated()/1e9:.2f}GB")
print(f"Reserved:  {torch.cuda.memory_reserved()/1e9:.2f}GB")

FIXES BY CAUSE:
────────────────
Model too large     → Use quantization (INT4/INT8)
                    → Use smaller model
                    → Get more VRAM

KV cache fills up  → Reduce max_model_len
                   → Reduce gpu_memory_utilization
                   → Add more GPU replicas

Memory leak        → Restart model server
                   → Check for model reloading in loops

Batch too large    → Reduce max_num_batched_tokens
```

### ⚠️ Failure 2: Model Loading Is Slow (Cold Start)

```
SYMPTOM:
First request after server start takes 2-5 minutes!
Users get timeout errors.
Health check fails during startup.

WHY IT HAPPENS:
────────────────
1. Downloading model from HuggingFace every restart
   (7B model = 14GB download every time!)
2. Loading weights from disk to GPU is slow
3. Health check timer too aggressive

FIXES:
───────
1. Pre-download models and mount as volume:
   - v ./models:/root/.cache/huggingface
   
2. Increase health check start period:
   healthcheck:
     start_period: 180s  ← Give 3 minutes before checking!

3. Model pre-loading at server startup (not on first request)

4. Use startup probe in Kubernetes:
   startupProbe:
     failureThreshold: 60
     periodSeconds: 10     ← Wait up to 10 minutes!
```

### ⚠️ Failure 3: Quantization Quality Regression

```
SYMPTOM:
Users complain AI gives worse answers after infrastructure change.
You switched from FP16 to INT4.
Quality dropped 10-15%.

WHY IT HAPPENS:
────────────────
INT4 has only 16 possible values per weight
Some model layers are very sensitive to precision
Especially: Attention layers, normalization layers

PREVENTION:
────────────
Always benchmark BEFORE switching quantization:
# Use same prompts, measure output quality
# MMLU benchmark, human eval, automated metrics

# Test output for specific use case:
for prompt in test_prompts:
    fp16_result = model_fp16.generate(prompt)
    int4_result = model_int4.generate(prompt)
    score = evaluate(fp16_result, int4_result)
    print(f"Quality retention: {score:.2%}")

# If quality < 95% → Use INT8 instead of INT4
# INT8 usually retains 98-99% quality
```

### ⚠️ Failure 4: Throughput Bottleneck Not Where You Think

```
SYMPTOM:
GPU utilization = 20% but requests are slow!
"My GPU is barely being used but still slow?"

COMMON CAUSES (Not the GPU!):
───────────────────────────────

1. Python GIL bottleneck:
   FastAPI overhead, not GPU
   Fix: Use async properly, multiple workers

2. Network bottleneck:
   Large request/response payloads
   Fix: Enable compression, check bandwidth

3. CPU preprocessing bottleneck:
   Tokenization is slow on CPU
   Fix: Batch tokenization, faster tokenizer

4. KV cache thrashing:
   Evicting and reloading cache constantly
   Fix: Optimize context length, increase cache size

5. Single-threaded vLLM setup:
   Only serving 1 request at a time
   Fix: Check continuous batching is enabled
   
DEBUGGING:
───────────
# Profile where time is spent:
import cProfile
cProfile.run('your_inference_function()', 'profile_output')

# Check GPU utilization over time:
nvidia-smi dmon -s u  # Sample every second
```

### ⚠️ Failure 5: Model Drift (Silent Degradation)

```
SYMPTOM:
AI worked great 3 months ago.
Nobody changed anything.
Users slowly complain it's worse now.

WHY IT HAPPENS:
────────────────
1. User input distribution changed
   (Users ask different questions over time)
2. Model was fine-tuned and re-deployed silently
3. Quantization artifacts accumulate (edge case)
4. Context gets corrupted (conversation history grows)

FIX:
─────
Monitor output quality continuously:
- Log 10% of requests with outputs
- Run automated quality checks weekly
- Set up human feedback collection
- Alert when quality metrics drop > 5%
```

## 📌 SECTION 12: Interview Questions & Answers

### Q1: "What is PagedAttention and why does vLLM use it?"

**Strong Answer:**
> *"PagedAttention is vLLM's key innovation, inspired by OS virtual memory. Traditional serving pre-allocates maximum possible KV cache memory per request — mostly wasted. PagedAttention allocates memory in small fixed-size blocks, only as needed. This eliminates waste, allows more requests to fit in GPU memory simultaneously, and enables sharing KV cache blocks between requests with identical prefixes — like a shared system prompt. Result: 3-10x more concurrent users from the same GPU hardware."*

---

### Q2: "When would you choose INT4 quantization over FP16?"

**Strong Answer:**
> *"I'd use INT4 when the model doesn't fit in available VRAM at higher precision. For example, LLaMA 70B in FP16 needs 140GB — two A100s. In INT4, it fits in one A100 80GB. The tradeoff: roughly 3-5% quality degradation, measured on benchmarks before production deployment. I'd prefer INT8 if memory permits — it retains 99% quality at half the memory cost. For production, I always run quality benchmarks comparing quantized vs original on task-specific prompts before switching."*

---

### Q3: "What is continuous batching and how does it improve throughput?"

**Strong Answer:**
> *"Static batching waits for N requests, processes them together, and releases all results — GPU goes idle between batches, padding wastes computation since sequences must match length. Continuous batching lets new requests join the batch mid-generation and completed requests leave immediately. The GPU never goes idle. Since AI requests naturally complete at different times — short answers finish before long ones — continuous batching fills those 'gaps' with new work. This improves throughput 5-10x for mixed workloads compared to static batching."*

---

### Q4: "vLLM vs Ollama — when do you use each?"

**Strong Answer:**
> *"Ollama is designed for developer experience — works on any machine including CPU-only and Apple Silicon, dead-simple setup, great for local development and privacy-first applications. I use it for development and small teams. vLLM is designed for production throughput at scale — requires NVIDIA GPU, more complex setup, but delivers dramatically higher throughput through PagedAttention and continuous batching. In production serving hundreds of concurrent users, vLLM's throughput advantage makes it the clear choice. TGI sits between them, particularly strong in the HuggingFace ecosystem."*

## 📌 SECTION 13: Common Beginner Mistakes

```
❌ Mistake 1: Running model.generate() in a for loop
   for prompt in 1000_prompts:
       result = model.generate(prompt)  # Sequential! 1000× slow
   
   Fix: Use batch inference or async concurrent calls
   results = model.generate(all_1000_prompts)  # All at once!


❌ Mistake 2: Not pre-downloading models
   Model downloads on first API call in production
   First user gets 15-minute timeout
   
   Fix: Download models at server startup, cache in volume


❌ Mistake 3: Setting context window too large
   max_model_len = 32768  "bigger = better?"
   
   Reality: Larger context = More KV cache = Less concurrent users
   LLaMA 8B, 32K context, A100 80GB = only 3 concurrent users!
   LLaMA 8B, 4K context, A100 80GB = 24 concurrent users!
   
   Fix: Set context length to what YOUR use case actually needs


❌ Mistake 4: Ignoring GPU memory fragmentation
   Running model multiple times in a loop without clearing cache
   Each iteration leaks memory until OOM
   
   Fix: torch.cuda.empty_cache() periodically
        Or use vLLM/TGI which handles this automatically


❌ Mistake 5: Using FP32 when FP16 is fine
   By default, some code loads in FP32
   2× more memory than needed!
   
   Fix: Always specify dtype=torch.float16 or bfloat16
        Modern GPUs run FP16 2x FASTER than FP32


❌ Mistake 6: No model warmup
   First request = slow (GPU not "warm", cache cold)
   Users experience 10× normal latency on first request
   
   Fix: Send dummy request on startup
   @app.on_event("startup")
   async def warmup():
       await generate("warmup request", max_tokens=1)
```
