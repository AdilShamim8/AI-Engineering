# 📦 SECTION 1 — JSON Output Prompting

## 1.1 — What Is JSON? (Truly From Zero)

### 🔍 First — What Is the Problem JSON Solves?

Imagine two people who speak different languages trying to share information.

They need a **common language** both can understand perfectly.

In the world of computers:
- Python speaks one way
- JavaScript speaks another way
- Databases speak another way
- APIs speak another way

They all need a **universal common language** to share data.

**JSON is that universal language.**

---

### 📖 What JSON Actually Is:

> **JSON (JavaScript Object Notation) is a standard format for representing structured data as text — using key-value pairs — that any programming language in the world can read and write.**

---

### 🧱 JSON Building Blocks — Learn Each One:

**Building Block 1: Key-Value Pair**
```json
"name": "John Smith"
   ↑         ↑
 key      value
(always  (the data
a string  itself)
in quotes)
```

**Building Block 2: Object (collection of key-value pairs)**
```json
{
  "name": "John Smith",
  "age": 28
}
```
Object = everything between `{` and `}`

**Building Block 3: Array (list of values)**
```json
{
  "skills": ["Python", "Java", "SQL"]
}
```
Array = everything between `[` and `]`

**Building Block 4: All Data Types**
```json
{
  "text_value":    "Hello",          ← string (always in quotes)
  "whole_number":  42,               ← integer (no quotes)
  "decimal":       3.14,             ← float (no quotes)
  "yes_or_no":     true,             ← boolean (true/false, no quotes)
  "empty_value":   null,             ← null (nothing, no quotes)
  "list_of_items": ["a", "b", "c"],  ← array
  "nested_data": {                   ← nested object
    "key": "value"
  }
}
```

---

### ⚠️ The 7 Rules of Valid JSON (LLMs Violate These!):

```
RULE 1: Keys MUST be in double quotes
  ❌ {name: "John"}
  ✅ {"name": "John"}

RULE 2: Strings MUST be in double quotes (not single)
  ❌ {"name": 'John'}
  ✅ {"name": "John"}

RULE 3: No trailing comma after last item
  ❌ {"name": "John", "age": 28,}
  ✅ {"name": "John", "age": 28}

RULE 4: No comments allowed
  ❌ {"name": "John" // this is the name}
  ✅ {"name": "John"}

RULE 5: Booleans are lowercase
  ❌ {"active": True}
  ✅ {"active": true}

RULE 6: Null is lowercase
  ❌ {"phone": Null}
  ✅ {"phone": null}

RULE 7: No undefined values
  ❌ {"score": undefined}
  ✅ {"score": null}
```

**LLMs violate these rules — especially Rules 1, 2, 3.**
This is why we need parsing strategies (Section 6).

```

```

**What LLM might output:**

```

```json

```
                  ← age is STRING not NUMBER
                  ← unwanted markdown wrapper
                  ← prose before JSON

```json

Better — but still not production-ready.

# 📦 SECTION 2 — Schema-Constrained Outputs

## 2.1 — What Is a Schema? (From Absolute Zero)

### 🔍 The Fundamental Question:

When you tell the LLM "return JSON" — which JSON?

There are infinite ways to structure the same data:

```
Version A:
{"name": "John", "age": 28}

Version B:
{"full_name": "John Smith", "age_in_years": 28}

Version C:
{"person": {"name": "John"}, "info": {"age": 28}}

Version D:
{"Name": "john", "Age": "twenty-eight"}
```

**All of these "return JSON." None are the same.**

Without a schema — the LLM chooses any version. Every time. Differently.

> **A schema is a contract. It defines EXACTLY one valid shape for the data. No more choices.**

---

### 🎭 The Analogy — The Universal Plug Adapter:

Different countries have different electrical outlets.

A universal travel adapter has ONE specific shape for each country — not "something plug-like."

A schema is the specific shape definition.

If the plug doesn't match the schema exactly, it doesn't fit. Period.

---

## 2.2 — Three Ways to Write Schemas for LLMs

Different situations call for different schema formats.

Here are the three most important:

---

### 📝 METHOD 1: Natural Language Schema

**Best for:** Simple prompts, quick prototyping

```
Return a JSON object with these exact fields:

- "product_name": text string
- "price": decimal number (e.g., 29.99)
- "in_stock": true or false
- "category": must be one of: "ELECTRONICS" | "CLOTHING" | "FOOD" | "OTHER"
- "tags": a list of text strings (empty list if none)
- "discount_percent": whole number from 0 to 100, or null if no discount
```

**Pros:** Easy to write, readable
**Cons:** Ambiguous, LLM interprets it loosely

---

### 📝 METHOD 2: TypeScript Interface Style

**Best for:** Most production use cases — compact, precise, LLMs understand it extremely well

```
Return JSON matching this TypeScript interface exactly:

interface ProductData {
  product_name: string;
  price: number;                           // decimal, e.g., 29.99
  in_stock: boolean;
  category: "ELECTRONICS" | "CLOTHING" | "FOOD" | "OTHER";
  tags: string[];                          // empty array [] if none
  discount_percent: number | null;         // 0-100, null if no discount
  last_updated: string;                    // ISO date: "2024-01-15"
}
```

**Why LLMs understand TypeScript so well:**

> During training, LLMs saw millions of TypeScript files. They deeply understand what `string`, `number`, `boolean`, `|` (union types), `[]` (arrays), and `null` mean. TypeScript-style schemas are practically native language for LLMs.

**Pros:** Compact, precise, very well understood by LLMs
**Cons:** Requires knowing basic TypeScript syntax

---

### 📝 METHOD 3: JSON Schema Standard

**Best for:** Production systems where you validate output programmatically

```json
{
  "type": "object",
  "properties": {
    "product_name": {
      "type": "string",
      "description": "Full name of the product"
    },
    "price": {
      "type": "number",
      "minimum": 0,
      "description": "Price in USD, decimal allowed"
    },
    "in_stock": {
      "type": "boolean"
    },
    "category": {
      "type": "string",
      "enum": ["ELECTRONICS", "CLOTHING", "FOOD", "OTHER"],
      "description": "Product category - must be exactly one of these values"
    },
    "tags": {
      "type": "array",
      "items": {"type": "string"},
      "maxItems": 10
    },
    "discount_percent": {
      "type": ["integer", "null"],
      "minimum": 0,
      "maximum": 100
    }
  },
  "required": ["product_name", "price", "in_stock", "category", "tags"],
  "additionalProperties": false
}
```

**Why JSON Schema is powerful:**
- Machine-readable — your code can VALIDATE against it
- Standard — works with every programming language
- Exact — no ambiguity at all
- `"additionalProperties": false` prevents LLM from adding fields

# 📦 SECTION 3 — Pydantic-Style Schema Thinking

## 3.1 — What Is Pydantic? (Build From Zero)

### 🔍 The Problem Pydantic Solves:

Python is what's called a **dynamically typed** language.

This means Python doesn't enforce data types:

```python
# Python allows this — no error:
age = 28          # integer
age = "twenty-eight"  # reassigned to string — Python is fine with this
age = [28, 29]    # now it's a list — still fine for Python!

# This causes problems:
def calculate_retirement(age):
    return 65 - age    # What if age = "twenty-eight"? CRASH!
```

In a large AI engineering system — data flows between many functions, APIs, databases.

If an LLM sends `"age": "28"` (string) but your database expects `28` (integer) — your system crashes at 3AM.

**Pydantic solves this by enforcing types at runtime:**

```python
from pydantic import BaseModel

class Person(BaseModel):
    name: str
    age: int
    email: str

# Try to create with wrong type:
person = Person(name="John", age="twenty-eight", email="john@test.com")
# ❌ ValidationError: age must be integer, got string

# Correct usage:
person = Person(name="John", age=28, email="john@test.com")
# ✅ Works perfectly
print(person.age)    # 28 (integer, guaranteed)
print(person.name)   # "John" (string, guaranteed)
```

> **Pydantic = A type-safety guard for your data. It refuses invalid data. Always. Immediately. With clear error messages.**

---

### 🎭 The Analogy — Airport Security:

When you go through airport security:
- ID is required
- ID must be valid (not expired)
- Age must be 18+ for certain things
- Liquids must be under 100ml

If anything fails — you don't get through.
The security process is **strict, consistent, automatic.**

**Pydantic is airport security for your LLM output data.**

## 3.2 — Pydantic Deep Dive — Every Feature You Need:

### 🐍 Basic Model:

```python
from pydantic import BaseModel

class SentimentResult(BaseModel):
    text: str
    sentiment: str
    confidence: float

# Create from dict (what you'd get from LLM)
data = {"text": "Great product!", "sentiment": "POSITIVE", "confidence": 0.95}
result = SentimentResult(**data)

print(result.sentiment)    # "POSITIVE"
print(result.confidence)   # 0.95
print(type(result.confidence))  # <class 'float'>  ← guaranteed float
```

---

### 🐍 Enums — Only Allowed Values:

```python
from pydantic import BaseModel
from enum import Enum

class SentimentEnum(str, Enum):
    POSITIVE = "POSITIVE"
    NEGATIVE = "NEGATIVE"
    NEUTRAL = "NEUTRAL"
    MIXED = "MIXED"

class PriorityEnum(str, Enum):
    HIGH = "HIGH"
    MEDIUM = "MEDIUM"
    LOW = "LOW"

class CustomerAnalysis(BaseModel):
    sentiment: SentimentEnum
    priority: PriorityEnum

# Test with valid value:
result = CustomerAnalysis(sentiment="POSITIVE", priority="HIGH")
print(result.sentiment)   # SentimentEnum.POSITIVE ✅

# Test with invalid value:
result = CustomerAnalysis(sentiment="HAPPY", priority="HIGH")
# ❌ ValidationError: "HAPPY" is not a valid SentimentEnum value
# Allowed: POSITIVE, NEGATIVE, NEUTRAL, MIXED
```

### 🐍 Field — Constraints and Descriptions:

```python

from typing import List, Optional

class ProductReview(BaseModel):
    
    # String with length limits
    product_name: str = Field(
        min_length=1,
        max_length=200,
        description="Full name of the reviewed product"
    )
    
    # Number with range constraint
    rating: float = Field(
        ge=1.0,    # greater than or equal to 1

## 3.3 — The Pydantic → LLM → Pydantic Pipeline:

This is the most important pattern in production LLM engineering:

```python
from pydantic import BaseModel, Field
from typing import List, Literal
import json
import openai

# ═══════════════════════════════════════════════════
# STEP 1: DEFINE YOUR OUTPUT AS PYDANTIC MODEL
# ═══════════════════════════════════════════════════

class ResumeAnalysis(BaseModel):
    candidate_name: str
    years_experience: int = Field(ge=0, le=60)
    top_skills: List[str] = Field(max_items=10)
    education: Literal["HIGH_SCHOOL", "BACHELOR", "MASTER", "PHD", "OTHER"]
    seniority: Literal["JUNIOR", "MID", "SENIOR", "LEAD"]
    hire_recommendation: Literal["STRONG_YES", "YES", "MAYBE", "NO"]
    recommendation_reason: str = Field(max_length=200)
    red_flags: List[str] = Field(
        default=[],
        description="Concerns about this candidate"
    )

# ═══════════════════════════════════════════════════
# STEP 2: AUTO-GENERATE JSON SCHEMA FROM MODEL
# ═══════════════════════════════════════════════════

schema = ResumeAnalysis.model_json_schema()
schema_str = json.dumps(schema, indent=2)

# ═══════════════════════════════════════════════════
# STEP 3: INJECT SCHEMA INTO PROMPT
# ═══════════════════════════════════════════════════

def build_prompt(resume_text: str) -> str:
    return f"""
You are an expert technical recruiter.
Analyze the resume and return JSON conforming EXACTLY to this schema:

{schema_str}

Rules:
- Return raw JSON only. Start with {{ end with }}
- No markdown, no explanation
- Use null where data is unavailable
- Never omit any required field

Resume:
\"\"\"{resume_text}\"\"\"
"""

# ═══════════════════════════════════════════════════
# STEP 4: CALL LLM + PARSE + VALIDATE
# ═══════════════════════════════════════════════════

client = openai.OpenAI()

def analyze_resume(resume_text: str) -> ResumeAnalysis:
    prompt = build_prompt(resume_text)
    
    response = client.chat.completions.create(
        model="gpt-4",
        messages=[{"role": "user", "content": prompt}],
        temperature=0.0    # Deterministic output
    )
    
    raw_output = response.choices[0].message.content
    
    # Parse JSON
    data = json.loads(raw_output)
    
    # Validate with Pydantic (raises ValidationError if invalid)
    result = ResumeAnalysis(**data)
    
    return result

# ═══════════════════════════════════════════════════
# STEP 5: USE THE VALIDATED OBJECT
# ═══════════════════════════════════════════════════

resume = """
Sarah Chen is a Senior ML Engineer with 7 years of experience.
She has worked at Google and Meta. Skills: Python, TensorFlow, 
PyTorch, Kubernetes, SQL. MS Computer Science from Stanford.
"""

analysis = analyze_resume(resume)

# Now you have a fully typed, validated Python object:
print(analysis.candidate_name)         # "Sarah Chen"
print(analysis.years_experience)       # 7
print(analysis.hire_recommendation)    # "STRONG_YES"
print(analysis.top_skills)             # ["Python", "TensorFlow", ...]
print(type(analysis.years_experience)) # <class 'int'> — guaranteed
```

# 📦 SECTION 4 — Function / Tool Calling

## 4.1 — What Is Function Calling? (The Deep Concept)

### 🔍 The Core Problem It Solves:

Even with perfect prompt engineering (Level 4), you are still asking the LLM to **try** to output JSON.

The LLM is still generating text token by token.
It can still make mistakes.

```
You: "Please output JSON"
LLM: generates token by token...
     { ← good
     " ← good
     s ← good
     e ← good
     n ← good
     t ← good
     i ← good
     m ← good
     e ← good
     n ← good
     t ← good
     " ← good
     : ← good
     " ← good
     P ← good
     O ← good
     S ← good
     ... ← continues generating
     
     But at some point it might generate:
     " ← missing comma before this!
     
     Now the entire JSON is invalid.
```

**Function calling solves this at a completely different level.**

---

### 🔬 What Function Calling Actually Does (The Mechanism):

```
WITHOUT FUNCTION CALLING:
┌────────────────────────────────────────────────┐
│  LLM generates tokens freely                  │
│  All tokens in vocabulary are possible        │
│  LLM tries to follow JSON format              │
│  Sometimes fails                              │
│  Output: text string (might be JSON)          │
└────────────────────────────────────────────────┘

WITH FUNCTION CALLING:
┌────────────────────────────────────────────────┐
│  LLM generates tokens                         │
│  BUT: API constrains which tokens are valid   │
│  Token must form valid JSON at every step     │
│  Token must match your schema at every step   │
│  Invalid tokens are impossible                │
│  Output: guaranteed valid JSON                │
└────────────────────────────────────────────────┘
```

> **Function calling doesn't ask the LLM to try harder. It makes it structurally IMPOSSIBLE to output invalid JSON.**

---

### 🎭 The Analogy — Mad Libs vs. Free Writing:

**Free writing** (prompt-based JSON):
> "Write a story about a [anything you want] who [anything]..."
> The writer chooses everything — can go off-topic, use wrong format

**Mad Libs** (function calling):
> "The _[noun]_ quickly _[verb]_ the _[adjective]_ _[noun]_."
> The writer fills in blanks. The structure is FIXED. Cannot deviate.

Function calling is Mad Libs for data.

---

## 4.2 — Function Calling Architecture:

```
NORMAL API CALL:
┌────────────────────────────────────────────────────┐
│  messages = [{"role": "user", "content": prompt}] │
│                       ↓                           │
│            LLM → text response                    │
└────────────────────────────────────────────────────┘

FUNCTION CALLING API CALL:
┌────────────────────────────────────────────────────┐
│  messages = [{"role": "user", "content": prompt}] │
│  +                                                 │
│  tools = [{"type": "function",                    │
│            "function": {                          │
│              "name": "...",                       │
│              "parameters": {JSON Schema}          │
│            }}]                                    │
│                       ↓                           │
│  LLM generates function call arguments            │
│  Constrained to match the JSON Schema             │
│                       ↓                           │
│  Output: structured function arguments (JSON)     │
│  Guaranteed valid. Guaranteed schema-compliant.   │
└────────────────────────────────────────────────────┘
```

# 📦 SECTION 5 — Deterministic Format Enforcement

## 5.1 — What Does "Deterministic" Mean Here?

> **Deterministic** = Given the same input, you ALWAYS get the same output format. 100% of the time. Not "usually." Not "mostly." Always.

This is what production systems need.

---

### 🎭 The ATM Analogy:

When you press "Check Balance" on an ATM:

- It ALWAYS shows: `$X,XXX.XX`
- It NEVER says: "Your balance is approximately one thousand"
- It NEVER sometimes shows it in a different currency
- It NEVER adds a "by the way" note at the end

**The format is deterministic — enforced by the machine, not by asking nicely.**

---

## 5.2 — The 6 Techniques for Deterministic Format Enforcement

---

### ⚙️ TECHNIQUE 1: Output Anchoring

**What it is:** You start the JSON in your prompt — the LLM can only continue it.

```
[Your full prompt here]

Respond with the following JSON (complete it):
{
  "sentiment": "
```

The LLM cannot add prose before the JSON because the JSON has already started.
It can only continue from where you left off.

**Why it works:** The LLM generates the most probable CONTINUATION of what's already there. If `{` is already there, it continues with JSON.

---

### ⚙️ TECHNIQUE 2: Temperature = 0

```python
response = client.chat.completions.create(
    model="gpt-4",
    messages=[...],
    temperature=0.0   # ← ALWAYS picks highest probability token
)
```

**What temperature does:**

```
TEMPERATURE = 1.0 (default):
Token probabilities: {"mat": 45%, "floor": 22%, "roof": 12%...}
LLM randomly samples from this distribution
Different runs → different outputs

TEMPERATURE = 0.0:
Token probabilities: same as above
LLM ALWAYS picks the highest: "mat" 100% of the time
Same input → same output → deterministic
```

**For structured output:** Always use `temperature=0.0` in production.

---

### ⚙️ TECHNIQUE 3: Stop Sequences

```python
response = client.chat.completions.create(
    model="gpt-4",
    messages=[...],
    stop=["}\n\n", "}\n```"]   # Stop after JSON closes
)
```

**What it does:** Forces the LLM to stop generating immediately after the JSON closes. Prevents any text after the JSON.

```
WITHOUT STOP SEQUENCE:
{"result": "positive"}
Here is my analysis of the sentiment...  ← Unwanted text

WITH STOP SEQUENCE (stop after "}\n\n"):
{"result": "positive"}
← Stops here. Nothing after.
```

---

### ⚙️ TECHNIQUE 4: JSON Mode

```python
response = client.chat.completions.create(
    model="gpt-4-turbo",
    messages=[...],
    response_format={"type": "json_object"}
)
```

**What it guarantees:** Syntactically valid JSON. Always.
**What it doesn't guarantee:** Your specific schema, field names, types.
**Use when:** You need valid JSON but schema is flexible.

---

### ⚙️ TECHNIQUE 5: Constrained Decoding (For Open Source Models)

For open-source models (Llama, Mistral, etc.) running locally:

```python
# Using Outlines library

# Load model

**Constrained decoding works at token generation level:**
- At each step, only tokens that can form valid JSON matching the schema are allowed
- Structurally IMPOSSIBLE to generate invalid output

### ⚙️ TECHNIQUE 6: The Instructor Library (Most Recommended)

```

**What Instructor does automatically:**
1. Converts your Pydantic model to a function calling schema ✅
2. Makes the API call ✅
3. Extracts the function call arguments ✅
4. Parses the JSON ✅
5. Validates with Pydantic ✅
6. **If validation fails — retries automatically with the error as feedback** ✅
7. Returns a validated Pydantic object ✅

**This replaces ~50 lines of boilerplate code with 1 line.**

## 5.3 — Instructor — Retry on Validation Failure (The Killer Feature):

```python
import instructor
from openai import OpenAI
from pydantic import BaseModel, validator

class StrictAnalysis(BaseModel):
    score: int  # Must be 1-10
    
    @validator('score')
    def score_in_range(cls, v):
        if not 1 <= v <= 10:
            raise ValueError(f'Score must be 1-10, got {v}')
        return v

client = instructor.from_openai(OpenAI())

# If LLM returns score=11 (out of range):
# ← Pydantic raises ValidationError
# ← Instructor automatically retries
# ← Passes error message back to LLM:
#    "ValidationError: Score must be 1-10, got 11. Please fix."
# ← LLM corrects itself
# ← Returns score=8 (valid this time)

result = client.chat.completions.create(
    model="gpt-4",
    response_model=StrictAnalysis,
    max_retries=3,   # ← Retry up to 3 times on failure
    messages=[{"role": "user", "content": "Rate this product review 1-10"}]
)
```

This is the most powerful feature of Instructor — **self-healing validation**.

## 5.4 — Choosing the Right Technique:

```
Decision Tree for Deterministic Format Enforcement:

Is this a prototype or production?
├── Prototype → Prompt JSON (Level 3) + temperature=0
└── Production
    ├── Using OpenAI/Anthropic API?
    │   ├── Need specific schema? → Function Calling + Instructor
    │   └── Just need valid JSON? → JSON Mode
    └── Using open source local model?
        → Outlines library (constrained decoding)

Special cases:

# 📦 SECTION 6 — Parsing Strategies

## 6.1 — Why Parsing Is Hard (The Real Production Story)

> *"In theory, with good prompts and function calling, you should always get perfect JSON. In production, with millions of requests, edge cases WILL happen."*

Here is what you learn after running LLMs in production:

```
📊 REAL PRODUCTION STATISTICS (typical):
├── 85% of requests → Perfect JSON, parse directly
├── 10% of requests → JSON with prose around it (needs extraction)
├── 3% of requests  → Malformed JSON (needs repair)
├── 1.5% of requests → Full format failure (needs retry)
└── 0.5% of requests → Cannot be fixed (graceful degradation)

If you only handle the 85% → you have 15% failure rate
In a system processing 100,000 requests/day → 15,000 failures/day
```

**You must handle ALL five scenarios.**

### 🎭 The Mail Room Analogy (Deep Version):

A mail room processes 1,000 packages per day.

- 850 arrive perfect → process normally
- 100 arrive with torn labels → extract what's readable
- 30 arrive with water damage → repair the label, read what you can
- 15 arrive completely wrong → return to sender with correction note
- 5 arrive impossible to process → log and alert supervisor

**Your parser needs the same 5-level strategy.**

## 6.2 — The 5-Level Parsing Strategy (Complete System)

```
LEVEL 1: Direct Parsing
  → Try json.loads() directly
  → Works 85% of the time
  → If fails → go to Level 2

LEVEL 2: Extraction Parsing
  → Strip markdown, extract JSON from text
  → Works for "Here is JSON: {...}" pattern
  → If fails → go to Level 3

LEVEL 3: Repair Parsing
  → Use json-repair library
  → Fixes trailing commas, single quotes, etc.
  → Works for malformed but recoverable JSON
  → If fails → go to Level 4

LEVEL 4: Retry with Error Feedback
  → Send the error BACK to LLM
  → "You returned invalid JSON. Error: {error}. Please fix."
  → If fails after N retries → go to Level 5

LEVEL 5: Graceful Degradation
  → Use safe defaults
  → Flag as low-confidence
  → Never crash the application
  → Log for investigation
```

## 6.4 — Level 2: Extraction Parsing

```python
import json
import re

def level2_parse(llm_output: str) -> dict | None:
    """
    Extract JSON from text that may have:
    - Prose before/after JSON
    - Markdown code blocks (```json ... ```)
    - Mixed content
    """
    text = llm_output.strip()
    
    # Strategy A: Remove markdown code blocks
    # Handles: ```json {...} ``` or ``` {...} ```
    cleaned = re.sub(r'```(?:json)?\s*', '', text)
    cleaned = re.sub(r'```\s*$', '', cleaned).strip()
    
    try:
        return json.loads(cleaned)
    except json.JSONDecodeError:
        pass
    
    # Strategy B: Extract {...} using balanced brace matching
    # More reliable than regex for nested JSON
    start = text.find('{')
    end = text.rfind('}')
    
    if start != -1 and end != -1 and end > start:
        json_candidate = text[start:end+1]
        try:
            return json.loads(json_candidate)
        except json.JSONDecodeError:
            pass
    
    # Strategy C: Find first valid JSON object
    # Handles multiple JSON objects in output
    json_pattern = re.compile(r'\{[^{}]*(?:\{[^{}]*\}[^{}]*)*\}', re.DOTALL)
    matches = json_pattern.findall(text)
    
    for match in matches:
        try:
            return json.loads(match)
        except json.JSONDecodeError:
            continue
    
    return None

# Tests:
print(level2_parse('Here is the JSON:\n```json\n{"name":"John"}\n```'))
# ✅ {"name": "John"}

print(level2_parse('Analysis complete. {"name":"John","age":28} Hope this helps!'))
# ✅ {"name": "John", "age": 28}
```

from json_repair import repair_json
import json

def level3_parse(llm_output: str) -> dict | None:
    """
    Attempt to repair and parse malformed JSON.
    
    Handles LLM JSON errors:
    - Trailing comma: {"name": "John",}
    - Single quotes: {'name': 'John'}
    - Missing comma: {"name": "John" "age": 28}
    - Unquoted keys: {name: "John"}
    - Truncated JSON: {"name": "John", "age":
    - Python True/False: {"active": True}
    """
    
    # First try extraction (might just have prose around it)
    text = llm_output.strip()
    start = text.find('{')
    end = text.rfind('}')
    
    if start != -1 and end != -1:
        json_candidate = text[start:end+1]
        
        # Try direct parse first
        try:
            return json.loads(json_candidate)
        except json.JSONDecodeError:
            pass
        
        # Try repair
        try:
            repaired = repair_json(json_candidate)
            if repaired:
                return json.loads(repaired)
        except Exception:
            pass
    
    # Try repairing the whole text
    try:
        repaired = repair_json(llm_output)
        if repaired:
            return json.loads(repaired)
    except Exception:
        pass
    
    return None

# Tests:

# ✅ {"name": "John", "age": 28}  ← Repaired!

## 6.6 — Level 4: Retry with Error Feedback

```python
import json
import time
from pydantic import BaseModel, ValidationError

def level4_parse_with_retry(
    original_prompt: str,
    llm_caller,           # Your function that calls the LLM
    response_model: type[BaseModel],
    max_retries: int = 3
) -> BaseModel | None:
    """
    On failure: send the error BACK to the LLM.
    The LLM sees its mistake and corrects it.
    """
    
    messages = [{"role": "user", "content": original_prompt}]
    
    for attempt in range(max_retries):
        
        # Call LLM
        raw_output = llm_caller(messages)
        
        # Try to parse
        try:
            # Try levels 1-3
            parsed = (
                level1_parse(raw_output) or
                level2_parse(raw_output) or
                level3_parse(raw_output)
            )
            
            if parsed is None:
                raise ValueError(f"No valid JSON found in: {raw_output[:100]}")
            
            # Validate with Pydantic
            validated = response_model(**parsed)
            
            print(f"✅ Success on attempt {attempt + 1}")
            return validated
            
        except (json.JSONDecodeError, ValidationError, ValueError) as e:
            error_msg = str(e)
            print(f"❌ Attempt {attempt + 1} failed: {error_msg[:100]}")
            
            if attempt < max_retries - 1:
                # Add error feedback to conversation
                messages.extend([
                    {"role": "assistant", "content": raw_output},
                    {
                        "role": "user",
                        "content": f"""Your previous response failed validation.

Error: {error_msg}

Your response was:
{raw_output[:200]}

Please provide ONLY valid JSON matching the required schema.
Fix the specific error mentioned above."""
                    }
                ])
                
                time.sleep(0.5)  # Brief pause
    
    print(f"❌ All {max_retries} attempts failed")
    return None
```

## 6.7 — Level 5: Graceful Degradation

```python
from dataclasses import dataclass
from typing import Optional, Any
import logging

@dataclass
class ParseResult:
    data: Optional[dict]
    success: bool
    confidence: float        # How confident we are in the result
    parse_level_used: int    # Which level succeeded (1-5)
    error: Optional[str]
    raw_output: str

def level5_graceful_parse(
    llm_output: str,
    response_model: type[BaseModel],
    safe_defaults: dict
) -> ParseResult:
    """
    NEVER raises an exception.
    ALWAYS returns something usable.
    Degrades gracefully when quality is low.
    """
    
    # Try all levels in order
    for level, parser in enumerate([level1_parse, level2_parse, level3_parse], start=1):
        result = parser(llm_output)
        if result is not None:
            try:
                validated = response_model(**result)
                return ParseResult(
                    data=validated.dict(),
                    success=True,
                    confidence=1.0 - (0.1 * (level - 1)),  # Level 1=1.0, 2=0.9, 3=0.8
                    parse_level_used=level,
                    error=None,
                    raw_output=llm_output
                )
            except ValidationError as e:
                # Try with defaults for missing fields
                try:
                    merged = {**safe_defaults, **result}
                    validated = response_model(**merged)
                    return ParseResult(
                        data=validated.dict(),
                        success=True,
                        confidence=0.5,   # Low confidence — used defaults
                        parse_level_used=level,
                        error=f"Used defaults for: {str(e)[:50]}",
                        raw_output=llm_output
                    )
                except Exception:
                    continue
    
    # Complete failure — return defaults
    logging.error(f"Complete parse failure. Output: {llm_output[:100]}")
    
    try:
        fallback = response_model(**safe_defaults)
        return ParseResult(
            data=fallback.dict(),
            success=False,
            confidence=0.0,
            parse_level_used=5,
            error="Complete parse failure — using all defaults",
            raw_output=llm_output
        )
    except Exception as e:
        return ParseResult(
            data=None,
            success=False,
            confidence=0.0,
            parse_level_used=5,
            error=f"Critical failure: {str(e)}",
            raw_output=llm_output
        )
```

## 6.8 — The Complete Production Parser (All Levels + Monitoring):

```python
from collections import defaultdict
import logging
import json
from typing import TypeVar, Type
from pydantic import BaseModel

T = TypeVar('T', bound=BaseModel)

class ProductionParser:
    """
    Production-grade LLM output parser.
    Implements 5-level fallback with monitoring.
    
    Usage:
        parser = ProductionParser(MyModel)
        result = parser.parse(llm_output)
    """
    
    def __init__(self, response_model: Type[T], safe_defaults: dict = None):
        self.response_model = response_model
        self.safe_defaults = safe_defaults or {}
        
        # Monitoring counters
        self.stats = defaultdict(int)
    
    def parse(self, llm_output: str) -> T:
        """
        Main parse method.
        Returns validated model or raises after all levels exhausted.
        """
        
        # Level 1: Direct parse
        result = self._try_level(1, lambda: json.loads(llm_output.strip()))
        if result:
            return self._validate(result, level=1)
        
        # Level 2: Extract from text
        result = self._try_level(2, lambda: self._extract_json(llm_output))
        if result:
            return self._validate(result, level=2)
        
        # Level 3: Repair
        result = self._try_level(3, lambda: self._repair_json(llm_output))
        if result:
            return self._validate(result, level=3)
        
        # Level 4+: Raise for retry handling upstream
        self.stats['complete_failure'] += 1
        raise ValueError(
            f"All parse levels failed.\n"
            f"Raw output (first 200 chars):\n{llm_output[:200]}"
        )
    
    def _try_level(self, level: int, parse_fn):
        """Try a parse function, return result or None."""
        try:
            return parse_fn()
        except Exception as e:
            logging.debug(f"Level {level} parse failed: {e}")
            return None
    
    def _validate(self, data: dict, level: int) -> T:
        """Validate parsed data with Pydantic."""
        try:
            result = self.response_model(**data)
            self.stats[f'level_{level}_success'] += 1
            return result
        except Exception as e:
            self.stats[f'level_{level}_validation_fail'] += 1
            raise
    
    def _extract_json(self, text: str) -> dict:
        """Extract JSON from text with prose around it."""
        import re
        text = re.sub(r'```(?:json)?\s*', '', text.strip())
        text = re.sub(r'```\s*$', '', text).strip()
        
        start = text.find('{')
        end = text.rfind('}')
        if start != -1 and end > start:
            return json.loads(text[start:end+1])
        raise ValueError("No JSON object found")
    
    def _repair_json(self, text: str) -> dict:
        """Repair malformed JSON."""
        from json_repair import repair_json
        repaired = repair_json(text)
        if repaired:
            return json.loads(repaired)
        raise ValueError("JSON repair failed")
    
    def get_health_report(self) -> dict:
        """
        Monitor parsing health in production.
        Alert if Level 3+ is happening frequently.
        """
        total = sum(v for k, v in self.stats.items() 
                   if 'success' in k or 'failure' in k)
        
        if total == 0:
            return {"status": "no_data"}
        
        level1_rate = self.stats['level_1_success'] / total
        repair_rate = self.stats['level_3_success'] / total
        failure_rate = self.stats['complete_failure'] / total
        
        status = "HEALTHY"
        if repair_rate > 0.05:    # >5% needing repair = warning
            status = "WARNING"
        if failure_rate > 0.01:   # >1% complete failure = critical
            status = "CRITICAL"
        
        return {
            "status": status,
            "total_parses": total,
            "level_1_rate": f"{level1_rate:.1%}",
            "repair_rate": f"{repair_rate:.1%}",
            "failure_rate": f"{failure_rate:.1%}",
            "raw_stats": dict(self.stats),
            "recommendation": (
                "Improve prompts or switch to function calling"
                if status != "HEALTHY"
                else "All good!"
            )
        }
```

**"Why is structured output important in AI engineering?"**

✅ Strong Answer:

Without structured output, every downstream system would need its own natural language parser, which is fragile and inconsistent. With structured output, the LLM becomes the brain of a larger software system — its outputs feed directly into APIs, databases, and other services. It's the difference between an LLM that can chat and an LLM that can power production applications."

### ❓ Question 2:
**"How do you get reliable JSON output from an LLM?"**

✅ Strong Answer:
> "There's a reliability hierarchy. At the basic level, you use prompt engineering — TypeScript-style schemas, explicit type specification, output anchoring, and temperature zero. For better reliability, you add JSON mode. For production-grade reliability, you use function calling with the Instructor library — this enforces schema compliance at the API level, not through instructions. On top of any generation method, you always add multi-level parsing: direct parse, extraction from text, JSON repair, retry with error feedback, and graceful degradation. In practice, Instructor plus Pydantic handles 95% of the work automatically."

---

### ❓ Question 3:
**"What is Pydantic and why do AI engineers use it?"**

✅ Strong Answer:
> "Pydantic is a Python data validation library that enforces type safety at runtime. In LLM pipelines, it serves as the contract between the AI and the rest of the system. You define your expected output as a Pydantic model with typed fields, enum constraints, range validators, and required fields. This serves two purposes: first, you can auto-generate a JSON Schema from the model to inject into your prompt; second, you validate the LLM's parsed output against the model, catching type mismatches, missing required fields, or invalid enum values immediately rather than discovering them as silent bugs in production. Pydantic moves bugs from 3AM runtime crashes to parse-time validation errors."

---

### ❓ Question 4:
**"Explain function calling and why it's better than prompt-based JSON."**

✅ Strong Answer:
> "Function calling is an API feature that constrains token generation at the model level — making it structurally impossible to output invalid JSON or deviate from your schema. Prompt-based JSON asks the model to comply through instructions, which it usually does but can fail. Function calling enforces compliance at inference time. In practice, prompt-based JSON fails roughly 15% of the time in edge cases; function calling reduces that to near zero. The Instructor library makes this easy — you provide a Pydantic model, and it handles the function calling schema generation, API call, response extraction, and Pydantic validation automatically. I use function calling via Instructor for all production structured output work."

---

### ❓ Question 5:
**"How do you handle structured output failures in production?"**

✅ Strong Answer:
> "I implement a five-level parsing strategy. Level one is direct JSON parsing — covers 85% of cases. Level two extracts JSON from text — handles markdown wrappers and prose around the JSON. Level three uses JSON repair — fixes syntax errors like trailing commas and unquoted keys. Level four retries with error feedback — sends the validation error back to the LLM so it can self-correct. Level five is graceful degradation — fills missing fields with safe defaults, flags low-confidence outputs, and never crashes the application. I also monitor parse success rates by level in production — if level three or four triggers frequently, it means my prompts or schemas need improvement."

# 🧠 SECTION 11 — Engineer Mindset

When a real AI engineer designs a structured output system, they ask:

```
1. "What is consuming this output downstream?"
   → Database: Need exact types and field names
   → Another API: Need specific schema format
   → Display: More flexibility allowed

2. "What is my acceptable failure rate?"
   → Medical/Legal: 0% → Function calling + strict Pydantic
   → Internal tool: 2% acceptable → Prompt-based + retry

3. "What is the cheapest method that meets my reliability bar?"
   → prompt JSON: cheapest, least reliable
   → function calling: slightly more expensive, most reliable
   → Engineering is about tradeoffs, not just perfection

4. "How do I test my schema at scale?"
   → Run 1000 diverse inputs through the pipeline
   → Measure parse level distribution
   → Measure validation failure rate
   → Test edge cases and adversarial inputs

5. "When does my schema need to change?"
   → Design for evolution: use Optional fields + defaults
   → Version your schemas
   → Think about backward compatibility

6. "What happens at 3AM when this breaks?"
   → Graceful degradation: never crash
   → Alerting: notify when failure rate spikes
   → Logging: capture raw output for debugging
```
