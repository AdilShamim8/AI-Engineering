# 📦 SECTION 1 — The Evaluation Framework

## 1.1 — Why LLM Evaluation Is Uniquely Hard (First Principles)

### 🔍 Start From The Fundamental Problem:

When you evaluate **traditional software**, evaluation is simple:

```
TRADITIONAL CODE EVALUATION:
Input: sort([3, 1, 2])
Expected output: [1, 2, 3]
Actual output: [1, 2, 3]
Result: ✅ PASS

There is ONE correct answer.
Checking it takes microseconds.
It's completely objective.
```

When you evaluate **LLM output**, everything changes:

```
LLM EVALUATION:
Input: "Summarize this article about climate change"

Expected output: ???

The article has many facts.
A good summary captures the KEY points.
But which points are KEY?
How long should the summary be?
What reading level?
Should it include numbers?
What tone?

There is NO single correct answer.
A human might read it and say "this is good" or "this is bad"
But can we automate that?
```

> **Traditional software: one right answer, easy to check.**
> **LLM output: many acceptable answers, hard to evaluate.**

---

### 🔬 The 3 Hard Problems in LLM Evaluation:

```
┌──────────────────────────────────────────────────────────────────────┐
│  HARD PROBLEM 1: NO GROUND TRUTH                                    │
│                                                                      │
│  For many tasks, there is no single "correct" answer.               │
│  "Write a good email" → what is "good"?                            │
│  "Summarize this" → which facts matter most?                       │
│  "Generate a response" → what makes it the right response?         │
│                                                                      │
│  Solution: Define your own evaluation criteria explicitly           │
│            Create rubrics before testing begins                     │
├──────────────────────────────────────────────────────────────────────┤
│  HARD PROBLEM 2: EVALUATION IS EXPENSIVE                            │
│                                                                      │
│  Human evaluation: most accurate, but slow and expensive            │
│  10,000 LLM outputs × 2 minutes each = 333 hours of human work    │
│                                                                      │
│  Solution: LLM-as-Judge (automated but approximate)                 │
│            + Human evaluation for validation sample                 │
├──────────────────────────────────────────────────────────────────────┤
│  HARD PROBLEM 3: METRICS DON'T CAPTURE EVERYTHING                   │
│                                                                      │
│  High task success rate + high hallucination rate = dangerous       │
│  Perfect format + wrong answer = useless                           │
│  Fast response + bad quality = bad product                         │
│                                                                      │
│  Solution: Multi-metric evaluation dashboard                        │
│            Never optimize for one metric alone                      │
└──────────────────────────────────────────────────────────────────────┘
```

## 1.2 — The 3 Dimensions of Prompt Quality:

Every prompt must be evaluated across THREE dimensions simultaneously:

```
┌──────────────────────────────────────────────────────────────────────┐
│                                                                      │
│   DIMENSION 1: QUALITY      DIMENSION 2: SAFETY    DIMENSION 3: EFFICIENCY │
│                                                                      │
│   • Task Success Rate       • Hallucination Rate   • Latency        │
│   • Format Accuracy         • Injection Resistance • Token Count    │
│   • Consistency             • Policy Compliance    • Cost per Call  │
│   • Relevance               • PII Safety           • Throughput     │
│                                                                      │
│   "Does it give         "Is it safe to         "Is it efficient    │
│    the right answer?"    use at scale?"          enough to ship?"  │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```

**The trap:** Most teams only measure Dimension 1.
**The mistake:** Optimizing Dimension 1 can secretly worsen Dimensions 2 and 3.

```
EXAMPLE OF THE TRAP:

You improve your prompt's task success rate from 88% → 95%.
You feel great. You ship.

What you didn't measure:
- Hallucination rate went from 3% → 12% (your prompt became more "helpful" = more confident = more hallucinations)
- Latency went from 0.8s → 3.2s (more CoT = more tokens = 4x slower)
- Cost per call went from $0.02 → $0.08 (4x more expensive)

Your "improvement" made the system 4x slower, 4x more expensive,
and 4x more likely to generate false information.

THIS IS WHY MULTI-METRIC EVALUATION EXISTS.
```

## 1.4 — Building the Evaluation Mindset (Before Any Code):

**The 5 questions every AI engineer must answer before shipping:**

```
QUESTION 1: "What does success look like — exactly?"
  → Not "good output" — SPECIFIC criteria
  → "Extracts all named entities with 95% precision"
  → "Summarizes in ≤50 words, covers ≥3 key points"

QUESTION 2: "What test data do I have?"
  → How many examples?
  → Is it diverse (not just easy cases)?
  → Does it have ground truth labels?

QUESTION 3: "How will I measure correctness?"
  → Exact match? Contains? LLM judge? Human?
  → What is my ground truth?

QUESTION 4: "What is my acceptable threshold?"
  → What accuracy is "good enough to ship"?
  → What accuracy triggers a regression alert?

QUESTION 5: "How will I monitor this in production?"
  → Sample + evaluate continuously
  → Alert on degradation
  → Track trends over time
```

# 📦 SECTION 2 — Qualitative Evaluation

## 2.1 — What Is Qualitative Evaluation? (First Principles)

> **Qualitative evaluation = assessing LLM output based on human judgment criteria — like quality, relevance, coherence, tone — that cannot be reduced to a simple right/wrong check.**

Not everything can be measured with a number.

Some important qualities require human-like judgment:
- Is this response **helpful** to the user?
- Is this summary **coherent** and **readable**?
- Is this email **appropriate** in tone?
- Does this code **solve the actual problem**?

---

### 🎭 The Analogy — The Wine Expert vs. The Breathalyzer:

A breathalyzer measures one thing: alcohol percentage. Objective. Exact.

A wine expert evaluates: color, aroma, body, tannins, finish, complexity. Subjective. Nuanced.

**Both are valuable. They measure different things.**

Quantitative metrics (Task Success Rate, Format Accuracy) = breathalyzer.
Qualitative evaluation = wine expert.

You need both.

---

## 2.2 — Method 1: Human Evaluation (The Gold Standard)

### 🔍 How To Do Human Evaluation Properly:

The biggest mistake in human evaluation:
> ❌ "Does this look good?" — Yes/No

The correct approach:
> ✅ Use a **rubric** — a specific scoring guide with defined criteria

---

### 📋 Building a Qualitative Evaluation Rubric:

```python
from dataclasses import dataclass
from typing import List
from enum import Enum

class Score(int, Enum):
    """Standard 5-point evaluation scale."""
    VERY_POOR  = 1   # Unacceptable, unusable
    POOR       = 2   # Below expectations, needs major improvement
    ACCEPTABLE = 3   # Meets minimum bar, could be better
    GOOD       = 4   # Meets expectations, minor improvements possible
    EXCELLENT  = 5   # Exceeds expectations, nothing to improve

@dataclass
class EvaluationCriteria:
    """A single evaluation dimension."""
    name: str
    description: str
    weight: float          # How much this matters (weights sum to 1.0)
    scoring_guide: dict    # Score → what it means for THIS criterion

# Define rubric for customer support response evaluation
CUSTOMER_SUPPORT_RUBRIC = [
    
    EvaluationCriteria(
        name="task_completion",
        description="Did the response actually solve the customer's problem?",
        weight=0.35,     # Most important criterion
        scoring_guide={
            1: "Did not address the problem at all",
            2: "Partially addressed but left key issues unresolved",
            3: "Addressed the problem but missing some details",
            4: "Fully solved the problem with minor gaps",
            5: "Completely solved the problem with proactive additional help"
        }
    ),
    
    EvaluationCriteria(
        name="accuracy",
        description="Was all information in the response factually correct?",
        weight=0.30,     # Second most important
        scoring_guide={
            1: "Contains multiple factual errors",
            2: "Contains at least one clear factual error",
            3: "Mostly accurate with minor imprecisions",
            4: "All statements accurate, well-supported",
            5: "Perfectly accurate with specific evidence cited"
        }
    ),
    
    EvaluationCriteria(
        name="tone",
        description="Was the tone appropriate for customer support?",
        weight=0.20,
        scoring_guide={
            1: "Rude, dismissive, or inappropriate",
            2: "Too formal/robotic or too casual, off-brand",
            3: "Acceptable tone but could be warmer",
            4: "Professional and empathetic throughout",
            5: "Perfectly warm, professional, and empathetic"
        }
    ),
    
    EvaluationCriteria(
        name="conciseness",
        description="Was the response appropriately concise?",
        weight=0.15,
        scoring_guide={
            1: "Extremely long, buried key information",
            2: "Too long or too short, poor structure",
            3: "Acceptable length with minor bloat",
            4: "Well-sized with good information density",
            5: "Perfect length, every sentence adds value"
        }
    ),
    
]

def calculate_weighted_score(scores: dict, rubric: list) -> float:
    """Calculate weighted overall quality score."""
    total = 0.0
    for criterion in rubric:
        if criterion.name in scores:
            total += scores[criterion.name] * criterion.weight
    return total

# Example human evaluation:
human_scores = {
    "task_completion": 4,
    "accuracy": 5,
    "tone": 4,
    "conciseness": 3
}

weighted_score = calculate_weighted_score(human_scores, CUSTOMER_SUPPORT_RUBRIC)
print(f"Overall quality score: {weighted_score:.2f}/5.0")
# Output: Overall quality score: 4.10/5.0
```

## 2.3 — Method 2: LLM-as-Judge (The Scalable Approach)

### 🔍 What Is LLM-as-Judge?

> **LLM-as-Judge = using one LLM to evaluate the output of another LLM — applying your rubric criteria automatically at scale.**

Instead of hiring 10 human evaluators to rate 10,000 outputs — you use a powerful LLM (like GPT-4) to rate the outputs according to your rubric.

---

### 🔬 Why It Works (The Mechanism):

GPT-4 and similar models have demonstrated **strong correlation with human judgments** on many evaluation tasks.

Research (LMSYS, 2023) shows GPT-4 as judge agrees with human judgment 80-85% of the time for typical tasks.

This means: **You can evaluate 10,000 outputs in minutes instead of weeks.**

The tradeoff: LLM judges are approximate, not perfect.
They have biases (prefer longer responses, prefer responses that sound like themselves).
But they scale infinitely.

---

### 🎭 The Analogy — The Apprentice Judge:

A master judge trains an apprentice for years.
The apprentice learns the master's standards, criteria, and reasoning.

Eventually the apprentice can evaluate cases independently.
Not perfectly — but 80-85% as good as the master.
And the apprentice can work 1000x faster.

**The LLM-as-Judge is your trained apprentice evaluator.**

### 🐍 LLM-as-Judge — Complete Implementation:

```python
import instructor
import openai
from pydantic import BaseModel, Field
from typing import Literal
import statistics

client = instructor.from_openai(openai.OpenAI())

# ═══════════════════════════════════════════════
# STEP 1: Define the evaluation output schema
# ═══════════════════════════════════════════════

class CriterionScore(BaseModel):
    score: int = Field(ge=1, le=5)
    reasoning: str = Field(max_length=200)

class ResponseEvaluation(BaseModel):
    """Structured evaluation of an LLM response."""
    
    task_completion: CriterionScore
    accuracy: CriterionScore
    tone: CriterionScore
    conciseness: CriterionScore
    
    overall_verdict: Literal[
        "EXCELLENT",      # 4.5-5.0
        "GOOD",           # 3.5-4.4
        "ACCEPTABLE",     # 2.5-3.4
        "POOR",           # 1.5-2.4
        "UNACCEPTABLE"    # 1.0-1.4
    ]
    
    improvement_suggestion: str = Field(
        max_length=300,
        description="Single most impactful improvement if score < 4"
    )

# ═══════════════════════════════════════════════
# STEP 2: Build the judge prompt
# ═══════════════════════════════════════════════

JUDGE_SYSTEM_PROMPT = """
You are an expert evaluator of customer support AI responses.
Your job is to evaluate responses against specific quality criteria.

Be STRICT and HONEST. Do not be lenient.
A score of 5 means truly exceptional — rare.
A score of 3 means just barely acceptable.
A score of 1 means completely unacceptable.

SCORING GUIDE:
task_completion:
  5 = Completely solved the problem with proactive additional help
  4 = Fully solved the problem with minor gaps
  3 = Addressed the problem but missing some details
  2 = Partially addressed but left key issues unresolved
  1 = Did not address the problem at all

accuracy:
  5 = Perfectly accurate with specific evidence cited
  4 = All statements accurate, well-supported
  3 = Mostly accurate with minor imprecisions
  2 = Contains at least one clear factual error
  1 = Contains multiple factual errors

tone:
  5 = Perfectly warm, professional, and empathetic
  4 = Professional and empathetic throughout
  3 = Acceptable tone but could be warmer
  2 = Too formal/robotic or too casual, off-brand
  1 = Rude, dismissive, or inappropriate

conciseness:
  5 = Perfect length, every sentence adds value
  4 = Well-sized with good information density
  3 = Acceptable length with minor bloat
  2 = Too long or too short, poor structure
  1 = Extremely long, buried key information
"""

JUDGE_USER_TEMPLATE = """
Evaluate this customer support interaction:

CUSTOMER QUESTION:
<question>{customer_question}</question>

AI RESPONSE TO EVALUATE:
<response>{ai_response}</response>

CONTEXT (what the correct answer should cover):
<context>{correct_context}</context>

Evaluate each criterion and provide your assessment.
"""

# ═══════════════════════════════════════════════
# STEP 3: The evaluation function
# ═══════════════════════════════════════════════

def evaluate_response(
    customer_question: str,
    ai_response: str,
    correct_context: str
) -> tuple[ResponseEvaluation, float]:
    """
    Evaluate an AI response using LLM-as-Judge.
    Returns: (evaluation, weighted_score)
    """
    
    evaluation = client.chat.completions.create(
        model="gpt-4",
        response_model=ResponseEvaluation,
        messages=[
            {"role": "system", "content": JUDGE_SYSTEM_PROMPT},
            {
                "role": "user",
                "content": JUDGE_USER_TEMPLATE.format(
                    customer_question=customer_question,
                    ai_response=ai_response,
                    correct_context=correct_context
                )
            }
        ]
    )
    
    # Calculate weighted score
    weights = {
        "task_completion": 0.35,
        "accuracy": 0.30,
        "tone": 0.20,
        "conciseness": 0.15
    }
    
    weighted_score = (
        evaluation.task_completion.score * weights["task_completion"] +
        evaluation.accuracy.score * weights["accuracy"] +
        evaluation.tone.score * weights["tone"] +
        evaluation.conciseness.score * weights["conciseness"]
    )
    
    return evaluation, round(weighted_score, 2)


# ═══════════════════════════════════════════════
# STEP 4: Batch evaluation
# ═══════════════════════════════════════════════

class BatchEvaluator:
    """Evaluate a batch of responses and generate metrics."""
    
    def __init__(self, rubric_weights: dict):
        self.rubric_weights = rubric_weights
        self.results = []
    
    def evaluate_batch(self, test_cases: list) -> dict:
        """
        test_cases: list of dicts with keys:
          - question, response, context, expected_verdict
        """
        print(f"🔍 Evaluating {len(test_cases)} responses...\n")
        
        for i, case in enumerate(test_cases):
            evaluation, score = evaluate_response(
                case["question"],
                case["response"],
                case["context"]
            )
            
            self.results.append({
                "case_id": i,
                "question": case["question"][:50],
                "score": score,
                "verdict": evaluation.overall_verdict,
                "task_completion": evaluation.task_completion.score,
                "accuracy": evaluation.accuracy.score,
                "tone": evaluation.tone.score,
                "conciseness": evaluation.conciseness.score,
                "improvement": evaluation.improvement_suggestion
            })
            
            print(f"  [{i+1}/{len(test_cases)}] Score: {score:.2f}/5.0 "
                  f"| Verdict: {evaluation.overall_verdict}")
        
        return self._generate_report()
    
    def _generate_report(self) -> dict:
        """Generate aggregate metrics report."""
        
        scores = [r["score"] for r in self.results]
        
        # Verdict distribution
        verdict_counts = {}
        for r in self.results:
            verdict_counts[r["verdict"]] = verdict_counts.get(r["verdict"], 0) + 1
        
        # Per-criterion averages
        criterion_avgs = {}
        for criterion in ["task_completion", "accuracy", "tone", "conciseness"]:
            criterion_avgs[criterion] = statistics.mean(
                r[criterion] for r in self.results
            )
        
        return {
            "total_evaluated": len(self.results),
            "mean_score": round(statistics.mean(scores), 3),
            "median_score": round(statistics.median(scores), 3),
            "std_dev": round(statistics.stdev(scores) if len(scores) > 1 else 0, 3),
            "min_score": min(scores),
            "max_score": max(scores),
            "verdict_distribution": verdict_counts,
            "criterion_averages": {
                k: round(v, 2) for k, v in criterion_avgs.items()
            },
            "weakest_criterion": min(criterion_avgs, key=criterion_avgs.get),
            "strongest_criterion": max(criterion_avgs, key=criterion_avgs.get),
            "responses_below_3": sum(1 for s in scores if s < 3),
            "responses_above_4": sum(1 for s in scores if s >= 4),
            "deployment_ready": statistics.mean(scores) >= 3.5 and
                               sum(1 for s in scores if s < 2) == 0
        }
```

## 2.4 — LLM-as-Judge Failure Modes and How to Fix Them:

```
┌──────────────────────────────────────────────────────────────────────┐
│  BIAS 1: LENGTH BIAS                                                │
│  LLM judges prefer LONGER responses, even if shorter is better     │
│  Fix: Explicitly add to judge prompt:                               │
│       "Do not reward length. Concise good answers score higher      │
│        than long mediocre ones."                                    │
├──────────────────────────────────────────────────────────────────────┤
│  BIAS 2: SELF-SIMILARITY BIAS                                       │
│  GPT-4 judge prefers GPT-4 responses over Claude responses         │
│  Fix: Use a different model as judge than the one being evaluated  │
│       Or use multiple judges and average                           │
├──────────────────────────────────────────────────────────────────────┤
│  BIAS 3: POSITION BIAS (in pairwise evaluation)                    │
│  Judge prefers whichever response is shown FIRST                   │
│  Fix: Evaluate A vs B, then B vs A, take consistent winner        │
├──────────────────────────────────────────────────────────────────────┤
│  BIAS 4: SYCOPHANCY BIAS                                            │
│  Judge inflates scores to avoid seeming harsh                      │
│  Fix: Add: "Be strict. A score of 3 means barely acceptable.      │
│             Scores of 5 should be rare and truly exceptional."     │
├──────────────────────────────────────────────────────────────────────┤
│  BIAS 5: RECENCY BIAS                                               │
│  Judge better remembers and evaluates the last criteria listed     │
│  Fix: Ask for criteria evaluation independently, not together      │
└──────────────────────────────────────────────────────────────────────┘
```

## 2.5 — Calibrating Your LLM Judge:

**The most important step that most people skip:**

> Before trusting your LLM judge — validate it against human judgments on a sample.

```python
def calibrate_llm_judge(
    human_scores: list,    # Ground truth human scores
    llm_scores: list,      # LLM judge scores for same examples
    tolerance: float = 0.8 # Correlation threshold to trust LLM judge
) -> dict:
    """
    Measure how well LLM judge correlates with humans.
    Only trust the LLM judge if correlation is high enough.
    """
    import statistics
    
    if len(human_scores) != len(llm_scores):
        raise ValueError("Must have same number of human and LLM scores")
    
    # Calculate correlation (Pearson)
    n = len(human_scores)
    mean_human = statistics.mean(human_scores)
    mean_llm = statistics.mean(llm_scores)
    
    numerator = sum(
        (h - mean_human) * (l - mean_llm)
        for h, l in zip(human_scores, llm_scores)
    )
    
    denom_human = sum((h - mean_human) ** 2 for h in human_scores) ** 0.5
    denom_llm = sum((l - mean_llm) ** 2 for l in llm_scores) ** 0.5
    
    correlation = numerator / (denom_human * denom_llm) if (denom_human * denom_llm) > 0 else 0
    
    # Calculate exact agreement and near agreement
    exact_agreement = sum(1 for h, l in zip(human_scores, llm_scores) if h == l) / n
    near_agreement = sum(1 for h, l in zip(human_scores, llm_scores) if abs(h - l) <= 1) / n
    
    is_trustworthy = correlation >= tolerance
    
    return {
        "correlation": round(correlation, 3),
        "exact_agreement": round(exact_agreement, 3),
        "near_agreement": round(near_agreement, 3),
        "is_trustworthy": is_trustworthy,
        "recommendation": (
            f"✅ LLM judge is reliable (correlation: {correlation:.2f})"
            if is_trustworthy else
            f"⚠️ LLM judge needs improvement (correlation: {correlation:.2f} < {tolerance})"
        )
    }

# Example:
human_scores = [4, 2, 5, 3, 4, 1, 3, 5, 4, 2]

# 📦 SECTION 3 — Task Success Rate

## 3.1 — What Is Task Success Rate? (First Principles)

> **Task Success Rate (TSR) = the percentage of times your LLM prompt correctly completes its intended task, measured over a defined test set.**

This is the **most important single metric** for any LLM application.

Everything else supports it, but TSR answers the fundamental question:
> *"Does this thing actually work?"*

---

### 🎭 The Analogy — The Surgeon's Success Rate:

When you choose a surgeon, what is the most important number?

**Surgery success rate.**

Not how long the surgery takes.
Not how clean the operating room looks.
Not how nice the surgeon is.

The fundamental question: **Does the procedure work?**

Task Success Rate is your LLM's surgery success rate.

---

## 3.2 — Defining "Success" (The Hard Part):

The hardest part of measuring TSR is defining what "success" means.

**It must be:**
- Objective (two different people check the same output → same pass/fail)
- Specific (not "good" — exactly what criteria must be met)
- Measurable (you can write code or a rubric to check it)

---

### 📋 Defining Success for Different Task Types:

```
TASK: Sentiment Classification
SUCCESS = output exactly matches expected label
          AND output is one of {POSITIVE, NEGATIVE, NEUTRAL, MIXED}
MEASUREMENT: exact_match(actual.upper(), expected.upper())

─────────────────────────────────────────────────────────────

TASK: Named Entity Extraction
SUCCESS = all expected entities are present in output
          AND no hallucinated entities are present
          AND all entities have correct type labels
MEASUREMENT: precision, recall, F1 on entity list

─────────────────────────────────────────────────────────────

TASK: Customer Email Response
SUCCESS = (a) addresses the customer's core issue
          AND (b) provides at least one actionable next step
          AND (c) does not contain factual errors
          AND (d) is under 200 words
MEASUREMENT: LLM judge for (a)(b)(c) + regex for (d)

─────────────────────────────────────────────────────────────

TASK: Code Generation
SUCCESS = code executes without errors
          AND all unit tests pass
          AND no security vulnerabilities detected
MEASUREMENT: execute code + run test suite + static analysis

─────────────────────────────────────────────────────────────

TASK: Document Summarization
SUCCESS = summary covers ≥3 of the 5 key points (defined in advance)
          AND is ≤100 words
          AND contains no information not in the document
MEASUREMENT: key point coverage check + word count + hallucination check
```

# EVALUATORS — each checks one specific success criterion
# ══════════════════════════════════════════════════════════════

class Evaluators:
    """Collection of reusable evaluation functions."""
    
    @staticmethod
    def exact_match(actual: str, expected: str) -> tuple[bool, str]:
        """Exact string match (case insensitive)."""
        passed = actual.strip().upper() == expected.strip().upper()
        reason = None if passed else f"Expected '{expected}', got '{actual}'"
        return passed, reason
    
    @staticmethod
    def valid_enum(actual: str, allowed_values: set) -> tuple[bool, str]:
        """Check if output is one of the allowed values."""
        normalized = actual.strip().upper()
        passed = normalized in {v.upper() for v in allowed_values}
        reason = None if passed else \
            f"'{actual}' not in allowed values: {allowed_values}"
        return passed, reason
    
    @staticmethod
    def contains_all(actual: str, required_items: list) -> tuple[bool, str]:
        """Check if output contains all required items."""
        actual_lower = actual.lower()
        missing = [item for item in required_items
                  if item.lower() not in actual_lower]
        passed = len(missing) == 0
        reason = None if passed else f"Missing required items: {missing}"
        return passed, reason
    
    @staticmethod
    def valid_json(actual: str, schema: dict = None) -> tuple[bool, str]:
        """Check if output is valid JSON, optionally matching schema."""
        try:
            parsed = json.loads(actual)
            if schema:
                # Check required fields
                required = schema.get("required", [])
                missing = [f for f in required if f not in parsed]
                if missing:
                    return False, f"JSON missing required fields: {missing}"
            return True, None
        except json.JSONDecodeError as e:
            return False, f"Invalid JSON: {str(e)[:100]}"
    
    @staticmethod
    def word_count_limit(actual: str, max_words: int) -> tuple[bool, str]:
        """Check if output is within word count limit."""
        count = len(actual.split())
        passed = count <= max_words
        reason = None if passed else f"Too long: {count} words > {max_words} limit"
        return passed, reason
    
    @staticmethod
    def no_hallucination(
        actual: str,
        source_document: str,
        client
    ) -> tuple[bool, str]:
        """Use LLM to check if response contains facts not in source."""
        # This is the LLM-as-judge approach for hallucination
        # Implementation in Section 5
        pass

# TASK SUCCESS RATE TRACKER
# ══════════════════════════════════════════════════════════════

class TaskSuccessRateTracker:
    """
    Measures and tracks Task Success Rate over time.
    Supports multiple evaluation criteria per task.
    """
    
    def __init__(self, task_name: str):
        self.task_name = task_name
        self.results: List[TaskResult] = []
        self.history: List[dict] = []  # Historical TSR by date
    
    def evaluate_single(
        self,
        test_id: str,
        actual_output: str,
        input_data: dict,
        expected_output: Optional[str],
        evaluators: List[tuple],    # [(eval_fn, *args)]
        latency_ms: float,
        token_count: int
    ) -> TaskResult:
        """
        Evaluate a single output against all criteria.
        All criteria must pass for the task to succeed.
        """
        
        all_passed = True
        failure_reasons = []
        
        for evaluator_fn, *args in evaluators:
            passed, reason = evaluator_fn(actual_output, *args)
            if not passed:
                all_passed = False
                if reason:
                    failure_reasons.append(reason)
        
        status = SuccessStatus.PASS if all_passed else SuccessStatus.FAIL
        
        result = TaskResult(
            test_id=test_id,
            input_data=input_data,
            actual_output=actual_output,
            expected_output=expected_output,
            status=status,
            score=1.0 if all_passed else 0.0,
            failure_reason="; ".join(failure_reasons) if failure_reasons else None,
            latency_ms=latency_ms,
            token_count=token_count
        )
        
        self.results.append(result)
        return result
    
    def compute_tsr(self, results: List[TaskResult] = None) -> dict:
        """
        Compute comprehensive TSR metrics from results.
        """
        results = results or self.results
        
        if not results:
            return {"error": "No results to compute TSR from"}
        
        total = len(results)
        passed = sum(1 for r in results if r.status == SuccessStatus.PASS)
        failed = sum(1 for r in results if r.status == SuccessStatus.FAIL)
        errors = sum(1 for r in results if r.status == SuccessStatus.ERROR)
        
        # Performance metrics
        latencies = [r.latency_ms for r in results if r.latency_ms > 0]
        tokens = [r.token_count for r in results if r.token_count > 0]
        
        # Failure analysis
        failure_reasons = [r.failure_reason for r in results
                          if r.failure_reason]
        
        # TSR over time (if we have historical data)
        tsr = passed / total if total > 0 else 0
        
        metrics = {
            "task_name": self.task_name,
            "timestamp": datetime.now().isoformat(),
            "total_cases": total,
            "passed": passed,
            "failed": failed,
            "errors": errors,
            "task_success_rate": round(tsr, 4),
            "task_success_percent": f"{tsr:.1%}",
            "performance": {
                "avg_latency_ms": round(statistics.mean(latencies), 1) if latencies else None,
                "p95_latency_ms": round(sorted(latencies)[int(len(latencies) * 0.95)], 1) if latencies else None,
                "avg_tokens": round(statistics.mean(tokens), 0) if tokens else None,
            },
            "failure_analysis": {
                "total_failures": failed,
                "sample_failures": failure_reasons[:5],  # First 5 reasons
            },
            "health": (
                "🟢 EXCELLENT" if tsr >= 0.95 else
                "🟡 GOOD"      if tsr >= 0.90 else
                "🟠 WARNING"   if tsr >= 0.80 else
                "🔴 CRITICAL"
            ),
            "deploy_recommendation": (
                "✅ Ready to deploy" if tsr >= 0.90 else
                "⚠️ Needs improvement before deploy" if tsr >= 0.80 else
                "🔴 Do NOT deploy"
            )
        }
        
        # Save to history
        self.history.append({
            "timestamp": metrics["timestamp"],
            "tsr": tsr,
            "total": total
        })
        
        return metrics
    
    def detect_regression(self, current_tsr: float, threshold: float = 0.03) -> dict:
        """
        Check if TSR has regressed from the previous measurement.
        threshold = acceptable drop (0.03 = 3% drop triggers alert)
        """
        if len(self.history) < 2:
            return {"has_regression": False, "message": "Not enough history"}
        
        previous_tsr = self.history[-2]["tsr"]
        drop = previous_tsr - current_tsr
        
        if drop > threshold:
            return {
                "has_regression": True,
                "previous_tsr": f"{previous_tsr:.1%}",
                "current_tsr": f"{current_tsr:.1%}",
                "drop": f"{drop:.1%}",
                "alert": f"🚨 TSR REGRESSION: dropped {drop:.1%} ({previous_tsr:.1%} → {current_tsr:.1%})",
                "action": "Investigate prompt changes or model API updates"
            }
        
        return {
            "has_regression": False,
            "previous_tsr": f"{previous_tsr:.1%}",
            "current_tsr": f"{current_tsr:.1%}",
            "change": f"{current_tsr - previous_tsr:+.1%}",
            "message": "TSR within acceptable range"
        }
```

# 📦 SECTION 4 — Format Accuracy Rate

## 4.1 — What Is Format Accuracy Rate? (First Principles)

> **Format Accuracy Rate (FAR) = the percentage of LLM outputs that comply with the required output format — correct structure, valid syntax, required fields present, correct data types.**

This is separate from task success rate.

```
A response can be:
- Correct content + Wrong format = ❌ FAIL (system can't parse it)
- Wrong content  + Correct format = ❌ FAIL (wrong answer, but parseable)
- Correct content + Correct format = ✅ PASS (good)

You need BOTH task success AND format accuracy.
```

---

### 🎭 The Analogy — The Tax Form:

Imagine you fill out a tax form.

You calculate everything correctly (task success = ✅).
But you write your income in the wrong box (format accuracy = ❌).

The IRS computer rejects your entire return.
Your correct calculation is useless because it's in the wrong format.

**In AI pipelines: correct content in wrong format = system crash.**

---

## 4.2 — What Format Accuracy Measures:

```
┌──────────────────────────────────────────────────────────────────────┐
│  FORMAT DIMENSION         │  WHAT IT CHECKS                        │
├──────────────────────────────────────────────────────────────────────┤
│  Structural validity      │  Is it valid JSON/XML/CSV?             │
│  Field presence           │  Are all required fields there?        │
│  Field naming             │  Are field names exactly right?        │
│  Data types               │  Are types correct (int vs string)?    │
│  Enum compliance          │  Are values from allowed set?          │
│  Length constraints       │  Is it within length limits?           │
│  Nesting structure        │  Is nesting depth correct?             │
│  No extra content         │  No prose before/after JSON?          │
│  No extra fields          │  No hallucinated schema fields?        │
└──────────────────────────────────────────────────────────────────────┘
```

import json
import re
from pydantic import BaseModel, ValidationError
from typing import Any
from dataclasses import dataclass

@dataclass
class FormatCheckResult:
    """Result of a single format check."""
    check_name: str
    passed: bool
    failure_detail: str | None

class FormatAccuracyChecker:
    """
    Comprehensive format accuracy checker.
    Run against every LLM output in your pipeline.
    """
    
    def __init__(self, pydantic_model=None):
        self.pydantic_model = pydantic_model
        self.check_history = []
    
    def check_all(self, llm_output: str) -> dict:
        """
        Run all format checks and return comprehensive report.
        """
        checks = []
        
        # ─── CHECK 1: No prose before JSON ─────────────────────
        check1 = FormatCheckResult(
            check_name="no_prose_prefix",
            passed=llm_output.strip().startswith('{'),
            failure_detail=None if llm_output.strip().startswith('{')
                          else f"Output starts with: '{llm_output.strip()[:30]}'"
        )
        checks.append(check1)
        
        # ─── CHECK 2: No markdown wrapper ─────────────────────
        check2 = FormatCheckResult(
            check_name="no_markdown_wrapper",
            passed="```" not in llm_output,
            failure_detail=None if "```" not in llm_output
                          else "Output contains markdown code block"
        )
        checks.append(check2)
        
        # ─── CHECK 3: Valid JSON syntax ─────────────────────────
        parsed = None
        try:
            parsed = json.loads(llm_output.strip())
            check3 = FormatCheckResult(
                check_name="valid_json_syntax",
                passed=True,
                failure_detail=None
            )
        except json.JSONDecodeError as e:
            check3 = FormatCheckResult(
                check_name="valid_json_syntax",
                passed=False,
                failure_detail=f"JSON parse error: {str(e)[:100]}"
            )
        checks.append(check3)
        
        # ─── CHECK 4-N: Schema validation (if model provided) ───
        schema_errors = []
        if self.pydantic_model and parsed is not None:
            try:
                self.pydantic_model(**parsed)
                check4 = FormatCheckResult(
                    check_name="schema_validation",
                    passed=True,
                    failure_detail=None
                )
            except ValidationError as e:
                errors = e.errors()
                error_summary = "; ".join(
                    f"{err['loc']}: {err['msg']}"
                    for err in errors[:3]
                )
                check4 = FormatCheckResult(
                    check_name="schema_validation",
                    passed=False,
                    failure_detail=f"Pydantic validation failed: {error_summary}"
                )
            checks.append(check4)
        
        # ─── COMPUTE AGGREGATE ──────────────────────────────────
        all_passed = all(c.passed for c in checks)
        failed_checks = [c for c in checks if not c.passed]
        
        result = {
            "format_valid": all_passed,
            "checks_passed": sum(1 for c in checks if c.passed),
            "checks_failed": len(failed_checks),
            "total_checks": len(checks),
            "pass_rate": sum(1 for c in checks if c.passed) / len(checks),
            "failed_checks": [
                {"name": c.check_name, "detail": c.failure_detail}
                for c in failed_checks
            ],
            "all_checks": [
                {"name": c.check_name, "passed": c.passed}
                for c in checks
            ]
        }
        
        self.check_history.append({
            "format_valid": all_passed,
            "output_sample": llm_output[:50]
        })
        
        return result
    
    def compute_far_metrics(self) -> dict:
        """
        Compute Format Accuracy Rate over all checks run.
        """
        if not self.check_history:
            return {"error": "No checks run yet"}
        
        total = len(self.check_history)
        valid = sum(1 for r in self.check_history if r["format_valid"])
        
        return {
            "format_accuracy_rate": round(valid / total, 4),
            "format_accuracy_percent": f"{valid / total:.1%}",
            "total_checked": total,
            "format_valid": valid,
            "format_invalid": total - valid,
            "health": (
                "🟢 EXCELLENT (>99%)" if valid/total >= 0.99 else
                "🟡 GOOD (>95%)"      if valid/total >= 0.95 else
                "🟠 WARNING (<95%)"   if valid/total >= 0.90 else
                "🔴 CRITICAL (<90%)"
            )
        }

## 4.4 — Format Drift Detection:

A subtle but critical production problem:

> **Format drift = your LLM starts violating format rules over time, even without prompt changes — due to model updates or distribution shifts.**

```python
class FormatDriftDetector:
    """
    Detect gradual degradation of format compliance over time.
    """
    
    def __init__(self, window_size: int = 100, alert_threshold: float = 0.05):
        self.window_size = window_size
        self.alert_threshold = alert_threshold
        self.rolling_results = []
        self.baseline_far = None
    
    def set_baseline(self, baseline_far: float):
        """Set the expected baseline FAR from initial evaluation."""
        self.baseline_far = baseline_far
    
    def add_result(self, format_valid: bool):
        """Add a single format check result to the rolling window."""
        self.rolling_results.append(format_valid)
        
        # Keep only the most recent window_size results
        if len(self.rolling_results) > self.window_size:
            self.rolling_results.pop(0)
    
    def check_for_drift(self) -> dict:
        """Check if FAR has drifted significantly from baseline."""
        
        if len(self.rolling_results) < self.window_size:
            return {
                "has_drift": False,
                "message": f"Insufficient data ({len(self.rolling_results)}/{self.window_size})"
            }
        
        if self.baseline_far is None:
            return {"has_drift": False, "message": "No baseline set"}
        
        current_far = sum(self.rolling_results) / len(self.rolling_results)
        drop = self.baseline_far - current_far
        
        if drop > self.alert_threshold:
            return {
                "has_drift": True,
                "baseline_far": f"{self.baseline_far:.1%}",
                "current_far": f"{current_far:.1%}",
                "drop": f"{drop:.1%}",
                "alert": (
                    f"🚨 FORMAT DRIFT DETECTED: "
                    f"FAR dropped {drop:.1%} over last {self.window_size} calls"
                ),
                "likely_cause": (
                    "Model API update" if drop > 0.10 else
                    "Gradual drift — monitor closely"
                )
            }
        
        return {
            "has_drift": False,
            "baseline_far": f"{self.baseline_far:.1%}",
            "current_far": f"{current_far:.1%}",
            "change": f"{current_far - self.baseline_far:+.1%}",
            "message": "Format accuracy stable"
        }
```

# 📦 SECTION 5 — Hallucination Rate

## 5.1 — What Is Hallucination? (Deep First Principles)

> **Hallucination = when an LLM generates information that is confidently stated but factually incorrect, fabricated, or not grounded in the provided context.**

This is the most dangerous failure mode of LLMs.

---

### 🔬 Why Do LLMs Hallucinate? (The Mechanism):

Remember Module 1: LLMs are probability machines.

They predict the **most statistically likely continuation** of text.

The key insight:

> **The most statistically likely continuation is NOT always the most factually correct continuation.**

```
EXAMPLE OF HALLUCINATION MECHANISM:

Input: "The capital of Australia is..."

Training data the LLM learned from:
- Thousands of documents mention "Sydney is Australia's largest city"
- Sydney appears near Australia more than Canberra in most text
- Many tourists think Sydney is the capital

Statistical probability:
- "Sydney" → HIGH probability (wrong answer)
- "Canberra" → LOWER probability (correct answer)

LLM might say: "The capital of Australia is Sydney"

It's not lying. It's not stupid.
It's generating the most statistically probable continuation.
That probability doesn't guarantee truth.
```

---

### 📊 The 3 Types of Hallucination:

```
┌──────────────────────────────────────────────────────────────────────┐
│  TYPE 1: INTRINSIC HALLUCINATION                                    │
│  LLM contradicts information that WAS provided in context           │
│                                                                      │
│  Context: "The meeting is on Tuesday at 3pm"                       │
│  LLM says: "Your meeting is on Wednesday at 3pm"                   │
│  Why: LLM misread or mis-weighted the provided context             │
├──────────────────────────────────────────────────────────────────────┤
│  TYPE 2: EXTRINSIC HALLUCINATION                                    │
│  LLM adds information not present in the provided context           │
│                                                                      │
│  Context: "Dr. Smith published a paper on climate"                 │
│  LLM says: "Dr. Smith from Harvard published a groundbreaking       │
│             paper in Nature on climate change"                      │
│  Reality: "Harvard" and "Nature" were never mentioned              │
│  Why: LLM "fills in" what seems statistically likely               │
├──────────────────────────────────────────────────────────────────────┤
│  TYPE 3: PARAMETRIC HALLUCINATION                                   │
│  LLM uses incorrect world knowledge from training                   │
│                                                                      │
│  LLM says: "The population of Bangladesh is 120 million"          │
│  Reality: 170 million (LLM's training data was outdated)           │
│  Why: Training data has errors, is outdated, or was sparse         │
└──────────────────────────────────────────────────────────────────────┘
```

---

### 🎭 The Analogy — The Overconfident Intern:

Imagine a new intern who:
- Wants to seem helpful and knowledgeable
- Is afraid to say "I don't know"
- Fills in gaps in their knowledge with plausible-sounding guesses
- States guesses with the same confidence as known facts

**That intern will sometimes be brilliantly helpful.**
**And sometimes will confidently give you completely wrong information.**

**LLMs are that intern.** At planetary scale.

---

## 5.2 — Measuring Hallucination Rate:

> **Hallucination Rate = percentage of LLM outputs that contain at least one factually incorrect or ungrounded claim.**

This is harder to measure than TSR or FAR because:
- You need to know what's true (ground truth)
- You need to check if claims are supported by context
- You need to verify against external knowledge

---

# METHOD 3: SELF-CONSISTENCY HALLUCINATION CHECK
# Run same query multiple times — if answers differ,
# the LLM is uncertain = higher hallucination risk
# ═══════════════════════════════════════════════

def self_consistency_hallucination_check(
    prompt: str,
    n_runs: int = 5,
    temperature: float = 0.7
) -> dict:
    """
    Estimate hallucination risk via response variance.
    High variance across runs = high hallucination risk.
    
    Based on: if the LLM is CERTAIN about something,
    it gives the same answer every time.
    If it's UNCERTAIN (=higher hallucination risk),
    it gives different answers.
    """
    
    oai_client = openai.OpenAI()
    responses = []
    
    for _ in range(n_runs):
        response = oai_client.chat.completions.create(
            model="gpt-4",
            messages=[{"role": "user", "content": prompt}],
            temperature=temperature
        )
        responses.append(response.choices[0].message.content.strip())
    
    # Check for consensus
    unique_responses = len(set(responses))
    consensus_rate = 1 - ((unique_responses - 1) / n_runs)
    
    # If all responses are the same = high certainty = low hallucination risk
    # If all responses differ = high uncertainty = high hallucination risk
    
    return {
        "n_runs": n_runs,
        "unique_responses": unique_responses,
        "consensus_rate": round(consensus_rate, 3),
        "hallucination_risk": (
            "LOW"    if consensus_rate >= 0.8 else
            "MEDIUM" if consensus_rate >= 0.6 else
            "HIGH"
        ),
        "responses": responses,
        "most_common": max(set(responses), key=responses.count),
        "recommendation": (
            "Use this response" if consensus_rate >= 0.8 else
            "Verify before using" if consensus_rate >= 0.6 else
            "Do NOT use without human verification"
        )
    }

STRATEGY 5: Self-Consistency

# 📦 SECTION 6 — Prompt A/B Testing

## 6.1 — What Is A/B Testing? (First Principles)

> **Prompt A/B testing = running two different prompt versions simultaneously on real traffic, measuring which performs better across your key metrics, and using statistical analysis to determine if the difference is real or just random.**

The key word is **statistical**.

Without statistics, you might see Prompt B outperform Prompt A on 100 examples — and that could just be random chance.

With proper statistics, you know if the difference is real.

---

### 🎭 The Analogy — Drug Trials:

Before a new drug is approved, it goes through randomized controlled trials:
- Group A gets the existing treatment
- Group B gets the new drug
- Neither patients nor doctors know which is which
- Results are measured across thousands of patients
- Statistical analysis determines if the new drug is actually better

**Prompt A/B testing is the same scientific discipline — applied to LLM prompts.**

---

## 6.2 — The Statistical Foundation (Made Simple):

### 🔢 The Two Questions You Must Answer:

**Question 1: Is the observed difference real, or random chance?**

This is answered by **statistical significance testing.**

```
EXAMPLE:
Prompt A: 87% task success rate (tested on 50 examples)
Prompt B: 91% task success rate (tested on 50 examples)

"B is 4% better" — but is it REALLY better?

Or did we just happen to pick 50 slightly easier examples for B?
How do we know?

→ Statistical significance test
```

---

### 🔢 Key Statistical Concepts (Simplified):

```
P-VALUE:
The probability that the observed difference happened by random chance.

p-value < 0.05 → The difference is REAL (less than 5% chance it's random)
p-value > 0.05 → The difference might be random noise

RULE OF THUMB FOR PROMPT TESTING:
Sample size needed for 4% improvement at 90% confidence:
  → n ≈ 500+ samples per variant

Sample size needed for 2% improvement at 90% confidence:
  → n ≈ 2000+ samples per variant

Practical rule: Run at least 1000 requests per variant
               before drawing conclusions
```

```python
import random
import hashlib
import math
import statistics
from dataclasses import dataclass, field
from typing import List, Optional
from datetime import datetime, timedelta
from collections import defaultdict

@dataclass
class ABTestConfig:
    """Configuration for a prompt A/B test."""
    
    # Identity
    test_name: str
    description: str
    
    # Prompts
    prompt_a: str           # Control (current version)
    prompt_b: str           # Treatment (new version)
    
    # Traffic
    traffic_split: float = 0.5    # 0.5 = 50/50, 0.2 = 80/20 A/B
    
    # Stopping criteria
    min_samples_per_variant: int = 1000
    max_duration_days: int = 14
    significance_level: float = 0.05  # p < 0.05 to declare winner
    minimum_effect_size: float = 0.02  # Must improve by at least 2%
    
    # Metrics to track
    primary_metric: str = "task_success_rate"
    secondary_metrics: list = field(default_factory=lambda: [
        "hallucination_rate",
        "format_accuracy_rate",
        "avg_latency_ms",
        "avg_token_count"
    ])
    
    # Test state
    started_at: str = field(default_factory=lambda: datetime.now().isoformat())
    status: str = "RUNNING"  # RUNNING, COMPLETED, STOPPED_EARLY

@dataclass
class VariantResult:
    """Collected results for one A/B test variant."""
    variant: str                         # "A" or "B"
    samples: int = 0
    task_successes: int = 0
    hallucination_count: int = 0
    format_failures: int = 0
    total_latency_ms: float = 0
    total_tokens: int = 0
    
    @property
    def task_success_rate(self):
        return self.task_successes / self.samples if self.samples else 0
    
    @property
    def hallucination_rate(self):
        return self.hallucination_count / self.samples if self.samples else 0
    
    @property
    def format_accuracy_rate(self):
        return 1 - (self.format_failures / self.samples) if self.samples else 0
    
    @property
    def avg_latency_ms(self):
        return self.total_latency_ms / self.samples if self.samples else 0
    
    @property
    def avg_tokens(self):
        return self.total_tokens / self.samples if self.samples else 0


class PromptABTester:
    """
    Production-grade prompt A/B testing framework.
    
    Features:
    - Consistent user assignment (same user = same variant)
    - Statistical significance testing
    - Multi-metric tracking
    - Early stopping capability
    - Comprehensive reporting
    """
    
    def __init__(self, config: ABTestConfig):
        self.config = config
        self.results = {
            "A": VariantResult(variant="A"),
            "B": VariantResult(variant="B")
        }
        self._user_assignments = {}
    
    # ─── VARIANT ASSIGNMENT ──────────────────────────────────────────
    
    def assign_variant(self, user_id: str) -> str:
        """
        Assign user to variant consistently.
        Same user always gets same variant (stable experience).
        """
        if user_id in self._user_assignments:
            return self._user_assignments[user_id]
        
        # Deterministic hash-based assignment
        hash_value = int(hashlib.md5(
            f"{self.config.test_name}:{user_id}".encode()
        ).hexdigest(), 16)
        
        variant = "A" if (hash_value % 100) / 100 >= self.config.traffic_split else "B"
        self._user_assignments[user_id] = variant
        return variant
    
    def get_prompt(self, user_id: str) -> tuple[str, str]:
        """Returns: (variant_name, prompt_template)"""
        variant = self.assign_variant(user_id)
        prompt = self.config.prompt_a if variant == "A" else self.config.prompt_b
        return variant, prompt
    
    # ─── RESULT RECORDING ──────────────────────────────────────────
    
    def record_result(
        self,
        user_id: str,
        task_success: bool,
        hallucination_detected: bool,
        format_valid: bool,
        latency_ms: float,
        token_count: int
    ):
        """Record the outcome of one LLM call."""
        
        variant = self.assign_variant(user_id)
        r = self.results[variant]
        
        r.samples += 1
        if task_success:
            r.task_successes += 1
        if hallucination_detected:
            r.hallucination_count += 1
        if not format_valid:
            r.format_failures += 1
        r.total_latency_ms += latency_ms
        r.total_tokens += token_count
    
    # ─── STATISTICAL TESTING ─────────────────────────────────────
    
    def _chi_square_test(
        self,
        successes_a: int,
        total_a: int,
        successes_b: int,
        total_b: int
    ) -> float:
        """
        Chi-square test for proportions.
        Returns p-value.
        
        H0: rate_A == rate_B (no difference)
        H1: rate_A != rate_B (there IS a difference)
        
        p-value < 0.05 → reject H0 → difference is real
        """
        if total_a == 0 or total_b == 0:
            return 1.0  # No data = no significance
        
        # Observed values
        fail_a = total_a - successes_a
        fail_b = total_b - successes_b
        total = total_a + total_b
        total_success = successes_a + successes_b
        total_fail = fail_a + fail_b
        
        # Expected values (if null hypothesis is true)
        if total_success == 0 or total_fail == 0:
            return 1.0  # All same result = no difference
        
        exp_success_a = total_a * total_success / total
        exp_fail_a    = total_a * total_fail / total
        exp_success_b = total_b * total_success / total
        exp_fail_b    = total_b * total_fail / total
        
        # Chi-square statistic
        chi_sq = (
            (successes_a - exp_success_a) ** 2 / exp_success_a +
            (fail_a      - exp_fail_a)    ** 2 / exp_fail_a    +
            (successes_b - exp_success_b) ** 2 / exp_success_b +
            (fail_b      - exp_fail_b)    ** 2 / exp_fail_b
        )
        
        # Convert chi-square to p-value (df=1)
        # Using approximation: p ≈ e^(-chi_sq/2) for df=1
        p_value = math.exp(-chi_sq / 2)
        return min(p_value, 1.0)
    
    def analyze(self) -> dict:
        """
        Full statistical analysis of the A/B test.
        Should call this periodically or after minimum samples reached.
        """
        a = self.results["A"]
        b = self.results["B"]
        
        # Check if enough data
        sufficient_data = (
            a.samples >= self.config.min_samples_per_variant and
            b.samples >= self.config.min_samples_per_variant
        )
        
        # Primary metric analysis
        rate_a = a.task_success_rate
        rate_b = b.task_success_rate
        absolute_diff = rate_b - rate_a
        relative_diff = (rate_b - rate_a) / rate_a if rate_a > 0 else 0
        
        # Statistical significance test
        p_value = self._chi_square_test(
            a.task_successes, a.samples,
            b.task_successes, b.samples
        )
        
        is_significant = p_value < self.config.significance_level
        meets_min_effect = abs(absolute_diff) >= self.config.minimum_effect_size
        
        # Determine winner
        if is_significant and meets_min_effect and sufficient_data:
            if rate_b > rate_a:
                winner = "B"
                recommendation = f"✅ DEPLOY PROMPT B — {absolute_diff:+.1%} improvement, statistically significant"
            else:
                winner = "A"
                recommendation = f"✅ KEEP PROMPT A — Prompt B is {abs(absolute_diff):.1%} WORSE, statistically significant"
        elif sufficient_data and is_significant and not meets_min_effect:
            winner = None
            recommendation = f"🟡 NO MEANINGFUL DIFFERENCE — {absolute_diff:+.1%} is below minimum effect size of {self.config.minimum_effect_size:.1%}"
        elif sufficient_data and not is_significant:
            winner = None
            recommendation = f"🟡 INCONCLUSIVE — Difference not statistically significant (p={p_value:.3f})"
        else:
            winner = None
            recommendation = f"⏳ STILL RUNNING — Need {self.config.min_samples_per_variant - min(a.samples, b.samples)} more samples"
        
        return {
            "test_name": self.config.test_name,
            "status": self.config.status,
            "sufficient_data": sufficient_data,
            
            "variant_a": {
                "samples": a.samples,
                "task_success_rate": f"{rate_a:.3%}",
                "hallucination_rate": f"{a.hallucination_rate:.3%}",
                "format_accuracy_rate": f"{a.format_accuracy_rate:.3%}",
                "avg_latency_ms": round(a.avg_latency_ms, 1),
                "avg_tokens": round(a.avg_tokens, 0),
            },
            "variant_b": {
                "samples": b.samples,
                "task_success_rate": f"{rate_b:.3%}",
                "hallucination_rate": f"{b.hallucination_rate:.3%}",
                "format_accuracy_rate": f"{b.format_accuracy_rate:.3%}",
                "avg_latency_ms": round(b.avg_latency_ms, 1),
                "avg_tokens": round(b.avg_tokens, 0),
            },
            
            "statistical_analysis": {
                "absolute_difference": f"{absolute_diff:+.3%}",
                "relative_improvement": f"{relative_diff:+.1%}",
                "p_value": round(p_value, 4),
                "is_significant": is_significant,
                "meets_minimum_effect": meets_min_effect,
                "significance_level_used": self.config.significance_level,
            },
            
            "winner": winner,
            "recommendation": recommendation,
            
            "multi_metric_comparison": {
                "TSR":        f"A={rate_a:.1%} B={rate_b:.1%} → {absolute_diff:+.1%}",
                "Hall. Rate": f"A={a.hallucination_rate:.1%} B={b.hallucination_rate:.1%}",
                "Format":     f"A={a.format_accuracy_rate:.1%} B={b.format_accuracy_rate:.1%}",
                "Latency":    f"A={a.avg_latency_ms:.0f}ms B={b.avg_latency_ms:.0f}ms",
                "Tokens":     f"A={a.avg_tokens:.0f} B={b.avg_tokens:.0f}",
            }
        }

## 6.4 — Common A/B Testing Mistakes:

```

│  MISTAKE 1: STOPPING TOO EARLY (Peeking Problem)                   │
│  You run 50 samples, see B winning, stop the test                  │
│  Reality: With 50 samples, you can't trust the result              │
│  Fix: Decide minimum sample size BEFORE starting. Don't peek.      │
├──────────────────────────────────────────────────────────────────────┤
│  MISTAKE 2: ONLY MEASURING ONE METRIC                               │

├──────────────────────────────────────────────────────────────────────┤

│  MISTAKE 4: INCONSISTENT USER ASSIGNMENT                            │

├──────────────────────────────────────────────────────────────────────┤
│  MISTAKE 5: TESTING DURING UNUSUAL PERIODS                          │

│  These bias your user population                                   │
│  Fix: Run tests during stable, representative traffic periods      │

# 📦 SECTION 7 — Latency vs Complexity Trade-offs

## 7.1 — What Is the Latency vs Complexity Trade-off? (First Principles)

> **The fundamental tension: more complex prompts (more context, more reasoning, more instructions) generally produce better quality outputs — but they also cost more tokens, take more time, and cost more money.**

There is no free lunch.

Better quality → more complex prompt → more tokens → higher latency → higher cost.

> **Your job as an AI engineer is to find the MINIMUM complexity that produces ACCEPTABLE quality — not the maximum quality you can possibly achieve.**

---

### 🎭 The Analogy — The Sports Car vs. The Truck:

A Formula 1 car can go 200mph.
A delivery truck goes 60mph.

For racing → Formula 1 is right.
For delivering packages → Truck is right.

Using a Formula 1 car for deliveries is:
- Expensive
- Hard to maintain
- Overkill for the job

**Using GPT-4 with 10,000-token CoT prompts for every customer support message is the same mistake.**

---

## 7.2 — The 4 Dimensions of Efficiency Cost:

```
┌──────────────────────────────────────────────────────────────────────┐
│  DIMENSION 1: LATENCY (Time to response)                           │
│  → Users wait longer for complex prompts                           │
│  → P95 latency matters more than average for user experience       │
│  → Rule of thumb: <1s = excellent, <3s = acceptable, >5s = bad    │
├──────────────────────────────────────────────────────────────────────┤
│  DIMENSION 2: TOKEN COST (Money per call)                          │
│  → Input tokens + Output tokens = total cost                       │
│  → GPT-4 costs ~100x more per token than GPT-3.5                  │
│  → At scale: 1M calls/day × $0.05/call = $50,000/day              │
├──────────────────────────────────────────────────────────────────────┤
│  DIMENSION 3: THROUGHPUT (Calls per second)                        │
│  → Long prompts reduce max concurrent requests                     │
│  → Rate limits are per-minute-tokens, not per-minute-calls         │
│  → More complex = fewer total users served                         │
├──────────────────────────────────────────────────────────────────────┤
│  DIMENSION 4: MODEL CAPABILITY NEEDED                               │
│  → Simple tasks don't need GPT-4                                   │
│  → Classification: GPT-3.5 often matches GPT-4                    │
│  → Reasoning: GPT-4 significantly better                           │
│  → Right model for right task = massive cost saving               │
└──────────────────────────────────────────────────────────────────────┘
```

from typing import Optional

class EfficiencyMetrics:

        self,
        call_fn,         # Function that makes the LLM call
        quality_evaluator,  # Function that evaluates quality
        *args, **kwargs
    ) -> EfficiencyMetrics:
        """
        Measure efficiency of one LLM call.
        """
        start_time = time.time()
        
        response = call_fn(*args, **kwargs)
        
        latency_ms = (time.time() - start_time) * 1000
        
        # Extract token usage
        usage = response.usage
        input_tokens = usage.prompt_tokens
        output_tokens = usage.completion_tokens
        total_tokens = usage.total_tokens
        
        # Calculate cost
        cost = (
            (input_tokens  / 1000) * self.pricing["input"] +
            (output_tokens / 1000) * self.pricing["output"]
        )
        
        # Evaluate quality
        output_text = response.choices[0].message.content
        quality = quality_evaluator(output_text)
        
        metrics = EfficiencyMetrics(
            latency_ms=latency_ms,
            input_tokens=input_tokens,
            output_tokens=output_tokens,
            total_tokens=total_tokens,
            cost_usd=cost,
            quality_score=quality
        )
        
        self.results.append(metrics)
        return metrics
    
    def compare_configurations(
        self,
        configurations: list,   # List of (name, prompt, model) tuples
        test_inputs: list,
        quality_evaluator
    ) -> dict:
        """
        Compare multiple prompt/model configurations.
        Find the optimal quality-cost point.
        """
        import openai
        oai_client = openai.OpenAI()
        
        comparison = {}
        
        for config_name, prompt_template, model in configurations:
            print(f"\n📊 Testing: {config_name}")
            config_metrics = []
            
            for test_input in test_inputs[:20]:  # Sample of inputs
                
                start = time.time()
                
                response = oai_client.chat.completions.create(
                    model=model,
                    messages=[{
                        "role": "user",
                        "content": prompt_template.format(input=test_input)
                    }],
                    temperature=0.0
                )
                
                latency = (time.time() - start) * 1000
                usage = response.usage
                output = response.choices[0].message.content
                
                pricing = self.PRICING.get(model, {"input": 0.01, "output": 0.03})
                cost = (
                    (usage.prompt_tokens  / 1000) * pricing["input"] +
                    (usage.completion_tokens / 1000) * pricing["output"]
                )
                
                quality = quality_evaluator(output, test_input)
                
                config_metrics.append({
                    "latency_ms": latency,
                    "total_tokens": usage.total_tokens,
                    "cost_usd": cost,
                    "quality": quality
                })
            
            # Aggregate metrics
            avg_latency = statistics.mean(m["latency_ms"] for m in config_metrics)
            avg_tokens  = statistics.mean(m["total_tokens"] for m in config_metrics)
            avg_cost    = statistics.mean(m["cost_usd"] for m in config_metrics)
            avg_quality = statistics.mean(m["quality"] for m in config_metrics)
            
            comparison[config_name] = {
                "model": model,
                "avg_latency_ms": round(avg_latency, 1),
                "avg_tokens": round(avg_tokens, 0),
                "avg_cost_usd": round(avg_cost, 5),
                "avg_quality": round(avg_quality, 3),
                "cost_per_quality": round(avg_cost / max(avg_quality, 0.01), 5),
                "cost_per_1000_calls": round(avg_cost * 1000, 2),
                "monthly_cost_100k_daily": round(avg_cost * 100000 * 30, 0),
            }
        
        # Find optimal: best quality-to-cost ratio
        best_efficiency = min(
            comparison.items(),
            key=lambda x: x[1]["cost_per_quality"]
        )
        best_quality = max(
            comparison.items(),
            key=lambda x: x[1]["avg_quality"]
        )
        
        return {
            "configurations": comparison,
            "best_efficiency": best_efficiency[0],
            "best_quality": best_quality[0],
            "recommendation": f"Use '{best_efficiency[0]}' for cost-efficiency, "
                             f"'{best_quality[0]}' when quality is critical"
        }

## 7.5 — The Latency Budget Framework:

```python
@dataclass
class LatencyBudget:
    """
    Define and enforce latency budgets for your pipeline.
    """
    total_budget_ms: float          # Total acceptable end-to-end latency
    
    # How budget is divided across pipeline stages
    input_validation_ms: float      # Guard rails check
    main_llm_ms: float              # Main LLM call
    output_validation_ms: float     # Format + safety check
    parsing_ms: float               # JSON parsing + Pydantic
    overhead_ms: float              # Network, database, etc.
    
    @property
    def allocated_total(self) -> float:
        return (self.input_validation_ms + self.main_llm_ms +
                self.output_validation_ms + self.parsing_ms +
                self.overhead_ms)
    
    @property
    def budget_utilization(self) -> float:
        return self.allocated_total / self.total_budget_ms
    
    def check_compliance(
        self,
        actual_breakdown: dict  # {"main_llm": 1200, ...}
    ) -> dict:
        violations = []
        for stage, budget in [
            ("input_validation", self.input_validation_ms),
            ("main_llm", self.main_llm_ms),
            ("output_validation", self.output_validation_ms),
        ]:
            actual = actual_breakdown.get(stage, 0)
            if actual > budget:
                violations.append({
                    "stage": stage,
                    "budget_ms": budget,
                    "actual_ms": actual,
                    "overrun_ms": actual - budget
                })
        
        return {
            "within_budget": len(violations) == 0,
            "violations": violations,
            "total_actual": sum(actual_breakdown.values()),
            "total_budget": self.total_budget_ms
        }


# Example: Customer support chatbot with 3-second budget
chatbot_budget = LatencyBudget(
    total_budget_ms=3000,
    input_validation_ms=200,    # Fast model for safety check
    main_llm_ms=2200,           # Main response generation
    output_validation_ms=400,   # Output safety check
    parsing_ms=50,              # JSON parsing
    overhead_ms=150             # Network + DB
)

print(f"Budget utilization: {chatbot_budget.budget_utilization:.1%}")
# Budget utilization: 100.0%
```

# 🎯 SECTION 9 — Interview Questions & Answers

---

### ❓ Question 1:
**"How do you evaluate whether a prompt is working well?"**

✅ Strong Answer:
> "I evaluate across three dimensions simultaneously: quality, safety, and efficiency. For quality, I measure Task Success Rate against a labeled test set, and qualitative scores using LLM-as-Judge with a predefined rubric. For safety, I measure hallucination rate using context grounding checks, and format accuracy rate using schema validation. For efficiency, I measure latency, token count, and cost per call. The key principle is that you never optimize for one metric alone — improving TSR at the cost of tripling latency or doubling hallucination rate is not an improvement. I track all metrics on a dashboard and use regression testing to catch degradation before it reaches production."

---

### ❓ Question 2:
**"What is LLM-as-Judge and when would you use it?"**

✅ Strong Answer:
> "LLM-as-Judge uses a capable model like GPT-4 to evaluate the outputs of another LLM according to a predefined rubric. It's used when human evaluation is too expensive or slow to run at scale — like evaluating 10,000 customer support responses. The key to making it work is defining explicit scoring criteria with clear anchors at each score level, rather than asking the judge vaguely 'is this good?' It has known biases — length bias, self-similarity bias, sycophancy — which I mitigate by adding explicit anti-bias instructions and calibrating the judge's scores against a sample of human evaluations first. I use it as the primary evaluation mechanism but always maintain a human-evaluated golden set for quarterly validation."

---

### ❓ Question 3:
**"Explain how you would measure and track hallucination rate."**

✅ Strong Answer:
> "I use three complementary methods. For RAG and document-grounded tasks, I use context grounding checks — an LLM judge that identifies every factual claim in the response and verifies whether each is explicitly supported by the provided context. For general factual tasks, I use fact verification prompts that classify claims as correct, incorrect, or uncertain. For uncertainty estimation, I use self-consistency checks — running the same query 5 times and measuring response variance, because high variance correlates with high hallucination risk. I track the aggregate hallucination rate as a percentage of all outputs containing at least one ungrounded claim, targeting under 3% for most applications and under 1% for high-stakes domains like healthcare or finance."

---

### ❓ Question 4:
**"How do you run a proper A/B test for prompts?"**

✅ Strong Answer:
> "I follow the scientific method: define the hypothesis, decide minimum sample size before starting, assign users consistently using hash-based routing, collect results across all key metrics simultaneously, then apply statistical significance testing before declaring a winner. The most common mistakes are stopping too early when you see one variant winning — this is the peeking problem and leads to false conclusions — and only measuring one metric. A new prompt might improve TSR but increase latency 3x and hallucination rate 2x, which is a net loss. I always measure TSR, hallucination rate, format accuracy, latency, and cost together. I only declare a winner when p-value is below 0.05 AND the improvement meets the minimum meaningful effect size threshold, usually 2-3%."

---

### ❓ Question 5:
**"How do you think about latency vs quality trade-offs in production?"**

✅ Strong Answer:
> "I treat it as an optimization problem: find the minimum complexity that achieves acceptable quality — not the maximum quality regardless of cost. Practically, I run benchmarks across a complexity ladder: simple zero-shot on a cheap model, few-shot on the same model, zero-shot on GPT-4, few-shot CoT on GPT-4. I measure quality score and cost-per-quality-point for each configuration. Often a GPT-3.5 few-shot prompt achieves 92% of GPT-4's quality at 10% of the cost for classification tasks. For simple tasks, that 8% quality gap doesn't justify 10x higher cost. I also set explicit latency budgets per pipeline stage and use tiered model routing — simple classification goes to cheap fast models, complex reasoning goes to capable expensive models."

# 🧠 SECTION 12 — Engineer Mindset

When a senior AI engineer approaches evaluation:

```
1. "What does success mean — EXACTLY?"
   → Write it down before you write the prompt
   → Specific, measurable, objective criteria only

2. "What is my quality floor vs ceiling?"
   → Floor: minimum acceptable (below this = do not ship)
   → Ceiling: optimal target (spend more to get this only if ROI justifies)

3. "What is my test set's blind spot?"
   → What input types am I NOT testing?
   → Edge cases, adversarial, multilingual, short inputs?

4. "Can I trust my LLM judge?"
   → When did I last calibrate against human evaluations?
   → What biases is it introducing?

5. "Is this improvement real or just random noise?"
   → What is the sample size?
   → What is the p-value?
   → Is the effect size practically meaningful?

6. "What is the full cost of this optimization?"
   → Does improving TSR hurt hallucination rate?
   → Does better quality require 3x the latency?
   → What is cost per quality point across model options?

7. "How will I know if this degrades in 3 months?"
   → Continuous monitoring pipeline
   → Automated alerts on metric degradation
   → Scheduled human evaluation samples
```
