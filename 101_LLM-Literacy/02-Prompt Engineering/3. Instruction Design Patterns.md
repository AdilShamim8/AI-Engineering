# 📦 PATTERN 1 — Zero-Shot Prompting

## 1.1 — What Is Zero-Shot? (First Principles)

### 🔍 Start From the Word:

**"Zero"** = no examples given
**"Shot"** = one attempt / demonstration

So:

> **Zero-shot prompting = giving the LLM a task with ZERO examples of what good output looks like — just a direct instruction.**

You are testing whether the LLM can **understand and complete a task purely from its training knowledge** — with no help from examples.

---

### 🧠 Why Does It Work At All?

This is the deep question. Let's answer it from first principles.

During training, the LLM saw trillions of text patterns like:

```
"Classify this review as positive or negative:
 'I love this product!' → POSITIVE"

"Translate this to Spanish:
 'Hello' → 'Hola'"

"Summarize this paragraph:
 [paragraph] → [shorter version]"
```

So when you give it a zero-shot instruction — it matches the instruction to similar patterns it has SEEN BEFORE during training.

It already has a mental model of what "classify," "translate," and "summarize" mean — from billions of examples of humans doing those things.

> **Zero-shot works because the LLM has "seen" millions of zero-shot tasks during pre-training. Your instruction activates the right pattern.**

---

### 🎯 Visual — Zero-Shot Architecture:

```
┌──────────────────────────────────────────────────────────┐
│                                                          │

│  ─────────────────────────────────────────────────────  │

│  ─────────────────────────────────────────────────────  │

```
✅ ZERO-SHOT WORKS WHEN:
┌──────────────────────────────────────────────────────┐

│  → LLM has seen this type of task in training       │
│                                                      │
│  Task is simple and unambiguous                      │

┌──────────────────────────────────────────────────────┐

## 1.3 — Zero-Shot Failure Modes:

| ❌ Failure | Why It Happens | ✅ Fix |
|-----------|---------------|--------|
| Wrong format | LLM chooses format from training | Add explicit format instruction |
| Over-explanation | LLM defaults to verbose | Add: "Answer in one word / sentence" |
| Wrong interpretation | Task is ambiguous | Add context to clarify intent |
| Hallucination | No grounding data | Add: "Only answer based on provided text" |
| Inconsistency at scale | Different runs, different formats | Move to few-shot for consistency |

# 📦 PATTERN 2 — Few-Shot Prompting

## 2.1 — What Is Few-Shot? (First Principles)

### 🔍 Start From the Word:

**"Few"** = a small number (typically 2-8)
**"Shot"** = one demonstration / example

So:

> **Few-shot prompting = giving the LLM 2-8 examples of INPUT → OUTPUT pairs BEFORE the actual task, so it learns the pattern and continues it.**

---

### 🧠 Why Does It Work? (The Deep Reason)

This is called **in-context learning** — one of the most remarkable properties of large language models.

Here is the key insight:

> **The LLM doesn't just see your examples as "examples." It sees them as the beginning of a TEXT PATTERN — and its entire job is to CONTINUE that pattern consistently.**

Think about it from the probability machine perspective:

```
You show:
Input: "I love this!" → Output: POSITIVE
Input: "This is terrible." → Output: NEGATIVE
Input: "It's okay I guess." → Output: ?????

The LLM asks: "What is the most probable continuation 
               of this pattern?"
Answer: NEUTRAL

It learned the pattern from your examples — not from 
your description of the task.
```

This is fundamentally different from zero-shot.

In zero-shot: **The LLM uses its training knowledge to understand the task.**
In few-shot: **The LLM uses your examples to understand YOUR specific version of the task.**

---

### 🎭 The Analogy — Teaching By Showing:

Imagine you want to teach someone a new card game.

**Zero-shot approach:**
> "The goal is to collect pairs of matching cards and score points."

**Few-shot approach:**
> *[You play 3 rounds with them, demonstrating every move]*
> "Now you try."

The few-shot learner has seen the **actual pattern of behavior** — not just a description of it.

They can imitate it much more accurately.

---

## 2.5 — The Science Behind Example Quality

This is where most beginners make mistakes.

Not all examples are equal. Here is what research shows:

```
┌─────────────────────────────────────────────────────────────────┐
│  WHAT MAKES FEW-SHOT EXAMPLES POWERFUL?                        │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  ✅ COVERAGE → Examples cover different cases                  │
│     Bad:  3 examples, all POSITIVE sentiment                   │
│     Good: 1 POSITIVE, 1 NEGATIVE, 1 MIXED                     │
│                                                                 │
│  ✅ DIVERSITY → Examples show variety of input types           │
│     Bad:  All short, simple sentences                          │
│     Good: Short, long, complex, edge cases                     │
│                                                                 │
│  ✅ REALISM → Examples look like real input you'll get         │
│     Bad:  Perfect clean examples                               │
│     Good: Examples that match actual data                      │
│                                                                 │
│  ✅ CONSISTENCY → Examples follow same exact format            │
│     Bad:  Different output formats across examples             │
│     Good: Identical format every time                          │
│                                                                 │
│  ✅ ORDER → Put the most representative example LAST           │
│     The last example has the most influence on the output      │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

# 📦 PATTERN 3 — Role Prompting (Deep Dive)

> *We touched on this in Module 2. Now we go deeper into the engineering science behind it.*

## 3.1 — Role Prompting — The Deep Mechanism

### 🔬 What Is Actually Happening When You Assign a Role?

Remember: The LLM was trained on text written by every type of human — doctors, lawyers, poets, engineers, teachers, children.

Each "type" of human writes with:
- Different vocabulary
- Different reasoning depth
- Different assumptions about the reader
- Different levels of formality
- Different problem-solving approaches

When you assign a role, you are doing **distribution selection** — you're saying:

> *"From your entire training data, only access the patterns written by THIS type of person."*

---

### 🧪 Proof — Same Question, 4 Different Roles:

**Question: "What is risk?"**

```
Role: None (zero-shot)
Answer: "Risk is the possibility of something bad happening."
→ Generic dictionary definition

Role: "You are a Wall Street hedge fund manager"
Answer: "Risk is quantified exposure to volatility — 
         measured as standard deviation of returns or VaR..."
→ Financial, quantitative, professional

Role: "You are a kindergarten teacher"
Answer: "Risk is like when you try something new 
         and it might not go perfectly — like jumping 
         over a puddle!"
→ Simple, child-friendly, relatable

Role: "You are a philosopher"
Answer: "Risk presupposes uncertainty about future states 
         and implies a value judgment about outcomes..."
→ Abstract, contemplative, precise

Role: "You are a startup founder pitching investors"
Answer: "Risk is the price of upside. No risk, no return. 
         The key is calculated risk with asymmetric reward..."
→ Energetic, pragmatic, persuasive
```

**Same word. Four completely different knowledge distributions.**

---

## 3.2 — The 4 Levels of Role Prompting:

```
LEVEL 1 — BASIC (Weak):
"You are an expert."
→ Too vague. Which expert? Expert at what?
→ LLM barely changes behavior

LEVEL 2 — DOMAIN (Better):
"You are a cybersecurity expert."
→ Activates a domain-specific distribution
→ Output becomes more technical and relevant

LEVEL 3 — PERSONA (Strong):
"You are a senior cybersecurity engineer at a Fortune 500 
company specializing in zero-trust architecture."
→ Very specific role activated
→ Output has correct expertise, vocabulary, approach

LEVEL 4 — FULL ROLE (Strongest):
"You are a senior cybersecurity engineer with 12 years 
experience at Fortune 500 companies, specializing in 
zero-trust architecture. You explain complex security 
concepts using real breach case studies. You speak to 
CTOs who understand technology but not deep security 
details. You always end recommendations with a risk score."
→ Full distribution activated:
   WHO they are + WHAT they know + HOW they communicate 
   + WHO they're talking to + WHAT their style is
```

---

## 3.3 — Role Stacking (Advanced Technique):

You can assign **multiple roles** to create hybrid expertise:

```
"You are a product manager who also has strong 
 engineering background. You evaluate features 
 from both a business viability AND technical 
 feasibility perspective — always giving both 
 perspectives side by side."
```

This creates a **composite distribution** — drawing from two expert patterns simultaneously.

---

```

# 📦 PATTERN 4 — Chain-of-Thought Prompting (CoT)

## 4.1 — What Is Chain-of-Thought? (First Principles)

> **Chain-of-Thought (CoT) prompting = forcing the LLM to show its reasoning step by step, BEFORE giving the final answer.**

This is one of the most important discoveries in prompt engineering history.

---

### 🧠 The Core Insight — Why CoT Changes Everything:

Remember: An LLM generates text **one token at a time**.

Each token it generates is influenced by **everything generated before it**.

This means:

> **If you make the LLM write out its reasoning FIRST — that reasoning becomes part of the context that shapes the final answer.**

It's not just showing its work.
The act of **generating the reasoning** actually **improves the reasoning**.

---

### 🔬 The Deep Mechanism (Very Important):

**Without CoT — The LLM jumps straight to the answer:**

```
Token generation:
Question → [skip reasoning] → Answer

The answer has no foundation.
It's based purely on statistical pattern matching.
For complex problems, this often fails.
```

**With CoT — The LLM builds a reasoning scaffold:**

```
Token generation:
Question → Step 1 → Step 2 → Step 3 → ... → Answer

Each step GENERATES NEW CONTEXT.
The answer is based on that generated reasoning.
The reasoning improves the answer.
```

This is why CoT works — it forces the LLM to **build a logical chain where each step constrains the next.**

---

### 🎭 The Analogy — The Detective:

Think of Sherlock Holmes.

He doesn't just say "It was Colonel Mustard."

He says:
> *"The mud on your shoes is from the north road. The north road goes to the manor. The manor was where the crime happened. The crime happened between 8-10pm. You were at the manor between 8-10pm. Therefore — you are the murderer."*

**Each reasoning step constrains the next.**
The conclusion is **forced by the chain**, not guessed.

CoT makes the LLM think like Sherlock Holmes.

---

## 4.2 — Two Types of CoT Prompting:

### 🔵 TYPE 1: Zero-Shot CoT (The Magic Phrase)

The simplest way to trigger chain-of-thought:

```
Just add: "Let's think step by step."
```

This single phrase was shown in research (Kojima et al., 2022) to dramatically improve accuracy on reasoning tasks.

**Why does this one phrase work?**

> During training, the LLM saw millions of examples where humans wrote "Let's think step by step" — and what followed was always careful, structured reasoning. So this phrase is a **pattern trigger** that activates a reasoning distribution.

**Example:**

```
❌ Without CoT:
Q: A store had 120 apples. They sold 45 in the morning 
   and 30 in the afternoon. Then received 20 new apples. 
   How many apples are there now?
A: 65

(Wrong! LLM jumped to answer too fast)

✅ With Zero-Shot CoT:
Q: [same question]
   Let's think step by step.

A: Step 1: Start with 120 apples.
   Step 2: Sold 45 in the morning: 120 - 45 = 75
   Step 3: Sold 30 in the afternoon: 75 - 30 = 45
   Step 4: Received 20 new apples: 45 + 20 = 65

   Final answer: 65 apples.

(Correct! And verifiable!)
```

---

### 🔵 TYPE 2: Few-Shot CoT (Teaching the Reasoning Pattern)

Here you don't just trigger CoT — you **show it how to reason** through examples:

```
Q: Roger has 5 tennis balls. He buys 2 more cans 
   of tennis balls. Each can has 3 balls. 
   How many tennis balls does he have now?

A: Roger starts with 5 tennis balls.
   He buys 2 cans × 3 balls per can = 6 new balls.
   Total: 5 + 6 = 11 tennis balls.
   The answer is 11.

---

Q: The cafeteria had 23 apples. If they used 20 for 
   lunch and bought 6 more, how many do they have?

A: [LLM now follows the same reasoning pattern]
```

---

## 4.3 — CoT for Non-Math Problems (Very Powerful):

CoT isn't just for math. It transforms ANY complex reasoning task:

**CoT for Logical Reasoning:**
```
Question: 
"Our app has high churn rate. We improved UX, 
 hired more support staff, and cut prices by 20%. 
 Churn is still high. What's the most likely issue?"

Prompt addition: 
"Reason through each possible cause systematically 
 before reaching a conclusion."

LLM Output (with CoT):
"Let me analyze each factor:

 UX improvement: We addressed it → likely not the issue
 Support: More staff means faster resolution → not this
 Pricing: 20% cut with no improvement → price is not the problem

 What else causes high churn?
 → Value mismatch: Product doesn't solve the core problem
 → Onboarding: Users may not reach the 'aha moment'
 → Competitor: Better alternative exists

 Given that price, UX, and support are addressed:
 The most likely root cause is PRODUCT-MARKET FIT —
 the product may not be solving the right problem for users."
```

The reasoning chain **forced** a better conclusion.

# 📦 PATTERN 5 — Self-Consistency Prompting

## 5.1 — What Is Self-Consistency? (First Principles)

### 🔍 The Problem It Solves:

Even with CoT, the LLM can generate a confident but **wrong reasoning chain**.

Why? Because it's still probabilistic — it generates **one** path through the reasoning space, and that path might be incorrect.

**Self-consistency solves this with a radical idea:**

> **Run the same reasoning task MULTIPLE TIMES with different reasoning paths. Then take the MAJORITY VOTE as the final answer.**

---

### 🎭 The Analogy — The Jury System:

One judge making a decision can be biased or wrong.

That's why courtrooms use **juries of 12 people**.

Each juror reasons independently.
The majority decision is more reliable than any single person's judgment.

**Self-consistency applies the jury system to LLMs.**

---

### 🔬 The Deep Mechanism:

```
NORMAL CoT (Single Path):
Question → [one reasoning path] → Answer A

SELF-CONSISTENCY (Multiple Paths):
Question → [reasoning path 1] → Answer A
Question → [reasoning path 2] → Answer B  
Question → [reasoning path 3] → Answer A
Question → [reasoning path 4] → Answer A
Question → [reasoning path 5] → Answer B

Majority Vote:
A: 3 votes ← ✅ WINNER
B: 2 votes

Final Answer: A
```

Because different reasoning paths EACH have noise, but they converge on the **correct answer** more often than a single path.

---

## 5.2 — How Self-Consistency Works in Practice:

### Method 1: Manual (Low-Cost Version)

```python
# Run the same prompt 5 times with temperature > 0
# (temperature adds variation to each run)

prompt = """
Q: [complex reasoning question]
Let's think step by step.
"""

# Run 5 times
answers = [call_llm(prompt) for _ in range(5)]

# Extract final answers
# Take majority vote
from collections import Counter
final_answers = [extract_answer(a) for a in answers]
winner = Counter(final_answers).most_common(1)[0][0]
```

---

### Method 2: In-Prompt Self-Consistency

```
Solve this problem using 3 different reasoning approaches.
For each approach, show your work.
At the end, compare all 3 answers and select the most 
consistent one as your final answer.

Problem: [your complex problem here]

Approach 1:
[LLM reasons here]

Approach 2:
[LLM reasons here]

Approach 3:
[LLM reasons here]

Most consistent answer:
```

---

## 5.3 — When To Use Self-Consistency:

```
USE IT WHEN:
✅ The task has a definitive correct answer (math, logic)
✅ Accuracy matters more than speed
✅ You need confidence levels in the answer
✅ The task is complex and single-path CoT feels risky
✅ You're building a high-stakes decision system

DON'T USE IT WHEN:
❌ The task is creative (no "correct" answer)
❌ Speed and cost are primary concerns
❌ The task is simple (single CoT is sufficient)
❌ You need one specific output (voting won't help)
```

---

## 5.4 — Self-Consistency Failure Modes:

| ❌ Failure | Why It Happens | ✅ Fix |
|-----------|---------------|--------|
| All paths reach same wrong answer | Systematic bias in training data | Use very different prompting styles per run |
| Too expensive | N API calls = N × cost | Use 3 runs minimum; 5-7 for critical tasks |
| Tie vote | Even split between two answers | Add one more run as tiebreaker |
| Creative tasks have no winner | No "correct" output | Don't use for open-ended tasks |

# 📦 PATTERN 6 — Step-by-Step Reasoning

## 6.1 — What Is Step-by-Step Reasoning?

### 🔍 The Difference from CoT:

Many people confuse CoT and Step-by-Step. Here's the distinction:

```
CHAIN-OF-THOUGHT:
→ Lets the LLM reason freely
→ The LLM decides how to structure the reasoning
→ "Let's think step by step" (open-ended)

STEP-BY-STEP REASONING (Structured Decomposition):
→ YOU define the steps explicitly
→ The LLM follows YOUR decomposition structure
→ "First do X. Then do Y. Finally do Z."
```

> **CoT = LLM chooses HOW to reason**
> **Step-by-step = YOU engineer HOW it reasons**

Step-by-step is **more controlled** and **more predictable** than CoT.

---

### 🏗️ The Analogy — The Recipe:

CoT is like telling a chef: *"Make something delicious."*
Step-by-step is like giving them a recipe with exact steps.

Both can produce good food.
But the recipe gives you **consistency and control**.

---

## 6.2 — Step-by-Step Architecture:

```
┌─────────────────────────────────────────────────────────────────┐
│  STEP-BY-STEP STRUCTURE                                        │
│                                                                 │
│  [ROLE]                                                         │
│  [CONTEXT]                                                      │
│  [INPUT DATA]                                                   │
│                                                                 │
│  Complete the following steps in order:                        │
│                                                                 │
│  STEP 1: [Specific sub-task 1]                                 │
│  STEP 2: [Specific sub-task 2]                                 │
│  STEP 3: [Specific sub-task 3]                                 │
│  STEP 4: [Final synthesis or output]                           │
│                                                                 │
│  Show your work for each step before moving to the next.       │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

---

STEP 2: List any bugs or errors found
STEP 3: List performance issues
STEP 4: List security vulnerabilities
STEP 5: Provide the corrected version with inline comments
STEP 6: Rate code quality 1-10 with one-line justification

Complete each step fully before moving to the next.

Code:

```
```

STEP 1: State the decision clearly in one sentence

```

### 🧪 Example 3 — Research Summarization:

## 6.4 — The Power Move — Conditional Steps:

You can add **logic** to your steps:

```
STEP 1: Read the customer message
STEP 2: Classify intent as: COMPLAINT, QUESTION, FEEDBACK
STEP 3: 
   IF COMPLAINT → Follow complaint resolution protocol
   IF QUESTION → Provide direct answer with one follow-up offer
   IF FEEDBACK → Thank and log key points
STEP 4: Draft a response under 100 words
STEP 5: Rate response tone: WARM / NEUTRAL / COLD
```

This is essentially **writing a workflow** for the LLM to execute.

**You are programming logic using natural language.**

## 6.5 — Step-by-Step Failure Modes:

| ❌ Failure | Why It Happens | ✅ Fix |
|-----------|---------------|--------|
| LLM skips steps | Steps feel redundant to the LLM | Add: "Do not skip any step" |
| Steps bleed into each other | Boundaries unclear | Number each step AND label with headers |
| LLM finishes too quickly | Treats steps as optional | Add: "Show complete work for EACH step" |
| Steps are wrong order | Bad decomposition design | Think through the logic order yourself first |
| Too many steps | Cognitive overload for the LLM | Keep to 5-7 steps maximum |

# 📦 PATTERN 7 — Ask-Verify-Improve Loop

## 7.1 — What Is the Ask-Verify-Improve Loop?

This is the most **powerful and underused** pattern in prompt engineering.

The big idea:

> **Instead of asking the LLM once and accepting the answer — you build a FEEDBACK LOOP where the LLM evaluates its own output and iteratively improves it.**

You make the AI into its own **critic, editor, and improver**.

---

### 🧠 Why Does This Work? (First Principles)

Here is a profound insight about LLMs:

> **LLMs are often better at EVALUATING outputs than at GENERATING perfect outputs on the first try.**

Think about it:

When you ask an LLM to write something, it generates based on the statistical flow of text.
It can easily make mistakes.

But when you show it the output and ask "Is this good? What's wrong?", the LLM now has **the entire output as context** — which it can analyze more carefully than it can generate from scratch.

This is like the difference between:
- Writing an essay from scratch (hard)
- Editing someone else's essay (easier — you can see the whole thing)

The LLM is a better editor than it is a first-draft writer.

**The Ask-Verify-Improve loop exploits this asymmetry.**

---

### 🎭 The Analogy — The Expert Self-Review:

A good lawyer doesn't just write a contract and submit it.

They write it → review it → find weaknesses → improve it → review again.

The **same person** wearing different hats:
1. Writer hat
2. Critic hat
3. Improver hat

The Ask-Verify-Improve loop makes the LLM do the same.

---

## 7.2 — The Three Stages of the Loop:

```
┌──────────────────────────────────────────────────────────────────┐
│                                                                  │
│  STAGE 1: ASK                                                   │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │ Give the LLM the original task                           │  │
│  │ Get a first draft response                               │  │
│  └───────────────────────────────────────────────────────────┘  │
│                          ↓                                       │
│  STAGE 2: VERIFY                                                │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │ Show the LLM its own output                              │  │
│  │ Ask it to evaluate against specific criteria             │  │
│  │ Identify weaknesses, errors, gaps                        │  │
│  └───────────────────────────────────────────────────────────┘  │
│                          ↓                                       │
│  STAGE 3: IMPROVE                                               │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │ Based on the evaluation — rewrite or improve             │  │
│  │ Apply the critique to fix specific issues                │  │
│  │ Repeat if needed                                         │  │
│  └───────────────────────────────────────────────────────────┘  │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
```

---

## 7.3 — Ask-Verify-Improve in Practice:

### 🧪 Example — Email Writing:

**STAGE 1 — ASK:**
```
Write a cold outreach email to a startup CTO 
offering our API testing tool.
Target: Technical decision maker
Goal: Get a 15-minute demo call
Tone: Professional but not stiff
Length: Under 150 words
```

*(LLM generates first draft)*

---

**STAGE 2 — VERIFY:**
```
You just wrote this email:
"""
[paste the first draft here]
"""

Now evaluate it critically against these criteria:
1. Does it address a pain point the CTO actually cares about?
2. Is the value proposition clear in the first 2 sentences?
3. Is the CTA specific and low-friction?
4. Are there any weak phrases that sound salesy or generic?
5. Is the tone right for a technical audience?

Give a specific score (1-5) for each criterion and explain why.
```

*(LLM evaluates its own output)*

---

**STAGE 3 — IMPROVE:**
```
Based on your evaluation above:
Rewrite the email fixing ALL the weaknesses you identified.
Pay special attention to the issues you rated 3 or below.
```

*(LLM produces improved version)*

---

### 🧪 Example — Code Generation:

```
STAGE 1:
Write a Python function that validates email addresses.

STAGE 2:
Review the function you just wrote for:
1. Edge cases it doesn't handle
2. Potential bugs
3. Performance issues
4. Missing error handling
List every problem you find.

STAGE 3:
Now rewrite the function fixing every issue you just identified.
Add a comment for each fix explaining what you fixed and why.
```

---

## 7.4 — Advanced Version — Constitutional AI Style:

This is how companies like Anthropic build safe AI systems.

You define **criteria** (a "constitution") that the output must follow — then the LLM evaluates itself against those criteria:

```
TASK:
Write a response to this customer complaint.
[complaint text]

CONSTITUTION (verify against ALL of these):
□ 1. Does the response acknowledge the customer's feelings?
□ 2. Does it take responsibility without admitting legal fault?
□ 3. Does it offer a concrete next step?
□ 4. Is it under 100 words?
□ 5. Does it avoid the word "unfortunately"?

STEP 1: Write the first draft.
STEP 2: Check each criterion. Mark ✅ or ❌.
STEP 3: For any ❌ items, rewrite to fix them.
STEP 4: Final version.
```

## 7.5 — The Self-Critique Pattern (One-Shot Version):

If you can't run multiple API calls, do it in ONE prompt:

```
Task: [your task]

Instructions:
1. Complete the task above (first draft)
2. Critique your own output for: accuracy, clarity, completeness
3. List the top 3 improvements needed
4. Write the improved final version

Clearly label each section:
[FIRST DRAFT], [CRITIQUE], [IMPROVEMENTS], [FINAL VERSION]
```

## 7.6 — Ask-Verify-Improve Failure Modes:

```
┌──────────────────────────────────────────────────────────────┐
│  FAILURE 1: SYCOPHANTIC VERIFICATION                         │
│  LLM evaluates its own output and says "it's perfect!"      │
│  The LLM is biased toward its own outputs                   │
│  Fix: Use specific criteria + ask "What could be better?"   │
│       Or use a different LLM call for verification          │

│  "Is this good?" → LLM says yes                             │

├──────────────────────────────────────────────────────────────┤
│  FAILURE 4: COST EXPLOSION                                   │
│  3 stages × complex tasks = many expensive tokens           │
│  Fix: Use one-shot self-critique version for simple tasks   │
└──────────────────────────────────────────────────────────────┘
```

# 🎯 SECTION 9 — Interview Questions & Answers

---

### ❓ Question 1:
**"What is the difference between zero-shot and few-shot prompting?"**

✅ Strong Answer:
> "Zero-shot prompting gives the model a task with no examples — it relies entirely on patterns from pre-training. Few-shot prompting provides 2-8 input-output examples before the actual task, enabling in-context learning. Few-shot is superior for format consistency, custom tasks, and domain-specific outputs — but costs more tokens. Zero-shot is faster and cheaper but less reliable for unusual or format-sensitive tasks. In production, I'd start with zero-shot for rapid prototyping and switch to few-shot when consistency becomes critical."

---

### ❓ Question 2:
**"Explain Chain-of-Thought prompting and why it improves accuracy."**

✅ Strong Answer:
> "Chain-of-Thought prompting forces the LLM to verbalize its reasoning before giving a final answer. The key mechanism is that each generated reasoning step becomes part of the context that shapes subsequent tokens — including the final answer. This means the answer is grounded in a logical chain rather than a single probability jump. Research shows adding 'Let's think step by step' significantly improves accuracy on multi-step reasoning tasks. The failure mode is that the LLM can produce convincingly wrong reasoning chains — which is why I combine it with self-consistency for high-stakes tasks."

---

### ❓ Question 3:
**"What is self-consistency prompting and when would you use it?"**

✅ Strong Answer:
> "Self-consistency runs the same CoT prompt multiple times with temperature greater than zero — generating diverse reasoning paths — then takes a majority vote on the final answers. It applies the wisdom-of-crowds principle to LLM outputs. I'd use it when there's a single correct answer and accuracy is more important than speed or cost — like in automated reasoning, math verification, or critical classification systems. The tradeoff is N API calls equals N times the cost, so it's not suitable for high-throughput or cost-sensitive applications."

---

### ❓ Question 4:
**"What is the Ask-Verify-Improve loop and why is it powerful?"**

✅ Strong Answer:
> "The Ask-Verify-Improve loop exploits the fact that LLMs are better at evaluating existing text than generating perfect text from scratch. First, you get a draft output. Then you prompt the LLM to evaluate that output against specific criteria. Finally, you prompt it to rewrite based on its own critique. The power is in the asymmetry — generation is hard, evaluation is easier because the entire output is in context. The failure mode is sycophancy — the LLM approving its own output — which I prevent by giving explicit evaluation rubrics and asking for specific improvements rather than just asking 'is this good?'"

---

### ❓ Question 5:
**"How do you choose which prompting pattern to use in production?"**

✅ Strong Answer:
> "I start with the task type. Simple, common tasks get zero-shot with format instructions. Custom or domain-specific tasks with strict format requirements get few-shot. Complex multi-step reasoning gets CoT — or step-by-step if I want to control the reasoning structure. High-stakes decisions with single correct answers get self-consistency. Production-quality outputs where first drafts aren't acceptable get the ask-verify-improve loop. And crucially — in real systems I almost always combine patterns: role prompting for distribution control, CoT or step-by-step for reasoning quality, and the verify loop for output quality. The patterns aren't mutually exclusive."

# 🧠 SECTION 12 — Engineer Mindset

When a real AI engineer selects prompting patterns, they think:

```
1. "What is the failure mode I'm most worried about?"
   → Wrong format?     → Few-shot
   → Wrong reasoning?  → CoT + Self-consistency
   → Low quality?      → Ask-Verify-Improve

2. "What is my token budget?"
   → Tight budget     → Zero-shot
   → Quality matters  → Few-shot or CoT

3. "Is this a pipeline or a single call?"
   → Pipeline         → Can afford multi-stage patterns
   → Single call      → One-shot self-critique

4. "How do I test that my pattern works at scale?"
   → Run 50+ test cases
   → Measure consistency, accuracy, format adherence

5. "What's the simplest pattern that solves the problem?"
   → Engineering rule: minimum complexity for needed quality

6. "Where will this pattern break in production?"
   → What edge cases?
   → What adversarial inputs?
```
