# 📌 TOPIC 1 — Proprietary Models

---

## What Is a Proprietary Model?

> **Proprietary model = A model owned and controlled by a company. You access it as a SERVICE — not as software you possess.**

```
Think of it like a TAXI:
→ You don't own the car
→ You don't control the engine
→ You don't know the route algorithm
→ You just pay per ride and get where you need
→ The taxi company can change prices, routes, or shut down

Proprietary LLMs:
→ You don't own the weights
→ You can't inspect the architecture fully
→ You don't know all the training details
→ You pay per token and get responses
→ The company can change the model, pricing, or retire it
```

## Proprietary Model Advantages

```
✅ ADVANTAGES:

1. BEST QUALITY (usually)
   → Frontier models have most parameters, most data, most RLHF
   → For complex tasks: GPT-4o and Claude 3.5 Sonnet hard to beat
   → Safety guardrails are most mature

2. ZERO INFRASTRUCTURE
   → No GPU needed. No setup. Just API calls.
   → Start building in 5 minutes.
   → Scale from 1 to 1,000,000 users without infra work.
   → The company handles GPU clusters, cooling, networking.

3. ALWAYS UPDATED
   → Model improves silently (and sometimes changes silently)
   → Security patches applied automatically
   → New capabilities added over time

4. RELIABILITY + SLA
   → 99.9%+ uptime guarantees
   → Enterprise support contracts
   → Audit logs for compliance
```

---

## Proprietary Model Disadvantages

```
❌ DISADVANTAGES:

1. DATA PRIVACY (The Biggest Risk)
   → Your data leaves your servers.
   → Sent to OpenAI/Anthropic/Google servers.
   → Training opt-out ≠ data leaving your network.
   → HIPAA, GDPR, SOC2 compliance issues.
   → Healthcare data, legal data, financial data: HIGH RISK.

   REAL EXAMPLE:
   Samsung engineers pasted confidential source code into ChatGPT.
   The data was processed on OpenAI servers.
   Samsung banned ChatGPT company-wide after this incident.

2. COST SCALES WITH USAGE
   → Works great for prototypes and small scale.
   → At scale: costs compound dramatically.
   → 10M tokens/day at GPT-4 prices = thousands of $/day
   → No cost ceiling — a bug can bankrupt you

   REAL EXAMPLE:
   Startup builds product with GPT-4.
   Goes viral overnight.
   Wakes up to $50,000 API bill in 24 hours.
   (Happens regularly in startup world)

3. NO CONTROL OVER MODEL BEHAVIOR
   → Model updated → behavior changes → your app breaks.
   → "GPT-4-turbo" in January ≠ "GPT-4-turbo" in June.
   → OpenAI changed models behavior multiple times silently.
   → Rate limits can be imposed suddenly.

4. VENDOR LOCK-IN
   → Your product depends on one company staying in business.
   → If OpenAI changes pricing 10x → you're stuck.
   → API deprecated → rewrite your whole system.
   → No negotiating power as a small customer.

5. RATE LIMITS
   → Requests per minute limits.
   → Token per minute limits.
   → Burst limits during high traffic.
   → Paid tiers affect limits significantly.
```

# 📌 TOPIC 2 — Open-Weight Models

---

## What Is an Open-Weight Model?

> **Open-weight model = A model whose weights (parameters) are publicly released. You can download, run, modify, and deploy it yourself.**

```
Think of it like BUYING A CAR:
→ You OWN the car
→ You control everything about it
→ You can modify the engine
→ No per-mile fees (just fuel = electricity)
→ It doesn't get taken away if the dealership closes
→ Mechanics can inspect everything

Open-weight LLMs:
→ You own the weight files (download them)
→ You run inference on your hardware
→ You can fine-tune and modify
→ No per-token fees (just compute costs)
→ Model available even if company disappears
→ Can inspect architecture completely
```

---

## IMPORTANT TERMINOLOGY CLARIFICATION

```
"OPEN SOURCE" vs "OPEN WEIGHT" — Not the same!

TRUE OPEN SOURCE (rare):
→ Model weights: publicly available ✅
→ Training code: publicly available ✅
→ Training data: publicly available ✅
→ Can be used commercially: ✅
Example: BLOOM, Falcon (some versions), TrOCR

OPEN WEIGHT (most "open" models):
→ Model weights: publicly available ✅
→ Training code: sometimes ✅, sometimes ❌
→ Training data: usually NOT available ❌
→ Commercial use: depends on license ⚠️
Example: LLaMA 2/3, Mistral, Gemma

IMPORTANT LICENSES:
→ LLaMA 2: Custom Meta license (commercial use OK up to 700M users)
→ LLaMA 3: More permissive Meta license
→ Mistral: Apache 2.0 (most permissive — commercial freely allowed)
→ Gemma: Google's custom license (restricted for some uses)

Always check the license BEFORE building commercial products!
```

## Open-Weight Advantages vs Disadvantages

```
✅ ADVANTAGES:

1. DATA PRIVACY (The Killer Feature)
   → Data NEVER leaves your servers.
   → Perfect for: healthcare, legal, finance, government, enterprise.
   → HIPAA, GDPR compliance possible.
   → Zero data breach risk from AI provider.

2. COST AT SCALE
   → No per-token fees.
   → Hardware cost amortized over millions of requests.
   → A $10,000 GPU serves millions of tokens per day.
   → At high volume: 10-100x cheaper than proprietary.

3. COMPLETE CONTROL
   → Model behavior locked to a specific version.
   → No silent updates breaking your product.
   → Fine-tune on your data to your exact behavior.
   → Customize system prompts, output format, safety thresholds.

4. NO VENDOR LOCK-IN
   → Model files stored on your servers.
   → No dependency on external company's survival.
   → Switch providers without rewriting your app.

5. CUSTOMIZATION DEPTH
   → Fine-tune on your domain data.
   → Full LoRA, QLoRA fine-tuning possible.
   → Modify tokenizer, add custom tokens.
   → Merge multiple models (model merging).

❌ DISADVANTAGES:

1. INFRASTRUCTURE BURDEN
   → YOU manage GPUs, cooling, networking, uptime.
   → DevOps expertise required.
   → Hardware failures, CUDA errors, memory issues: your problem.
   → Initial capital cost: $10,000-$100,000+ for good hardware.

2. QUALITY GAP (for frontier tasks)
   → Frontier open models (LLaMA 405B) approach but rarely beat
     GPT-4 / Claude on complex reasoning.
   → For most everyday tasks: gap is small.
   → For cutting-edge tasks: proprietary still leads.

3. SAFETY AND ALIGNMENT
   → Less mature safety guardrails.
   → More "jailbreakable" than proprietary models.
   → Your responsibility to add safety layers.
   → Misuse liability falls on YOU.

4. NO SUPPORT
   → Something breaks at 3am? No help desk.
   → Community support only (GitHub issues, Discord).
   → Enterprise support: rare and expensive.
```

---

## The Hybrid Strategy (What Smart Engineers Do)

```
REAL WORLD PATTERN: Use BOTH.

PROPRIETARY for:
→ Complex reasoning tasks (GPT-4, Claude for hard problems)
→ Initial prototype (fast, no infra)
→ Rare but important tasks (worth premium cost)
→ Tasks needing best available quality

OPEN-WEIGHT for:
→ High-volume, repetitive tasks (cheap at scale)
→ Data privacy-sensitive queries
→ Fine-tuned domain specialists (custom models)
→ Latency-sensitive tasks (no network round trip)
→ Offline applications

EXAMPLE ARCHITECTURE:
User message arrives
        │
        ▼
Classification: Is this a SIMPLE or COMPLEX query?
        │                         │
        ▼                         ▼
SIMPLE query               COMPLEX query
(routine Q&A, RAG)         (multi-step reasoning,
        │                   novel synthesis)
        ▼                         │
Local LLaMA 3.1 8B         GPT-4o / Claude 3.5
(free, fast, private)      (expensive, best quality)
        │                         │
        └──────────┬───────────────┘
                   ▼
            Final response

RESULT:
→ 80% of queries handled cheaply locally
→ 20% sent to proprietary for quality
→ Cost reduction: 60-80%
→ Quality maintained for complex tasks
```

# 📌 TOPIC 5 — Quantization: Making Big Models Fit Anywhere

---

## The Problem Quantization Solves

```
PROBLEM:
LLaMA 3.1 70B in full precision (FP32):
→ 70B parameters × 4 bytes = 280GB VRAM

REALITY:
Best consumer GPU (RTX 4090): 24GB VRAM
Best professional GPU (A100): 80GB VRAM
Best available GPU (H100): 80GB VRAM

280GB doesn't fit anywhere affordable!

Without quantization:
→ 70B model needs 4× A100s (80GB each) = $20,000+ hardware
→ $2,000+/month cloud cost

With quantization:
→ 70B model reduced to 35-70GB → fits on 1-2 GPUs
→ Cost drops dramatically
```

---

## What Is Quantization? (From First Principles)

> **Quantization = Reducing the number of bits used to store each parameter, making the model smaller at the cost of some precision.**

```
ANALOGY: Photo Resolution

Original photo: 4K resolution (high quality, huge file)
Compressed photo: 720p resolution (slightly lower quality, tiny file)
Thumbnail: 100×100px (lower quality, tiny file)

You can see the photo at all three resolutions.
Higher resolution = more detail = bigger file.
Lower resolution = less detail = smaller file.
The CONTENT (subject of photo) is preserved at all levels.

QUANTIZATION WORKS THE SAME WAY:
FP32 weights: High precision, huge memory
FP16 weights: Good precision, half memory
INT8 weights: Decent precision, quarter memory
INT4 weights: Reduced precision, eighth memory
```

---

## The Precision Formats — Explained Simply

```
FLOATING POINT 32-BIT (FP32):
─────────────────────────────
Bits: 32 total
└── 1 bit: sign (positive/negative)
└── 8 bits: exponent (scale)
└── 23 bits: mantissa (precision)

Range: can represent ±3.4 × 10^38
Precision: about 7 decimal digits of accuracy

Example: 3.14159265 ← 9 significant digits, needs FP32
Memory: 4 bytes per parameter

BRAIN FLOAT 16 (BF16) / FP16:
──────────────────────────────
Bits: 16 total
Range: BF16 maintains same range as FP32
Precision: about 3-4 decimal digits
Memory: 2 bytes per parameter
Quality loss: Negligible for inference
Standard for: Most modern LLM training and inference

INT8 (8-bit Integer):
─────────────────────
Bits: 8 total
Values: -128 to 127 (256 possible values)
Precision: Much lower, but usually sufficient
Memory: 1 byte per parameter
Quality loss: Small (0.5-1% degradation on benchmarks)
Speed gain: 2-4x faster on compatible hardware

INT4 (4-bit Integer):
─────────────────────
Bits: 4 total
Values: 0 to 15 (16 possible values!)
Precision: Very low
Memory: 0.5 bytes per parameter
Quality loss: Moderate (2-5% degradation)
Speed gain: 4-8x faster
Sweet spot: Run 70B model on consumer hardware

INT2 / Binary (research):
─────────────────────────
Bits: 2 or 1 total
Values: 0,1,2,3 or just 0,1
Precision: Very crude
Quality loss: Significant (5-15%+)
Memory: 0.25-0.125 bytes per parameter
Status: Research phase (BitNet b1.58 promising)
```

---

## Quantization Methods — The Technical Landscape

---

### Method 1: Post-Training Quantization (PTQ)

```
APPROACH:
Take a TRAINED full-precision model.
Quantize the weights AFTER training.
No retraining needed.

PROCESS:
FP32 model weights
        │
        ▼
Calibration dataset (small, representative)
→ Run inputs through model
→ Observe activation distributions
→ Determine optimal quantization parameters
        │
        ▼
Quantized model (INT8 or INT4)

POPULAR FORMATS:
GPTQ (GPU Post-Training Quantization):
→ Quantizes layer-by-layer
→ Minimizes quantization error per layer
→ Good quality INT4/INT3 quantization
→ Fastest on NVIDIA GPUs

AWQ (Activation-aware Weight Quantization):
→ Keeps important weights at higher precision
→ Identifies which weights matter most to activations
→ Better quality than naive quantization
→ Well-supported in vLLM
```

---

### Method 2: QLoRA — Quantization + Fine-Tuning

```
PROBLEM:
Want to fine-tune a 70B model but can't fit it in memory.

QLORA SOLUTION:
1. Quantize base model to INT4 (fits in memory!)
2. Add LoRA adapters (small trainable matrices) in FP16
3. Train ONLY the LoRA adapters (base model frozen)
4. Result: Fine-tuned behavior, INT4 memory footprint

MEMORY COMPARISON:
Full fine-tune of 70B (FP16):
→ 140GB VRAM for weights alone
→ Plus optimizer states: 420GB+
→ Needs 6+ A100s

QLoRA of 70B (INT4 base + FP16 adapters):
→ ~35GB VRAM for INT4 weights
→ ~2GB for LoRA adapters
→ Fits on 1-2 A100s or 2× consumer GPUs

QLORA democratized 70B fine-tuning.
Before QLoRA: only large companies could fine-tune 70B.
After QLoRA: a graduate student with 2 GPUs can do it.
```

---

### Method 3: GGUF Format (For Local CPU/GPU Inference)

```
GGUF = GPT-Generated Unified Format

WHAT IT IS:
A file format for storing quantized models.
Designed for llama.cpp (C++ inference engine).
Enables LLM inference on CPU (no GPU required!).

QUANTIZATION LEVELS IN GGUF:
Q2_K    → 2-bit quantization. Smallest, lowest quality.
Q3_K_M  → 3-bit. Better quality.
Q4_K_M  → 4-bit. ← MOST POPULAR. Good quality/size balance.
Q5_K_M  → 5-bit. High quality with modest compression.
Q6_K    → 6-bit. Near FP16 quality.
Q8_0    → 8-bit. Very close to original quality.

EXAMPLE: LLaMA 3.1 70B in different formats:
FP16:   140GB (needs multiple A100s)
Q8_0:    74GB (needs 2× A100s or H100)
Q4_K_M:  40GB (fits on 1× 48GB GPU or 2× 24GB GPUs!)
Q3_K_M:  30GB (fits on M2 Max Mac Studio!)
Q2_K:    22GB (runs on high-end laptop)

THIS IS REVOLUTIONARY:
Running a 70B parameter model on a $2,000 Mac Mini!
(via Apple M-series unified memory)
```

```

# 📌 TOPIC 6 — MoE: Mixture of Experts

---

## The Problem MoE Solves

```
TRADITIONAL DENSE MODEL:
All 70B parameters are used for EVERY token.
"cat" query: uses all 70B parameters.
"quantum physics" query: uses all 70B parameters.

PROBLEM:
Wasteful! Does every token need ALL 70 billion parameters?
Not really. Simple tokens need less. Complex ones need more.
Using all parameters for every token = expensive computation.
```

---

## MoE — The Core Idea

> **MoE = Instead of one big model, have many "expert" sub-networks. For each token, only activate the most relevant 1-2 experts.**

```
ANALOGY: Hospital Departments 🏥

DENSE MODEL = One super-doctor who handles everything.
Every patient gets ALL their attention. (Inefficient)

MoE MODEL = Hospital with specialists.
Cardiology expert, Neurology expert, Oncology expert...
Each patient routed to the RIGHT specialist.
Other specialists idle while their patient is handled.
More efficient. Better outcomes.

MoE STRUCTURE:
                    Input Token
                         │
                         ▼
                    ROUTER / GATE
                (learned neural network)
                "Which experts handle this?"
                         │
        ┌────────────────┼────────────────┐
        │                │                │
        ▼                ▼                ▼
   Expert 1         Expert 3         Expert 7
 (code domain)   (math domain)  (language domain)
        │                │                │
        └────────────────┼────────────────┘
                         │
                    Weighted Sum
                    of outputs
                         │
                         ▼
                   Final output
                (only 2 experts used,
                 others idle)
```

---

## MoE Numbers — The Efficiency Trick

```
EXAMPLE: Mixtral 8x7B (Mistral's MoE model)

Architecture:
→ 8 expert networks
→ Each expert: ~7B parameters
→ Total parameters: ~46.7B
→ Active parameters per token: ~12.9B (only 2 experts activate)

COMPARISON:
Dense 46.7B model:
→ Uses ALL 46.7B params for every token
→ 46.7B multiply-accumulate operations per forward pass
→ High compute, high memory bandwidth

Mixtral 8x7B MoE:
→ Uses ~12.9B params per token (2 out of 8 experts)
→ Only 12.9B operations per forward pass
→ But can draw on knowledge from all 46.7B params!

RESULT:
→ Mixtral 8x7B quality comparable to Llama 2 70B
→ But only uses 12.9B params worth of compute per token
→ Much faster inference than a real 46.7B dense model
→ But needs all 46.7B in memory (all experts loaded)

TRADEOFF:
MoE saves COMPUTE (faster inference)
but NOT MEMORY (all experts must be loaded)
```

```
TOKEN: "def fibonacci(n):"
              │
              ▼
         ROUTER NETWORK
         (small MLP that learns routing)
              │

## MoE Engineering Considerations

```
MEMORY:
All experts must be loaded into GPU memory.
Mixtral 8x7B needs ~87GB (FP16) — needs 2× A100s minimum.
With Q4 quantization: ~25-30GB → fits on 1× A100 or 2× consumer GPUs.

LOAD BALANCING PROBLEM:
Router might always pick the same 2 experts.
Other experts never learn (underutilized).
Solution: Auxiliary loss term during training forces balanced usage.
"You MUST use all experts roughly equally across the batch."

ROUTING OVERHEAD:
Router adds a small compute cost for each token.
Worth it for quality per compute gains.

MEMORY BANDWIDTH:
Even though only 2 experts compute, ALL expert weights
must be accessible in memory.
MoE is memory-bandwidth bound, not compute bound.
Works best with high memory bandwidth (NVLink, HBM).
```

## How Vision Understanding Works (Intuition)

```
HOW GPT-4o SEES AN IMAGE:

Step 1: IMAGE ENCODING
Image → Image Encoder (like CLIP or ViT)
       → Splits image into patches (like tokens for images)
       → Each patch → embedding vector

A 1024×1024 image might become:
→ 64×64 = 4096 image "tokens" (patches)
→ Each patch represented as a vector

Step 2: PROJECTION
Image patch vectors → Linear projection → Same dimension as text tokens
Now image is expressed in the SAME embedding space as text!

Step 3: INTERLEAVED PROCESSING
Text tokens + Image tokens fed together into Transformer.
Attention mechanism operates across BOTH text and image tokens.
Model learns relationships between text and visual content.

Step 4: TEXT GENERATION
Transformer generates text tokens as response.
Attention to relevant image patches informs the text.

EXAMPLE:
Image: [photo of car engine with smoke]
Text: "What's wrong with this car?"

Image tokens and text tokens attend to each other.
Model finds: smoke patches ↔ "overheating" knowledge
Output: "The engine appears to be overheating — visible smoke..."
```

# 📌 TOPIC 8 — Reasoning Models vs Chat Models

---

## The Two Paradigms of LLM Usage

```
THE FUNDAMENTAL QUESTION:
"How does the model approach a problem?"

CHAT MODEL:
→ Read question
→ Immediately start generating answer
→ Fast, conversational, fluid
→ Quality depends on prompt engineering

REASONING MODEL:
→ Read question
→ THINK FIRST (generate internal reasoning chain)
→ Then generate final answer
→ Slower, more expensive, dramatically better on hard problems
```

---

## Chat Models — Deep Understanding

```
WHAT THEY ARE:
Standard LLMs after SFT + RLHF.
Optimized for: helpful, conversational responses.
Training goal: Be useful, harmless, and honest in conversation.

HOW THEY GENERATE:
User input → immediately generates next token
No explicit "thinking" phase.
Reasoning happens implicitly in the forward passes.
Chain-of-thought can be prompted but not built-in.

STRENGTHS:
→ Fast response time (low TTFT)
→ Great for conversation and interaction
→ Good for content generation, creative tasks
→ Excellent at tasks with well-defined answers
→ Cost-effective for high volume

WEAKNESSES:
→ Struggle with novel multi-step problems
→ Can make calculation errors without thinking
→ "Snap judgment" quality — doesn't deliberate
→ Performance plateaus on complex reasoning

EXAMPLES:
GPT-4o (chat), Claude 3.5 Sonnet (chat),
Gemini 1.5 Pro (chat), LLaMA 3.1 (instruct)
```

---

## Reasoning Models — The New Paradigm

```
WHAT THEY ARE:
Models trained to generate extended "thinking" before answering.
Sometimes called: "System 2" thinking models.
OpenAI's o-series. DeepSeek-R1. QwQ. Claude's extended thinking.

THE KEY INNOVATION:
Models trained specifically to:
1. Generate a long internal reasoning chain (chain-of-thought)
2. Explore multiple solution paths
3. Verify their reasoning
4. Backtrack when wrong
5. THEN provide the final answer

HOW THEY GENERATE:
User input
      │
      ▼
[THINKING PHASE — internal]
"Let me analyze this step by step..."
"First, I need to consider X..."
"Wait, that doesn't work because Y..."
"Let me try another approach..."
"Actually, the answer must be Z because..."
[500-10,000+ thinking tokens generated]
      │
      ▼
[ANSWER PHASE — shown to user]
"The answer is Z, because..."
[Final concise answer]

TRAINING DIFFERENCE:
Chat models: trained on (prompt → good response) pairs
Reasoning models: trained with RL to MAXIMIZE correctness
                  of final answer, rewarded for RIGHT answers
                  not "good-sounding" answers
                  Model learns to develop reasoning strategies
```

## When Reasoning Models Shine vs Fail

```
REASONING MODELS EXCEL AT:
──────────────────────────────────────────────────────────────────
Complex math problems
"Solve this differential equation..."
→ o1: thinks through steps, checks work, gets right answer
→ GPT-4o (chat): might make arithmetic error mid-solution

Algorithm design
"Design an O(n log n) algorithm for..."
→ o1: considers multiple approaches, evaluates tradeoffs
→ Chat model: often gives first plausible algorithm without analysis

Logic puzzles
"10 people in a room. Each shakes hands with everyone else..."
→ o1: carefully counts, verifies combinatorially
→ Chat model: often gets wrong number

Code debugging (complex)
"Why does this race condition occur in my concurrent code?"
→ o1: traces execution paths, identifies edge cases
→ Chat: might miss subtle timing issues

Scientific reasoning
"Given these experimental results, which hypothesis is supported?"
→ o1: weighs evidence systematically
→ Chat: may confirm bias in question

Legal/medical reasoning (complex edge cases)
→ o1: considers multiple interpretations, flags ambiguity
→ Chat: may oversimplify

REASONING MODELS OVERKILL FOR:
──────────────────────────────────────────────────────────────────
Simple Q&A: "What's the capital of France?" → Use chat model
Creative writing: → Chat models are BETTER (reasoning hurts creativity)
Conversation: → Users don't want to wait 30 seconds for a reply
Data extraction: → Simple structured tasks, chat is fine
Summarization: → No complex reasoning needed
```

For simple tasks: might be acceptable.

# 🎤 INTERVIEW QUESTIONS & ANSWERS

---

## Q1: "What's the difference between proprietary and open-weight models? When would you choose each?"

**Strong Answer:**
> "Proprietary models like GPT-4 and Claude are owned by companies and accessed via API — you get best-in-class quality and zero infrastructure management, but data leaves your servers and cost scales with usage. Open-weight models like LLaMA and Mistral have publicly released weights you can run on your own hardware — giving you data privacy, cost control at scale, and no vendor lock-in, at the cost of infrastructure burden and a quality gap for frontier tasks. I'd choose proprietary for prototyping, frontier reasoning tasks, and cases where quality is paramount. I'd choose open-weight for data-sensitive applications (healthcare, legal, finance), high-volume repetitive tasks where the math favors owned compute, and cases requiring fine-tuning to specific domain behavior that I can't achieve through prompting alone."

---

## Q2: "Explain quantization. What are the real engineering tradeoffs?"

**Strong Answer:**
> "Quantization reduces the bit precision of model weights — going from 32-bit floats to 16-bit, 8-bit, or 4-bit integers. Each step roughly halves memory requirements. A 70B model that needs 140GB in FP16 shrinks to about 40GB at Q4, making it deployable on 2 consumer GPUs instead of a cluster of A100s. The engineering tradeoff is quality versus memory: INT8 causes roughly 0.5-1% benchmark degradation, Q4 causes 2-3%, and Q2 can degrade significantly. For production I generally recommend Q4_K_M as the sweet spot — 87% memory reduction with acceptable quality loss for most tasks. The key insight is that a quantized 70B model often outperforms a smaller full-precision model on complex tasks, so better to run LLaMA 70B at Q4 than LLaMA 7B at FP16 if the task demands it."

---

## Q3: "What is Mixture of Experts? Why does DeepSeek use it?"

**Strong Answer:**
> "MoE architectures replace a single dense feed-forward network with multiple 'expert' networks, routing each token to only the top-1 or top-2 most relevant experts via a learned router. The total parameter count is large (DeepSeek V3 has 671B parameters across all experts), but only a fraction activate per token (37B active for V3). This creates massive parameter capacity without proportional compute cost — the quality of a 671B model with the inference cost of a 37B model. DeepSeek uses MoE because it enables much higher parameter efficiency, allowing them to train frontier-quality models at a fraction of the compute cost of dense models like GPT-4. This is why DeepSeek V3 reportedly cost ~$5 million to train versus hundreds of millions for comparable dense models. The tradeoff is that all expert weights must remain in memory, so memory usage stays proportional to total parameters while compute scales only with active parameters."

---

## Q4: "When should you use a reasoning model vs a chat model?"

**Strong Answer:**
> "The decision comes down to three factors: problem complexity, latency tolerance, and cost budget. Reasoning models like o1 generate extensive internal thinking chains before answering — they're dramatically better at multi-step math, novel algorithm design, complex debugging, and tasks requiring systematic verification. But they take 10-60 seconds to respond and cost 15-50x more than chat models. Chat models are better for everything conversational, creative, or time-sensitive. In production I'd build a complexity router: classify incoming queries as simple or complex, route simple queries to fast, cheap chat models, and reserve reasoning models for genuinely hard problems where accuracy matters more than speed. For most applications, 90%+ of queries should never touch a reasoning model."

---

## Q5: "What multimodal models would you consider for a document processing system?"

**Strong Answer:**
> "For document processing I'd evaluate based on three dimensions: document complexity, volume, and data sensitivity. For complex documents with mixed layouts, tables, and charts — Claude 3.5 Sonnet has the best document understanding currently, particularly for preserving layout context. For very long documents (hundreds of pages), Gemini 1.5 Pro's 1M token context gives an architectural advantage. For high-volume, cost-sensitive processing where data must stay private, I'd self-host LLaMA 3.2 11B with vision capabilities — it can handle standard document extraction at a fraction of API costs. For invoice and receipt extraction specifically, the image tokens matter — I'd use detail:low where full resolution isn't needed to cut token costs by 10x. The real decision point is always: does this data need to stay on-premises? If yes, the entire API option space collapses to self-hosted open-weight models."

# ⚠️ COMMON BEGINNER MISTAKES

---

```
❌ Mistake 1: "OpenAI = AI. AI = OpenAI."
✅ Reality: The AI model ecosystem has 50+ companies and hundreds
   of models. OpenAI is one provider among many. Defaulting to
   OpenAI without evaluating alternatives leads to overpaying,
   privacy risks, and missing better options for specific tasks.

❌ Mistake 2: "Bigger model = better model"
✅ Reality: A well-trained 7B model often outperforms a larger
   poorly-trained or generic model on specific tasks. A
   fine-tuned Mistral 7B on your domain can beat GPT-4 (generic)
   for your specific use case. Always benchmark on your task.

❌ Mistake 3: "Open source = free to use commercially"
✅ Reality: "Open-weight" ≠ "open source" ≠ "free commercial use."
   LLaMA 3 has Meta's custom license. Some models restrict
   commercial use. Some require attribution. Always read the
   license before building commercial products.

❌ Mistake 4: "Quantization always degrades quality significantly"
✅ Reality: INT8 and Q4_K_M quantization cause minimal quality loss
   (typically <3%) for most tasks. A Q4-quantized 70B model
   almost always outperforms a smaller unquantized model.
   Quantization enables practical deployment, not just compromise.

❌ Mistake 5: "MoE models are always better than dense models"
✅ Reality: MoE models save compute but need ALL experts in memory.
   For memory-constrained environments, a dense model might be
   more practical. MoE benefits appear at training time (compute
   efficiency) and inference throughput — not necessarily quality
   per parameter.

❌ Mistake 6: "Reasoning models are just chat models with better prompting"
✅ Reality: Reasoning models are trained differently — using RL to
   maximize answer correctness, developing self-verification and
   backtracking. The quality improvement on hard problems isn't
   achievable by prompting a chat model to "think step by step."
   That's a helpful technique but doesn't replicate o1-style training.

❌ Mistake 7: "Self-hosting is always cheaper"
✅ Reality: Self-hosting has high FIXED costs (GPU hardware, DevOps,
   maintenance, reliability engineering). At LOW volume, proprietary
   API is cheaper. Self-hosting only wins financially at HIGH volume.
   Calculate the break-even point before deciding.
   Break-even formula: (API cost/month) vs (GPU cost + DevOps cost/month)

❌ Mistake 8: "Vision models see images the same way humans do"
✅ Reality: Vision models encode images as patches → vectors.
   They can fail on: fine detail, exact counts of objects, reading
   cursive text, understanding spatial relationships precisely,
   and "seeing" things humans see immediately. Always test vision
   models on YOUR specific image types before trusting them in production.
```

# 🧠 ENGINEER MINDSET

---

```
THE 8 QUESTIONS EVERY AI ENGINEER ASKS BEFORE CHOOSING A MODEL:

1. "What is the TASK type?"
   → Classification, generation, reasoning, extraction, creative?
   → This narrows the model type immediately.

2. "What are the DATA PRIVACY requirements?"
   → Healthcare, legal, financial? → Must self-host.
   → General SaaS? → API probably fine.
   → Internal tools? → Depends on company policy.

3. "What is the VOLUME?"
   → Low volume (<100K tokens/day) → API cheapest
   → High volume (>10M tokens/day) → self-host probably cheaper
   → Calculate break-even before deciding

4. "What QUALITY level is actually needed?"
   → Not "best possible" but "minimum acceptable"
   → Find cheapest model that meets quality threshold
   → Benchmark first, choose model second

5. "What are the LATENCY requirements?"
   → Real-time (< 1s): smaller models, Groq, streaming
   → Near real-time (< 5s): most models work
   → Batch (minutes okay): beam search, biggest models

6. "Does this need FINE-TUNING?"
   → Generic task → prompting probably sufficient
   → Domain-specific behavior → fine-tune open model
   → Custom persona/style → fine-tune

7. "What's the FAILURE MODE?"
   → What happens when model is wrong?
   → High stakes (medical, legal): need reasoning model + human review
   → Low stakes (content generation): chat model + retry

8. "What's the MONITORING strategy?"
   → How will I know if quality degrades?
   → How will I detect model version changes?
   → What's the eval pipeline?
```
